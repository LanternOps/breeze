## 4. Highest-risk five (most likely to break a customer upgrade)

1. **#6295 — DB role verification now runs on every startup, not just prod.** A self-hosted instance whose `DATABASE_URL_APP` resolves to a superuser/bypassrls role (common in dev-grade Postgres setups) will now refuse to boot at all post-upgrade, where before it only refused in production. This is the single highest blast-radius change: it can turn a successful upgrade into a hard outage with no traffic served, and the only relief is the new `BREEZE_ALLOW_UNSAFE_DB_ROLE` break-glass var, which is easy to miss in release notes.
2. **#6233 — Settings consolidation moves Billing and Ticketing to new routes** (`/settings/billing`, `/settings/ticketing` standalone instead of tabs inside Partner Settings). Any bookmarked admin link, saved runbook, or third-party doc referencing the old paths breaks silently unless a redirect was added; worth explicitly verifying the old URLs still resolve.
3. **#6310/#6309/#6299 — Move-org step-up + `mfa_src` claim now gate a previously simple operation.** Device move-org used to be a plain admin action; it now requires an interactive session with a fresh step-up grant. Any automation, API-key integration, or scripted MSP workflow that calls move-org programmatically will start failing with 403s post-upgrade — a classic "worked in staging, broke in the field" regression for MSPs with automation around org moves.
4. **#6072 — Removal of `DEVICE_COMMAND_OFFLINE_QUEUE_ENABLED`.** Any self-hosted operator who had explicitly set this flag to `false` (to restore pre-#5128 hard-fail semantics) loses that override entirely on upgrade — offline queuing becomes unconditional with no opt-out, which changes dispatch behavior for anyone relying on immediate `device_offline` failures.
5. **#6194/#6181 (W01 sender contract) + #8c9045ab7f/#9a25b92d14/#f18b287116/#be78744389 (sending-domains stack) — a large, multi-wave rewrite of the entire outbound email path** (`resolveSender`, `deliverRaw`, purpose registry) that every notification, invite, and ticket email now flows through. Even with the feature flag (`EMAIL_DOMAINS_PROVIDER`) off by default, this is a foundational refactor of email sending touched across 6+ PRs — a subtle regression here silently breaks ticket notifications or password-reset emails fleet-wide, and would not be caught by a flag-off smoke test alone.

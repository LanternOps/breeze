**DEFECT (#6346, agent) — the `trash` category can never be cleaned for root on Linux.**
`{"path":"/root/.local/share/Trash","status":"rejected","reason":"agent_guard","error":"cleanup guard rejected: /root/.local/share/Trash is not inside its anchor /root/.local/share/Trash"}`
`agent/internal/remote/tools/fileops.go:687` rejects when `rel == "."`, i.e. when the target **equals** its confinement anchor. The anchor is the rule pattern's literal prefix (`cleanupRuleAnchorFor` → `concreteAnchor`), so any **fully literal** pattern anchors on itself and is structurally unexecutable. `agent/internal/remote/tools/cleanup_rules.json:123` has exactly one such pattern today: `/root/.local/share/Trash` (granularity `contents`). Its sibling `/home/*/.local/share/Trash` has a wildcard, so its anchor is `/home` and it passes — the bug is root-only, but root's trash is the common case on a server. The preview happily offers the 20 MB and the execute always returns it rejected. Not covered by CI: the Go tests exercise the wildcard form.

2. **Server validation errors leak the request field path.** The output-dir rejection renders as **"restoreConfig.outputDir: absolute path required"** — accurate but it names an API field the operator has never seen, and it appears at the top of the modal rather than under the **Output directory** input it belongs to. The same 400 body already carries `fieldErrors` keyed well enough to place it inline.
3. **Saving a plan is not atomic, and the list goes stale on a partial failure.** Save fires `PATCH /dr/plans/:id` first and `PATCH …/groups/:groupId` second. Renaming the plan *and* entering a bad output dir in one save produced **plan PATCH 200, group PATCH 400** — the rename was committed (DB: `Sweep DR plan RENAMED`) while the group change was rejected, and after cancelling out the plans table still displayed the **old** name. The operator is told the save failed, is looking at the old name, and the new name is what is actually stored.
4. **Nothing on this screen has a `data-testid` except the three #6321 added.** `Create Plan`, `Add group`, `Save plan`, `Cancel`, `Edit`, `Execute`, the execution-type cards and the whole plans table are addressable only by text — the repo's e2e convention (`e2e-tests/README.md`) is `data-testid` only, so DR cannot be covered by an E2E spec today. #6321 added `dr-group-step-type` / `dr-group-rebuild-options` / `-output-dir` / `-wait-timeout` and stopped there.
5. **No toast on a successful plan save.** Create and update both close the modal silently; the only confirmation is the row appearing/updating in the table behind it. Every other mutation surface in the app toasts (`runAction`).
6. **A `BARE_METAL_REBUILD` group saves happily with no rebuild host.** `rebuildHostDeviceId` is `.optional()` in the schema but is *required at dispatch for a rehearsal* (`drBareMetalRebuildStep.ts:24`), so the editor lets an operator build a plan that cannot rehearse and only find out when they press Execute during an incident. The panel should at least warn inline when the host is empty.
7. **Empty output directory saves as the default with no feedback.** Clearing the field returns a 200 and stores `/var/lib/breeze/rebuild/out`; on reopen the field shows that value as if the operator typed it. Harmless, but the field is the one that decides where multi-GB VHDX images land, so a silent substitution is worth a hint.

### Group 5 — Auth errors + AI (#6317, #6341/#6345, #6347)

1. **`UsersPage` ships its own toast implementation with no `data-testid`.** `apps/web/src/components/settings/UsersPage.tsx:44` defines a local `addToast` and renders its own markup (`relative rounded-lg px-4 py-3 pr-10 shadow-lg bg-destructive …`), instead of the shared host at `apps/web/src/components/shared/Toast.tsx:129-139` which carries `data-testid="toast-container"` / `data-testid="toast"`. Every invite/edit/MFA-reset outcome on this page is therefore invisible to `data-testid`-based e2e and to any toast assertion — it reads exactly like a silent mutation until you walk the DOM for the text. Swap it for the shared toast.
2. **The 409 message is the API's sentence, not the user's.** "User already exists in this scope" leaks the API's tenancy vocabulary ("scope") and does not tell the admin what to do — the user is right there in the table behind the modal. "admin@breeze.local is already a user here" plus focusing the existing row would be one step shorter.
3. **The 428 rotation costs a visible failed login on every fresh client.** The first submit after clearing cookies returns `428 auth_binding_rotation_required` and the form just sits there; the operator has to press Sign in again. Known noise on this stack, but it is the first interaction a new user has with the product, and nothing in the UI says "try again" — worth either auto-retrying once or saying so.
4. **The hot/cold tool report cannot distinguish "unused" from "unreachable".** `GET /admin/ai/tool-usage` lists `manage_tickets` among the 238 cold tools exactly as it lists a tool nobody happened to call, even though `manage_tickets` is structurally impossible to call from chat (`KNOWN_MISSING_TOOL_TIERS`). The report is the instrument that is supposed to surface this class of problem, so it should mark the tools that are not in `TOOL_TIERS` as *unreachable*, not merely cold.
5. **`#1105` tripwire fires on every AI chat message.** The API logs `rateLimiter(ai) ran inside a held withDbAccessContext transaction — it pins a pooled connection idle-in-transaction across slow work (#1105). Move it after the context closes or wrap it in runOutsideDbContext().` **twice per** `POST /ai/sessions/:id/messages`. Not new to this window and not a functional failure here, but the AI chat is the slowest request on the box, which is precisely the shape #1105 warns about.

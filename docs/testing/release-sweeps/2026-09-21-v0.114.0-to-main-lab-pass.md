### Defects found

**None.** No API/DB defect was reproduced in any of the six rows. Two observations that are *not* defects but are worth recording:

1. **Lab trap — the stale-command reaper's CAS fence needs millisecond-precision `executed_at`.** My first #6434 attempt looked like a total reaper failure: the 25 h row, a 30 h row and even a 20-minute `list_processes` control all sat `sent` through 8+ reaper ticks with the job returning `{"deviceCommands":0,…}` and no error, while the reaper's candidate `SELECT` — run by hand in psql as both `breeze` and `breeze_app`, including the `NOT COALESCE(self_uninstall …)` arm — returned all of them. Cause: I seeded the rows with bare `now()`, which stores **microsecond** precision (`04:14:21.326317`). The reaper re-reads the row through postgres.js/drizzle into a JS `Date` (millisecond) and then fences its UPDATE on `eq(deviceCommands.executedAt, cmd.executedAt)` (`staleCommandReaper.ts:491-503`), so the CAS matches 0 rows and the row is silently skipped with no log. `UPDATE … SET executed_at = date_trunc('milliseconds', executed_at)` made all three reap on the very next tick. Not a product bug — every real row is written by drizzle at millisecond precision — but any future SQL-seeded reaper test must truncate, and any *new* SQL path that writes `executed_at` with sub-millisecond precision would create permanently un-reapable rows with no error anywhere.
2. **#6424's fixed path is unreachable from outside on this build, by design.** That is the PR's own claim and I confirmed the mechanism in source; recorded so a later sweep does not spend budget re-attempting the WS repro.

### Defects found

#### D1 (RELEASE BLOCKER) — #6487 file-index hydration can never be enqueued; BMR recovery 500s on any snapshot with cross-snapshot references

Repro (no special state needed beyond an incremental backup):
1. Run two file backups back-to-back so job 2 has `referenced_files > 0`.
2. `POST /api/v1/backup/bmr/recoveries?orgId=<org>` `{"snapshotId":"<that snapshot's uuid>","identity":"original"}`.
3. → `HTTP 500` `{"error":"Internal Server Error","message":"Custom Id cannot contain :"}`.

Cause: `apps/api/src/jobs/backupSnapshotFileIndexWorker.ts:47` — `const jobId = \`hydrate:${snapshotDbId}\``. bullmq 5.81.2 allows a `:` in a custom job id **only** when the id splits into exactly three `:`-separated parts (`classes/job.js:1072-1076`); a single colon throws. Every enqueue site fails:
- `services/bareMetalRecoveryService.ts:130` (recovery create) — unguarded `await` → 500 to the caller.
- `services/backupResultPersistence.ts:1441` — try/caught, so it fails silently: API log `[backupResultPersistence] Failed to enqueue file-index hydration for snapshot <id>: Error: Custom Id cannot contain :`. `backup_snapshots.file_index_status` therefore stays `'agent'` forever and `backup_snapshot_files` stays empty, so `negotiateRecoveryCapabilities` could only ever return `snapshot_index_pending`.
- `routes/backup/bmr.ts:1192` / `routes/backup/bmrRecoveries.ts:491` (authenticate/exchange pending branch) — same throw.

Net: the W09a feature is inert on main and the primary path it added is a hard 500. Fix is one character class — e.g. `hydrate-${snapshotDbId}` or `bmr:hydrate:${snapshotDbId}` (3 parts). Worth a unit test that asserts the id is accepted by bullmq's validator, since no existing test exercises a real `Queue.add`.

#### D2 — `DELETE /api/v1/monitor-definitions/:id` 500s with a raw Postgres FK message once the monitor has produced an alert

`DELETE /api/v1/monitor-definitions/2d4ee6ab-…?orgId=…` →
`HTTP 500 {"error":"Internal Server Error","message":"update or delete on table \"alert_rules\" violates foreign key constraint \"alerts_rule_id_alert_rules_id_fk\" on table \"alerts\""}`.
Reproduced on all three network_check definitions I created, each of which had at least one alert row. Two problems: the delete is not possible at all for any monitor that has ever fired (no cascade, no "resolve/detach alerts first" path), and the raw constraint text is returned to the client. `PATCH …{"enabled":false}` works and is what I used instead. Note `PUT` on the same path 404s — only `PATCH` is registered (`routes/monitorDefinitions.ts:216`), which is a small API-shape wart.

#### D3 — an `expectStatus` of any 3xx can never evaluate healthy: `followRedirects` is not expressible through the monitor API

The agent honours `followRedirects` (`handlers_monitor.go`, default **true**), but `networkCheckConditionSchema` has no such field and `monitorCompiler.ts:220-254` emits only `port` and `expectedStatus`. So a monitor authored with `expectStatus: 301` (exactly the case #6409 fixed) makes the agent follow the redirect and compare the *final* hop's status — it reports `degraded "expected status 301, got 200"` when the target is healthy, and `offline` when the redirect target is unresolvable. Observed both, verbatim, on `lab3-http-301`. Not a regression from #6409 — #6409 is what made the value reach the agent at all — but the feature is unusable for 3xx expectations until `followRedirects` is added to the condition schema and the compiler. Suggest a follow-up issue.

#### D4 (lab/ops, not product) — watchdog silently restarts `breeze-agent`, invalidating an "agent stopped" test

`sudo systemctl stop breeze-agent` on KIT at 07:32:54 was undone by `breeze-watchdog` at **07:34:55** with no operator-visible signal on the server side; the device simply went back `online`, and my first #6410 offline run was measuring an online device. Anyone scripting an offline test must stop `breeze-watchdog.service` first. Worth a line in the lab/testing docs.

#### Non-defect worth recording (cost me ~20 min, twice)

1. **`details` key names for an S3 backup config are asymmetric.** The API accepts `accessKeyId`/`secretAccessKey` **or** `accessKey`/`secretKey` (`services/backupSnapshotStorage.ts:66-68`), but the **agent reads only `accessKey`/`secretKey`** (`agent/cmd/breeze-backup/exec_backup.go:78-85`). A config saved with the AWS-idiomatic spelling validates, persists, and dispatches — and every upload then runs with empty credentials, falls into the SDK's default credential chain, and dies on an IMDS/DNS timeout that `attemptFileUpload` (`agent/internal/backup/snapshot.go:1557-1576`) reports as **`upload stalled: no completion within 5m0s` after 5.001 s**. `net.DNSError.Is(context.DeadlineExceeded)` is true for a DNS timeout, so a plain connectivity error is laundered into the mid-body-stall message, and the log even prints `deadlineMs=300000 elapsedMs=5001` side by side without complaint. Two cheap improvements: (a) reject unknown/AWS-spelled credential keys at `validateS3Details`, or normalise them the way the endpoint is normalised; (b) in `attemptFileUpload`, only claim "stalled" when `elapsed >= deadline`. Not filed as a defect because nothing shipped in this window touches it — but it is the same class of "green test that lies" the endpoint-coercion comment in `schemas.ts` was written about.
2. **The lab has TWO MinIO backends, not one.** `http://…:9012` and `https://…:9022` do **not** share storage: objects written over 9022 are invisible over 9012 and vice versa. I briefly mis-read this as a GC/retention data-loss incident. Not a product defect; worth a line in COMMON.md so the next agent does not chase it.

### Defects found

#### D1 (new, p1) — an `offline` monitor never fires for a WebSocket-connected agent, so #6378 is unreachable in production

**Repro.** Attach an `offline` monitor to a device running a live agent (any duration) and
stop the agent. Observed: `alerts` stays empty indefinitely; `offline_transition_effects` never
gets a row for the device. Held for 11 minutes at 30-second resolution
(07:16:53Z → 07:27:33Z), `alerts = 0`, `offline_transition_effects` rows for the device = 0.

**Mechanism (verified by reading the code, then by forcing the state):**

1. `agentWs.ts`'s close handler calls `updateDeviceStatus(agentId, 'offline')`
   (`routes/agentWs.ts:3486`, `:3496`, `:3547`), which sets
   `{ status: 'offline', lastSeenAt: new Date(), … }` (`:1161-1177`). Confirmed in the DB:
   `status` was `offline` 38 s after `docker stop`, with `last_seen_at` equal to the
   disconnect instant.
2. `processDetectOffline` — the *only* caller of `persistOfflineTransition`
   (`jobs/offlineDetector.ts:448`) — selects on
   `or(eq(devices.status,'online'), eq(devices.status,'updating'))` **and**
   `lt(devices.lastSeenAt, thresholdTime)` (`:333-336`). Step 1 has already falsified both
   halves. The device is never selected, so no transition is persisted, so
   `expandOfflineAlertPlan` — the function #6378 fixes — is never invoked.
3. The compensating sweep does see already-offline devices
   (`processReevaluateOfflineSweep`, `eq(devices.status,'offline')`, 60 s cadence,
   `:614-621`) but `processReevaluateOffline` calls only
   `triggerConfigPolicyOfflineAlerts` → `evaluateDeviceAlertsFromPolicy(device.id)`
   (`:500-522`, `:566`) — the config-policy alert path, not compiled monitor rules. #6378
   did not extend this second path. Consistent with the empirical result: that sweep ran
   ~11 times during the window and created nothing.

The two seeded e2e fixtures **do** produce transitions (rows at 07:09:30) precisely because
they have no WebSocket — their rows sat at `status='online'` with a stale `last_seen_at`, which
is the only shape `processDetectOffline` accepts.

**Blast radius (inferred, not exhaustively checked):** this is not monitor-specific at the
transition layer — *no* device with a live agent WS ever produces an
`offline_transition_effects` row on a clean disconnect, so everything hanging off
`expandOfflineAlertPlan` is affected. Legacy config-policy offline rules survive only because
rung 3 re-evaluates them separately. Monitor-kind `offline` has no such second path and is
therefore dead in the field.

**Suggested fix direction (not implemented):** either have the WS close handler persist the
offline transition it is effectively declaring, or extend `processReevaluateOffline` to cover
monitor rules the way `expandOfflineAlertPlan` now does. The second is the smaller change and
reuses the deferral logic #6378 already added.

#### D3 (minor) — `GET /devices/:id/monitors` returns `{"error":"PAM actuator is disabled"}`

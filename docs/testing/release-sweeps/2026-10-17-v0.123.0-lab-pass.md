- Fault on (03:16:57) [verified]: Linux 03:17:14 and Windows 03:17:27 → `retainState=["pam","helper"]`, `uacInterceptionEnabled` / `helperEnabled` / `helperSettings` omitted. On Windows, Assist kept running (pid 5504, started 03:11:27, unchanged at 03:17:43), and no `UAC interception disabled` or `breeze assist uninstalled` line was logged.

So this run shows the kill switch removing `retainState`; it does not show the legacy downgrade. That would need an uncached resolver failure, and see the next bullet.
- **Finding (API, pre-existing).** Once the remote-access policy cache expired (03:25), every heartbeat for both agents returned **HTTP 500** [verified]. The log shows `[heartbeat] Failed to resolve remote access policy: … permission denied for table device_group_memberships`, then the request fails with the same error. The resolver's `try/catch` (`heartbeat.ts:2238–2244`, from #8053) runs inside the org transaction with no savepoint. [inferred] The caught error aborts the transaction, and the commit re-throws it. The log shows the same `permission denied` error after the caught one, not Postgres's "current transaction is aborted", so a later statement in the request hitting the revoked table would look the same. Which statement threw is not pinned down. So #8660's "the remote-access resolver threw → tell a v1 agent to retain remote management" can't be reached for a database error: the agent gets a 500 instead. The agents stay safe (they keep current state on a failed beat and retry). The code is in v0.122.1. Filed as #8997.
- The fault was lifted at 03:26:38 (`GRANT SELECT`); the 500s ran 03:25–03:26:38. Heartbeats were normal again from the next beat, which is why row 3's shipper states (Windows failing since 03:23:27, Linux since 03:28:48) kept arriving.

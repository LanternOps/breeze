## Phase 0 findings (before the stack)

### Portal Dev E2E (hydration) — standing FAILURE on main, not flake

The job is `continue-on-error` on `pull_request` **and** was failing on the
`merge_group` runs of #6442, #6434, #6426 and #6451 — i.e. every entry that
landed, landed with this job red. It is only green where it is `skipped`
(#6481, docs-only). So it is a real break on `main` that the non-blocking flag
has been absorbing, not per-PR noise.

Two specs, both timing out at 30 s:

1. `tests/partner-sending-domains.spec.ts:48` — "The tab is offered and opens
   on its own hash". `page.getByTestId(rootTestId).waitFor()` never resolves;
   the run then reports `Target page, context or browser has been closed`.
   Partner sending domains is feature #6180, whose waves are specced but
   reportedly not implemented — so this spec may be asserting a surface that
   does not exist yet, which would make the spec the defect rather than the app.
2. `tests/multi-currency.spec.ts:97` — "org currency selection, manual invoice,
   and quote acceptance in a EUR org". Fails on
   `expect(an authenticated /api/v1 request from the app).toBeTruthy()` — the
   portal never issues an authenticated API call within 30 s, which reads as a
   hydration or session failure rather than a currency bug.

**RESOLVED — both are E2E test defects, not application defects.** Reproduced
locally against the sweep stack, then diagnosed to root cause.

**Finding 1 — `partner-sending-domains.spec.ts` asserted a testid that does not
exist.** `PartnerSendingDomainsPage.navTab()` looked for
`settings-nav-tab-sending-domains`. That string appears **nowhere** in
`apps/web/src` — the only occurrence in the repo is the page object itself.
`SettingsSectionNav` emits `<testIdPrefix>-tab-<key>`, and `PartnerSettingsPage`
passes `testIdPrefix="partner-settings"` with the camelCase `TabKey`, so the
real id is `partner-settings-tab-sendingDomains`. Verified in a live browser:
15 `partner-settings-tab-*` ids render and the sending-domains one is present
and visible. Step 1 could never have passed. **Fixed** (page object).

**Finding 2 — the same spec waited for a native `confirm()` that the app never
shows.** Step 7 registered `authedPage.once('dialog', …)`, but the tab confirms
removal through its own `ConfirmDialog` (`confirmTestId=
"sending-domains-remove-confirm"`). No native dialog event ever fires, the modal
stays open, and **no DELETE is ever issued** — confirmed against the API log,
which shows create `201`, check `202`, identity `200`, test-send `202` and no
DELETE at all. This is the repo's own documented trap (CLAUDE.md: modals are
`fixed inset-0` divs, assert on testid, not a dialog container). **Fixed**
(click the confirm testid instead of handling a dialog).

Net: steps 2–6 of this spec were already exercising the feature correctly
against a real API. The app is fine; the spec's first and last steps were wrong.

**Still open on this spec:** not yet proven green end to end. Each failed run
leaves a `partner_sending_domains` row behind, and the recommendation card only
renders in the empty state, so a re-run then fails at step 1 for a *third*,
unrelated reason. The spec is not idempotent against its own leftovers — worth
a follow-up issue. A raw `DELETE` is correctly refused by
`breeze_sending_domain_release_guard()` (provider-managed domains must be
released first), so cleanup needs the release path, not SQL.

**Finding 3 — `multi-currency.spec.ts` was a false alarm from my own session.**
Its `readAccessToken()` failures (landing on `/login`, no Bearer request) were
caused by my concurrently signed-in browser session and a tripped login rate
limiter, not by the app. Verified separately that the app does send
`authorization: Bearer …` on every `/api/v1/` call. **Re-measure this one on a
clean stack before drawing any conclusion.**

**Operational note for future sweeps:** the login limiter keys on the *caddy*
IP (`login:ip:::ffff:172.31.2.10`, `login:socket:…:<email>`), so every browser
login on the stack shares one bucket — an agent logging in repeatedly will
rate-limit `globalSetup`. Clear with
`redis-cli --scan --pattern 'login:*' | xargs redis-cli del` using
`REDIS_PASSWORD` from `.env`.

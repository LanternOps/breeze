## Self-Hosting / Upgrade Notes (fold into the release body)

- **Agent: reconnect and Retry-After pacing (W09, #8148).** After a stable connection drops, agents now redial after a random 1–30 s (was 1–5 s); the first dial after process start waits 0–10 s. A device can show offline up to ~30 s longer after an API restart. Agents honour a `drain` frame (`{"type":"drain","reconnectWithinMs":N}`, spread over max(N, 5 s)); dormant until the API sends it (W5c). A `503`/`429` with `Retry-After` on a periodic upload (inventory incl. event logs, recovery keys and the daily patch scan, monitoring results, process samples, peripherals, boot/reliability, message events, logs, UniFi) now defers that route until the delay passes (max 300 s) instead of retrying next cycle; heartbeats and command results are never deferred. Startup inventory/hardware/patch uploads each wait 0–120 s; the first monitoring pass waits up to min(interval, 60 s). Command results produced while the socket is down go straight to the durable outbox. New `agent.yaml` keys: `ws_first_reconnect_window_seconds` (default 30, 0–300; 0–5 restores the 1–5 s spread) and `loop_retry_after` (default true). New agent log lines: `initial connect delayed`, `drain hint received`, `route deferred by server Retry-After`, `command result held for reconnect; persisting to the outbox`, `startup task delayed`, `monitoring first run delayed`; `disconnected` gains `drainWithin` when a hint applied. Docs: deploy/upgrades → Agent reconnect settings.
- **Install scripts (#6958).** Install scripts stored on software versions before this release stay inactive until the version is re-created; the version manager shows a notice.
- **`software_compliance_status` forced RLS (#10022).** The table now has forced row-level security on databases created from the baseline.
- **Boot task: pinned built-in package refresh (#6958).** On start the API moves provisioned DNS built-in packages to the code-pinned version. Log line: `[startup] pinned built-in package refresh: refreshed N, failed M`.
- #6958 adds no new environment variables.
- **AI chat tool index: new optional `AI_TOOL_INDEX` (#10065).** `lazy` (default) or `full`. `full` restores the previous system prompt that lists every tool; set it in the `api` service if the AI assistant picks tools worse after upgrading. A conversation picks up a change when its AI session is next started (new conversations, or existing ones after an API restart); no migration.
- **Wisp migrations (hosted-only feature; nothing changes with the flag unset).** This release carries the Wisp schema: `2027-01-04-100000-partner-entitlements.sql` (partner entitlements), `2027-01-04-100100-wisp-grants.sql`, `2027-01-04-100110-ai-workspace-execute-permission.sql`, `2027-01-04-110100-ai-memory-blocks.sql`, `2027-01-04-110200-wisp-threads.sql`, `2027-01-04-110300-wisp-concerns-watches.sql`, `2027-01-04-110350-ai-agent-runs-assessment-profile.sql`, `2027-01-04-110400-wisp-nudge-preferences.sql`, and (arriving with the specialist wave) `2027-01-05-100400-wisp-specialist-lineage.sql`. They run on boot like any other migration. Wisp itself is hosted-only: with `BREEZE_WISP_ENABLED` unset (the default) no Wisp route, job or UI is active, and a production API refuses the flag without `IS_HOSTED=true`. Self-hosters do not need to set anything. `BREEZE_WORKSPACE_ENABLED` (Wisp's file/email knowledge connector, needs pgvector) is a separate, independent flag.
- #9840 adds no new environment variables, no migration and no setting; the new route needs no proxy change beyond what `POST …/messages` already needs for SSE.
- **Windows feature releases are now decided by the update ring (agent default changed).** The agent's local `patch_exclude_feature_updates` used to default to `true` and silently kept every Windows feature release ("Windows 11, version 25H2") out of Breeze. It now defaults to `false` and acts only as a kill switch; the ring's new **Windows feature updates** setting (block, default) decides instead, pushed in the heartbeat block `feature_update_settings`. Nothing changes until a ring is set to Allow or Pin. A ring pinned to a release writes the Windows Update for Business target-release policy on each device (`TargetReleaseVersion`, `TargetReleaseVersionInfo`, `ProductVersion` under `HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate`) with a Breeze ownership marker; switching back removes only values Breeze wrote. That is Windows' own policy: unless the patch policy's exclusive-Windows-Update setting is on, Windows may install the pinned release on its own schedule. Optional (BrowseOnly) non-feature updates stay hidden as before; installed feature releases now appear in the installed inventory. Agent log lines: `applied Windows feature-update policy`, `ignoring feature_update_settings`. The agent that ships with this release is needed for the device-side filter and the registry policy; older agents keep excluding feature releases locally (their default was `true`).
- **IOC sweeps: nine optional settings (#6263 W05).** All are optional and default sensibly: `SECURITY_SWEEP_MAX_DEVICES` 10000 (devices per sweep request), `SECURITY_SWEEP_MAX_ACTIVE_PER_ORG` 5, `SECURITY_SWEEP_PUMP_INTERVAL_MS` 30000, `SECURITY_SWEEP_PUMP_BATCH` 100 (scans admitted per sweep per organization per tick), `SECURITY_SWEEP_PARTNER_RUNNING_CAP` 200, `SECURITY_SWEEP_TTL_HOURS_DEFAULT` 24 (a request may ask for 1 to 72), `SECURITY_SWEEP_MFA_DEVICE_THRESHOLD` 50, `SECURITY_SWEEP_RUNNING_GRACE_MINUTES` 65 and `IOC_HUNT_FOUR_EYES_DEVICE_THRESHOLD` 25 (AI-started sweeps above this many expected devices need a second approver). They are not mapped in the Compose files; add them to the `api` service `environment:` if you want to change one. "MFA" here means multi-factor authentication as the organization's policy requires it: a sweep above 50 devices needs an interactive sign-in with that check satisfied, and API keys are refused above 50 whether or not `ENABLE_2FA` is on.

- **S3 destination prefixes now relocate new snapshots (#7081).** A destination
  with a **Path Prefix** writes its new snapshots under `<prefix>/snapshots/`
  instead of bucket-root `snapshots/`. Existing snapshots are not moved and keep
  restoring from where they are. Applies automatically to every destination that
  already has a prefix:
  - The first backup after upgrading on such a destination is a **full backup**
    (an incremental never builds on a snapshot stored under another prefix). The
    same happens after any later prefix change; an incremental already scheduled
    against a base under the old prefix is refused (`base_key_root_mismatch`) and
    the next run is full.
  - **IAM:** a policy scoped to `bucket/snapshots/*` must also allow
    `bucket/<prefix>/*`. **Test connection** writes under the prefix and catches
    this. The conditional-write capability probe now also writes under
    `<prefix>/breeze-capability-probe/`.
  - A destination whose stored prefix is invalid (empty or `.`/`..` segments,
    characters outside `A–Z a–z 0–9 ! _ . * ' ( ) -`, a `snapshots` segment, over
    256 characters) is no longer backed up: its backups fail with
    `invalid_destination_prefix` and a message asking for a corrected prefix, and
    **Test connection** now fails for it (it used to pass). Fix it in the
    destination form (it flags the problem inline).
  - Do not roll back below v0.124.0 after this release has written prefixed
    snapshots: older API versions cannot read them.

## Features / API

- **Update rings: Windows feature updates (block / allow / pin).** Each ring now says whether its devices receive Windows feature releases: **Block** (default, the previous behaviour), **Allow the newest release**, or **Pin to a release** (Windows 11 or 10 plus a release like `25H2`). Allowed or pinned releases go through the ring's normal approval rules; a pin also sets the Windows Update for Business target-release policy on each device so Windows offers and holds at that release. API: `featureUpdates` on `POST/PATCH /api/v1/update-rings` and in the list response; the `manage_update_rings` AI tool takes the same field. A release the ring blocks shows as excluded on the device Patches tab (`blocked_by_feature_update_policy`). The agent types Windows Update's **Upgrades** classification as the `feature` category, so a Feature Updates category override now matches feature releases.
- **Install scripts, zip packages and built-in DNS packages (#6958).** Software versions can use the `zip` package type (extract-only; a post-install script is required) and carry pre/post-install scripts that run as SYSTEM/root with a 10-minute timeout each. Creating a version with a script requires `devices.execute`. Partner admins can also add two Breeze-pinned DNS filtering clients, Control D and NextDNS CLI for Windows, from Software → Catalog → Built-in packages. Agent 0.125.0 or newer is required for zip packages and scripts; older agents fail the device with `agent_update_required` and nothing is dispatched.
- **Move AI conversations between the side panel and the AI Assistant (#9840).** A conversation moves from the side panel to an AI Assistant tab (**Open in AI Assistant**) and back (**Continue in side panel**, in the chat header and the tab menu) with its history, device binding, model and unsent text; nothing is duplicated or deleted. A reply that is still streaming carries over and keeps streaming, and a pending approval card moves with its original deadline. The side panel's History and the AI Assistant's new **Open a past conversation** picker share one list with organization and **Device** chips, and label a conversation open on the other surface. `/workspace#session=<id>` deep-links a conversation and the URL follows the active tab. API: `GET /api/v1/ai/sessions/:id/stream` is a new read-only route that follows a session's current turn; `GET /api/v1/ai/sessions` and `/search` return only chat conversations and now carry `orgId`, `type` and `deviceId` (search also `status`). The mobile app's history list stops showing script-authoring and MCP sessions — intended.
- **Smaller AI chat prompt (#10065).** The AI assistant's system prompt now describes tools by domain instead of listing every tool (about 4.4 KB smaller); a chat opened on a device or alert page also lists that page's tools. Every tool stays available: the model still sees every tool name, in the deferred-tool list with tool search or as the full tool list without it. Golden eval: mean first-call accuracy unchanged (24.7 → 24.7 of 75 with tool search, 23.5 → 24.5 without), with one case lost in every run (a backup-SLA question now picks `query_backup_sla`) and one page-context case lost (on a device page the model first looks the device up before disabling a startup item). `AI_TOOL_INDEX=full` restores the old prompt.
- **Service compliance (#6958).** New `service_running` detection clause and two new software-policy violation types, `not_running` (high) and `service_unverified` (low, never triggers a reinstall). Allowlist rules derive per-device service watches, shown on the device monitoring tab, and an armed policy restarts a stopped service automatically.
- **Wisp (hosted, paid plans): a continuous triage companion.** Wisp works for one person under a self-only, 90-day grant (partner-wide or one organization, step-up MFA to create), watches what that person may see, and nudges them about concerns with quiet hours, a proactivity dial, a morning brief and feedback on each nudge. It keeps confirmable memory (`/settings/wisp-memory`), meters spend against a per-grant daily budget (defaults 200 / 500 / 1000 cents for Pro / Enterprise / Unlimited, raisable to 5x), and can request specialists (`sweep`, `analysis`, `operator_recipe`, `patch_plan`, `remediation_research`, `bulk_ticket_reply`); `sweep` and `analysis` start on their own, the rest wait for a yes on an approval card. Anything that changes something goes through the existing approval tiers. Dark unless `BREEZE_WISP_ENABLED=true` on a hosted deployment (`IS_HOSTED=true`, `BREEZE_AI_AGENTS_ENABLED=true`) and the partner's `wisp` entitlement is on. New docs page: Features, Wisp.

- **PAM: agents report an elevation they cannot act on (#9517).** New agent route `POST /api/v1/agents/:id/pam/elevation-unable` (admission class `protected`). When the agent gives up on the PAM flow (requester session found but not active, helper did not start within the 30-second wait or lacks the PAM scope), it reports the request; uncertain cases (session unresolved, session check failed, session not in the snapshot before or during the helper wait, lease refused, a ready helper not found, no session broker or lifecycle manager yet) stay pending for the stale-request expiry; a still-pending request is closed as `expired` and the server then withdraws its mobile approvals (best-effort; a phone approval of a closed request is refused either way), and the PAM requests list shows that the device could not act under the Expired or All filter. New log lines: agent `pam: reported the elevation as unable to the server` / `pam: could not report the elevation as unable`; the API publishes `elevation.expired` with `cause: device_unable` (best-effort, like the stale-request expirer's: a failed publish is logged and the row stays the record). Older agents keep the previous behavior (the request stays pending until the stale-request expiry).

- **IOC sweeps (#6263 W05).** Run published detection rule sets across many devices at once. New routes under `/api/v1/security`: `POST /sweeps/preview`, `POST /sweeps` (needs the `previewDigest` from the preview), `GET /sweeps`, `GET /sweeps/:id`, `GET /sweeps/groups/:groupId`, `POST /sweeps/:id/cancel` and `POST /sweeps/groups/:groupId/cancel` (writes need `devices:execute`, reads `devices:read`). The console gets **Sweep now** on a rule set and a **Sweeps** tab on **Security → IOC Scans** (`#sweeps&group=<groupId>` deep link). Sweeps are detect-only and never start a Defender scan. Each sweep pins the rule-set versions it was approved with; threats show **Version N**, and a republish mid-sweep fails the remaining scans with `rule_set_changed`. Scans gain two states, `cancelled` and `expired`, so API consumers filtering `GET /security/scans/:deviceId` by status will now see them. The AI assistant and MCP get an `ioc_hunt` tool: reads are Tier 1, `cancel_sweep` Tier 2, and `sweep` and `import_iocs` Tier 3 (approved; a second approver above 25 devices; one organization per AI sweep; importing into an auto-quarantine set is refused). Also fixed: a throttled scheduled security scan was previously never retried; the AI `security_scan` `scan` action now records a scan row and returns without waiting; custom scan paths on `POST /security/scan/:deviceId` are now capped at 1024 characters.

- **Destination form:** the Path Prefix field explains the new layout and
  validates as you type; Save stays disabled while the prefix is invalid.
- **BMR:** the recovery authenticate and exchange routes refuse with `409`
  `recovery_requires_token_mode` if a prefixed snapshot's bootstrap ever lacks the
  token-mode download descriptor (defensive; the descriptor is always issued today).

## Migrations

- `2027-01-06-140000-patch-policies-feature-updates.sql`: one defaulted jsonb column `feature_updates` on `patch_policies` (`{"mode":"block"}`) plus an object-type CHECK; DDL only, no rewrite.
- `2027-01-02-180000-elevation-device-unable.sql`: three nullable columns on `elevation_requests` (`device_unable_at`, `device_unable_reason`, `device_unable_detail`) and the `device_unable` value on `elevation_audit_event_type`. The column adds are metadata-only, but the new CHECK `elevation_requests_device_unable_chk` is validated in the same statement, so Postgres scans `elevation_requests` once under the migration's lock (no rewrite). The table holds every elevation request (UAC prompts, technician JIT grants, governed AI tool actions), so the lock is held for one sequential scan of it. Scan time depends on the table's size on disk, its live row count (each row's CHECK is evaluated) and the storage's read speed. Measured on one idle host (PostgreSQL 16, local NVMe, a synthetic copy of the table at about 600 bytes a row): 1 million rows (600 MB) validated in 0.21 to 0.22 s over three warm runs; 10 million rows (6 GB) in 5.0 s with the OS and Postgres caches cleared and 2.1 s warm (one run each). Anything that reads or writes `elevation_requests` (new UAC requests, approvals, the requests list) waits that long. These are single-host measurements, not a guarantee: slower, shared or busy storage, lock waits and concurrent traffic can make it materially longer. Check `SELECT pg_size_pretty(pg_relation_size('elevation_requests'))` before upgrading and plan a quiet window when that size is large for your storage.
- `2027-01-05-100400-wisp-specialist-lineage.sql` (arrives with the Wisp specialist wave): three nullable/defaulted columns on `ai_agent_runs` and `ai_operator_tasks`; DDL only.
- `2027-01-04-140000-security-scan-sweeps.sql` (#6263 W05): creates `security_scan_sweeps` (empty at upgrade, row-level security forced) and adds three nullable columns to `security_scans` (`sweep_id`, `dispatched_rule_sets`, `command_id`; metadata-only, no table rewrite) plus one partial index on `sweep_id IS NOT NULL`, which is empty until the first sweep.

### Flows W05 (#5215 / #5220, PR A)

Everything below is behind `FLOWS_ENABLED` (default off); with the flag off the new route answers 404 and nothing changes.

- **Webhook trigger (ingress only in this PR).** New public route `POST /api/v1/webhooks/flows/:flowId`. A sender signs with the Breeze scheme automations already use (`X-Breeze-Timestamp` + `X-Breeze-Signature: sha256=<HMAC-SHA256 of "<timestamp>.<raw body>">`, ±5 minutes) or, in token mode, sends the flow's secret in `X-Breeze-Webhook-Token`; `?token=` is not supported. JSON object bodies only, at most 256 KB. An optional `X-Breeze-Delivery-Id` (`^[A-Za-z0-9._:-]{1,128}$`) makes sender retries idempotent; a replayed signed request, with or without a new delivery id, answers `200 duplicate` with the first run. Partner-wide flows map the delivery to an organization through `organization_external_links` (or a Breeze organization id). Every authenticated delivery is logged without its body (`GET /api/v1/flows/:id/webhook-deliveries`). Webhook runs never honour pre-approvals. Flow documents cannot use a webhook trigger yet (the validator refuses it until W5 PR B), so no delivery is accepted until then.
- **Webhook secret.** `POST /api/v1/flows/:id/webhook-secret` (`automations.write` + MFA, interactive session) creates or rotates the flow's secret and shows it once; rotation cuts the old secret off immediately. Enabling a webhook flow requires a secret (`webhook_secret_missing`).
- **Monthly run caps.** Every run is counted against a per-flow cap (default 10,000 a month) and a per-owner cap (default 100,000; a partner-wide flow counts against the partner). At a cap the run is refused (`flow_monthly_cap_reached` / `owner_monthly_cap_reached`, `429` for webhook and manual starts) — the flow is not paused — and the flow's delegator gets one notice per flow, month and cap. Limits are read from `flows` in partner / organization settings (an organization may only lower the partner's value); there is no settings page for them yet.
- **Parallel for-each.** A Tier-1 or Tier-2 step (never `wait`) with `forEach.concurrency` above 1 now runs that many items at once (at most `FLOW_FOREACH_MAX_PARALLEL`, 20 per worker process). Enabling refuses `concurrency > 1` only on a Tier-3 or `wait` step.
- **Retention.** Refused, org-unresolved and invalid webhook delivery rows are deleted after `FLOW_WEBHOOK_DELIVERY_RETENTION_DAYS`; accepted rows live as long as their run. Usage counters are deleted 13 months after their month.
- **New optional environment variables:** `FLOW_WEBHOOK_RATE_PER_MINUTE` (default 120, 1–6000; per flow, after authentication), `FLOW_WEBHOOK_DELIVERY_RETENTION_DAYS` (default 30, 1–365), `FLOW_FOREACH_MAX_PARALLEL` (default 5, 1–10).
- **Migration** `2027-01-07-140000-flow-webhooks-tools-budgets.sql`: creates `flow_webhook_deliveries` and `flow_usage_counters` (empty at upgrade, forced row-level security), adds nullable columns to `flows` (webhook secret and markers), `flow_runs` (`ai_tokens_used` defaulted 0, `parent_agent_run_id`, `triggered_by_api_key_id`), `flow_run_steps` (AI usage), `action_intents.invoked_flow_id` and `ai_invocations.flow_run_id`, and widens the flow-run CHECKs by name; DDL only, no backfill.

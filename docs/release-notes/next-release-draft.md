## Self-Hosting / Upgrade Notes (fold into the release body)

- **PostgreSQL 17 and 18 are now tested and supported; the default stays 16** (#11416, #11418). `docker-compose.yml` pins `PGDATA` on `postgres` (no-op on 16/17: the container restarts once) and adds an optional second data volume selected by `POSTGRES_DATA_VOLUME`, used only by the new [PostgreSQL 16 to 18](https://docs.breezermm.com/deploy/upgrades/#postgresql-16-to-18) runbook. **Already running 18 with your volume at `/var/lib/postgresql`:** check `SHOW data_directory` and keep `PGDATA` on `/var/lib/postgresql/18/docker` (see the Compose file changes entry). If you take the release's `postgres` block with that mount, Postgres now refuses to start and logs the `PGDATA` to set, instead of initializing an empty database. Merging only the `PGDATA` line gives you no such check.
- **Portal Sign in with Google (new, optional, off by default)** (#11384). Three new env vars: `PORTAL_GOOGLE_CLIENT_ID`, `PORTAL_GOOGLE_CLIENT_SECRET` and `PORTAL_GOOGLE_CALLBACK_BASE_URL` (optional; falls back to `PUBLIC_URL`, `PUBLIC_APP_URL`, `PUBLIC_API_URL`). With them unset nothing changes: no Google row, button or copy appears and every Google route answers 404. Leave them unset until Google sign-in is announced as supported. Once the client is set, boot also needs a valid callback base (`PORTAL_GOOGLE_CALLBACK_BASE_URL` or one of the fallbacks). The only redirect URI to register is `https://<your-breeze-domain>/api/v1/portal/auth/oidc/google/callback`. The client id must be lower-case and end in `.apps.googleusercontent.com`; a malformed value fails boot.
- **Behaviour change: conflicting portal access requests** (#11384). A Microsoft (or Google) portal sign-in in approval mode at an address that already has a pending request for a different identity (another account, another provider, or a pending self-registration) is now refused instead of silently keeping the first request. The portal tells the person a request for their address is already waiting (`/login?sso=request_pending`) instead of the generic failure. The MSP denies the pending request, then the person signs in again.


## Features / API

- **Jobs can be created again while Flows is on; Flows is marked as a preview** (#12310). Since v0.125.0, **New job** opened Flows and `POST /api/v1/automations` answered `410 automations_moved_to_flows` whenever `FLOWS_ENABLED` was on (the default). A flow can only be drafted by Breeze AI or moved from an existing Job, so a tenant without AI had no way to create an automation. **New job** now opens the Job form and `POST /api/v1/automations` creates a Job whatever `FLOWS_ENABLED` says; the 410 is no longer sent. The Flows nav entry and page carry a **Preview** tag, and the empty Flows page explains what a flow is and how to make one. Moving a Job to a flow, and moving it back, are unchanged. The create refusal returns in a later release, together with a flow editor (#10336).

- **Tool profiles and context window in the model drawer** (#11393 W05, #11398). Partners can now set a model's tool profile (Auto, Full, Standard, Minimal, Custom) and, on OpenAI-compatible endpoint models, a context window override, under **AI Providers & Models → Models → (model) → Tools and context**. `PATCH /ai/models/offerings/:id` accepts `toolProfile`, `toolAllowlist` and `contextWindowOverride`, behind the same billing-management, partner-wide and MFA gates as the rest of the model record, and audited with the values before and after. A write that would take a required tool away from a feature the model serves is refused (`422 tool_profile_underpowered`). Nothing changes until a partner saves a profile or override: existing rows stay `auto`. A profile change restarts open conversations on that model at their next message (the user is asked to resend). The drawer also shows each feature's verify round trip and states that verify is real traffic billed by the partner's provider (up to about 128k tokens per request on chat Full).

- **Analysis investigations from Wisp chat** (#11844 W06, #11850). Wisp can run a sandboxed analysis across a whole customer, a site or chosen devices, bring the result and its files back to the conversation, and continue from an earlier step with that step's files. Chains stop at 8 continuations deep, 12 runs or $6.00 by default; the grant's daily budget (200 ¢ on Pro) usually stops first, so a partner admin raises it for long investigations. The run card shows the step, goal, findings, cost and files; the run page lists the chain and the device scope. Hosted only, behind the existing AI workspace and Wisp switches; no new env var.

- **Jobs to Flows conversion census: three more counts** (#12439, part of #12433). `apps/api/scripts/automationConversionCensus.ts` now also prints `byClass.C` (config-policy automations that are not retired, total and enabled), `notFormShapedEnabledUnswitchedS` (enabled Jobs not yet moved whose converted flow the editor opens read-only on the Document tab) and `webhookScriptJobs` (enabled Jobs not yet moved that have a webhook trigger and run a script or command). A row the converter or the form recognizer fails on is counted (`conversionErrors`, `formRecognizerErrors`) instead of stopping the run. The census still prints aggregates only, never an id, a name or an error message. Nothing changes for users.
- **Flows: an on-failure notice no longer fails every clean run** (#12481). A for-each step whose `when` is not true (and does not use `item`) is now recorded `skipped` when its items are not a list. Before, the step failed with `input_invalid` and the run ended `failed`. This is the shape of the on-failure notice the Job converter emits (and the upcoming flow editor's on-failure Notify): on a run where no device failed, the run ended `failed`. No change for a true `when`, for listable items, or for `too_many_items`.

- **Build flows by hand in the new flow editor** (preview). **New automation** on the Flows page opens a guided form for a trigger (schedule, event, webhook or manual), a target and ordered actions (run a script, send a notification, raise an alert), with a **Document** tab for the flow as JSON, with completion and inline validation. Save from the editor, or use **Save and enable**. Enabled flows are read-only until you choose **Disable and edit**, and a never-enabled draft can be deleted from its flow page (needs the delete permission and MFA). A document the form cannot fully show opens read-only in the form; edit it on the Document tab.
- **Flows: four new API routes**, all under `/api/v1` and answering 404 when `FLOWS_ENABLED` is off: `POST /flows` (create a draft), `PUT /flows/:id` (replace a draft's document), `DELETE /flows/:id` (delete a draft) and `POST /flows/validate` (check a document without saving). `PUT` and `DELETE` require `expectedVersion`. See the [API reference](/reference/api/#flows).
- **One "Automations" sidebar entry** replaces the separate Jobs and Flows entries. It opens Flows when Flows is enabled, otherwise Jobs. The Flows and Jobs pages share a tab strip. Old links still work: `/automations` goes to `/flows` (or `/jobs` when Flows is off), `/automations/new` goes to `/jobs/new`, and `/automations/<id>` goes to `/jobs/<id>`.
- **Breeze AI `draft_flow` updates without `expectedVersion` now return a warning** (`expected_version_required_soon`). A later release will refuse them, so send the version you loaded.
- **Breeze AI `draft_flow` now also needs `automations.read`** (#12435). It already needed `automations.write`. The REST routes it mirrors sit behind the flows router's read permission, and the tool now requires the same. No built-in role grants write without read. A custom role that grants `automations.write` without `automations.read` can no longer draft flows through Breeze AI or MCP until read is added.
- **Flows is still marked Preview.**
- **Behaviour change: an empty Automations or Compliance list on a closer configuration policy now overrides a broader one** (#12488). These two features now resolve like every other feature: the closest assigned policy that carries the feature wins, even when its list is empty. Before, a closer policy with the feature and no items (or, for Automations, only retired items with no live monitor conversion) was skipped, and devices ran the automations and compliance rules of the next policy up the hierarchy. After upgrading, **those broader automations and compliance rules stop running on the devices the empty closer policy covers**, and open compliance alerts from the broader rules close with "configuration policy … now takes precedence for this device". The device's Effective Configuration tab already showed the closer policy as the source; the runtime now agrees with it. To keep the broader list on those devices, remove the Automations or Compliance feature from the closer policy rather than leaving it empty.

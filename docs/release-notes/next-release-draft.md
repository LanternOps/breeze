## Features / API

- **AI tool-discovery telemetry (passive, no model-visible change)** (#12421 W01). Web chat and Wisp sessions now record, once per turn after settlement, which ToolSearch queries the model ran, which tools each returned and which of those it called, in the new table `ai_tool_search_events`; each `ai_tool_executions` row gains `discovery` (how the tool reached the model: `always_loaded`, `searched_this_turn`, `loaded_earlier`, `unknown`) and `tool_use_id`. Queries are redacted, then bounded to 1,024 bytes. Two new Prometheus counters: `breeze_ai_tool_search_total{outcome="hit"|"empty"}` and `breeze_ai_tool_call_total{status}` (no per-tool label). The nightly AI tool-output retention job now **deletes** these rows at the org's tool-output window, never later than 180 days (keep-forever orgs included), and blanks the ToolSearch query inside assistant transcript rows of the same age. A write failure is logged and never fails the turn. Operators can summarise it with `pnpm --filter @breeze/api ai:discovery-report --days 7 [--org <id>]` (output under `apps/api/.ai-reports/`, gitignored, pruned after 30 days). No new env var.

- **Jobs can be created again while Flows is on; Flows is marked as a preview** (#12310). Since v0.125.0, **New job** opened Flows and `POST /api/v1/automations` answered `410 automations_moved_to_flows` whenever `FLOWS_ENABLED` was on (the default). A flow can only be drafted by Breeze AI or moved from an existing Job, so a tenant without AI had no way to create an automation. **New job** now opens the Job form and `POST /api/v1/automations` creates a Job whatever `FLOWS_ENABLED` says; the 410 is no longer sent. The Flows nav entry and page carry a **Preview** tag, and the empty Flows page explains what a flow is and how to make one. Moving a Job to a flow, and moving it back, are unchanged. The create refusal returns in a later release, together with a flow editor (#10336).

- **Jobs to Flows conversion census: three more counts** (#12439, part of #12433). `apps/api/scripts/automationConversionCensus.ts` now also prints `byClass.C` (config-policy automations that are not retired, total and enabled), `notFormShapedEnabledUnswitchedS` (enabled Jobs not yet moved whose converted flow the editor opens read-only on the Document tab) and `webhookScriptJobs` (enabled Jobs not yet moved that have a webhook trigger and run a script or command). A row the converter or the form recognizer fails on is counted (`conversionErrors`, `formRecognizerErrors`) instead of stopping the run. The census still prints aggregates only, never an id, a name or an error message. Nothing changes for users.
- **Flows: an on-failure notice no longer fails every clean run** (#12481). A for-each step whose `when` is not true (and does not use `item`) is now recorded `skipped` when its items are not a list. Before, the step failed with `input_invalid` and the run ended `failed`. This is the shape of the on-failure notice the Job converter emits (and the upcoming flow editor's on-failure Notify): on a run where no device failed, the run ended `failed`. No change for a true `when`, for listable items, or for `too_many_items`.

- **Build flows by hand in the new flow editor** (preview). **New automation** on the Flows page opens a guided form for a trigger (schedule, event, webhook or manual), a target and ordered actions (run a script, send a notification, raise an alert), with a **Document** tab for the flow as JSON, with completion and inline validation. Save from the editor, or use **Save and enable**. Enabled flows are read-only until you choose **Disable and edit**, and a never-enabled draft can be deleted from its flow page (needs the delete permission and MFA). A document the form cannot fully show opens read-only in the form; edit it on the Document tab. If a script can't be sent to a device, **Notify** sends one summary per channel for that script, with the succeeded and failed device counts (#12596); a flow moved from a Job keeps its one-notice-per-failed-device shape. Validation problems are explained in your language, with the server's text as the fallback for a problem the editor does not know (#12497). **Disable and edit** on a webhook flow warns that re-enabling after an edit clears the webhook secret (#12598). The event trigger says what happens when the event you picked arrives without a device.
- **Flows: four new API routes**, all under `/api/v1` and answering 404 when `FLOWS_ENABLED` is off: `POST /flows` (create a draft), `PUT /flows/:id` (replace a draft's document), `DELETE /flows/:id` (delete a draft) and `POST /flows/validate` (check a document without saving). `PUT` and `DELETE` require `expectedVersion`. See the [API reference](/reference/api/#flows).
- **One "Automations" sidebar entry** replaces the separate Jobs and Flows entries. It opens Flows when Flows is enabled, otherwise Jobs. The Flows and Jobs pages share a tab strip. Old links still work: `/automations` goes to `/flows` (or `/jobs` when Flows is off), `/automations/new` goes to `/jobs/new`, and `/automations/<id>` goes to `/jobs/<id>`. Searching `jobs` in the command palette opens the Jobs tab, and `G` then `J` opens the same page as the Automations entry (#12498).
- **Breeze AI `draft_flow` updates without `expectedVersion` now return a warning** (`expected_version_required_soon`). A later release will refuse them, so send the version you loaded.
- **Breeze AI `draft_flow` now also needs `automations.read`** (#12435). It already needed `automations.write`. The REST routes it mirrors sit behind the flows router's read permission, and the tool now requires the same. No built-in role grants write without read. A custom role that grants `automations.write` without `automations.read` can no longer draft flows through Breeze AI or MCP until read is added.
- **A flow's notification now links the run that sent it** (#12597). A notice from a flow's Notify step used to link the flow page. This also applies to flows moved from Jobs. Notices already sent keep their old link.
- **A flow that is shadowing a job no longer offers an Enable button that always fails** (#12499). Until the job is switched, the flow page and the editor point to the job's **Switch**, and the editor is **Save** only. A flow whose job has been switched or reverted enables as before.
- **Flows is still marked Preview.**
- **Behaviour change: an empty Automations or Compliance list on a closer configuration policy now overrides a broader one** (#12488). These two features now resolve like every other feature: the closest assigned policy that carries the feature wins, even when its list is empty. Before, a closer policy with the feature and no items was skipped, and devices ran the automations and compliance rules of the next policy up the hierarchy. An Automations list whose items have all been retired (with no live monitor conversion) is still skipped, as before, so retiring a policy's last automation does not switch off broader automations. After upgrading, **those broader automations and compliance rules stop running on the devices the empty closer policy covers**, and open compliance alerts from the broader rules close with "configuration policy … now takes precedence for this device". For an empty list, the device's Effective Configuration tab already showed the closer policy as the source; the runtime now agrees with it. To keep the broader list on those devices, remove the Automations or Compliance feature from the closer policy rather than leaving it empty.

- **Configuration policies show where they apply** (#12306). The policy page has an always-visible **Applies to** line above the feature tabs. It names the first targets, opens the target editor in a side panel, and warns "Not applied to any device" when an active policy reaches nothing. An inactive one reads "Not applied yet"; a parent reads "In use through N policies".
- The policy list has an **Applies to** column, a **Not applied** chip and "In use through N policies" for parents. The ownership badges are gone; org-managed rows read "Managed by <organization>".
- The device **Effective Configuration** tab links the policy that won each feature (when you can open it), names the level it arrived through, and says in plain text why each other policy lost: a more specific level, a lower priority number, or an earlier assignment.
- The create page, editors and device tab use one vocabulary: Applies to, Managed by, Parent policy / Based on, Precedence. A new policy now opens with the Applies-to editor open.
- `GET /configuration-policies` rows and `GET /configuration-policies/:id` gain `appliesTo`; `GET /configuration-policies/effective/:deviceId` gains `policyOwners` (additive). Old `#assignments` links still work.

- **One Applies-to editor for every configuration policy** (#12462, #12467). Changes are staged and committed with one **Apply**, which first states how many devices it adds and removes. All staged changes land together or none do; if someone else changed the policy's targets meanwhile, nothing is applied and the editor offers **Reload**. A change that would leave the policy matching 0 devices you can see shows a warning.
- MSP-managed policies can now target sites, device groups and devices, picked by organization and searched on the server.
- Device counts show on the policy page and in the list. They count only devices you can see, and read "At least N" on very large fleets.
- An MSP-managed policy assigned at a site now shows on that Site page for users who can see the policy.
- **Devices → Groups → Apply policy** applies the policy to every selected group in one change.
- New routes: `POST /configuration-policies/:id/assignments/apply` (staged add, update and remove, with `dryRun`), `GET /configuration-policies/:id/reach` and `GET /configuration-policies/reach?ids=…`. `GET /orgs/sites` accepts `search`.

- **"Outranked on N devices" on each feature of a configuration policy** (#12472) shows where a more specific policy wins that feature. The open feature and its entry in the feature list show the count; it covers only devices you can see. On a very large fleet the page says there are too many devices to count instead of showing a number. New route: `GET /configuration-policies/:id/precedence`.

- **New configuration policies start inactive** and are switched on with **Activate**, which states how many devices it reaches (#12462, #12468, #12469, #12470, #12471). A policy is created on the policy page itself: every feature can be set before anything is saved, and the first Save creates the policy, inactive. Activating a policy that applies nowhere asks where it applies first, or **Don't apply yet**.
- A grouped feature rail replaces the tab strip; the Overview tab is gone. Each feature reads **Set here**, **From parent** or **Not set**, with one rule for **Remove** and **Reset to parent**, and leaving a feature with unsaved changes asks first.
- New policies default to MSP-managed for partner users with access to every organization. Managed by and Based on are fixed at the first save, and the page says so.
- Customer admins see, read-only, the MSP-managed policies that apply to their organization. Users limited to some organizations no longer see MSP-managed policies that apply only to other organizations.
- With one organization selected, the policy list shows the policies that apply to it, plus inactive ones that apply nowhere yet. The list filters by state, not applied and organization, and pages and searches on the server.
- `GET /configuration-policies` accepts `appliesToOrgId` and `notApplied`; `GET /configuration-policies/:id` returns `access`.

- **Copy a configuration policy** (#12309, #11776), to the same owner or to another organization or your MSP. The copy starts inactive and unapplied, and before it is made the dialog lists any feature the new owner cannot carry, with the reason. Copy is in the policy header and on each list row, and it is how to change a policy's Managed by or Based on, or to set OneDrive Helper from an MSP-managed policy. A customer's own admin can copy an MSP-managed policy that applies to them into their organization. New route: `POST /configuration-policies/:id/copy`.

## Self-Hosting / Upgrade Notes (fold into the release body)

- **System Protection (#4609):** deploy the API and web first; there are no new environment variables. The migrations below run automatically on API start. Nothing changes on devices until an agent release that supports System Protection ships.

- **New API env `AGENT_ECH_ENABLED` (#8869, #8882), default `true`.** It is in `docker-compose.yml` and `deploy/docker-compose.prod.yml` (`AGENT_ECH_ENABLED: ${AGENT_ECH_ENABLED:-true}`) and in `.env.example`, and is validated as `true`/`false` in `apps/api/src/config/validate.ts`. Carry it into each droplet's compose `api` environment before deploying. It is the server-side kill switch for agent Encrypted Client Hello, pushed to agents as `configUpdate.ech_enabled`. **Setting it to `false` is a last resort, never a casual flip on a production region:** live connections are not torn down, but the next dial is plain, so every device that can only reach the API over ECH (one behind an SNI-filtering ISP gateway) goes offline and cannot receive the restore until it is on an unfiltered network. #8881 tracks an expiring persisted-off to remove that trap.
- **Agent admission control ships observe-only (#8147, #8456).** The variable is `BREEZE_ADMISSION_MODE` (`off | observe | enforce`). The default is `observe` (`ADMISSION_DEFAULTS.mode` in `apps/api/src/services/admission/admissionConfig.ts`; an empty or invalid value falls back to it with a startup warning). Both compose files pass it through as `${BREEZE_ADMISSION_MODE:-}`, i.e. empty, so a stock deploy only measures and counts. Nothing is refused (503 + `Retry-After` on low-priority agent telemetry, paced agent WebSocket upgrades) until an operator sets `BREEZE_ADMISSION_MODE=enforce`. Heartbeats and recovery traffic are never refused. The tuning knobs (`BREEZE_ADMISSION_LAG_MS`, `_DB_WAIT_MS`, `_EMERGENCY_MS`, `_BULK_MAX_IN_FLIGHT`, `_WS_RATE_PER_SEC`, `_WS_BURST`, `_WS_MAX_SETUPS`) are documented, commented out, in `.env.example`.
- **Migrations: 51 new files** in `apps/api/migrations/` since v0.122.1 (none modified or removed). All are idempotent and apply automatically on API start. Ones worth knowing about are listed under *Migrations* below.

## Features / API

- **Agent: Encrypted Client Hello for control-plane TLS (#8869, #8882).** Some ISP gateway "security" filters (CUJO-based, such as Comcast xFi Advanced Security and Spectrum Security Shield) match the Breeze hostname in the TLS SNI and answer with a plaintext redirect, so the agent logs `tls: first record does not look like a TLS handshake` and never connects. The agent now dials plain TLS exactly as before, and only after it sees that filter signature twice within 10 minutes does it fetch the server's ECH config over DNS-over-HTTPS and retry with the hostname encrypted. Any ECH failure falls back to plain inside the same dial, and repeated failures put the host in a one-hour cooldown. One-shot commands (`enroll`, `bootstrap`, `support`) retry with ECH on the first signature so installs work on a filtered network. Operators can opt a device out with `ech: false` in `agent.yaml`; the server-wide switch is `AGENT_ECH_ENABLED` (see Upgrade Notes). It needs this release's agent, so it takes effect as the fleet updates. Self-hosted edges whose DNS publishes no `ech=` HTTPS record never engage ECH; the device's `control_plane` health component reports the filter and the agent stays plain. Not covered: HTTP-proxied connections and the `install.sh` / PowerShell installer downloads (#8874). Not lab-verifiable: whether the real Comcast/Spectrum gateway passes an ECH ClientHello; that is confirmed only on a blocked PC after release.

- **Windows System Restore: policy-controlled System Protection and per-action reporting (#4609, #4751).** A new **System Protection** policy tab (also available on partner-wide "All orgs" policies) sets whether Breeze requests a System Restore checkpoint before patch installs, scripts and software installs. The server resolves the setting per device, records every request in a new per-device attempts ledger, and shows the outcome as a badge on patch history, script execution details and software deployments, plus a **System Restore** tab on Windows devices. **The agent side is not in this release.** Checkpoint creation and reporting by the agent roll out with a future agent release, so until devices run it every attempt reads **Awaiting the device** and no outcome is reported. Patch installs keep their existing best-effort behavior (a command with no System Protection setting is treated the legacy way: patch installs requested, scripts and software installs not). Turning patch checkpoints *off* cannot be enforced on a device until its agent reports support, and the policy tab says so. Scripts and software installs take no checkpoint until you opt in **and** an agent release that supports it is deployed. System Restore is not a backup. Separately, the native Windows call used for restore points had the wrong struct layout (the SDK header declares both structs under `#pragma pack(1)`); the corrected layout is in the agent code and takes effect with the agent release that includes it. Docs: Configuration Policies > System Protection (includes the support matrix; only Windows 11 25H2 and Server 2022 are verified so far, Windows 10 and Server 2025 are tracked in #8265).

- **Mobile: arrival suggestions (#8209, W2).** With the partner's *Location suggestions* setting on (off by default) and the technician's own opt-in, the app suggests starting a timer when opened at a pinned client site. Foreground only; the phone's position is compared on the device and never sent. Adds the `expo-location` dependency and iOS/Android location permission strings, so it ships with the next **mobile app build** (not an API/web deploy). Technicians with the *Set site location* permission can pin a site from the phone. Docs: Mobile app > Arrival suggestions.

## Migrations

- `2026-12-24-110000-system-protection-feature-type.sql` adds the `system_protection` value to the `config_feature_type` enum. Idempotent (re-running is a no-op), but Postgres cannot drop an enum value, so this one is effectively one-way.
- `2026-12-24-160000-device-restore-point-attempts.sql` creates the `device_restore_point_attempts` table (RLS enabled and forced, org-cascade and export registered). Additive.
- `2026-12-26-230000-ring-app-rules-backfill.sql` (#8186) is a data migration, not just a normalisation: it moves per-app block/pin rules from configuration-policy patch links (`config_policy_feature_links.inline_settings->'apps'`) onto Update Rings (`patch_policies.app_rules`), normalised the way the runtime salvage does. To preserve each policy's effective rules it may **create new rings** (named `<policy> — app rules`, approving nothing) for ring-less links that carry rules, and **clone rings** (named `<ring> — <policy>`, with that ring's patch approvals copied) where linkers of one ring disagree; operators will see these rings appear. Links to an invalid ring are skipped and counted, and those policies now fail closed (`ring_reference_invalid`). It **aborts the migration** if a rule it would move has a non-ASCII package id, or if a ring already carries different non-empty rules; check the API start log for `ring_app_rules_backfill <metric>=<n>` lines. Policy-level auto-approve is not converted. `patch_policies` is partner-axis (no org cascade); its size on each region was not checked.
- `2026-12-27-170000-pam-org-move-unactuated-elevation-restamp.sql` (#8746) adds a `SECURITY DEFINER` function and an `AFTER UPDATE OF org_id ON devices` trigger (`devices_restamp_unactuated_elevation_requests`) that restamps only un-actuated elevation requests on a device org move, and removes `elevation_requests` from the generic device-child cascade list. Fixes org moves of a device whose earlier-epoch actuated request made the move abort with 42501.
- Other backfills over existing rows:
  - `2026-12-23-150000-pam-chain-epoch-anchor.sql` (#8514) sets `device_epoch` on existing `elevation_requests` and `pam_actuations` from `devices.ownership_epoch`, on first application only.
  - `2026-12-27-070000-invoice-line-description-edited.sql` (#8606) adds `invoice_lines.description_edited boolean NOT NULL DEFAULT false` (metadata-only on PG 11+) and, only when it creates the column, marks every time-entry line on a **draft** invoice as edited, so "Refresh from time entries" never overwrites a description that existed before the upgrade. Issued and void invoices are untouched.
  - `2026-12-27-190000-endpoint-messaging-permissions.sql` (#8741) seeds the `endpoint_messages:send` and `endpoint_messages:read` permissions and grants them to the system roles Org Admin, Org Technician and Partner Technician (Partner Admin already holds `*:*`).
- No migration in the range adds a `NOT NULL` column without a default or runs `SET NOT NULL` on an existing column (checked by grep). The `NOT NULL` adds (`backup-key-root` `key_layout ... DEFAULT 'legacy_flat'`, `description_edited ... DEFAULT false`) carry constant defaults. The other `UPDATE`/`INSERT`/`DELETE` statements in `topology-presence-*` and `backup-key-root` are inside trigger function bodies, not backfills.
- Other one-way enum adds (idempotent `ADD VALUE IF NOT EXISTS`, cannot be dropped): `security_provider` `'unknown'` (`2026-12-25-100300`), `monitor_kind` `'container_image_currency'` (`2026-12-26-180000`), `config_feature_type` `'security_agents'` (`2026-12-27-180000`), `notification_type` `'integration'` (`2026-12-29-100000`).

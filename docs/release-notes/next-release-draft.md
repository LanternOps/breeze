## Self-Hosting / Upgrade Notes (fold into the release body)

- **Upgrade deletes the stored credentials of inactive SentinelOne and Huntress integrations. This cannot be undone** (#12743, for #12730). Migration `2027-01-30-190000-clear-credentials-on-inactive-security-integrations.sql` sets to NULL the stored secrets of every SentinelOne and Huntress integration that is not active: the SentinelOne API token and site registration tokens, and the Huntress API key, account key and webhook secret. It reports each cleared count as a `WARNING` in the migration log. This brings integrations deactivated before **Disconnect** existed (through `isActive: false` on the connect route, or an earlier duplicate clean-up) in line with ones disconnected by the new action (#12719): an inactive integration holds no credential. Active integrations and their mappings are not touched, nor is any other column, and a second run changes nothing. Reverting the release does not bring the secrets back. **To use an inactive integration again, reconnect it and enter its credentials again**; a reconnect already did not carry any stored secret over.

- **New env var `MCP_TOOL_LIST_DEFAULT`** (`full` | `progressive`, default `full`; #12427 W01). It sets the external MCP server's default tool list mode. Leave it unset: with `full`, `tools/list`, `initialize` and `server/discover` are unchanged (the `whoami` result gains a `toolListMode` field, and the request audit row of a tool call whose result is an error gains `toolIsError`), and `progressive` lists a small core plus `search_tools`, `get_tool_details` and `call_tool`. Only API keys and OAuth connections set to inherit follow it (next entry). A client can ask for `progressive` on a single request with the `Mcp-Tool-List` header, which is now in the CORS allow list. An unrecognised value falls back to `full` and logs one error. Partner service principal keys stay on `full` unless the request opts in. Mapped in both compose files.

- **MCP tool list mode per API key and per OAuth connection** (#12427 W02). Migration `2027-01-30-160000-mcp-tool-list-mode.sql` adds the nullable column `mcp_tool_list_mode` to `api_keys` and `oauth_grants` and stores `full` on every existing row, once. Nothing changes for existing keys and connections, and they do not follow a later change of `MCP_TOOL_LIST_DEFAULT`. New ones start on inherit (the deployment default, still `full`); an app reconnected after its authorization ended counts as new. The migration updates every existing row of the two tables once and adds a validated CHECK constraint to each, in one transaction. The mode is set in **Settings > API Keys** (create, and a key's details; `mcpToolListMode` on `POST`/`PATCH /api-keys`), on the OAuth consent screen, and under **Account > Connected apps**; **Settings > Connected Apps** shows it read-only. `whoami` can now report the source `credential`. New route: `PATCH /api/v1/me/oauth-clients/:clientId/mcp-tool-list-mode` (signed-in user, own connections only, across all partners). A client's `Mcp-Tool-List` header still wins for the request that carries it.

- **v0.131.0: macOS agent assets without a signed minimum-OS value are refused at sync** (#12258, announced in the v0.130.0 body). Self-hosters who sign their own packages: the self-host signing template already includes it.

- **Deploy caution: two backup migrations can make the first start slow** (#12762, wave of #12737). `2027-01-31-120000-backup-tree-checkpoints.sql` takes exclusive locks on `backup_snapshot_files`, `backup_snapshots` and `backup_configs` and holds them until it commits, while it scans `backup_snapshots` three times, so backup snapshot and file-index reads and writes wait for it to finish, and its last few statements briefly block writes to devices and organizations. It waits at most 5 seconds for each lock and otherwise fails and runs again on the next start, rather than queueing traffic; a long file-index hydration in flight is the likeliest cause of such a failure. `2027-01-31-120100-backup-index-concurrent-indexes.sql` runs `DROP INDEX CONCURRENTLY` on `backup_snapshot_files`, usually the largest table, then builds one partial index on `backup_snapshots` concurrently. It does not block reads or writes, but each statement waits for every open transaction that touches its table, including a long file-index hydration, and API start waits with it. This file has no timeout; if it fails, it runs again from the top on the next start. Deploy when no large hydration is in flight, or accept the wait.

- **`breeze-backup` updates work again on servers that sync releases from their own repository** (#12769, for #11028). With `BINARY_GITHUB_REPOSITORY` (or the legacy `GITHUB_REPO`) set to a non-official repository, the server now signs `breeze-backup` rows with its deployment key like the agent, watchdog and helper rows. Before, agents refused every `breeze-backup` download with `update manifest signature verification failed for signing key id "release-artifact-manifest-ed25519"` and upgraded without it. Rows the upgraded server writes are correct; agents that move to that release fetch the matching `breeze-backup` within about 30 minutes. Rows already stored for earlier releases are not rewritten, so agents held on an earlier release keep failing until they move. Official-repository servers write the same rows, bytes and key ID as before. **Two behaviour changes on every server:** (1) a `breeze-backup` asset that fails verification (absent from the signed manifest, size mismatch, not distributable) now stops the whole GitHub sync before anything is written, like a bad watchdog or user-helper asset; before, the agent rows were registered and promoted first. A release that has no `breeze-backup` asset for a platform is still skipped without error. (2) A sync that asks GitHub for a specific tag (the pinned boot release, the current-version safety net, `POST /agent-versions/sync-github?version=`) now refuses a response for any other tag instead of registering it.

- **Behaviour change: Windows PowerShell scripts now report their real exit code** (#12798). The Windows agent has reported every non-zero `exit N` from a PowerShell script as 1. An updated agent reports N for N > 0, the same code `powershell.exe -File` gives: `exit 3` is 3, `exit 3010` is 3010, a thrown or terminating error is still 1, and a script that ends without `exit` is still 0, even when its last native command failed (end the script with `exit $LASTEXITCODE` to report that command's code). No run changes between success and failure: 0 is still success and any non-zero code is still a failed run, for Run Script, scripted software install steps, script monitors ("breach on non-zero exit code") and every other feature that runs a PowerShell script on a Windows device. What changes is the number. **Check scripts that have an exit-code severity mapping:** a key such as `3` or `3010` that never matched on Windows (every failure arrived as 1) now matches, and a code without its own key takes the severity of the nearest lower key, where before every failure was evaluated as code 1. Alert titles and messages show the real code. A script that exits 3010 is still a failed run; nothing treats it as a pending reboot. **Negative codes stay 1:** a PowerShell script that exits with a negative code (for example `exit -1`) is still reported as 1, as before. The change takes effect per device when its agent updates; cmd, bash and Python scripts, and PowerShell on macOS and Linux, are unchanged. Learned fixes for script alerts are keyed by exit code, so fixes learned from PowerShell runs that were recorded as exit code 1 will not match the real code and are learned again from the next occurrence.

Dell Command | Update's settings code selects the policy root `HKLM\SOFTWARE\Policies\Dell\ClientDeviceManager\UpdateModule\UpdateService\Clients\CommandUpdate` when Dell Client Device Manager policy is configured (read from the tool, not observed at run time). The agent read only the default policy root, so an automatic schedule set there passed the check. The agent now reads both roots on every run with the same rule: a schedule other than manual updates under either root refuses with `vendor_schedule_policy_not_manual`, and either root present (any `…\Policies\Dell\ClientDeviceManager` key counts) without a manual-updates schedule where Breeze looks refuses with `vendor_schedule_policy_unknown`. Other `Policies\Dell` keys, such as the empty `Telemetry` key, change nothing. No new error codes. The Dell lane stays closed by default.

- **Devices without Breeze Assist: the native prompts no longer re-ask, block or burst** (refs #12794; takes effect when the agent updates). Applies only where `PROMPT_HOST_ENABLED_KINDS` enables `restart.prompt` or `notice.info`. (1) After **Postpone** on the native restart dialog, the dialog is not redrawn when the restart moves; it comes back at the next reminder for the new time or as the closing notice, so one click spends one postponement. (2) A notice on the native path is an operating-system notification again (macOS, Linux; Windows as before), not a dialog that stayed up to 24 hours. The macOS permission notice stays a dialog because it has **Open Settings**. A notice that has to be a dialog closes after at most 60 seconds, never opens over a restart, consent or **End session?** dialog, and never stacks on another notice: it waits for the other dialog to close and is then shown, never dropped; the safe-mode restart warning waits at most until one minute before the restart. On Windows quiet hours or nobody present the notification is raised as well, so the notice stays in the notification centre. After **Postpone** a notification announces the new restart time. Without Assist an unanswered macOS permission notice is shown again after four hours. A burst of notices no longer makes a restart, consent or elevation question list-only (the ten-cards-in-ten-minutes limit now applies to notices only). (3) When Assist goes away, notices the person already saw (on screen or in Assist's list) are not shown again by the native fallback or the legacy notification; a pending restart question still moves (consent is never re-asked, as before). On a replay, seen notices go to the list, only the newest unseen notice is restored, and a notice never takes the one restored decision card. A lab re-run on a device without Assist is still owed before these kinds are enabled region-wide.

- **Workspace index agent setting `workspace_index.endpoint_base`** (#12711, for #12690; takes effect when the agent updates). It is the base URL path the agent's Workspace indexing client calls. Leave it unset (agents already in the field keep the old behaviour until they update): the default is now `/api/v1/workspace/agent/<agent ID>`. The old default had no agent ID, so every Workspace index request answered `401 Invalid agent credentials`. A value that is set is used exactly as written, so an existing workaround that already ends in the agent ID keeps working.

- **Agents back off when the Workspace extension is unavailable** (#12717, for #12713; takes effect when the agent updates). A `503` or `403` from the agent's `crawl-config` request now makes the agent wait 30 to 60 minutes before asking again, instead of every minute. A `Retry-After` header is honoured between 1 minute and 6 hours. `403` covers a parked or quarantined device and a draining tenant, so after such a device is released, Workspace indexing can start up to an hour later; heartbeat and commands are unaffected. The extension gateway now sends `Retry-After: 1800` on the `503` for a registered extension that is disabled or withdrawn. A single refusal does not stop running crawls (a sustained outage does: see #12761 below), and `404` and `401` handling is unchanged. Tested only, not against a live server.

- **Workspace indexing pauses while the Workspace extension stays unavailable** (#12761, for #12727; takes effect when the agent updates). If the server keeps refusing the agent's workspace-index config poll (`503`, or `403` for a parked device) on two or more polls in a row spanning at least 30 minutes (about an hour with the default back-off), the agent stops its running crawls and file watchers and records a `workspace_index_deactivated` event in the agent's local audit trail and log, with the reason `workspace index unavailable on server (HTTP 503)` (or `403`). The first refusal still only backs off, so a short proxy or deploy blip does not stop indexing. Indexing resumes by itself on the next successful poll. No action is needed.

- **Backup: files with very long names are stored under a hashed key** (#12722, for #12692; takes effect when the agent updates). A file name of 253 to 255 bytes made the stored object name longer than 255 bytes once `.gz` was added, so filesystem-backed stores refused it and the file failed on every run. Such files, files in a folder segment over 255 bytes, and keys over 1,024 bytes now go to `files/long-names/<sha256 of the snapshot path>.gz`. Every other file keeps exactly the key it had. Restore, verify and clean-up read the key recorded in the snapshot, so older agents can still restore these snapshots, and restores use the original file name. Checked in tests and in a lab run against an S3-compatible store with a Windows device. On a store with no name limit (such as AWS S3), an unchanged long-named file in an incremental run is inferred to keep its old object; only a changed file uploads under the new key.

- **Agents warn about a plaintext server connection** (#12734, for #12729; takes effect when the agent updates). An agent whose `server_url` is `http://` to a host other than the device itself (loopback is exempt; a private LAN address is not) logs one warning on its first `ws://` connection, and it is meant to reach the server's agent logs whatever the log level (not tested above a raised shipping level). The device's health report carries a `server_connection` warning while that is true, `GET /devices/:id` returns `plaintextServerConnection: { observedAt }` (otherwise `null`), and the device **Details** tab shows a notice. **Nothing is refused or changed**; to clear the warning, use the server's `https://` address.

- **Restore results report where the files were written** (#12745, for #12736; takes effect when the agent updates). A file restore sent without `targetPath` writes into the backup helper's staging folder, never the original locations (unchanged). The restore result now carries `restoredTo`, the folder the files were written under, and restore job responses expose it. The restore wizard's **Latest restore job** panel shows "Files written to: …". Until the agent updates, `restoredTo` is `null`. The `restore_snapshot` AI tool's `targetPath` description now says omitting it means the staging folder.

- **Backup jobs say why they are waiting** (#12723, for #12693). A run that follows an interrupted run waits, for up to about 21 minutes, until the earlier writer can no longer write to the same snapshot; the job used to show `running` at 0 bytes with no reason. The job list, job detail and the device **Backup** tab now show "Waiting for the interrupted run to be released" and "starts in about N min". The wait itself is unchanged. No migration and no agent change.

- **Backup: snapshot file index groundwork** (#12762, wave of #12737). Adds two tables (`backup_tree_checkpoints`, `backup_tree_checkpoint_entries`) and three columns for a smaller incremental-snapshot file index, drops a redundant index on `backup_snapshot_files` and builds a partial index on `backup_snapshots`. Nothing uses them yet and behaviour does not change. See the deploy caution under Self-Hosting / Upgrade Notes.

- **Fleet filter and group checks no longer fail because of a slow timeout restore** (#12724, for #12715). A check whose reads had all finished could be refused as "could not be checked in time" when only the step that restores the session's statement timeout was cancelled. It now stands. A check whose reads themselves time out is still refused. No setting to change.

- **Re-importing a Pax8 product updates its catalog item instead of creating a second one** (#12689, for #12527). The import looks up the product's existing mapping first. Prices follow the SKU re-import rules (a price is added only for a currency that has none; existing prices are kept). The item's SKU is replaced only if it is still the old JSON-style value an earlier importer stored; a SKU edited by hand stays. If another item of the partner already holds the real SKU, the mapped item keeps its SKU and pricing still applies. Items already duplicated, or holding the old JSON-style SKU, are not corrected or merged by this change, and a mapped item that was archived is still updated.

- **Approval cards no longer show a tool's raw action list as the impact line** (#12774). A `manage_tickets` card (edit or delete a comment, move to another organization, merge, a public reply, a resolve, a requester change) now says what approving does: whether the requester is emailed, and who can see the change (a merge lets each requester read the other ticket's public replies in the customer portal). An approval-gated action with no summary of its own shows a generic line naming the tool and action, for example `Runs "Manage update rings: delete". There is no plain-language summary of this action, so check its arguments before approving.`, instead of the tool's catalog description, which for many tools is model-facing text. `approval_requests.risk_summary` stores the same line. Cards filed before the upgrade keep their stored text.
- **Ticket search finds the customer number as the customer sends it** (#12775, follow-up to #12681). A pasted `#CODE`, with or without surrounding spaces, now matches the customer-facing ticket number; surrounding spaces are ignored for every search field, and a box of only spaces is treated as no filter. The staff ticket header now shows that number (`#CODE`) beside the Breeze number so a technician can read it back to the customer.

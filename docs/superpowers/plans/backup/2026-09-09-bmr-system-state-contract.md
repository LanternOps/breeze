# Bare-Metal Recovery System-State Contract — Implementation Plan

## 0. What's actually true right now (ground truth, not the doc)

The consumer (`bmr.go`) was already written for a **separate `system-state/` prefix**: `systemStatePath = "system-state"` (`agent/internal/backup/bmr/bmr.go:21`), and `applySystemState` downloads `snapshots/<id>/system-state/manifest.json` (`bmr.go:228`) then each artifact from `snapshots/<id>/system-state/<artifact.Path>` (`bmr.go:265-266`). The producer (`backup.go`) never wrote that layout — it appends the staging dir straight into `backupPaths` (`backup.go:518-523`) so artifacts upload through the ordinary per-file loop and land at `snapshots/<id>/files/path_N/<relpath>` (`snapshot.go:594-595`, rootLabel `path_%d` is **positional**, set at `backup.go:1126,1189`, not stable). That mismatch is D15/O10. Two more things are already half-built and currently inert:

- `agent/internal/backup/backup.go:1094-1099` already carries a `backupFile.systemState bool`, set by `markSystemStateFiles` (`incremental.go:210-247`) — but it's **dropped** when the `SnapshotFile` entry is built (`snapshot.go:745-753` has no `SystemState` field to set; `SnapshotFile` struct at `snapshot.go:100-128` has none).
- `AuthenticatedSnapshot.SystemStateManifest json.RawMessage` is already parsed into the bootstrap payload (`agent/internal/backup/bmr/types.go:38-41`) and already populated server-side from `backup_snapshots.system_state_manifest` at both `apps/api/src/services/recoveryBootstrap.ts:178,332` and `apps/api/src/routes/backup/bmr.ts:1400` — but `session.go:80-81` only pulls `bootstrap.Snapshot.SnapshotID` out of it; the manifest itself is never read by the agent.

Both are exactly the seams a fix should use.

## 1. Producer/consumer contract — recommend Option A (dedicated `system-state/` prefix)

**Option A** (dedicated prefix + own manifest): producer stops appending the staging dir to `backupPaths`; instead adds a second, independent publish step that uploads each artifact to `snapshots/<id>/system-state/<artifact.Path>` and writes `snapshots/<id>/system-state/manifest.json` — the exact shape `bmr.go` already expects.

**Option B** (flag ordinary entries): add `SystemState bool` + a stable `originalPath` (`system-state/etc/hostname`) to `SnapshotFile`, carry `backupFile.systemState` through at `snapshot.go:745-753`, and make `bmr.go` filter `manifest.Files` by the flag instead of downloading a separate manifest.

**Comparison:**
- *Consumer change surface*: A is ~zero (`bmr.go` already speaks this format); B requires rewriting `applySystemState`/`restoreFiles` to filter one file list instead of downloading two.
- *Producer change surface*: A is larger — needs a new upload path with its own sha256, and must fix the `len(files)==0` hard-fail at `backup.go:641-663` (a system-state-only run now correctly produces zero *ordinary* files even on success, so that branch must check "did state publish succeed" not just `len(files)`). B is smaller — mostly plumbing an existing field through, plus giving artifacts a stable relative path instead of the positional `path_%d` label at `backup.go:1126/1189`.
- *API/browse/restore blast radius*: A never appears in `backup_snapshot_files`, so `backupResultPersistence.ts:1183-1210` (which builds that table from `result.snapshot.files`), the browse tree, and `POST /backup/restore` selective/in-place logic are **untouched by construction** — no risk of repeating O10 (artifacts restored to a temp path) through the ordinary restore route. B requires new filtering logic in all three places to keep system-state entries out of ordinary restore, and any missed spot silently re-introduces O10 via the normal restore path.
- *GC*: **both options require the same fix** — see below, this isn't a factor in the choice.
- *Backward compat*: A's manifest is a wholly new object per snapshot; old `system_image` snapshots simply have none, and `applySystemState`'s existing soft "not found" path (`bmr.go:238-242`) already degrades safely — just needs to become fail-loud per §2. B requires distinguishing an old manifest (state artifacts with `originalPath="path_N/etc/..."`, no `SystemState` flag) from a new one — an extra compatibility branch.
- *Windows VSS `originalPath`*: state artifacts are collected **after** the VSS snapshot from the live volume and are deliberately excluded from the VSS path rewrite (`backup.go:462-473` comment, `incremental.go`'s `isUnderDir`) — under A this is moot (separate prefix, never touches `OriginalPath`); under B, `SnapshotFile.OriginalPath` (`snapshot.go:120-127`) is VSS-specific machinery that must NOT be reused or repurposed for the state's stable key, or it collides with D8/D12's fix.

**Recommendation: Option A.** It matches the consumer that already exists, keeps every ordinary-restore code path (D4, D5, D8, D12's fixes) untouched, and confines the new complexity to one new agent-side publish function plus one GC change.

**Schema additions needed** (`agent/internal/backup/systemstate/types.go:9-30`): `SystemStateManifest` currently has `Platform/OSVersion/Hostname/CollectedAt/Artifacts/IncompleteSteps/HardwareProfile` and no collector version, no per-step status, no per-artifact checksum. `Artifact` (`types.go:26-30`) has `Name/Category/Path/SizeBytes`, no `Checksum`. `artifactFromFile` (`systemstate/helpers.go:14-26`) already computes a stable relative `Path` — extend it to also sha256 the file. `missingRequired` (`systemstate.go:38-49`) already models a required-step policy but only as an in-process error path, never serialized — add `RequiredSteps []string` (or per-step `{Name, Status}`) to the manifest so the *consumer* can independently enforce it (not just trust the producer's own gate). The API's result schema is permissive here already (`apps/api/src/routes/backup/resultSchemas.ts:40-46`, `artifacts: z.array(z.record(...))`), so new fields don't need a schema change; `backup_snapshots.system_state_manifest`/`hardware_profile` are existing jsonb columns (`backupResultPersistence.ts:1160-1161`) — **no DB migration needed**, this is pure JSON-shape growth.

**GC — mandatory change regardless of option chosen.** `markLiveBackupObjects` (`backupRetention.ts:731-775`) only marks `snapshots/<id>/manifest.json` plus `manifest.files[].backupPath` — it has no idea `system-state/` exists. `sweepStorageIdentity` (`:787-855`) then applies the "manifest-bearing prefix → per-object 48h grace" rule to *every* object under that snapshot-id group, including anything under `system-state/`. Once state artifacts stop being in `manifest.files` (true under both options, since A moves them out and B would presumably also want them excluded from GC's naive `files[]` walk unless it's taught to check the flag), **GC will delete them after 48h** — a live regression, not a hypothetical. Separately: `system_image` rows are explicitly excluded from `retainedSnapshotIds` (`backupRetention.ts:970-987`, with the comment already anticipating a "different keys" layout that doesn't exist yet), so protection today depends entirely on `listedManifestSnapshotIds` finding the ordinary `snapshots/<id>/manifest.json` object in the live bucket listing. **Fix required in wave 1**: keep publishing a (possibly empty-`files`) `snapshots/<id>/manifest.json` for every system_image run (so the snapshot-id group is still "manifest-bearing" and not swept as an abandoned partial prefix under the `BACKUP_GC_MANIFESTLESS_PREFIX_MAX_AGE_MS` rule at `backupRetention.ts:829-854`), and extend `markLiveBackupObjects` to also fetch `system-state/manifest.json` when present and mark its own key plus every artifact's remote key as live.

## 2. Consumer side (`bmr.go`)

Discovery/download already correct for Option A (`bmr.go:228,261-274`); add: (a) sha256 verify against the manifest's new `Checksum` field after each artifact download — today nothing is checked (matches campaign finding B1c); (b) required-step enforcement — if the manifest's `RequiredSteps` intersects `IncompleteSteps`, or if `provider.Download` of the state manifest fails **for a token whose bootstrap said state exists**, treat it as fatal, not the current soft warning at `bmr.go:238-242`. The signal for "this token's snapshot has state" is the already-wired-but-unused `bootstrap.Snapshot.SystemStateManifest` (`types.go:38-41`, `session.go:80-81`) — thread it into `RecoveryConfig` (new field, e.g. `ExpectSystemState bool`) so `RunRecoveryContext` can distinguish "no state ever existed" (fine, current soft path) from "state existed but couldn't be applied" (must fail). Also fix the status derivation at `bmr.go:130-137` — today `status = "completed"` whenever `filesErr == nil && stateErr == nil`, and `applySystemState` returns `err = nil` even when it skipped state entirely (`bmr.go:241`), which is exactly how D15 produced `completed`/`stateApplied: false`. New rule: `stateApplied` must be `false` AND overall `status` must not be `completed` whenever `ExpectSystemState` was true and application didn't happen.

Path scoping is already safe for this layout with no API change: `getAuthenticatedRecoveryDownloadTarget`'s `expectedPrefix = "snapshots/${snapshotId}"` (`recoveryDownloadService.ts:134`) and `normalizeSnapshotPath` (`:27-35`) accept any subpath under that prefix, including `system-state/...` — confirmed by the same mechanism already serving `files/...`. `recoveryBootstrap.ts:106`'s incremental-reference rejection (older-prefix downloads refused) is moot for system_image runs specifically because they skip incremental dedupe entirely — `backup.go:683`, `incrementalDedupeActive := !m.config.SystemStateEnabled || len(m.config.Paths) > 0` — so a system-state-only run never references an older snapshot's objects, and Option A's artifacts are never candidates for that rejection either way.

## 3. Linux/Windows restorer fixes

Three, not one, producer/consumer name mismatches on Linux (only the first is in the campaign doc as S1c):
- Packages: producer writes `packages/dpkg.txt` / `packages/rpm.txt` (`systemstate/state_linux.go:119,128,140`); consumer looks for flat `packages_dpkg.txt` / `packages_rpm.txt` (`bmr/restore_linux.go:72,78`).
- Services: producer writes `services/systemd.txt` (`state_linux.go:158,163`); consumer looks for `services_enabled.txt` at staging root (`restore_linux.go:130`).
- Firewall: producer writes `firewall/iptables.rules` (`state_linux.go:185,190`); consumer looks for `iptables_rules` (no extension, staging root) (`restore_linux.go:155`).
- Crontabs: producer writes `crontabs/crontab` (the `/etc/crontab` copy) **and** `crontabs/spool/<user>` (nested) (`state_linux.go:207,217,224-231`); consumer reads `stagingDir/crontabs` as a *flat* directory of per-user files, skips subdirectories outright (`restore_linux.go:172-186`) — it never sees `spool/`, and would mis-restore the `/etc/crontab` copy as a user crontab named "crontab". (`/etc/crontab` is redundant with the `/etc` tree restore anyway.)

Fix: rename either side to agree (recommend the *restorer* matches the collector's already-nested layout, since `state_linux.go` also drives the `Artifact.Category`/`Name` metadata other tooling may rely on) and fix the crontab restorer to walk `crontabs/spool/*` for per-user files.

`cp -a` of `/etc` over a live system (`restore_linux.go:54-67`) needs an exclude policy before it's safe on a real reinstall-then-recover: **must exclude** `/etc/fstab` (points at the *old* machine's block device UUIDs — silently unbootable/unmountable on the new hardware), `/etc/machine-id` (systemd identity; duplicating it across machines breaks D-Bus/journald machine tracking and can collide DHCP leases), `/etc/hostname` (arguably restorable, but only if the fresh install's hostname was a placeholder — needs a product decision, default to skip so BMR doesn't silently rename the recovery target), and network config (`/etc/netplan/*.yaml` or `/etc/network/interfaces`) unless the recovered NIC topology is verified identical (default to skip, since a mismatched interface name papers the machine unreachable — matches the campaign's own open question). Everything else under `/etc` is reasonable to overwrite in a genuine reinstall-then-recover flow. Package reinstall (`apt-get dselect-upgrade`) and service enablement are structurally fine once the name mismatches are fixed; add a real service-health probe (see below) before calling the run validated.

`validate.go:96-102`'s `checkServices` is a hardcoded stub returning `true` unconditionally — `ValidationResult.Passed` can never be dragged down by a stopped service today (B1b). Needs a platform probe: `systemctl is-active` over the restored `services_enabled.txt` list on Linux, `sc query` over a fixed critical set on Windows.

**Windows** (`restore_windows.go:69-92`): `reg restore HKLM\SYSTEM|SOFTWARE|SAM|SECURITY` targets **live, in-use hives of the running OS** the agent process itself is executing under — `SYSTEM`/`SOFTWARE` are memory-mapped by the kernel and cannot be safely replaced this way; `reg restore` against them either fails outright (file in use) or, if it succeeds, doesn't take effect until reboot and can leave the boot volume inconsistent with what's actually loaded. This is not a "make it more robust" fix — it's a different model. Recommend (do not implement here): an offline apply — either boot a WinPE/WinRE recovery environment (matching what `bare-metal-recovery.mdx` already claims, per §8 of the campaign doc) and run `reg load`/`reg restore` against the *offline* hive files, or drop live-registry-hive restore from the Windows BMR path entirely and scope Windows BMR to files + best-effort config (firewall/certs, which don't have this problem) until an offline path exists. `certutil -restoreDB`/`netsh advfirewall import` (`restore_windows.go:107-128`) don't have this constraint and can stay live-applied.

## 4. Tests

- **Agent unit seams**: a fake `systemstate.Collector` that returns a manifest with a mix of required/incomplete steps, to unit-test the new backup.go control flow (state-only run success without ordinary files) without a real OS. A fake `providers.BackupProvider` in `bmr` tests that serves a scripted `system-state/manifest.json` + artifacts (including a deliberately wrong-sha256 one, and a "manifest present but no artifacts" case) to unit-test `applySystemState`'s new checksum/required-step enforcement and the `status` derivation fix, mirroring the existing `download_provider_test.go` style. Per-OS `Restorer` fakes (implementing the existing `Restorer` interface, `bmr/types.go:133-139`) so `RunRecoveryContext`'s orchestration is testable without shelling out to `reg`/`cp`/`systemctl`.
- **Integration cell** (`scripts/backup-assurance/`): extend the existing B1 harness — fresh QEMU VM, mint a token against a `system_image` snapshot, run `bmr-recover`, then assert (not just job status) `/etc/hostname` (or whichever fields the exclude policy allows), `systemctl is-enabled` for the collected service list, `crontab -l` per user against the source VM's crontab, and `dpkg --get-selections` diff against the source VM's package list — this is the only way to catch a silent "completed but nothing applied" regression like D15 again.
- **API contract tests**: extend `backupResultPersistence.test.ts` for the new manifest shape (checksum/required-steps fields flowing into `system_state_manifest` unchanged as opaque JSON), and `backupRetention.test.ts` for the GC fix — a system_image snapshot's `system-state/*` objects must survive a sweep when referenced by `system-state/manifest.json`, and must NOT survive if superseded/expired the same way file snapshots are (mirrors the existing per-object-grace test shape already in that suite).

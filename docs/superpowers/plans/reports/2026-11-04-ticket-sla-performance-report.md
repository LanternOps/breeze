# Customer SLA Performance Report (`ticket_sla_performance`): Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give an MSP a customer-facing SLA report for one organization and period. Per ticket priority it shows tickets opened, the SLA target, % within SLA, median and mean SLA-clock time to first response and to resolution, and a list of breaches. The MSP can schedule and email it like any report (W1), and the customer can see it in the portal once the MSP delivers it as service-plan evidence (W2).

**Architecture:** A new org-only report type `ticket_sla_performance` with `audience: 'any'`, a sibling of the MSP-internal `ticket_sla_attainment`. It reuses that report's ticket filter and stored-deadline SQL, which this plan extracts into one shared fragment module. Its SQL returns one row per (ticket, target) whose outcome was *decided* in the period. TypeScript then folds those rows into per-priority stats, using the shared business-time calculator, so durations run on the same clock as the targets. W2 registers the type as managed evidence, so a service-plan deliverable produces it on cadence and the portal lists it after delivery.

**Tech Stack:** Hono + Drizzle (raw `sql`, bound params via `db/sqlValues.ts`), zod v4, Vitest (unit tests with the PgDialect-compiling `db.execute` mock from `ticketSlaReport.test.ts`, plus `vitest.integration.config.ts` against real Postgres), jsPDF in `packages/shared/src/reportPdf`, Astro + React islands (web and portal), Playwright (`data-testid` only).

**Spec:** none. This is a `track:plan` item; source issue #11018. The Design section is the argument, and executors treat it as binding.

### Decisions

- **D1. A new type, not a widened `ticket_sla_attainment`.** Rejected alternative: flip the shipped type to `audience: 'any'` and portal-visible. That would undo ruling F1 for a report whose axes (technician, category, partner scope) and fields (assignee, internal number, stamp discrepancy) are MSP-internal, and it would change shipped partner-only-delivery behaviour. The new type is org-only and exposes only customer-safe fields. It shares the SQL that decides *which tickets count and when they were due* (D6), so the two reports cannot drift on eligibility.
- **D2. Outcomes are counted in the period they were decided, not by ticket creation date.** A target's `decided_at = LEAST(completed_at, due_at)`. Postgres `LEAST` ignores NULL, so an unanswered target is decided at its due time. A target counts in the window `[period.start, min(period.end, generatedAt))`. `met` = completed and `completed_at <= due_at`; anything else in the window is `missed`. Rejected alternative: the staff report's created-in-period cohort. With that cohort a ticket opened on the 30th and resolved on the 3rd is "pending" in month 1 and absent from month 2, so a recurring customer report never measures it. Under D2, consecutive periods partition every decided outcome exactly once. Volume ("tickets opened") stays on the created basis and is labelled as such. The staff report is unchanged, and the difference goes in both reports' docs.
- **D3. Durations run on the SLA clock.** That is the ticket's business calendar, minus paused time, the same clock its target uses, so "median 3 h vs target 4 h" is comparable. Computed exactly from the stored frozen deadline: `elapsed = target − businessMinutesBetween(completed, due)` when on time, `target + businessMinutesBetween(due, completed)` when late, clamped at 0. For a 24×7 ticket this reduces to `completed − created − paused-at-freeze`. Rejected alternatives: wall-clock elapsed, which is not comparable to business-hour targets, and SQL `percentile_cont`, which would need a second, SQL-only copy of the calendar arithmetic. Durations need a target and a completion: targetless tickets are counted (`ticketsWithoutTarget`) but not timed, as in the staff report. Missed and still open contributes to attainment and to `missedOpen`, not to durations.
- **D4. The "SLA target" per priority is the mode of the stored per-ticket targets** among the measured targets, with the smallest value winning a tie. `varies: true` when more than one distinct target was measured, for example after a category override or a mid-period policy change. Targets are what was agreed on each ticket, never the current policy.
- **D5. No ticket subjects by default.** A delivered portal run is visible to *every* portal user of the org, but a portal user may only read their own tickets. So subjects are omitted unless `includeSubjects: true`, which the options form labels as visible to every portal user. Breach rows carry `ticketNumber` (never `internal_number`), priority, target kind, target, due, completion, elapsed and the minutes over target.
- **D6. Portal visibility = managed evidence only (W2).** The MSP opts in per service plan by adding a deliverable. Rejected alternative 1: `PORTAL_REPORT_TYPES` self-service. Every org that already enabled portal reports would start showing live SLA numbers with no MSP opt-in. Rejected alternative 2: a new `portal_branding.enable_sla_report` column. That is a new setting and an org-cascade column, when the deliverable already is the per-org opt-in. The type stays absent from `PORTAL_REPORT_TYPES` and from both portal-user allowlists in `reportGenerationService.ts:335,932`.
- **D7. Fan-out is the deliverable template (W2), not a report series.** `assertSeriesTypeSupported` (`services/reportSeries/validation.ts:31`) refuses `execution !== 'user'`, and its web mirror `seriesConfig.ts:24` refuses `MANAGED_EVIDENCE_REPORT_TYPES`. W1 must not grant an eligibility that W2 would revoke, because an existing series row would then start failing. So W1 refuses the type explicitly on both sides through a one-entry `SERIES_PENDING_MANAGED_EVIDENCE_TYPES = new Set(['ticket_sla_performance'])` with reason `'managed_evidence'`. W2 deletes the constant, because the registry flag then covers the type.
- **No advisor quorum.** No table, column or tenancy shape is introduced, only an enum label (CLAUDE.md quorum trigger not met).
- **Settings Rule 9 statement (for both PR bodies):** no new setting. `period` and `includeSubjects` are per-definition report config. The SLA *targets* keep their single home (ticket config / categories, unchanged). The count of places the "SLA report" concept is configured goes from 1 to 2: the staff definition, and in W2 the evidence deliverable, which is the existing home for customer evidence.
- **AI exposure: none.** `GENERATE_REPORT_TYPES` = legacy six + `BUSINESS_REPORT_TYPES` (`services/aiReportTypes.ts:25`). The new type is in neither list. No AI tool, route or `mcp-coverage` change.

## Review Focus

1. **A reopened ticket is re-measured.** A ticket resolved on time in October and reopened in November loses `resolved_at`. Re-running October then shows a different number. Expected: it is disclosed in notes, not hidden. Test: `notes disclose that a report reflects ticket state at generation time` (Task 1.5).
2. **Calendar revision not visible or missing.** An org-scope staff caller may not read a partner-owned calendar revision, and `loadTicketCalendars` (`ticketSlaDeadlines.ts:180`) then omits it. Expected: that target still counts toward attainment (its outcome comes from stored timestamps), its duration is excluded, `unmeasuredDurations` counts it, and a note says why. It never throws and never falls back to wall clock. Test: `a target whose calendar revision cannot be loaded counts for attainment but not durations` (Task 1.5).
3. **Pre-#8973 tickets with no stored deadline.** Expected: they are judged against the same COALESCE wall-clock formula as the staff report, so they are never dropped. Test: `a NULL stored due falls back to created + target + paused` (Task 1.1, which pins it at the fragment).
4. **Evidence run generated on the due day.** The occurrence period ends on the generation day, so outcomes decided after `generatedAt` on that day fall outside this run and also before the next occurrence's start. Expected: the window is clipped at `generatedAt`, and `period.measuredThrough` plus a note state the clip. Test: `an evidence run clips the window at generatedAt and says so` (Task 2.1).
5. **Subjects leaking to every portal user.** Expected: with no `includeSubjects` the SQL selects no subject column at all, so the subject is absent rather than nulled after the fact. Test: `without includeSubjects the breach query selects no subject` (Task 1.5). In the integration test, a portal user of org A reads org A's delivered run and finds no subject strings (Task 2.4).

### Task 1.4: The two statements

**Files:**
- Create: `apps/api/src/services/businessReports/ticketSlaPerformanceQueries.ts`, `.test.ts`

**Interfaces:**
- Consumes: Task 1.1 fragments
- Produces:
  - `decidedTargetsQuery(orgId: string, window: { start: Date; end: Date }, includeSubjects: boolean): SQL`. It is a `UNION ALL` of a response arm and a resolution arm over eligible tickets with a non-null target. Each arm computes `due = effectiveDueSql(kind)`, `completed = first_response_at | resolved_at` and `decided_at = LEAST(completed, due)`, and filters `decided_at >= start AND decided_at < end`. ## CI traps

- **Migration naming:** the newest migration on `main` today is `2027-01-20-120000-m365-mailbox-connect-baseline.sql`. If any newer file lands first, rename this one before enqueueing (a merged newer migration poisons the queue).
- **Series eligibility never flips.** D7 refuses series from W1 onward, so no series row with this type exists when W2 lands. Do not drop `SERIES_PENDING_MANAGED_EVIDENCE_TYPES` in W1 to make a test pass.
- **`detailRowCap: UNCAPPED` + breach cap inside summary:** `reportRegistry.test.ts` may assert caps only for business types. Do not add the type to `BUSINESS_REPORT_TYPES` to satisfy a test; that would make it partner-only-delivery and `msp_staff`-adjacent.
- **Integration suites run only in the `integration-test` job.** A stacked W2 PR (base ≠ main) runs no CI. Use `gh workflow run CI --ref <branch>`.
- **`tsc | tail` hides an out-of-memory kill.** Check the exit code.

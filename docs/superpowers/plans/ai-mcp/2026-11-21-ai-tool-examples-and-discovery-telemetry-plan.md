# Tool-use input examples and tool-discovery telemetry — plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** production telemetry that shows which ToolSearch queries users' words produce, which tools surface, which are called and how each call ends; then hand-written input examples on ten endpoint-execution tools, bridged to the model through the advertised description, measured by that telemetry and by a harness A/B before and after.

**Architecture:** one pure observer (`aiToolDiscoveryObserver.ts`) folds the SDK message stream the chat path already consumes, sharing one content walk with the eval harness's `streamObserver.ts`; at turn end the stream writes one `turn` row plus one `search` row per ToolSearch into the new session-keyed table `ai_tool_search_events` (parent-FK-join RLS through `ai_sessions`), and the pre/post tool hooks stamp a `discovery` scalar on `ai_tool_executions` from the observer's loaded set. Examples live on the registry entry (`AiTool.inputExamples`), are validated by contract against all three schema surfaces, and reach the model as a bounded description suffix applied in `attachRegistryMeta` under an explicit registration option (`toolExamples: 'auto' | 'off'`), because the pinned Agent SDK carries no `input_examples` plumbing (spike 0a, answered). A report script and later an admin endpoint plus a dashboard tab read the same aggregation module.

**Tech stack:** Hono/TypeScript, Drizzle (queries only), hand-written SQL migrations, Vitest (unit + integration + RLS coverage), prom-client, `@anthropic-ai/claude-agent-sdk` `^0.3.323`, React (web), 8 locales.

**Spec:** `docs/superpowers/specs/ai-mcp/2026-11-08-ai-tool-examples-and-discovery-telemetry-spec.md` (APPROVED 2026-11-21).

## Review Focus

1. **A search whose `tool_result` never arrives** (turn aborted between the ToolSearch `tool_use` and its result) → T3 `an unmatched ToolSearch tool_use at endTurn yields a search row with empty=true, result_tool_names=[] and the turn row aborted=true`.
2. **A resumed session replays `tool_reference` blocks from an earlier process** → T3 `a tool_search_tool_result whose tool_use_id matches no ToolSearch tool_use of this process seeds loaded names and emits no event`; T4 `the replayed turn's discovery for such a name is loaded_earlier`.
3. **A query that is not valid UTF-8-bounded text** (a 3,000-char model query, a query containing a secret pattern) → T3 `query is cut at 1,024 bytes on a code-point boundary and ends with …[truncated]`; T4 `the stored query passed redactAiToolOutputText (a bearer token in the query is replaced)`.
4. **A forged row attaching a query to another session's user message** → T2 integration `INSERT with a turn_message_id from another session of the same org is refused (42501) and the lifted-predicate control succeeds`.
5. **A tool that gains an action after its examples were written** → T10 `the shape table lists every TIER3_ACTIONS action of each wave-1 tool (an action added to the fixture copy of TIER3_ACTIONS fails the test)`.

## Decisions surfaced while planning

1. **When the suffix is applied (spec §3.3 vs OD8).** The resolved search policy is not available when the server is built (0.4), and chat is the only surface whose tool search is on. Rule: the suffix is applied iff `toolExamples === 'auto'` **and** the registering caller passes it (only `streamingSessionManager.getOrCreate` on the `chat` surface — web chat and Wisp; office uses `mcpServerFactory`, helper/script builder/agents/topology never pass it) **and** `exposure.promptMode !== 'constrained'`. Whether search then turns out enabled or not (gateway host, low budget, `AI_TOOL_SEARCH=off`), a `full`-profile chat session carries the wave-1 bytes (≤ 15 KB in the prefix), which satisfies OD8-B for gateway chat and the §3.3 "chat + full" clause; non-chat surfaces get nothing in v1. Stated here because §3.3 and OD8 disagree on gateway hosts. The justification is OD8-B plus §3.3's "chat + full" clause, not impossibility: the server could be built after the policy (0.4 is construction order, not a constraint), but the chat/full rule needs no policy, so the simpler rule wins.
2. **Examples are a registration option, not a process gate.** `breezeServerTools(..., { toolExamples?: 'auto' | 'off' })`; the template keeps a third memo `withExamplesMeta` beside `withRegistryMeta`/`withCompactMeta`, so a flipped env is read by the next session's caller (`toolExamplesMode(process.env)`) with no template rebuild and no stale descriptions. `toolSurfaceGateKey()` is unchanged. Deviation from spec §3.3 ("the mode must join that key"): the key is per process; a per-session bit there would rebuild the template per session.
3. **`TOOL_SURFACE_FINGERPRINT` is per session**, computed once in `getOrCreate` from what that session's server advertises: `toolSurfaceFingerprint({ tools: advertised SdkTool[], examplesApplied: boolean, searchEnabled: boolean })` = sha256 of `JSON.stringify({ t: sorted [name, description, zod-to-JSON input schema], e, s })`.slice(0, 16). It is not the sibling plan's exposure fingerprint (`toolExposure.ts:136 fingerprintOf`, which hashes names, extras, `compactSchemas` and `promptMode` — never descriptions or examples); the search row stores both (`surface_fingerprint` = this one; the exposure one is already on `ai_invocations`). Spec §3.3 asked for "the same function when both land" — they hash different inputs, so one column each.
4. **Core budget binds `execute_command` and `manage_alerts`** (0.6). Both get exactly two examples each, ≤ 256 B each, 1,024 B combined pinned; `execute_command` is base tier 3 (`aiToolsScripts.ts:774`; it is **not** a `TIER3_ACTIONS` key), so every `commandType` is escalated; its discriminator is `TOOL_ACTION_INPUT_KEYS.execute_command = 'commandType'` (`aiGuardrails.ts:73`), its shape table is keyed by the `commandType` enum of `toolInputSchemas.execute_command`, and its two examples cover the two `commandType` values marked `priority` rather than every shape. `set_device_context` (deferred) gets one `full` example with a nested `details` object (#3094).
5. **Turn attribution without `message_id`.** The report groups a session's executions and dropped results into questions by `ai_messages` `role = 'user'` windows `[created_at, next user created_at)`; the `turn` row's `turn_message_id` names the same user row. `settleSdkTurn` sets `session.turnUserMessageId = null` after the flush so a helper/office/topology turn (which never sets it) cannot inherit a stale web-chat id.
6. **Counter names are the spec's:** `breeze_ai_tool_search_total{outcome="hit"|"empty"}` and `breeze_ai_tool_call_total{status}` in a new leaf `services/aiToolDiscoveryMetrics.ts`. The unprefixed `ai_*` series (`aiOperatorCoordinatorMetrics.ts:10`) describe themselves as a recorded exception; the product prefix is the rule (`filesystemAnalysisPolicyMetrics.ts`, `clusterCacheMetrics.ts`).
7. **`discovery` is stamped provisionally at insert and reconciled by `tool_use_id` at the turn flush.** The SDK dispatches the MCP call concurrently with the stream consumer (`aiToolUseCorrelation.ts:11`), and the consumer awaits its database writes before reading the next message (`streamingSessionManager.ts:2033`), so a hook can run before the consumer has processed the user message carrying the search result that loaded the tool — the provisional stamp would then read `loaded_earlier`/`unknown`. So: T1 adds `ai_tool_executions.tool_use_id`; every hook insert stamps `discovery` from the observer's current state **and** `tool_use_id`; the observer records every non-ToolSearch `tool_use` id it sees; `endTurn` returns `discoveryByToolUseId` (final, computed with the whole turn in view); the flush issues one `UPDATE … WHERE session_id = $s AND tool_use_id = $id AND discovery IS DISTINCT FROM $d` per entry, inside the same `withDbTransaction` as the insert. The `-32602` drop row (`ai_messages.tool_output`) is written by the consumer itself, in stream order, so its `discovery` is final at persist time.
8. **E1/E2 are reported per question** (sibling decision §6: user turn → next user turn), not per session; **dependency depth is reported as a labelled diagnostic**, `depthProxy` = the question's `work_round_trips` (`RoundTripTally.workCalls`, rounds that contained ≥ 1 call — an upper bound on chain length, not the chain). It does **not** satisfy the sibling's gate, which reads the longest input-from-output chain (`2026-11-08-programmatic-tool-calling-decision.md:119-132`): before that gate is called, a reviewer measures true dependency depth on a sampled set of fleet-shaped questions by hand (inputs are kept; outputs are tombstoned), and the report counts the fleet-shaped sample (`calls ≥ 10 OR depthProxy ≥ 3`) separately from all questions.
9. **Write isolation is proven on real Postgres, not in the unit file.** The spec's "ledger insert failure is captured and later statements succeed" case goes to an integration test with `__tests__/integration/caughtQueryFaults.ts` (tenancy doc: mocked Drizzle cannot see 25P02).

# Progressive disclosure for the external MCP server — plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** an MCP client with no tool search of its own can ask for a `progressive` tool list (about 18 tools), then reach any of the ~370 through `search_tools` → `get_tool_details` → `call_tool`, with every authority gate, approval continuation and audit event identical to a direct `tools/call`; `full` stays byte-identical to today and every existing credential keeps it.

**Architecture:** one pure resolver (`services/mcpToolListMode.ts`) turns header / `_meta` / stored mode / env default into `{ mode, source }` once per request; `handleToolsList` is split into a per-caller list builder (`buildToolsListEntries`, the catalog every surface reads) and a mode-aware presenter; three server-intrinsic meta-tools live in `services/mcpMetaTools.ts` (ranker in `services/mcpToolSearch.ts`) and `call_tool` is unwrapped **once** in `handleJsonRpc` (and once more in the pre-auth DB-context classifier) so every reader of the tool name sees the inner name; the sealed approval state gains a surface byte. W02 adds one nullable text column to `api_keys` and `oauth_grants` and the UI homes.

**Tech Stack:** Hono/TypeScript API (`apps/api`), Vitest unit + integration suites, hand-written SQL migrations + Drizzle mirrors, Astro + React islands (`apps/web`) with `runAction`, Starlight docs (`apps/docs`). No new dependency: the BM25 ranker is a small in-process implementation (builder's choice per OD-3; a vetted dependency is allowed if it stays under 50 KB and has no transitive deps).

**Spec:** `docs/superpowers/specs/ai-mcp/2026-11-08-external-mcp-progressive-disclosure-spec.md` (APPROVED 2026-11-21, every OD at its recommended option). The plan argues from the spec; executors read both.

## Global Constraints (from the spec)

- **Modes:** `full | progressive`. Resolution order per request: header `Mcp-Tool-List` (accepted on both transports; added to `CORS_ALLOW_HEADERS` in `services/corsPolicy.ts:29` so browser preflights pass) and/or `params._meta['app.breeze/toolList']` (read **only when `ctx.era` is modern**; ignored on legacy) (both present and different → `-32602`, `data.reason: 'tool_list_mode_conflict'`; an unknown value → `-32602`, `reason: 'tool_list_mode_invalid'`) → stored credential mode (W02) → `MCP_TOOL_LIST_DEFAULT` (ships `full`, OD-1 A). The override applies only to the request that carries it (never session-persisted). The mode is resolved from the **original** envelope before `call_tool` is unwrapped; protocol classification (`Mcp-Name` must equal the outer `call_tool`, `mcpModernEnvelope.ts`) stays on the original envelope.
- **`full` is byte-identical to today** for `tools/list`, `initialize` and `server/discover` (same principal, same client capabilities): no new keys, no `_meta['anthropic/*']`, no meta-tools listed. OD-7 hints (`anthropic/searchHint`, `anthropic/alwaysLoad`) appear on `progressive` lists only.
- **`progressive` lists exactly:** the registry's `alwaysLoad` tools (14 declarations on `main`: `query_devices get_device_details resolve_device_context list_organizations get_fleet_health manage_alerts manage_patches search_logs analyze_metrics get_security_posture query_change_log list_scripts search_documentation execute_command`) that pass `isToolListedForCaller`, plus the intrinsics listed today (`whoami`; `get_action_status` when the caller owns intents; `cancel_action` when it owns intents and has write authority), plus the three meta-tools. No tenant or flow tools. `_meta.ui` only for an eligible Apps client on the streamable transport, as today.
- **Catalog for search / details** is mode-independent: exactly the set `tools/list` lists in `full` for this caller (registry, intrinsics, tenant and flow tools). Nothing outside it is ranked, described or named in instructions. `get_tool_details` answers `Unknown tool: <name>` uniformly for anything not in the set; a direct `tools/call` keeps today's split (`-32003 domain_not_granted` for a known ungranted registry tool, `-32602 Unknown tool` for an unknown name).
- **Meta-tool names** `search_tools`, `get_tool_details`, `call_tool` are reserved in `services/aiToolNames.ts` through `registerReservedAiToolNamePredicate` (the `whoami` pattern, `:63-72`). They are intrinsics: `MCP_TOOL_COUNT_APPROX`, `TOOL_TIERS`, `WISP_TOOL_SUBJECTS` and the chat tool-index budget are untouched. They are callable in either mode (mode governs listing and instructions only), never listed in `full`.
- **`call_tool` rules (§3.3):** canonicalize the inner name with `resolveDeprecatedToolAlias` first; when `surface === 'call_tool'` and the canonical name is a meta-tool → `-32602` (`reason: 'meta_tool_target'`), checked **before** the `requestState` continuation branch (direct `search_tools` / `get_tool_details` stay callable); the inner spelling as sent is kept for the alias warning and `requestedToolName`; every gate (domain `-32003`, approval / intent filing, guardrails on the effective tier, scope tiers, production allowlist, RBAC, per-tool rate limit, Tier 3 ledger) runs on the inner name because the inner call **is** `handleToolsCall`; results (incl. `isError`, `input_required`, `task`) pass through unchanged; annotations `readOnlyHint: false, destructiveHint: true, idempotentHint: false, openWorldHint: true`.
- **Continuation (§3.4, OD-8 A):** `McpRequestStatePayload` gains `w: 0 | 1` (0 direct, 1 through `call_tool`); a state is valid only on the surface that issued it; the check runs with the other bindings, before `payload.a` is exposed. A retry through `call_tool` is unwrapped like the first call, so `payload.t` / `payload.d` bind to the inner name and digest as today.
- **Audit (§3.5):** the one request row (`dispatchAndAudit`, `routes/mcpServer.ts:792`) gains `metaTool: 'call_tool'`, `toolName: <canonical inner>`, `requestedToolName: <as sent, when aliased>`, and `toolIsError: true` whenever a `tools/call` result carries `isError: true` (direct and wrapped). `domainDenialAuditDetails` (`:731`) and `noteMcpAppToolCall` (`:1892`) use the inner name. No second execution row; `mcp.tool.<name>` and the ledger are produced inside the handler, unchanged.
- **Instructions:** `progressive` is a **separate compact body** (today's body is ~3.5 KB before any index, so "replace one sentence" cannot meet the budget): the W19 domain index (label + `DOMAIN_VOCABULARY`) for the domains the caller can list, a filtered `DOMAIN_NOTES` line (sentences naming an unlistable tool dropped, `renderDomainNote`, `services/aiToolIndex.ts:109`), the three-line recipe, the tenant-hierarchy and approval rules condensed, and `UNTRUSTED_TOOL_OUTPUT_RULE` verbatim. **Every** named-tool reference in the compact body (not only `DOMAIN_NOTES`) is filtered against `listableNames` — `read_artifact`, `get_action_status`, `cancel_action` included. ## Review Focus

1. **A wrapped Tier 3 call whose client retries the wrapper verbatim** must continue, and a wrapper retry must not open a state issued to a direct call (nor the reverse) → T7 `wrapper retry with same inner name/arguments → accepted`, `direct retry of a wrapped state → invalid_request_state`, `wrapped retry of a direct state → invalid_request_state`, `state sealed before this change (no w) opens on a direct retry only` (unit: `isPayload` accepts a missing `w`, rejects `w: 2`; route: a no-`w` state is accepted on a direct retry and refused through `call_tool`).
2. **The pre-auth DB-context classifier sees `call_tool`** and leaves a tenant tool or a context-managing tool inside the ambient request transaction → T6 `isMcpTenantToolCallRequest: call_tool wrapping a tenant tool → true`, `wrapping a toolManagesDbContext tool → true`, `wrapping query_devices → false`.
3. **Existence leakage through discovery**: a restricted grant must learn nothing about an ungranted tool from `search_tools`, `get_tool_details` or the instructions, and a wholly gated / MFA-gated / partner-wide-refused tool must be invisible the same way → T4 `restricted core+devices grant: search over every registry name returns only listed names`, `get_tool_details('manage_tickets') → Unknown tool` (same bytes as a made-up name); T3 `progressive instructions name no domain and no tool outside the listable set`.
4. **Header and `_meta` disagree, or a value is misspelt**: the request must be refused, not silently resolved → T1 `header full + _meta progressive → -32602 tool_list_mode_conflict`, `header 'Progressive' (case) → tool_list_mode_invalid`, and T2 `the refusal is audited as a failure row with method tools/list`.
5. **A later default flip must not move an existing integration**: rows backfilled `'full'` ignore a flipped env default; `null` rows follow it; the backfill never re-runs on replay → T1 `grandfathered 'full' with MCP_TOOL_LIST_DEFAULT=progressive → full/credential`; T9 `replay after inserting a null row leaves it null`.

## Decisions surfaced while planning

1. **OAuth edit home (spec §3.6 named the partner's Connected Apps row, which does not exist per grant).** `oauth_grants` rows belong to a user (`account_id`); the partner page is per client and gated on full partner authority, so a write there would let an admin rewrite other users' grants. **Chosen:** the grant owner edits on Account → Connected apps. This is **two** deviations from the approved text, stated separately for Todd at plan review (this PR) and again in the W02 PR body: (a) the edit home moves from the partner page to the owner's page; (b) edit granularity becomes per **client** for that owner — `PATCH /api/v1/me/oauth-clients/:clientId/mcp-tool-list-mode` updates every active grant of that user for that client **across all partners** (the page deduplicates by client, so one control per row is the only honest shape). The owner GET reports `toolListMode: { kind: 'uniform'; stored; effective; grantCount } | { kind: 'mixed'; grantCount } | { kind: 'none'; grantCount: 0 }`; `mixed` is never collapsed to `null`, the UI shows "Multiple values" and disables Save until an explicit choice, and the copy says it applies to all of the user's active connections to this app across all partners. The partner Connected Apps list shows the value read-only per client (`full` / `progressive` / `mixed` / `default`, **with** a partner filter). Consent keeps "set at authorization", with the prior value **per partner** (Decision 8). If Todd prefers per-grant controls on the owner page instead, T10/T11 change the PATCH to `/me/oauth-grants/:grantId/...` and the page gains one row per grant; the rest of W02 is unchanged.
2. **`initialize` / `server/discover` report `{ toolListMode, source }` only when the resolved mode is `progressive`.** §3.1 (report everywhere) and §6 (`full` byte-identical) conflict; byte-identity wins for `full`. `whoami` reports it in both modes (no byte-identity promise there).
3. **One unwrap, two call sites.** `unwrapCallToolRequest(params)` (pure, `services/mcpMetaTools.ts`) is applied in `handleJsonRpc` before `noteMcpAppToolCall` and `handleToolsCall`, and in `isMcpTenantToolCallRequest`. `handleToolsCall` itself never sees `call_tool` as a name; it receives `surface: 'direct' | 'call_tool'`.
4. **Invalid `MCP_TOOL_LIST_DEFAULT`** resolves to `full` with one `console.error` at first read (fail closed to today's behaviour), not a boot refusal; the value is an enum, not a boolean, so the `*_ENABLED` boot rule is not extended to it.
5. **Grandfathering at every flip, not only at W02.** A `null` row created between the W02 migration and a future flip would change at the flip. W03's gate therefore includes: notice one release before; then the flip PR ships the env-default change **and** a run-once backfill of `'full'` for `null` rows in the **same** release, with the backfill ordered before the default change takes effect (migrations run before the new API serves), so no credential existing at the flip boundary changes mode. A backfill in the *preceding* release would leave rows created between it and the flip exposed. W02's backfill is guarded by its own CHECK constraint's existence (`conname` + `conrelid = 'public.<table>'::regclass`) so a raw replay never re-grandfathers.
6. **No MFA on the owner's mode edit.** The self-revoke route (`routes/lifecycle.ts:32`) has no `requireMfa()`; this preference edit is less consequential than a revoke, so it uses the same authentication only (session, not API key). Stated here so it is a choice, not an omission; a test pins that an API-key principal gets 403.
7. **Deployment default travels to the UI.** The API-key form metadata, the owner's connection GET and the consent interaction GET expose `mcpToolListDefault` (from `mcpToolListDefault()`), and every mode field receives it, so "Inherit" can say what it inherits and a cleared value shows the right effective mode. Copy says "deployment default", never "when this key was created": creation-time freezing is implemented by the backfills (Decision 5), not by the resolver.
8. **Re-consent pre-selection is per partner.** The consent form picks the partner after the interaction GET (`ConsentForm.tsx:155`), so each `partners[]` entry carries `prior_mcp_tool_list_mode` and its effective value from the owner's latest active grant for this client and that partner (`created_at DESC, id DESC`); the field initialises from the selected partner and resets when the partner changes.
9. **Rotation copies the most recent active key's exact stored mode** (`servicePrincipals.ts:140`): active keys ordered `createdAt DESC, id DESC`, first wins; no active key → the most recent prior key; no prior key → `null`. There is no intersection semantics for a scalar, unlike `narrowestMcpDomains`.
6. **Search catalog excludes nothing listed and includes nothing unlisted,** so tenant and flow tools (no `searchHint`) are ranked on name, description and domain vocabulary only, as the spec says.
7. **Measurement script** lives at `services/llm/__scripts__/mcp-tools-list-measure.ts` (package script `mcp:tools-list-measure`), calls the exported list builder with dynamic (tenant/flow) tools off, so it needs no database.

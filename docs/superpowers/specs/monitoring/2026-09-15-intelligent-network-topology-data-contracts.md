Date: 2026-09-15
Status: Engineering specification; no migrations or application changes performed
Companion: [main design](2026-09-15-intelligent-network-topology-design.md)

This document owns canonical enums, identity, storage, authorization, and public API spellings. [Collection](2026-09-15-intelligent-network-topology-collection.md) owns agent observation payload details and reconciliation rules. ## 1. Canonical vocabulary

Shared types and Zod validators live in `packages/shared/src/types/topology.ts` and `packages/shared/src/validators/topology.ts`. API responses are camelCase; SQL columns are snake_case. IDs are server-issued UUIDs. Big integer revisions and counters are decimal strings in JSON; finite coordinates/rates are numbers. Timestamp fields use UTC ISO-8601. Unknown values are null with a reason, not zero or empty strings.

| Field | Values and meaning |
| --- | --- |
| `nodeKind` | `endpoint`, `network`, `gateway`, `internet`, `manual`; kind describes the graph entity, while `role` describes device/gateway function. |
| `relationshipKind` | `network_member`, `default_route`, `egress_path`, `physical_link`, `attachment`. |
| `evidenceClass` | `observed`, `inferred`, `manual`. Observed logical routes are still logical. |
| `confidence` | `high`, `medium`, `low`, `asserted`. Discrete evidence rules, not a model probability. |
| `freshness` | `fresh`, `stale`, `unknown`, separately for structural observations and health streams. |
| `lifecycle` | `active`, `withdrawn`, `archived` for canonical entities/relationships. A stale relationship can still be active. |
| `collectionOutcome` | `complete`, `partial`, `failed`, `unsupported`, `not_attempted`. Completeness applies to a named source/protocol/context, never a whole site by implication. |
| `health.status` | `healthy`, `degraded`, `failed_check`, `unknown`; port operational status is a separate source field. |
| `health.coverage` | `monitored`, `partial`, `unmonitored`, `unsupported`, `unavailable`. Diagnostic run coverage is separately `complete`, `partial`, `none`. |
| `view` | `overview`, `physical`, `logical`; `health` is an optional overlay. |
| `directness` | `direct`, `via_unmanaged`, `unknown` for attachment evidence. FDB alone cannot assert `direct`. |
| `diagnosticState` | `queued`, `running`, `completed`, `failed`, `cancelled`, `expired`; cancellation request is a timestamp, not another terminal state. |

`reportKind` (`full|unchanged`) describes transport, separate from `collectionOutcome`; unchanged is not a new completeness outcome.

An observation includes `method` (`os_route`, `os_interface`, `neighbor_cache`, `profile`, `lldp`, `cdp`, `fdb`, `unifi`, `probe`, `manual`, or `legacy`), source identity, collection run, and method-specific validated attributes. Preserve multiple methods rather than selecting one destructive winner.

Presentation-only placeholders/group summaries use string IDs in the namespace `presentation:<view>:<scopeHash>:<role>`. Their edges have `presentationOnly:true`, `relationshipKind:null`, and `meaning:'schematic'|'aggregate'`. They are never accepted where a canonical UUID is required. A collapsed aggregate references a count/frontier and real contributing relationship IDs, not one invented connection. A schematic edge has no contributing IDs or diagnostic authority.

## 2. Identity and isolation rules

1. Organization and site form the graph boundary. API clients must select a site; server resolves its org through authorized records. Partner/system callers do not obtain a graph by omitting an org/site filter.
2. Canonical UUIDs survive refreshes, label/IP changes, and layout changes. Deterministic scoped `identity_key` values control upsert identity; hashes contain organization/site/routing context and never replace authorization.
3. A managed device and its explicitly linked discovered asset bind to one endpoint. Use the existing accepted `linkedDeviceId` identity relation, honoring suppression/manual unlink. Names, shared IPs, or OUIs alone cannot merge devices.
4. A controller device/client has a source key scoped by integration/collector, controller site, and controller ID. Until a unique permitted inventory match exists, it can remain a topology endpoint without an inventory binding. Never manufacture a managed agent record.
5. A gateway role key includes address family, scoped next-hop identity, and routing/attachment context. Link-local IPv6 includes interface/zone identity. A virtual gateway service can refer to physical members without merging those members. A hostname or VRRP-style shared address does not establish one chassis.
6. Network keys include verified routing domain plus prefix when that domain is known. Otherwise retain observer/interface-local context and provide a separate inferred site/prefix display group. Matching CIDRs or reused RFC1918 addresses alone do not establish an identical segment/VRF.
7. Internet nodes are scoped diagnostic destination groups per site/policy/context, not public-address identities for the site. They can exist before probes and remain unknown. Multiple uplinks/proxies have separate measurement contexts.
8. IP assignments and interface indices are temporal. Interface keys include owner and identity epoch; addresses, ifIndex, labels, and aliases are attributes. MAC reuse, cloned VMs, DHCP reuse, VPN interfaces, and device replacement require ambiguity handling described in Collection.
9. Known identity enrichment prefers adding a binding to the existing canonical node. When duplicate canonical nodes must merge, select the oldest canonical UUID, record an alias, migrate references in one scoped transaction, preserve pins/manual assertions, and audit the evidence. Conflicting pins or weak identity stop automatic merging. Alias lookup still checks site access; aliases cannot cross sites.
   When an accepted inventory link is explicitly revoked, suppressed, retargeted, or loses its source through a move/deletion, partition the retained source identities using current accepted links under the site publication lock. Reactivate the relevant retained source UUIDs and reassign only live inventory bindings; preserve historical relationships, manual facts and pins at their existing IDs unless their ownership is provable. Audit the split, advance `build_fence`, and publish one structural revision atomically. Ordinary refresh or stale replay cannot restore an alias independently; only this authoritative revocation path may split it. Relinking uses the normal accepted-link merge and its conflict checks.
10. Site reassignment is not an in-place move of historical observations. Inventory binding rows describe current identity only: detach/delete those binding rows in the inventory move transaction before updating the live inventory site, retain the old node and an immutable audited binding snapshot, then establish new-site nodes/bindings. Fence outstanding commands. Historical graph/run references point to original-scope canonical entities; any copied inventory identifier is audit metadata, not a live cross-site foreign key or authority to fetch current details. Historical reads remain under the original scope.

Relationship keys:

| Kind | Identity and direction |
| --- | --- |
| `network_member` | `(memberNode, memberInterfaceOrUnknown, networkContextNode, addressFamily)`; oriented endpoint→network; evidence identifies whether membership is measured or inferred. |
| `default_route` | `(observerNode, interface, routingContext, family, destinationPrefix, nextHopNode, routeDiscriminator)`; observer→gateway. Multiple simultaneous selected/alternate routes are retained. |
| `egress_path` | `(originNode, routingContext, family, destinationGroup, proxyOrDirectMode)`; origin→destination, with supporting route/probe IDs. A known configured route and tested reachability are separate attributes. |
| `physical_link` | Sorted endpoint interface tuples; undirected. Reciprocal LLDP/CDP observations support one link. Distinct port pairs remain parallel edges; LAG membership is explicit. |
| `attachment` | `(upstreamNode, knownPortOrUnresolvedSlot, clientNode, context)`; logical upstream→client. Preserve unknown port/directness, multiple observers, and conflicting alternatives. |

Incomplete physical observations remain candidate attachments until both endpoint identities/port pairing permit a safe physical key. Do not combine every device-pair observation into one cable. A confirmed manual cable requires both endpoints and a unique manual connection key; it remains `manual/asserted` even if drawn solid.

## 3. Storage model

Add new normalized graph tables alongside existing `network_topology`, `topology_layout`, and `topology_manual_nodes`. Do not overload the legacy pair-plus-method uniqueness to represent canonical physical links. Existing tables remain compatibility sources until retirement.

Every runtime graph/execution table below has non-null `org_id`, `site_id`, created/updated timestamps where mutable, enabled and forced RLS using `breeze_has_org_access(org_id)`, and same-scope foreign keys. The reusable template library defined separately below deliberately has partner-XOR-org ownership and no site column. No table in this feature is intentionally system-scoped. Existing `device_commands` retains its documented exception; a command reference does not confer topology access.

| Table / milestone | Required fields and constraints |
| --- | --- |
| `topology_site_state` / M0 | PK `(org_id,site_id)`; `dirty_revision`, `materialized_input_revision`, `graph_revision`, `health_revision`, `build_fence`; effective collection settings/digest, disabled-source reasons, last build status/time. Atomic counters use bigint. Settings have a distinct revision. No feature flags: resolve partner/org JSON flags as Main §11 specifies. |
| `topology_nodes` / M0 | UUID PK, scoped `identity_key` unique, `kind`, `role`, label override/null, validated attributes, first/last observed, lifecycle, optional alias target. Unique `(id,org_id,site_id)` for child FKs. Identity material is bounded and not editable by the client. |
| `topology_node_bindings` / M0 | UUID, canonical node FK, exactly one of `device_id`, `discovered_asset_id`, `manual_node_id`; CHECK exactly one non-null; same-scope composite FKs to inventory, partial unique indexes on each bound ref. Binding provenance/audit. External controller keys stay in node/observation source identities until inventory binding is justified. |
| `topology_interfaces` / M1 | UUID, owner node FK, owner-scoped `interface_key` + `epoch` unique; type/role, names/alias, current ifIndex, validated address/prefix list, controller port key, optional parent/LAG FK, last observation/outcome. Interface reference must also match the relationship's endpoint node. |
| `topology_collection_sources` / M1 | UUID, scoped producer/source/context/protocol key unique, authenticated owner/config authority reference, current server epoch, accepted/materialized sequences, normalized content digest/version, bounded current typed baseline, last full validation, compact confirmed-through sequence/time and `fresh_until`, expected cadence, last outcome/receipt, revoked_at. Keep accepted and published digests/checkpoints separate. Pending bounded complete-miss transition records belong to this source state; no per-tick event log. Epoch rotation/reset is server-owned. Current compact baseline survives raw evidence retention. |
| `topology_collection_runs` / M1 | Changed source snapshots only: UUID; authenticated producer identity snapshot, server epoch, source/context/protocol, monotonic sequence, content digest/version, optional authorized job/command reference, started/observed/received/effective times, outcome, completion scope, row/chunk counts, truncation/errors, cadence; unique source/epoch/sequence. Store a bounded normalized snapshot/manifest for deferred reconciliation. Unchanged confirmations and identical daily full revalidations insert no run or observation rows. Collection's quotas bound changed-history growth. |
| `topology_observations` / M1 | UUID, run FK, source-local observation key unique per run, subject node/interface FKs, optional relationship FK, method/evidence class, bounded normalized attributes, observed/effective/received times, `fresh_until`; support withdrawal metadata. Observation bodies immutable; lifecycle metadata may change. |
| `topology_relationships` / M0 | UUID, scoped canonical key unique, kind, source/target node and optional interface FKs, normalized logical context, directness, aggregate confidence, lifecycle, first/last support, current support count, current graph revision. Raw evidence remains in observations. |
| `topology_relationship_support` / M1 | PK `(relationship_id,source_id)` with same-scope FKs; latest observation, source epoch/sequence, first/last positive/effective time, fresh_until, complete-miss count and last counted miss sequence/time, support lifecycle. Advance only in ordered materialization; independent sources retain independent support. Expiring detailed observations clears their optional pointer while preserving the compact support summary. |
| `topology_view_exclusions` / M2 | UUID, relationship FK, exclusion scope/view, reason, created_by, revoked_at; one active exclusion per relationship/view. Changes display, not evidence or alert policy. |
| `topology_layouts` / M0 | UUID, unique `(org_id,site_id,view)`, revision, algorithm/version and settings. One shared layout per view; private pan/zoom/filter state stays client-side. |
| `topology_node_positions` / M0 | PK `(layout_id,node_id)` with same-scope FKs, finite bounded x/y, pinned, position source `auto\|user\|legacy`, row revision, updated_by. No placeholder positions in canonical node rows. |
| `topology_change_outbox` / M0 | UUID, scope, event kind, aggregate ID, source revision, idempotency key unique, bounded payload, delivered/attempt state; captures legacy/manual changes and diagnostic dispatch intents atomically. |
| `topology_probe_targets` / M1 | UUID, unique site/key, revision, label, target kind `dns_name\|tcp\|https`, hostname/address/family, port/path/expected response, provider/independence label, validated resolution/redirect/proxy policy, enabled, created/updated_by. No credentials. Target edits increment revision; deleting referenced targets disables them until retention permits removal. |
| `topology_monitoring_policies` / M1 | UUID, unique site/key, revision, enabled, recipe/version, canonical subject/context/family selection, origin-selection policy, interval/jitter, budget/alert settings, requester/authority generation and digest, last/next scheduled time, blocked reason. Target references are enforced through the binding table below. |
| `topology_policy_targets` / M1 | Policy FK + target FK with same-org/site composite constraints, target revision, purpose/order; unique `(policy_id,target_id,purpose)`. Authority digest includes target revisions. |
| `topology_monitor_bindings` / M1 | UUID, site-scoped subject node or relationship (CHECK one), monitor FK and/or recurring policy key, routing-context/origin policy, family, metric role. Same monitor may serve multiple authorized subjects without duplicating checks; explicit association, never IP-only joins. |
| `topology_diagnostic_runs` / M1 | UUID, recipe/version, requester or schedule authority, canonical subject/origin-node FKs, immutable origin device/agent/site-at-acceptance snapshot, graph/settings/context/target revisions, accepted normalized plan/digest, idempotency key/body hash, run state, assessment, coverage, queue/start/deadline/finish/cancel-request times, failure reason. Unique scoped request identity; terminal CAS. Historical origin snapshot is not a live inventory site FK. |
| `topology_diagnostic_steps` / M1 | UUID, run FK, attempt/step unique, command ID, state/result, origin/target/interface/context attribution, protocol and units, evidence refs, bounded details, timestamps, truncation. Command ownership is validated against the parent origin at ingestion. |
| `topology_interface_samples` / M3 | Scope/interface FK + identity epoch, source run/sequence, sample/effective time, resolution `raw\|5m\|1h`, directional counters/gauges/units, discontinuity metadata, coverage/valid-duration, derived rates and invalid-window reasons. Partition by time/resolution; idempotent source/interface/sample key. |

Source/producer sequence values are decimal uint64 strings at API/Go boundaries and PostgreSQL `numeric(20,0)` with a `0..18446744073709551615` CHECK, never JavaScript Number or signed PostgreSQL bigint. Server-owned revision/fence counters remain nonnegative bigint.

M3 extends the existing diagnostic run table with policy/context/family/scheduled-occurrence columns and a scoped unique occurrence key. It adds bounded validated `alert_state` JSONB and independent `alert_state_revision` to existing monitoring policies, keyed by explicitly configured context/family. State includes claim, processed-occurrence high-water and origin continuity; duplicate or older results/gaps cannot reset or advance a newer streak. This is runtime state, excluded from the policy authority digest/config revision and classified `excludedOpen`; no additional tenancy shape or streak table is required.

Tables ship only when their milestone needs them. Defining later tables here does not require creating an unused telemetry subsystem in M0.

Targets and recurring policies are site-scoped execution records compiled from the template library and explicit site overrides below, with pinned effective revisions. There is no shared cross-site execution record. One-off recipes use configured site target IDs without requiring a recurring policy. Target/policy edits increment revision and audit the change. Material target, origin, context, recipe, interval, or authority changes invalidate queued plans and re-arm the existing recurring-authority envelope before the next dispatch; no successful re-arm means `enabled=false` with a blocked reason. Disable cancels queued occurrences and preserves history; deleting a referenced record first disables/tombstones it. Accepted runs retain an immutable normalized target/plan snapshot, not a dependency on mutable current policy text. Monitor bindings reference a policy UUID through a same-scope FK, not an unenforced free-form key.

### Partner and organization template library

Follow [partner-wide-first #2135](https://github.com/LanternOps/breeze/issues/2135), with `contract_templates`/versions as an ownership precedent. Runtime observations stay site-scoped. These three M1 tables are required; “templates” is not an undocumented copy operation:

| Table | Contract |
| --- | --- |
| `topology_config_templates` | UUID; nullable `org_id`, `partner_id`, CHECK exactly one owner; owner-scoped stable key/name unique; description, revision, lifecycle `active\|archived\|revoked`, audit actor/times. No `site_id`. |
| `topology_config_template_versions` | UUID, template FK, denormalized XOR owner columns matching the parent, unique `(template_id,version)`; `draft\|published`, schema/resolver/defaults versions, bounded typed payload ≤256 KiB, SHA-256 content digest, published time/actor. Published content immutable; lifecycle metadata separate. Own enabled/forced RLS, not inherited via FK. |
| `topology_site_template_bindings` | UUID, non-null org/site, unique `(org_id,site_id)`; nullable `partner_version_id` and `org_version_id`, explicit bounded site overrides ≤256 KiB, pinned defaults/schema/resolver versions, revision, compiled effective digest, apply operation ID/status and audit metadata. Null layer means absent, not permission to select arbitrary defaults. Composite site FK. |

Payload schema contains passive collection controls, named target definitions, and named monitoring recipes. It forbids credentials, arbitrary scripts/expressions, and concrete org/site/device/node/interface IDs. Only typed selectors such as `reported_gateway` and `configured_dns` may resolve per site, against fresh permitted origin/context evidence. Missing or ambiguous resolution blocks that setting/check; it cannot select an arbitrary local device. Limits: 64 targets and 64 policies/version, stable keys ≤64 characters, no duplicate keys. Policy references use target keys resolved after inheritance; absent/tombstoned keys are validation failures.

Resolution is **pinned code defaults → selected published partner version → selected published org version → explicit site overrides**. Only allowlisted scalar fields inherit; absence inherits, an explicit allowed `false` disables, and null is rejected except on fields whose schema explicitly defines “unset.” Named target/policy objects replace the entire lower-layer object with the same key; arrays replace rather than concatenate, and arbitrary recursive JSON merge is forbidden. A typed tombstone removes a named object; a higher layer can restore it only through an explicit full definition in the reviewed diff. Type changes require full replacement and revalidation of all references. Clearing a site override reveals the lower layer and therefore requires the same preview as any other effective change. Pinning defaults/schema/resolver versions prevents a software deploy from silently changing existing settings.

Publishing makes a version available; it does not alter a binding, enable monitoring, or run probes. A single bulk Preview/Apply action can select up to 500 sites across authorized organizations, including a 200-site MSP fleet. Versions are pinned, with updates adopted explicitly. New sites start with code defaults until explicitly bound; there is no silent follow-latest behavior. Preview returns each site's effective diff, local overrides, expected binding revision, validation errors, and activation effects. Its digest binds template versions, defaults/resolver versions, overrides, affected target/policy revisions and per-site effects. Apply is one user operation with atomic **per-site** commits and durable per-site outcomes, not a transaction across 500 sites. Idempotent jobs recheck auth and expected revisions; a changed/unauthorized site conflicts without overwriting its local edits, and successful sites are not replayed on retry. Existing overrides survive adoption. Use the existing audited job/task mechanism plus topology outbox for progress; outbox intent/result rows retain the operation ID and idempotency key for at least 30 days for template applications.

Applying creates/updates explicit site targets and policies by stable key, incrementing affected revisions and recording source version IDs, effective digest and field provenance. Template references on runtime rows use same-owner validation; historical runs keep version ID/digest as non-authoritative snapshot metadata rather than a live cross-owner lookup. Retired targets disable/tombstone before removal. Authority is separate: compilation may save disabled policies, but activation requires the recurring-monitor permission/MFA/approval envelope. A material change fences queued dispatch in the same site transaction and requires re-arm; failure leaves the affected policy disabled with a reason. Publishing or applying a template never silently confers execution rights.

Template administration requires `topology:write` + `devices:write`. Partner writes additionally require `canManagePartnerWidePolicies(auth)` and owner identity derived from the authenticated partner; org-library writes require `canMutateOrgWideGovernance` as well as org access, so a site-restricted technician cannot administer an org-wide library. General partner-library administration retains its existing gate. A separate site-scoped selection endpoint deliberately permits graph readers to see eligible **published** versions from their own org's partner and org, with no drafts, hidden credentials or library-edit authority. Site-restricted writers can apply those versions only to their permitted sites. Applying passive settings requires the passive-settings grant; creating/editing probe targets or recurring policies requires the stronger monitoring/target grant in §6. Mixed bulk requests must satisfy every affected capability; unauthorized effects are rejected, not silently applied disabled.

Both XOR tables have enabled/forced policies for `breeze_has_org_access(org_id) OR breeze_has_partner_access(partner_id)`, plus the required separate own-partner **SELECT-only** policy `org_id IS NULL AND partner_id = breeze_current_partner_id()`. Register both in `DUAL_AXIS_TENANT_TABLES` and `XOR_OWNERSHIP_DUAL_AXIS_TABLES`. Database readability does not grant administration, binding or execution authority. Enforce version/parent owner equality, site/org equality, partner-layer partner ownership, and org-layer exact org ownership in the database as well as services. Nullable FKs alone do not enforce XOR or layer ownership: add deferrable constraint triggers on versions, bindings, parent ownership and `organizations.partner_id` changes. Those triggers validate surviving final rows at commit, and lock the relevant org/template/binding rows in a fixed order shared with apply/move/merge to prevent concurrent reference races. Composite org-bearing FKs are `DEFERRABLE INITIALLY IMMEDIATE`.

Ordinary template services refuse owner mutation and PATCH schemas omit owner fields. Published-content immutability guards cover payload, content digest and schema/resolver/defaults-version fields only, **not `org_id` or `partner_id`**; do not REVOKE all UPDATE permission from `breeze_app`. Owner consistency is enforced by the deferred final-state constraints above, while ordinary API ownership immutability is an application rule. The central same-partner org merge service may repoint org-owned templates, versions, bindings and runtime rows together, preserving IDs and immutable version content/digest and retaining original owner in audit metadata. This uses existing `withSystemDbAccessContext` and deferred constraints, not a new GUC/trigger bypass. Partner-owned rows remain unchanged. Resolve owner-scoped stable-key collisions by suffixing the source key with its template UUID; never merge payloads by name. Invalidate affected execution authority and classify every BEFORE UPDATE trigger's allowed column set in `orgMergeRegistry.integration.test.ts`. Cross-partner org transfer is **blocked** while any binding or live runtime provenance references the former partner's versions. An explicit detach/rebind preview must clear those references and disable dependent execution first; retained historical snapshots travel with the org without access to the old partner's library. The new partner must explicitly approve execution authority.

Archive prevents new adoption but preserves already pinned use. Revocation is a separate audited emergency action disabling dependent execution and refusing new adoption; workers recheck it before dispatch. Unbind previews inherited fallback and revalidates authority. Referenced versions cannot be hard-deleted by ordinary administration (service rule; no ordinary hard-delete endpoint). Tenant erasure uses `cascadeDeleteOrg`; partner erasure uses `cascadeDeletePartner` in `tenantCascade.ts`, which erases partner orgs before dynamically deleting partner-owned rows. Delete runtime dependents/bindings before their owned versions/templates; unrelated org/partner templates survive. The nullable `partner_version_id` and `org_version_id` binding FKs use `ON DELETE SET NULL`; version→template uses `ON DELETE CASCADE`. An ownership constraint trigger remains necessary in addition to the nullable UUID FK. If a binding survives owner erasure, the purge hook first disables/fences affected execution and clears live runtime version references, then invalidates its effective digest and requires explicit fallback preview/re-arm. SET NULL cannot silently activate inherited defaults. Dispatch validates the current layer/version provenance and digest, failing closed if a referenced version disappeared even after a direct database cascade. Test both normal purge order and surviving-binding SET NULL behavior. Payload/override JSON is `excludedOpen` in exports, so ordinary export intentionally omits reusable template bodies and cannot reconstruct configurations. Audited scalar version/digest/ownership metadata remains exportable.

The advisor disposition and completed quorum are recorded in Main §13. Configuration-policy feature-link integration is deferred; these templates use the explicit topology library/application workflow. Do not add a new `PARTNER_LINKABLE_FEATURE_TYPES` value without specifying and testing that integration separately.

### Referential and RLS constraints

- Reuse `sites_id_org_id_uniq`; M0 adds `devices_id_org_id_site_id_uniq`, `discovered_assets_id_org_id_site_id_uniq` and `topology_manual_nodes_id_org_id_site_id_uniq`, each on `(id,org_id,site_id)`, before current-binding FKs. The index-only prerequisite uses the runner's existing `-- @no-transaction` support and `CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS`, followed by validity/definition checks; the later table/FK/RLS migration stays transactional. Keep the existing device `(id,org_id)` key. Binding site equality is database-enforced by the triple-column FK, not delegated to the move trigger; M0 Task 2 defines interrupted-index recovery and write-load review. `devices.site_id` is NOT NULL: there is no null-site managed-device population to backfill. Audit mismatched existing associations; handle null sites only on legacy tables that actually permit them, without fabricating a site. For individual inventory moves/deletions, central services detach/delete bindings before updating scope; a database BEFORE trigger backstop detaches on `site_id IS DISTINCT FROM OLD.site_id` or deletion, audits the old association, fences producer/queued dispatch eligibility, and marks affected sites dirty. An individual cross-org device move necessarily changes its site because a site belongs to one org; an org-only update retaining the same site is governed by the coordinated merge rule and deferred final-state FKs below. Register `topology_node_bindings` in `CORE_DEVICE_CASCADE_DELETE_TABLES`, `CORE_DEVICE_ORG_DENORMALIZED_TABLES`, and `DEVICE_SITE_DENORMALIZED_TABLES`, with tests proving individual-move pre-detachment means the generic app and `breeze_device_child_orgid_tables()` database rewrites match zero rows. Do not cascade-update historical graph entities for an individual-device move. Historical canonical node/observation/run references remain in their original scope; immutable inventory IDs are audit metadata, not live cross-site FKs.
- Node/interface/relationship/run/layout child references use composite `(id,org_id,site_id)` FKs, explicitly `DEFERRABLE INITIALLY IMMEDIATE` wherever `org_id` is referenced. The same requirement applies to `(id,org_id)` and new inventory/site/monitor constraints. A foreign UUID with a valid local `org_id` cannot pass insertion. Endpoint/interface ownership is a composite FK or a constrained mapping table, not an unchecked JSON assertion. Choose explicit `ON DELETE` behavior: graph-owned dependents cascade with their graph parent; live inventory references detach through lifecycle hooks; nullable template-layer UUID references use SET NULL with the disabling/invalidation contract above. Verify actual child-before-parent deletion, not alphabetical-list membership alone.
- Diagnostic/monitor targets must reference their node/relationship/policy in the same scope. References to existing org-only monitor records require explicit site binding and server validation; add `site_id` to `network_monitors` with composite site/asset constraints for topology-created virtual-target monitors. Backfill asset-based site values. Legacy asset-less monitors keep null site and are ineligible for topology binding until assigned explicitly. Moving an asset disables its old topology monitoring authority and detaches live monitor/binding references in the same lifecycle transaction; never silently move an active monitoring policy with it. Preserve historical monitor IDs/results and require explicit rebinding before execution.
- All referenced asset/device/monitor IDs are resolved under both org access and `auth.allowedSiteIds` / `requireSiteAccess` on reads and writes. **Site authorization is application-layer only**, matching repo precedent: RLS enforces the org/partner axis and there is no `breeze_has_site_access` helper/policy. Same-scope FKs defend referential integrity, not per-user site visibility. Jobs, caches, templates, AI, diagnostics and history must call the scoped service checks; direct same-org SQL can see other sites under the current RLS contract. Real tests must distinguish DB org denial from API same-org site denial.
- Every new org-bearing table, including both dual-owner template tables, enters `CORE_ORG_CASCADE_DELETE_ORDER` and `CORE_TENANT_EXPORT_POLICY` in the same migration PR, plus an explicit `orgMergeRegistry` disposition. `topology_node_bindings` needs all four core registrations: those two plus the device cascade and org-denormalized lists above. Adding `network_monitors.site_id` also updates its existing export-policy entry. Every column must be classified; all `json`/`jsonb`/`bytea` columns, even bounded validated attributes, payloads, snapshots, settings and overrides, are `excludedOpen` with a reason. Reviewed non-secret digest/hash scalar columns use `reviewedIncluded` when the suspicious-name classifier requires it. Verify partner purge includes both template tables and dependent runtime bindings. Any REVOKE DELETE/append-only trigger also requires `AUDIT_ADMIN_REQUIRED_TABLES` coverage.
- Whole-org merge differs from individual-device reassignment. Extend the existing same-partner merge transaction to repoint `sites.org_id` and **all** associated topology runtime/history rows and template ownership metadata with constraints deferred, and rekey org-scoped identity/relationship keys without changing canonical UUIDs. Preserve original ownership/producer snapshots as audit metadata. Keep pins/manual facts; invalidate source epochs, pending execution authority and cache tokens; bump `build_fence` and graph/settings revisions and enqueue reconciliation. Retaining the same `site_id` avoids the individual-site-move detachment trigger; there is no hidden GUC or privileged trigger bypass. An isolated device org-only change cannot commit unless the site, graph and bindings also satisfy every final-state org FK. Classify table dispositions/trigger column sets in `orgMergeRegistry` and its coverage test. Deferred ownership triggers validate current final rows, not stale queued OLD/NEW images. A merge fixture must prove final FKs, preserved edits/history and rejected late results, avoiding 23503 from non-deferrable FKs.
- **Merge asset-collision branch:** `orgMergeCustomExecutors.ts` currently deduplicates discovered assets by IP and reparents monitor asset references to the survivor, including assets from different sites. That existing behavior must change in the schema/lifecycle PR before adding monitor site/asset FKs. IP equality across sites is not topology identity. For a source asset removed by collision, keep its canonical node, manual relationships, layout and diagnostic history in the source site (under the merged org), detach its current inventory binding, and audit the old association. Preserve each affected monitor's source `site_id`, clear its invalid `asset_id`, disable it and dependent topology policies, detach live monitor bindings, and fence queued commands before deleting the source asset. Do not reparent those monitors to the other site's asset or move their history/site. Unresolved legacy monitor scope remains disabled and needs explicit site assignment. Results already retained remain readable in their original site; future execution requires authorized rebinding/re-arm. The existing same-IP/different-site fixture in `orgMergeCustomExecutors.integration.test.ts` must be extended to prove this final state, plus no FK failure, no inferred cross-site identity and no late-command resurrection. No collision-deleted binding uses the ordinary merge-preserve exception.
- Direct runtime `org_id` tables are auto-discovered by the RLS contract; XOR template/versions additionally require the dual-axis and XOR allowlists and functional second-axis tests above. No deferred RLS migration or application-only tenancy fallback.
- Data cleanup migrations report row counts; suspected cross-tenant mismatches log counts including zero. Never copy mismatched data into a new graph and silently delete the originals.

### Indexes and retention

Index current graph rows by `(org_id,site_id,lifecycle)`, source and target node IDs, current interface lookup keys, and evidence `(org_id,site_id,relationship_id,effective_at DESC)`. Index runs by source/epoch/sequence, diagnostic state/deadline, and run owner/site. Layout writes use unique constraints and revision CAS. Partition telemetry before enabling production polling; a sample row groups one interface's readings for one sample time.

Defaults: changed normalized collection evidence/runs and diagnostics retain 30 days; raw interface samples 7 days, 5-minute aggregates 30 days, hourly aggregates 90 days. Unchanged acknowledgments create no retained run/observation rows; identical 24-hour full revalidations also create none. Current bounded typed baselines/digests/source freshness survive detailed evidence expiry. With 10,000 stable agents this means zero appended run/observation rows after initial baselines, while ~2.88 million compact confirmation updates/day (~33/second before source fan-out) still require write-budget/load testing. Collection bounds changed-history traffic by producer/org; instrument rows, bytes, contexts and quota gaps in addition to retention. Stale discovered relationships archive after 7 days without fresh support, subject to complete-miss withdrawal rules. Inventory/manual assertions/pins remain until their owning lifecycle explicitly removes them. Archive does not delete manual facts.

Keep a compact current-support summary on relationships/nodes when old observation details expire: method, origin, last successful time, effective TTL, confidence, and `detailsExpired`. Evidence links return `expired` rather than inventing detail. Never retain bulk raw payloads merely to preserve a current label. Diagnostic/model answers referencing expired evidence must say detail is unavailable.

Outbox delivered records retain 7 days, except template bulk-apply intents/outcomes retain at least 30 days; undelivered records remain until handled or operator-reviewed with a bounded retry/dead-letter policy. Idempotency mappings live at least 24 hours and at least the operation retry window. Report storage estimates from enabled interfaces × 86,400 / polling interval before recurring port monitoring is enabled. Retention runs are scoped, chunked, and observable; user audit retention follows the existing audit policy.

## 4. Observation ingestion and materialization

Use additive `networkContextV1` capability/payload as specified in Collection. Agent-authenticated heartbeat ingestion derives producer/org/site from enrollment. Agent-supplied org/site IDs are rejected/ignored as authority. A bounded typed payload failure records collection failure without rejecting unrelated valid heartbeat inventory. Unknown future versions are unsupported, not empty-success.

Authorized scans publish versioned source/protocol outcomes through the existing discovery result path. Older adjacency payloads contribute positive observations only and cannot withdraw missing links. UniFi adapters preserve collector/controller site ownership. Chunked source snapshots become `complete` only after all manifest chunks are validated; missing chunks mean `partial`.

For changed content, ingestion commits validated immutable source snapshots in collection runs, accepted-source high-water metadata, and the site's dirty revision atomically under the appropriate DB context. For unchanged content, validate Collection's epoch/source-scoped digest protocol, advance only compact confirmation/freshness metadata, and append no run/observation rows. No new observation, health success or structural graph revision is fabricated by a freshness acknowledgment. An unchanged complete-empty snapshot may advance a pending complete-miss transition once when it supplies the qualifying second miss; that bounded lifecycle change marks the site dirty. Pending newer content cannot renew support from an older published digest. Canonical observations, nodes, interfaces and relationships are written only by publication; staged content cannot leak into graph reads. Fold changed snapshots and compact pending miss transitions in source sequence order. Server epoch + monotonic sequence fences retired producers; a late result cannot update current support, identity, health or run terminal state. Accepted and materialized high-water/digest checkpoints remain separate.

Read a consistent source snapshot with its dirty high-water revision, compute outside the transaction, and publish under per-site `build_fence` and monotonic materialized-input CAS. A snapshot may publish only if newer than the last published input. Ingestion during computation marks another build due; do not erase that dirty state. Derivation never deletes authoritative inventory/manual source rows. Another worker with an obsolete fence cannot commit. A complete graph revision is visible atomically, including nodes, relationships, exclusions, and binding projections.

Topology `graphRevision`, `healthRevision`, and per-view `layoutRevision` are independent. Health polling does not mutate structural revision; user arrangement does not change connectivity. Each response returns an `asOf` timestamp and revision tuple. Paginated traversals use one pinned structural revision; a changed graph returns 409 `graph_revision_changed` rather than silently combining pages from different snapshots.

## 5. API surface

Routes mount from a thin `routes/topology/index.ts` hub. Site graph/execution routes require normal auth, allowed organization scope, and authorized site. Library routes below use explicit partner/org ownership authorization; bulk workflows reauthorize every requested site. Unknown/out-of-scope object IDs return 404; missing operation permission returns 403 without object details. Malformed request is 400; conflicts 409; payload limits 413; rate limits 429 with retry metadata; unavailable queue 503. Errors carry stable codes and localized client-facing messages.

Counts apply to the same permissions/filter/revision as visible entities. Omitted counts and frontiers are mandatory when a projection is bounded. Include boundary stubs for connections to unloaded groups; never claim complete impact/path analysis from a truncated canvas. Server path/impact calculation uses authorized canonical relationships and returns `coverage:'partial'` if its own traversal limit is reached (default10,000 nodes/20,000 relationships, 2-second budget). Search is constrained, indexed, and escaped; no arbitrary Cypher/SQL/query DSL.

Graph envelope (illustrative TypeScript contract, not code already present):

```ts
type GraphResponse = {
  schemaVersion: 1;
  siteId: string;
  view: 'overview' | 'physical' | 'logical';
  asOf: string;
  revisions: { graph: string; health: string; layout: string };
  nodes: GraphNode[];
  relationships: GraphRelationship[];
  presentation: { nodes: PresentationNode[]; edges: PresentationEdge[] };
  layout: { algorithm: string; version: number; positions: Position[] };
  counts: { totalNodes: number; totalRelationships: number; visibleNodes: number;
    visibleRelationships: number; omittedNodes: number; omittedRelationships: number };
  coverage: { state: 'complete' | 'limited' | 'unknown'; reasons: CoverageReason[] };
  frontier: { token: string; label: string; memberCount: number }[];
  permissions: { canEdit: boolean; canDiagnose: boolean; canConfigureMonitoring: boolean };
};
```

`GraphNode` includes stable ID/kind/role/label, permitted identity references, lifecycle, structural freshness, evidence summary, health summary, and `availableActions`. `GraphRelationship` includes IDs/kind/directionality, endpoint/interface references, meaning, directness, evidence classes/methods/counts, confidence, lifecycle/freshness, relevant health, and exclusion state. A summary health field always carries scope/origin/result IDs/reasons and freshness; bare boolean `online` is insufficient.

Layout positions refer only to canonical node IDs; projection-only group/placeholder coordinates are deterministic local derivatives anchored to their context. Viewport state is separate and keyed by user/org/site/view so shared browsers cannot reuse another tenant's map state. Clear relevant caches/state on logout or scope change.

All action responses distinguish accepted work from completed results. Mutations emit audit records and use the standard error envelope; no HTTP200 `{success:false}` for new endpoints. The web nevertheless uses `runAction` for all mutation feedback.

A successful layout PATCH returns `{siteId,view,layoutRevision,positions}` (`LayoutWriteResult`): positions contain only the accepted batch with server-owned source and row revisions. Clients merge by node ID and retain saved positions outside that batch. `layoutWriteResultSchema` validates the response.

`If-Match`/expected revision conflicts return409 with current revision and affected IDs without overwriting anything. For graph-derived actions, harmless label/layout revision changes need not reject execution; changed subject identity, route context, authorization, or target plan does. The server returns an accepted normalized plan so this distinction is reviewable.

HTTP target policy records use hostname, port, path, expected status/address family and an optional configured proxy mode. Credential-bearing URLs, usernames/passwords, fragments, arbitrary schemes, and wildcard ranges are rejected. All network execution and resolution constraints come from Operations. IDs and policy references are preferred to arbitrary ad-hoc destinations.

## 6. Permission matrix

| Capability | Required permissions and conditions |
| --- | --- |
| Read graph/evidence/layout | `topology:read` AND `devices:read`, site access; alert or other restricted detail additionally intersects its existing read permission. Do not leak restricted details through counts, labels, AI, or evidence. |
| Local pan/zoom/search/arrange | Graph read only; no server write. |
| Shared layout, manual facts, view exclusions | `topology:write` and graph read/site access. |
| One-off diagnostics | New `topology:execute` AND `devices:execute`, graph read, applicable target/origin read access and current MFA requirement equivalent to monitor checks. |
| Rescan | Existing discovery execution authority (`devices:execute`), topology execution for topology entry point, profile/site scope, MFA. |
| Configure recurring monitoring/targets | `topology:write`, `devices:write`, `devices:execute`, graph read, current MFA and recurring authority rules. |
| Change passive collection settings | `topology:write` + `devices:write`, graph read/site access; changes cannot enable active discovery schedules implicitly. |
| Administer template library | `topology:write` + `devices:write`; org owner also requires `canMutateOrgWideGovernance`, partner owner also requires `canManagePartnerWidePolicies(auth)`. Publishing grants no execution. |
| Preview/apply existing versions | Graph read for eligible published version selection; applying requires site access and the passive-settings or stronger monitoring/target permissions for every affected field, plus authority/MFA for activation. |
| Read interface/monitor history | Graph read plus existing device/monitor read, and subject/metric site access. |
| AI reads/actions | Same underlying per-resource permissions; action approval/step-up and budgets are inherited from normal AI policy, not bypassed through graph tools. |

Define `topology:execute` once in the registry/migration. Grant it to built-in administrator/technician roles only where the role already has both topology read and device execute; custom roles retain current grants until explicitly configured. No new partner-wide execution grant or implicit `topology:write → execute` escalation.

Permission-filtered projections, ETags, cache keys, cursors, tokens, and AI caches include org/site/effective allowed-site set and permission version, view/filter, graph revision, and user where private state applies. Use private/no-store for sensitive run/evidence responses; graph conditional caches cannot be public/CDN shared. Revalidate scope and permission at lookup, dispatch, result binding, and replay of idempotent requests.

## 7. Legacy migration contract

- `network_topology` rows import as source observations/assertions. `method=manual` is manual/asserted. Known legacy LLDP/CDP/FDB rows retain their method/timestamps but have incomplete endpoint-port identity; do not promote them to a precise cable until re-observed. Unknown/fabricated legacy kinds are quarantined as unverified, not rendered as measured links.
- Bind each discovered asset and manual node to a canonical node within its actual org/site. Managed device binding uses accepted inventory links; do not auto-link by IP/name. Managed devices always have a site; legacy records from tables that permit null site wait outside site graphs until explicitly assigned.
- Import saved positions per site and preserve explicit legacy pins. Where older writes saved a position without reliable pin intent, treat an existing saved drag position as `legacy,pinned=true` to avoid moving user work; display a one-time explanation and allow Unpin. Do not infer pin=false from missing legacy metadata.
- Use a mapping table/metadata keyed by legacy table+ID with a unique scoped canonical binding. Repeated backfills and outbox deliveries are no-ops. Record imported/skipped/conflicted counts per batch.
- Legacy manual/layout writes route through the same scoped service transaction and change outbox once adapters are deployed. A v2 manual physical assertion lacking legacy representation remains retained and visible in v2; rollback must not delete it.
- Capture every legacy writer before taking the backfill snapshot. Import at a recorded source revision/high-water, replay/drain edits and deletion tombstones in order with revision fences, then shadow-compare at a common barrier. No backfill or pilot before capture; no parity claim before drain. Main §11 owns the exact rollout gates.
- Legacy reads keep their old contract and return representable inventory/manual nodes and legacy relationship projections. Do not insert synthetic gateways/networks into old responses expecting discovered asset IDs. New clients use the versioned API.
- The old frontend type definitions in `discovery.ts` remain until consumers migrate. New contracts use separate exported types to avoid silently broadening legacy meaning. Add compatibility tests for both clients and old/new agents.

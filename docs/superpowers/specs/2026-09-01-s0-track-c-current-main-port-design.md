# S0 Track C Current-Main Port Design

**Goal:** Port the reviewed Track C branch (`fix/s0-readiness-offline-scaling`, exact reviewed head `ece39ca5c`, PR #4007) onto current `main` (analysis pinned at `6f496f4d0`) without weakening either side: Track C's continuous consumer-readiness, admission-probe, and durable offline-sweep invariants survive, and main's lazy role-aware worker registry, `BREEZE_ROLE` split, worker entrypoint, ordered shutdown, and every worker landed since the merge base survive. GitHub reports #4007 `CONFLICTING`; a fresh rerere-disabled trial merge reproduces 10 conflicted files (11 hunks) plus a set of obligations git raises no conflict for.

**Method note:** every contract below was derived from two independent read-only analyses of both sides against merge base `879b9889025` (per-hunk contracts with commit attribution; silent post-merge obligations), cross-checked by the controller against the bytes. Claims are verified unless marked *inferred*. The tracker directive holds: do not bulk-prefer either side.

## Non-goals and boundaries

- No production deployment, hosted-fleet enablement, customer-device mutation, or rollout claim. Task 5 exact-candidate evidence (RMM-QA-020/038) stays open and is not part of this port.
- No new `WORKER_REGISTRY` entries and no reordering: `workerRegistry.test.ts` pins exactly 115 names in order and `workerEntrypointClosure.contract.test.ts` walks every `global` entry's runtime closure. Track C adds no registry entries; the port must not either.
- No migration, schema, RLS, tenant-cascade, or tenant-export surface: Track C adds none (verified `git diff --stat base..C` on `apps/api/src/db`, `apps/api/migrations`, `*.sql` shows only `db/dbPoolHealthWiring.test.ts`).
- No `apps/web`, `apps/portal`, or locale change (verified: none in Track C's 84-file diff).
- No change to the offline-detector semantics: main never touched `jobs/offlineDetector.ts` or its three test files since base; Track C's durable continuation + CAS diff applies cleanly and is not re-litigated here.
- No unrelated refactoring. The only cleanup included is what this port itself creates or ratifies (§9).

## 1. Port mechanics

- The merge MUST run `git -c rerere.enabled=false merge --no-ff origin/main`. The repo's 350-entry `rr-cache` silently replays stale resolutions; the trial merge verified all 10 files show `<<<<<<<` markers when rerere is off, so any "using previous resolution" line means the flag was not applied — abort and retry.
- The merge commit is committed `--no-verify` (the naming hook false-positives on main's incoming migrations; precedent #4105/#4064). Every later commit runs the hooks.
- Post-merge follow-up commits (§4–§8) each carry their own RED→GREEN gate. Only the PR head must be green.

## 4. Manifest rekeyed to the registry; hooks for main's new workers (follow-up commit, RED first)

Track C already funnels every attach through the pre-existing `#1379` helper `attachWorkerObservability(worker, name)` (`jobs/workerObservability.ts`, one added line), so the "2-line hook" is that helper's import + call, not a new API. Main's `StartWorkersHooks.onResult(name, ok, err)` is the natural seam for initializer-level failure (§3.2); per-consumer lifecycle stays where the instance is.

**D2 (decision): the manifest is keyed by `WORKER_REGISTRY` entry name plus the two out-of-registry consumers, and its completeness is asserted against the registry, not against `index.ts`.**

## 5. Role-scoped required consumers (follow-up commit, RED first)

**D3 (decision): the required-consumer set is a function of `breezeRole()` derived from `selectWorkers(role)`, never a role-blind "all 102".** Track C's plan predates the `BREEZE_ROLE` split (no mention of roles in the plan). On main, `selectWorkers('api')` starts only the 25 `socket-owner` entries and `selectWorkers('worker')` only the 90 `global` ones; Track C's `declareExpectedConsumers` declares every manifest consumer required whenever Redis is up. Consequence if left alone: a `BREEZE_API_ROLE=api` process (worker-split profile) would have 78 consumers stuck in `expected` forever, `/ready` and `/health/ready` permanently 503, and `deploy.sh`'s new `readiness_ok` would fail every deploy. Under the compose default `all` the behavior matches Track C's design, which is why Track C's own CI never saw this.

Shape:

- `declareExpectedConsumers({ role, redisAvailable, abuseSignalsEnabled, registry })`: required = consumers of every manifest entry whose initializer is in `selectWorkers(role).map((e) => e.name)`, plus `eventDispatch`/`eventDispatchMaintenance` when `role !== 'api'`, plus `agentCommandRelay` when `role !== 'worker'`. `abuseSignalsWorker` is a `global` entry, so its `abuse_signals_enabled` rule applies only in `worker`/`all`. Consumers of entries NOT selected for the role are not declared at all (not "optional", not "disabled": they do not exist in that process, and the public aggregate must not count them).
- `consumersForInitializer(name)` is unchanged (it is used by the `onResult` failure path in both entrypoints).
- **D3a (decision): conditional and optional consumers are resolved at declare time by manifest rules; `disable()` and its reviewed invariant are untouched.** A full audit of the 115 registry initializers plus the two out-of-registry ones (review C3(b)) found exactly three consumers whose construction is gated by a feature flag — `eventDispatch` (`EVENT_DISPATCH_MODE`, default `off`; the initializer constructs the main `Worker` only when the mode is on or an off-mode backlog remains), `aiAgentRunner` (`AI_AGENTS_ENABLED`, default `false`), `abuseSignalsWorker` (already handled by Track C) — plus four initializers gated on `isRedisAvailable()` (`wingetIndexSyncWorker`, `cveEnrichmentWorker`, `patchComplianceReportWorker`, `reportScheduleWorker`), which are consistent with the `redisAvailable` predicate `declareExpectedConsumers` already uses. Everything else constructs unconditionally.
  - Two new `requiredWhen` rules beside `abuse_signals_enabled`, resolved at declare time with the identical shape (`expect(name, false)` + `disable(name, 'feature_disabled')` when the rule is off): `event_dispatch_enabled` (from `eventDispatchMode() !== 'off'`) for `eventDispatch`, and `ai_agents_enabled` (from `AI_AGENTS_ENABLED`) for `aiAgentRunner`. An off-mode backlog drain that does construct the dispatch worker then attaches as optional-running — no readiness effect, no throw, no new registry API. `declareExpectedConsumers` takes these flags as inputs (like `abuseSignalsEnabled`), never reads env itself.
  - `eventDispatchMaintenance` is declared **optional** (`expect(name, false)`) by a per-consumer optional marker in its manifest row. Main's initializer deliberately isolates maintenance-registration failure from readiness ("must degrade to 'retention/shadow-compare didn't get scheduled this boot' rather than pinning `/ready` to not-ready", verified in the module); Track C's auto-expect would silently make it required the moment it attaches.
  - `agentCommandRelay` constructs its `Worker` unconditionally inside its initializer (verified) and is plain required in `api`/`all`.
  - Track C's `workerReadinessRegistry.test.ts` invariant "fails closed for required disabled consumers" is kept as-is; nothing in the port calls `disable()` from inside a job module (main's `eventDispatchWorker.test.ts` runs mode-off inits against the real registry singleton with nothing declared, so an in-module `disable()` would throw there).
  - The auto-expect-as-required fallback in `attach()` stays (fail-closed for a consumer nobody declared); with D2's set-equality contract and A2's attach relocation it can only fire on a name the static tests already reject, so it is a runtime backstop, not a declaration path.
  - RED first in `workerReadinessManifest.test.ts`: with each flag off the consumer is declared optional and disabled; with it on, required. `abuseSignalsWorker` is `global`, so its rule applies only in `worker`/`all`.
- **D3b (decision, ratified compatibility change): optional-Redis admission.** Main's evaluator admits a process when Redis is declared optional and absent; Track C keeps admission closed because no queue consumer can run (reviewed test "keeps admission closed" in `services/readiness.test.ts`). The port keeps Track C's fail-closed rule — that is the RMM-QA-020 finding — and records it in the PR body as an intentional behavior change for deployments running without Redis.
- RED tests first, in `workerReadinessManifest.test.ts`: with `role: 'api'` exactly the socket-owner consumers + `agentCommandRelay` are declared; with `role: 'worker'` exactly the global consumers + `eventDispatch` + `eventDispatchMaintenance`; with `role: 'all'` every consumer; the union of `api` and `worker` equals `all`; and each declared consumer carries the `required` flag its rule yields (plain rows `true`; `eventDispatchMaintenance` `false`; the three flag-gated rows `true`/`false` per the flag inputs). The expected sets are computed in the test from `WORKER_REGISTRY` placements and the rules, so the literals do not rot when placements flip.
- `index.ts` passes `role: breezeRole()`; `worker.ts` passes `role: 'worker'` (§6).

## 6. Worker entrypoint port (follow-up commit, RED first)

`apps/api/src/worker.ts` is main-only and untouched by Track C, yet it is a verified compile break: it builds its evaluator with the base `workersHealthy: (redisOk) => computeWorkersHealthy({...})` option, which Track C removed in favor of the required `workerRegistry` + `workersInitialized` options. Git raises no conflict. `worker.boot.test.ts` cannot even load until this is fixed.

**D4 (decision): port `worker.ts` onto Track C's evaluator contract rather than widening the evaluator to accept the legacy option.** A legacy escape hatch would let the worker container's `/health/ready` keep reporting the boot-time `workerStatus` snapshot — exactly the RMM-QA-020 defect Track C removes — on the one container whose compose healthcheck actually probes `/health/ready`.

Shape:

- Options: `workerRegistry: workerReadinessRegistry`, `workersInitialized: () => workerInitPhase === 'started'`, `isShuttingDown`, `requireRedis: true`, timing from `resolveReadinessTiming(process.env, warn)` (so both entrypoints clamp `READINESS_*` identically; today they differ), `onProbeFailure` unchanged. `setWorkerReadinessTransitionHandler(() => readiness.invalidate())` after construction. Drop the `computeWorkersHealthy` import from `worker.ts` (the function itself is deleted below).
- Before `startRegisteredWorkers('worker', …)`: `declareExpectedConsumers({ role: 'worker', redisAvailable: true, abuseSignalsEnabled: abuseSignalsEnabled(), eventDispatchEnabled: eventDispatchMode() !== 'off', aiAgentsEnabled: AI_AGENTS_ENABLED, registry: workerReadinessRegistry })` (Redis is mandatory in this entrypoint, so `redisAvailable` is always true at that point; the dispatch flag matters here because `eventDispatch` is declared under `worker`). In `onResult`, on `!ok`, add the same per-consumer `recordInitializationFailure` loop as `index.ts`. The event-dispatch consumer main starts after the registry in `worker.ts` is already attached by its module.

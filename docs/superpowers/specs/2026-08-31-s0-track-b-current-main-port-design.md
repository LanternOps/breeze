# S0 Track B Current-Main Port Design

**Goal:** Port the reviewed Track B branch (`fix/s0-track-b-fleet-execution-truth`, exact reviewed head `b8d24ed8d`, PR #4064) onto current `main` (analysis pinned at `bd7d95f41`) without weakening either side: Track B's fleet-execution-truth invariants and main's landed Track A (#4062), Track D (#4035), Track E (#4105), and AI-agents behavior all survive. GitHub currently reports #4064 `CONFLICTING`/`DIRTY`; a fresh trial merge reproduces 22 conflicted files (~42 hunks) plus a set of obligations git raises no conflict for.

**Method note:** every resolution contract below was derived by independent per-area analysis of both sides of each hunk against merge-base `b4a825dc5`, with provenance attributed per commit. Claims are verified against blobs/DDL unless explicitly marked *inferred*. The tracker directive holds throughout: do not bulk-prefer either side.

## Non-goals and boundaries

- No production deployment, hosted-fleet enablement, customer-device mutation, or rollout claim.
- Track E's `blocks-merge` org-merge policy class and the `SPECIAL.pam_actuations` / `SPECIAL.pam_actuation_results` registrations are not touched, weakened, or extended (§5).
- No unrelated refactoring. The only cleanup included is dead code this port itself creates or ratifies (§9).

## 1. Port mechanics

**Approach: one deliberate merge commit of `origin/main` into the branch, followed by small contract-closing commits, keeping `b8d24ed8d` as the reviewed evidence anchor.**

- Alternatives rejected: (a) rebase/rebuild of the ~60-commit branch — destroys the reviewed lineage and the exact-head CI evidence recorded in #4060/#4064 for no semantic gain; (b) resolving everything inside the merge commit — several obligations (org-merge registry, UI fix re-port) have natural RED checkpoints only *after* the merge exists, and hiding them in the merge forfeits the RED→GREEN evidence.
- The merge MUST run with `git -c rerere.enabled=false merge origin/main`. The repo carries a 354-entry `rr-cache`, and the trial merge proved a recorded resolution replays a take-ours-wholesale result for `automationsPartnerRls.integration.test.ts`, silently reverting main's landed coverage (§7). Verified: the trial-merge copy of that file is byte-identical to the Track B blob.
- The merge commit is committed `--no-verify` (known false positive: the naming hook treats main's incoming migrations as new files; the PR-base gate stays authoritative — precedent from the #4105 merge).
- Post-merge follow-up commits (§4–§9) each carry their own gates. The PR head must be green; intermediate commits need not be.
- Two lineage gates clear by construction once main is merged: `check-migration-immutability.sh` currently fails on the un-ported tip ("checked lineage is behind mainline release" — `v0.108.0` is not an ancestor of `b8d24ed8d`), and `test:release-lineage` uses synthetic repos and cannot be affected.

## 5. Org-merge registry and trigger classification (follow-up commit; the silent break)

`orgMergeRegistry.ts` and its contracts did not exist at the merge base, so the trial merge shows zero conflicts — yet main's completeness test (`orgMergeRegistry.integration.test.ts`: "every required table has exactly one policy", required = cascade order ∪ extras) reds the moment Track B's five tables enter `getOrgCascadeDeleteOrder()`. This is the same failure mode that blocked Track E's own CI. The natural post-merge RED is the checkpoint; this commit discharges it.

> **Amended in fix round 1 of Task 3 after review disproved the derived rationale.** D2 below originally classified all five Track B tables `repoint`; task review (C1/I1/I2) established that `agent_health_observations` and `software_inventory_observations` have `UPDATE` (and `TRUNCATE`) REVOKEd from `breeze_app` in their own append-only-evidence migrations (`2026-09-28-100000-agent-health-observations.sql` line 144, `2026-09-28-100002-software-inventory-observations.sql` line 166), so `repoint`'s unconditional `UPDATE ... SET org_id` as `breeze_app` raises 42501 on those two the instant it runs — even against zero matching rows — aborting every merge after the loser org is already fenced. The org-merge contract test is blind to this because it connects as the schema owner, not `breeze_app`, and nothing else in the port's battery executes a real merge as the app role. The corrected split below is 3 `repoint` + 2 `derived`; the discriminating privilege assertion described at the end of this section closes that blind spot going forward.

**D2 (decision, corrected): three tables are plain `repoint`; two are `derived`.**

- `automation_action_results`, `device_agent_health_latest`, `device_software_inventory_state` — plain `repoint`, inserted alphabetically into `REPOINT_TABLES`. All three carry `FOREIGN KEY (device_id, org_id) REFERENCES devices(id, org_id) ON UPDATE CASCADE … DEFERRABLE INITIALLY DEFERRED`, and `breeze_app` retains `UPDATE` on all three (verified: not among the two migrations' `REVOKE UPDATE` targets), so `repoint`'s direct `UPDATE ... SET org_id` executes cleanly. Precedent: Track D's own repoint block for `agent_rollback_*` / `peripheral_policy_*` evidence tables of the same shape.
- `agent_health_observations`, `software_inventory_observations` — `derived`, in `SPECIAL`, beside `partner_export_device_material_state`/`partner_export_site_material_state` (the same mechanism: `derived` describes org_id moving via a repointed parent's `ON UPDATE CASCADE` FK, not a trigger). Physical ground truth: both carry the identical `(device_id, org_id) -> devices(id, org_id) ON UPDATE CASCADE` FK — Postgres moves these rows for free the moment `devices.org_id` repoints, regardless of what the registry says — but their own migrations `REVOKE UPDATE, TRUNCATE ON <table> FROM breeze_app` as part of hardening them into append-only evidence. `repoint` would therefore have the correct physical outcome (the FK cascade still fires) but the wrong *mechanism* — the registry's own `UPDATE` statement, issued as `breeze_app`, never reaches the cascade at all; it fails closed with 42501 before Postgres gets the chance. `leave-for-erasure` would still be a false statement (the rows are not destroyed) and would mis-count the merge preview.
- No `repoint-dedupe` needed for any of the five: uniques are device-disambiguated or globally unique (verified per table).
- **`blocks-merge` is explicitly NOT extended to any of the five.** It is reserved for tables whose repoint is physically unreachable *by any mechanism, including cascade* (revoked UPDATE + unconditional 42501 + no cascade path) — extending it here would make any org merge impossible for any org holding a single health or inventory observation, when in fact the FK cascade delivers the repoint for free. `SPECIAL.pam_actuations`/`pam_actuation_results` stay untouched; the discharge assertion ("every conditionally-blocking trigger is discharged by a live blocks-merge policy") pins them.
- **New privilege gate (fix round 1):** `orgMergeRegistry.integration.test.ts` gained `'every repoint / repoint-dedupe table grants breeze_app UPDATE'`, which asserts `has_table_privilege('breeze_app', <table>, 'UPDATE')` for every table classified `repoint`/`repoint-dedupe`, naming any offender and pointing at the derived-vs-repoint distinction. This is what should have caught the original misclassification before commit, and is the guard against the next table that revokes UPDATE without a matching registry review.

**Trigger classification (main's `table.trigger`-keyed contract):** Track B creates exactly two enumerated triggers (BEFORE UPDATE FOR EACH ROW on org_id tables): `agent_health_observations_immutable_trg` and `software_inventory_observations_immutable_trg`. Both guard bodies verified to deliberately omit `org_id` from their compared set ("the device move contract may restamp tenant metadata"), so an org_id-only repoint passes. Both go in **`ORG_ID_BENIGN_TRIGGERS`** with the note `'org_id-only device-owner restamp'`, beside the identical `agent_rollback_events`/`peripheral_policy_delivery_events` pair. Warning recorded: the "unreviewed trigger" failure text nudges toward `ORG_ID_BLOCKING_TRIGGERS`; that would force a non-mutating policy kind and be factually wrong. B's two AFTER-timing guards are not enumerated by the contract and already exist on main via Track A. The other three tables create no triggers.

Also stated for the record (no code change): a PAM-bearing device's move-org is refused by `devices_pam_history_move_guard` at the `devices` UPDATE, before any Track B table is touched — B's tables ride the FK cascade downstream of the guarded update, so Track E's device-move contract is preserved by construction. And `automation_action_results` is the first org_id-bearing child of `automation_runs` (which has no org_id and sits in no registry) — a pre-existing gap, not widened here: the child repoints; the single-column `run_id` FK stays valid.

## 6. Command-result handler type (D1, inside the merge commit)

Ordering constraint verified in the cleanly-merged `commands.ts` and preserved as-is: Track E's `isTerminalPamCommand` supplemental block stays ahead of the terminal CAS; B's terminal-evidence call stays after the CAS zero-row check; PAM early-returns never reach B's automation reconciliation.

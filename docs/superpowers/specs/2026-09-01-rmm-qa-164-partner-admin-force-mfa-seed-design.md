# RMM-QA-164 Partner Admin `force_mfa` Seed Design

**Goal:** Make `force_mfa = true` an invariant of every system-defined Partner Admin role on every creation path — the global template seeded by `seedRoles()`, the per-tenant copy inserted by `createPartner()`, and rows that already exist on installed databases — so that a password-only Partner Admin is told to enrol (`mfaEnrollmentRequired: true`), is minted an access token with `mfa: false`, and is refused by every `requireMfa()` gate until a real factor exists. Finding RMM-QA-164 (S1, `docs/qa/evidence/2026-08-22-partner-role-mfa-matrix.md` in the QA repo) proved the opposite on a fresh stack: the applied migration `2026-05-25-f-role-force-mfa.sql` promised the flag, the freshly seeded row stored `false`, login minted `mfa: true`, and a command-free invalid write behind `requireMfa()` reached child validation.

**Branch:** `fix/rmm-qa-164-partner-admin-force-mfa-seed`, cut from `origin/main` at `0fb5af40d`. The verified brief was written against `6f496f4d0`; main moved by two commits on this surface (`c77fceaa2` #3608 partner inbound-email default, `b04192a76` #4215 device org-move migration). The only consequence is the migration ordering ceiling: the max shipped migration is now `2026-09-29-detach-ticket-runs-on-device-org-move.sql`, not `2026-09-28-quickbooks-entity-mappings.sql` as the brief states (§D4).

## 2. Decisions

**D1 — `SYSTEM_ROLES` carries an explicit `forceMfa: boolean` on every entry, typed.** Add `type SystemRoleDefinition = { name; scope; description; permissions: string[]; forceMfa: boolean }` and declare `SYSTEM_ROLES: readonly SystemRoleDefinition[]` (or `satisfies`), with `forceMfa: true` on Partner Admin and `forceMfa: false` on the other nine. Rationale: an optional field on one entry makes `roleDef.forceMfa` a union-typed access and hides the posture of every other role; an explicit boolean per role makes the definition the readable source of truth and lets the unit test assert "exactly one role is forced". Cost-if-wrong: nine extra lines; zero runtime cost.

**D2 — `seedRoles()` narrows its `existing` lookup to the global system row and reconciles one-directionally.** The lookup becomes `and(eq(roles.name, roleDef.name), eq(roles.isSystem, true), isNull(roles.partnerId), isNull(roles.orgId))` (`isNull` is a new import from `drizzle-orm`; `and` already imported). The insert passes `forceMfa: roleDef.forceMfa`. On the existing branch: `if (roleDef.forceMfa && !existing.forceMfa)` → `db.update(roles).set({ forceMfa: true }).where(eq(roles.id, existing.id))`, logged as `Role reconciled (force_mfa): <name>`. This satisfies verifier concern 1 verbatim: a custom `is_system = false` "Partner Admin" or a tenant copy (`partner_id` set) can no longer be matched by the seed, so it cannot be flipped or mistaken for the template. One-directional because the migration header (F5) frames Org Admin et al. as per-deployment opt-ins; a bidirectional "make it equal the definition" would silently revert an operator's raised flag on every `pnpm db:seed`. Tenant copies are reconciled by the migration alone (D4), exactly as the verifier asked. Side effect accepted: on a database whose global template is missing but a custom same-name row exists, the narrowed lookup now creates the missing template — the correct outcome, since `createPartner()` (F6) requires that exact row. Cost-if-wrong: if a future definition ever needs to *relax* a role, it must ship an explicit migration — the right friction for an auth flag.

**D3 — `createPartner()` writes `forceMfa: true` as a literal on the tenant Partner Admin insert.** Not copied from the global template: the template lookup happens after the insert (F6), and the invariant is "system Partner Admin forces MFA", not "whatever the template currently says". The env kill switch (F10) remains the single relief valve, and it applies uniformly to every tenant. Cost-if-wrong: an operator who wants no forcing must set `MFA_FORCE_FOR_PARTNER_ADMIN=false` rather than editing a row — which is the documented mechanism.

**D4 — One idempotent forward migration reconciles installed databases, filtered to system rows.** File `apps/api/migrations/2026-09-30-100000-partner-admin-force-mfa-reconcile.sql` (preferred `HHMMSS` form; sorts strictly after `2026-09-29-detach-ticket-runs-on-device-org-move.sql` — re-verify the max at execution time, main moves; a `2026-09-29-100000-…` name would sort *before* the `-d…` file because digits precede letters). Body:

```sql
DO $$
DECLARE n integer;
BEGIN
  UPDATE roles
  SET force_mfa = true
  WHERE scope = 'partner'
    AND name = 'Partner Admin'
    AND is_system = true
    AND force_mfa = false;
  GET DIAGNOSTICS n = ROW_COUNT;
  IF n > 0 THEN
    RAISE WARNING 'partner-admin force_mfa reconcile: flipped % system Partner Admin role(s) to force_mfa=true', n;
  ELSE
    RAISE NOTICE 'partner-admin force_mfa reconcile: 0 rows needed flipping';
  END IF;
END $$;
```

It flips the global template (`partner_id IS NULL`) and every tenant copy (`partner_id` set); it excludes `is_system = false` rows by construction (openDecision 4). No inner `BEGIN;`/`COMMIT;`; re-application is a true no-op (`force_mfa = false` predicate). The count is always logged (the `2026-06-10-c` lesson: a zero is evidence too). Verifier concern 3 satisfied: `2026-05-25-f` is untouched and the new file sorts last.

**D5 — The epoch side effect is accepted and documented, not suppressed.** Each flipped tenant row fires `breeze_roles_permissions_epoch` (F11), which bumps `permissions_epoch` for every member of that role: a one-time permission-cache invalidation and, for every unenrolled Partner Admin, a 428 enrollment wall on their next non-exempt request. That is the intended security outcome of the finding. The migration test (§4 T5) pins it: exactly one bump per member on first apply, zero on re-apply. The rollout note (§6) names `MFA_FORCE_FOR_PARTNER_ADMIN=false` as the relief valve. Verifier concern 2 satisfied.

**D6 — Make the relief valve reachable in the self-host stack.** Add `MFA_FORCE_FOR_PARTNER_ADMIN: ${MFA_FORCE_FOR_PARTNER_ADMIN:-}` to the `api` service environment block of the root `docker-compose.yml` (beside `ENABLE_2FA`, F17) and a commented `# MFA_FORCE_FOR_PARTNER_ADMIN=true` entry with the kill-switch explanation in the root `.env.example` (mirroring `deploy/.env.example:181-184`). Without this, a self-hoster locked out by D4/D5 has no documented escape short of `psql`. The parity guard (F17) requires the two edits to land together. Cost-if-wrong: none at runtime (`${VAR:-}` passes an empty string, which `envFlag` treats as unset).

**D7 — CI smoke keeps its 200 expectations via the relief valve and gains a stored-flag assertion.** Add `MFA_FORCE_FOR_PARTNER_ADMIN=false` to the smoke job's generated `.env` (F18) so the bootstrap admin's token is minted `mfa: true` and the endpoint sweep stays meaningful; add one step after "Login and export token" that asserts the seeded template stored the flag: `docker compose exec -T postgres psql -U … -d breeze -tAc "SELECT force_mfa FROM roles WHERE name = 'Partner Admin' AND is_system AND partner_id IS NULL"` must print `t` (exact service name/credentials to be taken from the job's own compose invocation at implementation time — *inferred*, not yet executed). This is the compose-stack replica of the finding's headline symptom ("fresh stack stored false") and complements the real-Postgres integration proof. Alternative rejected: enrolling TOTP inside the smoke — heavier, and the integration suites already prove the mint behaviour on real Postgres. Cost-if-wrong: the smoke no longer exercises the 428 wall; that is covered by §4 T3/T4 and the existing `auth.test.ts` gate tests.

**D8 — No web change in this PR.** `mfaEnrollmentRequired` is not threaded through `apiLogin`/`apiVerifyEmail` (F21). The exit-evidence contract is API-level; the existing 428 handler lands the user on `/auth/mfa/setup?forced=1` on the first protected fetch after login. Recorded as a follow-up UX item (one extra round trip and a possible flash of the dashboard shell), not smuggled into an auth/migration PR. Cost-if-wrong: UX only; no assurance impact.

**D9 — Org Admin and all other system roles stay `forceMfa: false`.** Matches the migration header (F5) and openDecision 1. The reconcile in D2 never lowers a raised flag, so an MSP that opted Org Admin in keeps it.

**D10 — `MFA_FORCE_FOR_PARTNER_ADMIN` stays the runtime relief valve; no new flag.** The resolver already scopes it to the role-force component only (F8); settings-driven `requireMfa` is unaffected.

**D11 — Custom same-name roles are excluded on every path**: the D2 lookup filter, the D4 `is_system = true` predicate, and the D3 literal apply only to rows the system creates. Pinned by §4 T2 and T5.

**D12 — `registerPartnerMfaPolicy` loses its role trigger and gains a kill-switch control.** Remove `breeze_test_role_force_mfa` (install + attach + drop) and rewrite the header (F12 lines 21-25) to state that `createPartner` now stores the corrected row itself; keep the settings-axis trigger. The role-axis test asserts, with no trigger, that the real `createPartner` row is `force_mfa = true`, `body.mfaEnrollmentRequired === true`, `accessClaims.mfa === false`, `enrollUrl === '/auth/mfa/setup'`. The existing control ("still mints `mfa: true` when nothing requires MFA") can no longer be produced by `createPartner` — after D3 every fresh tenant admin is forced — so it becomes "kill switch off → still mints `mfa: true`": set `process.env.MFA_FORCE_FOR_PARTNER_ADMIN = 'false'` inside that test (restored in `finally`), which is legal because `mfaForcePartnerAdmin()` reads the env at call time (F10). This keeps the pair self-checking: the role-axis assertions (`mfa === false`) can only pass when `ENABLE_2FA` resolved true (F7's short-circuit would mint `true`), and the control can only pass when the kill switch is honoured. Verifier concern 4 satisfied (the file already sets `ENABLE_2FA='true'` before its dynamic imports; the spec keeps that and makes the role-axis assertion the guard).

**D13 — Deviation from the brief's test list, stated.** The brief puts "insert values include `forceMfa`" in `seed.test.ts`. `seed.test.ts` imports `seed.ts` without mocking the DB and asserts definitions only (F13); mocking the Drizzle chain for `seedRoles()` there would duplicate what the real-Postgres test proves. The insert-values proof therefore lives in `seedPartnerAdminForceMfa.integration.test.ts` (§4 T2), and `seed.test.ts` asserts the definition posture (T1). `partnerCreate.test.ts` already captures insert values (F13), so its assertion is unit-level as the brief lists.

## 6. Rollout note (for the PR body and release notes)

On the first boot after upgrade, `2026-09-30-100000-partner-admin-force-mfa-reconcile.sql` flips every system Partner Admin role that is still `force_mfa = false` — the global template and one row per tenant. Each flipped tenant row bumps `permissions_epoch` for that tenant's Partner Admin members (one-time cache invalidation), and every Partner Admin without an enrolled factor receives `428 mfa_enrollment_required` on their next non-exempt request until they enrol at `/auth/mfa/setup` (the web app redirects there automatically). Fresh installs seed the flag directly, so the bootstrap admin must enrol MFA before the setup wizard's protected calls succeed. Relief valve, if an enrolment outage locks operators out: `MFA_FORCE_FOR_PARTNER_ADMIN=false` in `.env` (now mapped in the root compose as well as the prod compose), which suppresses only the role-force component; settings-driven `requireMfa` stays enforced. The migration logs the flipped-row count as a `WARNING` (or `NOTICE … 0 rows`) in the Postgres log.

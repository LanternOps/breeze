# Build-time display branding for the agent (Phase 1): Design

Discussion: LanternOps/breeze#7567
Related: LanternOps/breeze#6365 (Helper white-labeling at runtime)
Date: 2026-10-02
Revised: 2026-10-05 (maintainer review on PR #7841)
Status: draft, pre-implementation
Blast radius: display strings in the MSI, in the agent's service registration (Go) and in the systemd unit generated in Go; an explicit contract plus tests on the API's reliability rule, and service-name normalization in the agent's collector. No route or protocol changes.

## 1. Summary

MSPs that self-host Breeze and run their own managed service want the agent's user-visible display strings to carry their identity without maintaining source patches on every release. This spec proposes optional build parameters for those strings. With no parameters, official output text remains identical to today's.

The strings are display-only, with **one exception**: the API's reliability scoring recognizes Breeze's own services by name. That dependency and the proposed handling are in section 6.6.

This spec covers Phase 1 only, as scoped in Discussion #7567.

## 2. Goals

- Let an operator supply, at build time, display strings for: the MSI `Manufacturer`, the MSI package description, the display name and description of the agent and watchdog services, and the equivalent descriptions in the systemd units generated in Go.
- With no parameters, official output text is identical to today's, and CI tests prove it.
- The same branding profile can be applied to every upstream release, so a branded N upgrades to a branded N+1 with the same visible identity.
- Device reliability scoring is not affected by branding.

## 3. Non-goals / out of scope

- **Identifiers.** `BreezeAgent`/`BreezeWatchdog` service names, event-log sources, MSI `UpgradeCode` and `ProductName`, binary and asset names, install paths, IPC names, `com.breeze.*` labels. MSI upgrade, the updater and agent self-inventory key on them.
- **Icons.** Deferred to their own spec (they touch the signed binary and the build pipeline).
- **Helper titles, welcome text and colours.** Covered at runtime by the Helper config policy (#6365).
- **Phase 2** (OS-language i18n) gets its own spec.
- **Branded release infrastructure.** Upstream carries the parameters only. It does not build, sign, or publish branded releases.
- **The install script generated by the API** (`apps/api/src/routes/agents/download.ts`, which embeds `Description=Breeze RMM Agent` in the systemd unit).
- **Unifying the MSI and Go default names.** It would change official output.
- **macOS.** Where its display strings live has not been verified.

## 4. Technical background

Line numbers refer to upstream `main` at `ed93a4443`.

- `Manufacturer="Breeze RMM"` and the package description are hardcoded (`agent/installer/breeze.wxs:58,65`), as are the service display names and descriptions (`breeze.wxs:451-452,486-487`).
- Go registers the Windows service through `winsvcinstall.Spec{Name, DisplayName, Description}`, for the agent (`agent/internal/agentapp/service_cmd_windows.go:92-93`) and the watchdog (`agent/cmd/breeze-watchdog/service_cmd_windows.go:64-65`).
- On Linux, units are generated in Go (`agent/internal/agentapp/systemd_unit.go:35` and `agent/cmd/breeze-watchdog/service_cmd_linux.go:22`). The root commands carry a branded `Short` text (`agentapp/main.go:214` and `breeze-watchdog/main.go:108`).
- `build-msi.ps1 -Edition` already passes WiX variables via `-d`, and `allowedHosts` is injected through ldflags in `agent/scripts/build-edition.sh`.
- The reliability collector extracts the service name from the SCM event message with the expression `the (.+?) service` (`reServiceName`, `parseServiceName`, `agent/internal/collectors/reliability.go`), or falls back to the event source, and sends it to the API. The SCM message is expected to quote the service's display name. The API compares the name in `isBreezeSelfServiceFailure` (`apps/api/src/services/reliabilityScoring.ts:911`), whose comment describes the name received on Windows as the display name. Existing tests use synthetic messages. Confirming with a real 7031 event is part of the implementation (6.6).

Today's defaults differ between the MSI and Go:

| Item | MSI | Go (Windows) |
|---|---|---|
| Agent, name | "Breeze Agent" | "Breeze RMM Agent" |
| Agent, description | "Breeze RMM endpoint agent" | "Breeze Remote Monitoring and Management Agent" |
| Watchdog, name | "Breeze RMM Watchdog" | "Breeze RMM Watchdog" |
| Watchdog, description | "Monitors and recovers the Breeze RMM Agent" | "Breeze Agent Watchdog - monitors and recovers the agent process" |

## 6. Design

### 6.1 Parameters (names are a proposal)

| Parameter | Affects |
|---|---|
| `Manufacturer` | `breeze.wxs` `Package/@Manufacturer` |
| `PackageDescription` | `breeze.wxs` `SummaryInformation/@Description` |
| `AgentServiceDisplayName`, `AgentServiceDescription` | `breeze.wxs` `ServiceInstall`, the agent's `winsvcinstall.Spec`, and the agent systemd unit `Description=` |
| `WatchdogServiceDisplayName`, `WatchdogServiceDescription` | `breeze.wxs` `ServiceInstall`, the watchdog's `winsvcinstall.Spec`, and the watchdog systemd unit `Description=` |

### 6.2 Mechanism and validation

- **MSI:** optional `build-msi.ps1` parameters mapped to WiX `-d` variables, with `<?ifndef?>` defaults equal to today's literals (the pattern already used for `ProductName`).
- **Go:** a small internal package (for example `agent/internal/branding`) holding the display strings as variables, set through `-ldflags -X`, with defaults equal to today's literals. `build-edition.sh` forwards optional values and emits no extra flags when none are given.
- When a value is supplied, the MSI and Go paths receive the **same** value.
- **Validation.** The build scripts (`build-msi.ps1` and `build-edition.sh`) reject newlines and control characters and enforce a maximum length, and the build fails on an invalid value. A newline would inject directives into the generated unit, and Windows caps service display names at 256 characters. The description limit is to be agreed in review. Values passed to WiX are XML-escaped.
- **systemd unit.** Branding replaces only the `Description=` line of the generated unit. The `linuxUnit` constant and the static files under `agent/service/systemd/` do not change.

### 6.3 Preserved defaults

With no parameters, **each path keeps its current default**: the MSI stays "Breeze Agent" and Go stays "Breeze RMM Agent". Unifying the defaults would change official output and is out of scope.

### 6.4 Default-output guarantee

A Go binary does not stay byte-identical once the new package and its variables are added, even with no flags. The guarantee is therefore stated over the **output strings**, with golden tests that, with no branding parameters, compare against today's literals:

- the `DisplayName` and `Description` of the agent's and the watchdog's `winsvcinstall.Spec`;
- the generated systemd unit text for the agent and the watchdog;
- the root command `Short` of the agent and the watchdog.

Windows service registration lives in build-constrained files. For the test to run on Linux CI, building the `Spec` should live in a platform-independent function (to be confirmed during implementation).

**MSI:** since an MSI is not byte-reproducible by nature (GUIDs, timestamps), the comparison is done over its tables (`Property`, `ServiceInstall`, `SummaryInformation`) against a baseline. The exact method is to be agreed in review.

### 6.5 Static unit and existing installs

- `TestStaticUnitMatchesEmbedded` keeps holding unchanged: the static files remain byte-identical to the `linuxUnit` constant, which keeps the default description. New tests check that generating the unit with no parameters yields exactly `linuxUnit`, and that generating it with a branded value differs from it only on the `Description=` line.
- An installed unit is only rewritten when its version (`currentUnitVersion`) is higher than the installed one. A `Description` changed by branding does not reach existing installs until the next unit version bump. Branding does not change `currentUnitVersion`.

### 6.6 Reliability scoring

**Dependency.** The API recognizes Breeze's own services by name (`isBreezeSelfServiceFailure`: the name contains "breeze" and also "agent", "watchdog" or "helper"). This keeps failures and restarts of our own services, for example during an auto-update, from counting against the customer's device reliability score. On Windows, the name the collector extracts from the SCM event message is the display name. With branding, a service such as "Example MSP Agent" would stop matching, and the agent's own restarts would start costing customers points. On Linux and macOS, unit names and labels are fixed and are not affected.

**Change 1 (API).** `isBreezeSelfServiceFailure` additionally recognizes the fixed service names (`BreezeAgent`, `BreezeWatchdog`) explicitly, alongside the current rule, which stays as is. Today those names already match through the loose rule (they contain "breeze" and "agent" or "watchdog"), so this does not change behavior: it makes the contract explicit and locks it with tests, so that a future tweak to the rule cannot break it. Tests: the fixed names match, today's display names keep matching, and unrelated names do not match.

**Change 2 (agent).** The SCM event carries the display name, so Change 1 alone does not reach a branded service. The collector, which knows the configured display names (through the same branding package), reports the fixed service name for the agent's or the watchdog's own service when the extracted name, compared case-insensitively, is a configured display name that differs from the default. With no branding configured, the collector reports exactly what it reports today. The normalization lives in a single place, used by both classification branches (the SCM one and the message-based one).

**Tests.** With branded names configured, a 7031 event for "Example MSP Agent" reaches the API as `BreezeAgent` and is ignored by scoring. With no branding, the collector output does not change. Unrelated services are untouched.

**To confirm during implementation.** The name Windows writes in the 7031 event message for a service with a branded display name, verified with a real event.

## 7. Operator contract

1. A branded fleet **must** update from the operator's own release source (`BINARY_GITHUB_REPOSITORY` plus their manifest key). Pointed at official releases, the next auto-update restores Breeze branding.
2. `selfhost-signing-template` signs only the official unsigned outputs, verified against the official manifest and `sourceCommit`. A rebuilt binary fails that check by design. A branded build needs the operator's own build-and-sign pipeline and manifest key.
3. The API already serves unsigned self-host assets after the manifest verifies, with a warning. No new opt-in flag is introduced.

## 8. Testing

- Default-output golden tests and the MSI table comparison (6.4).
- systemd unit tests (6.5).
- API: tests for `isBreezeSelfServiceFailure` (Change 1), locking the fixed-name contract. Agent: tests for the service-name normalization (Change 2).
- Validation (6.2): newlines, control characters and over-limit lengths fail the build.
- Branded build: the MSI tables and `sc qc` output show the supplied strings, and `agent service install` and the MSI agree.
- Upgrade: a branded N updated to a branded N+1 from the operator's release source keeps the same Manufacturer and service display names.

## 9. Open questions

1. **Reliability (6.6).** Does the maintainer confirm the combination (explicit contract in the API plus the fixed name reported by the agent), or prefer another way to reach the fixed name?
2. **API-generated install script.** `download.ts` generates a unit with a fixed description. In a branded build, a unit installed through that script would show "Breeze RMM Agent". Acceptable for Phase 1?
3. Should the `go-winres` resource strings (`--product-name`, `--file-description`, `--copyright`) be part of Phase 1, or a follow-up?

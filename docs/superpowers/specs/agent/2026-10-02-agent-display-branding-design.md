# Build-time display branding for the agent (Phase 1): Design

Discussion: LanternOps/breeze#7567
Related: LanternOps/breeze#6365 (Helper white-labeling at runtime)
Date: 2026-10-02
Status: draft, pre-implementation
Blast radius: display strings in the MSI installer, in the agent's service registration (Go), and in the systemd unit generated in Go. No API, route, or protocol changes.

## 1. Summary

MSPs that self-host Breeze and run their own managed service want the agent's user-visible display strings to carry their identity without maintaining source patches on every release. This spec proposes optional build parameters for those strings. With no parameters, official output remains identical to today's.

This spec covers Phase 1 only, as scoped in Discussion #7567.

## 2. Goals

- Let an operator supply, at build time, display strings for: the MSI `Manufacturer`, the MSI package description, the display name and description of the agent and watchdog services, and the equivalent descriptions in the systemd units generated in Go.
- With no parameters, official output is identical to today's, and CI proves it.
- The same branding profile can be applied to every upstream release, so a branded N upgrades to a branded N+1 with the same visible identity.

## 3. Non-goals / out of scope

- **Identifiers.** `BreezeAgent`/`BreezeWatchdog` service names, event-log sources, MSI `UpgradeCode` and `ProductName`, binary and asset names, install paths, IPC names, `com.breeze.*` labels. MSI upgrade, the updater and agent self-inventory key on them.
- **Icons.** Deferred to their own spec (they touch the signed binary and the build pipeline).
- **Helper titles, welcome text and colours.** Covered at runtime by the Helper config policy (#6365), not by a second build-time mechanism.
- **Phase 2** (OS-language i18n) gets its own spec.
- **Branded release infrastructure.** Upstream carries the parameters only. It does not build, sign, or publish branded releases.
- **The install script generated by the API** (`apps/api/src/routes/agents/download.ts`, which embeds `Description=Breeze RMM Agent` in the systemd unit). Changing it would require an API change, which this spec does not make.
- **Unifying the MSI and Go default names.** It would change official output, so it would be a separate change.
- **macOS.** Where its display strings live has not been verified. Out of scope until verified.

## 6. Design

### 6.1 Parameters (names are a proposal)

| Parameter | Affects |
|---|---|
| `Manufacturer` | `breeze.wxs` `Package/@Manufacturer` |
| `PackageDescription` | `breeze.wxs` `SummaryInformation/@Description` |
| `AgentServiceDisplayName`, `AgentServiceDescription` | `breeze.wxs` `ServiceInstall`, the agent's `winsvcinstall.Spec`, and the agent systemd unit `Description=` |
| `WatchdogServiceDisplayName`, `WatchdogServiceDescription` | `breeze.wxs` `ServiceInstall`, the watchdog's `winsvcinstall.Spec`, and the watchdog systemd unit `Description=` |

### 6.2 Mechanism

- **MSI:** optional `build-msi.ps1` parameters mapped to WiX `-d` variables, with `<?ifndef?>` defaults equal to today's literals (the pattern already used for `ProductName`).
- **Go:** a small internal package (for example `agent/internal/branding`) holding the display strings as variables, set through `-ldflags -X`, with defaults equal to today's literals. `build-edition.sh` forwards optional values and emits no extra flags when none are given.
- When a value is supplied, the MSI and Go paths receive the **same** value, so they cannot disagree.

### 6.3 Preserved defaults

With no parameters, **each path keeps its current default**: the MSI stays "Breeze Agent" and Go stays "Breeze RMM Agent". This guarantees identical official output. Unifying the defaults would change official output and is out of scope.

### 6.4 Default-output guarantee

CI builds with no branding parameters and verifies nothing changed:
- **Go:** the binary built without the new `-X` flags matches today's.
- **MSI:** since an MSI is not byte-reproducible by nature (GUIDs, timestamps), the comparison is done over the MSI tables (`Property`, `ServiceInstall`, `SummaryInformation`) against a baseline.

The exact method is to be agreed in review.

## 7. Operator contract

1. A branded fleet **must** update from the operator's own release source (`BINARY_GITHUB_REPOSITORY` plus their manifest key). Pointed at official releases, the next auto-update restores Breeze branding.
2. `selfhost-signing-template` signs only the official unsigned outputs, verified against the official manifest and `sourceCommit`. A rebuilt binary fails that check by design. A branded build needs the operator's own build-and-sign pipeline and manifest key.
3. The API already serves unsigned self-host assets after the manifest verifies, with a warning. No new opt-in flag is introduced.

## 8. Testing

- Default-output tests (6.4).
- Branded build: the MSI tables and `sc qc` output show the supplied strings, and `agent service install` and the MSI agree.
- Linux: the generated unit contains the supplied descriptions.
- Upgrade: a branded N installed, then updated to a branded N+1 from the operator's release source, keeps the same Manufacturer and service display names.

## 9. Open questions

1. **API-generated install script.** `download.ts` generates a systemd unit with a fixed description. In a branded build, a unit installed through that script would show "Breeze RMM Agent". Acceptable for Phase 1, or should the parameter reach the API in a separate change?
2. **Static unit files.** There are two static unit files, `agent/service/systemd/breeze-agent.service` and `breeze-agent-user.service`, with fixed `Description=`. Should they be in Phase 1 (for example, generated from the same parameter) or left as they are?
3. Should the `go-winres` resource strings (`--product-name`, `--file-description`, `--copyright`) be part of Phase 1, or a follow-up?

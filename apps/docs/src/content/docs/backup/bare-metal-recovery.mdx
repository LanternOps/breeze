Bare Metal Recovery (BMR) is a **reinstall-then-recover** flow, not disk imaging. You put a working OS on the target machine yourself — by installing one normally or, on Linux/amd64 hardware, by booting an ISO Breeze builds from your own boot-template directory — then run the `breeze-backup` recovery binary with a one-time token. It downloads the snapshot and reapplies OS system-state artifacts and files on top of whatever is already booted. Breeze does not ship boot media, and there is no WinPE/WinRE environment: on Windows and macOS you provide the booted OS yourself before recovery starts.

A recovery token is scoped to **one snapshot**. A `file`-mode snapshot recovers data; a `system_image`-mode snapshot recovers OS system state. To recover both on one machine, generate two tokens (one per snapshot) and run `bmr-recover` twice.

---

## How It Works

1. Get a working OS onto the target machine — install one normally, or boot the Linux/amd64 recovery ISO if you built one from your boot template.
2. Generate a **recovery token** from a backup snapshot and download the recovery bundle (the `breeze-backup` binary, a launch script, and `bootstrap.json`).
3. On the target machine, run the recovery binary with the token — no Breeze enrollment needed.
4. It downloads the snapshot and applies OS system-state artifacts (if the snapshot is `system_image`) or files (if the snapshot is `file`).
5. A post-restore validation probe runs and reports pass/fail; nothing reboots the machine for you.

## Generating a Recovery Token

<Steps>
1. Find the snapshot you want to recover from (via the Backup dashboard or device backup tab).
2. Select **Bare Metal Recovery** from the restore options.
3. Configure the recovery:
   - **Snapshot** — the single backup to recover from (one snapshot per token)
   - **Token lifetime** — how long the token remains valid, 1–168 hours
   - **Restore type** — Full, Selective, or Bare Metal
   - **Target configuration** — optional `source=target` path remappings applied on the recovery machine
4. Click **Generate Token**.
5. The token is displayed **once**. Copy it immediately — it's stored as a SHA-256 hash and cannot be retrieved later.
</Steps>

<Aside type="danger">
  Recovery tokens are shown only once at creation time. Store the token securely and use it promptly. If lost, generate a new one.
</Aside>

<Aside type="note">
  Recovering both OS state and data for one machine takes two tokens and two runs: one against the device's `system_image` snapshot, one against its `file` snapshot.
</Aside>

## Running the Recovery

<Steps>
1. Get the target machine to a booted OS: install one normally, or boot it from the Linux/amd64 recovery ISO if you built one.
2. Download and extract the recovery bundle for the target platform/architecture, then run the launch script (`run-recovery.sh` / `run-recovery.ps1`) or the binary directly:
   ```
   breeze-backup bmr-recover --token <recovery-token> --server <breeze-server-url>
   ```
   Add `--target-path <source>=<target>` (repeatable) to remap individual file paths from the snapshot onto different locations on the recovery machine; anything not remapped restores to its original path.
3. The recovery agent authenticates with the token and downloads the snapshot manifest.
4. For a `system_image` snapshot, system-state artifacts are applied directly onto the live, already-booted OS:
   - **Linux** — the backed-up `/etc` tree is copied over, packages are reinstalled from the captured `dpkg`/`dnf` list, systemd services are re-enabled, `iptables` rules and crontabs are restored.
   - **Windows** — registry hives (`SYSTEM`, `SOFTWARE`, `SAM`, `SECURITY`) are `reg restore`d onto the **live** registry, the BCD store is imported with `bcdedit /import`, the certificate store is restored with `certutil -restoreDB`, firewall policy is imported with `netsh advfirewall import`, and drivers are installed with `pnputil`.
   - **macOS** — preference plists, LaunchDaemon/LaunchAgent items, and network configuration are copied back and `configd` is poked to reload.
5. For a `file` snapshot, files are downloaded and written to their original paths (or their `--target-path` remapping).
6. A post-restore validation probe checks network reachability, presence of critical files, and service status, and reports the result — it does not repair or retry anything it finds wrong.
</Steps>

<Aside type="caution">
  Nothing in this flow reboots the machine or replaces its running OS. System-state artifacts are applied as file/registry writes to the OS you already booted, in place, while it's running.
</Aside>

## What a Recovered Machine Is — and Isn't

A machine that has gone through BMR is: the OS you installed or booted, with the backed-up system-state artifacts applied on top of it, plus the files from the `file` snapshot. It is **not** a byte-identical clone of the original machine — there is no disk or partition imaging anywhere in this flow, and hardware-specific state (disk partitioning, bootloader identity beyond the imported BCD store on Windows, kernel/driver binaries on Linux) is not reproduced.

## When to Use BMR

| Scenario | Approach |
|----------|----------|
| **Hard drive failure** | Install/boot an OS on the new disk, then recover system state and data with BMR |
| **Machine replacement** | Install a base OS on the replacement hardware, then recover with BMR (drivers for the new hardware are not injected automatically outside Windows `pnputil`) |
| **Disaster recovery** | BMR as part of a [DR plan](/backup/disaster-recovery/) |
| **Migration** | Recover system state and files onto different hardware; expect to reconcile driver and boot differences yourself |

For recovering individual files or databases onto an already-enrolled device, use the standard [restore workflow](/backup/restoring/) instead — it's faster and doesn't require a recovery token.

---

## Recovery Token Security

- Tokens authenticate recovery agents the same way JWT authenticates regular users — they grant time-limited access to a specific snapshot
- Tokens are hashed (SHA-256) at rest and cannot be retrieved after creation
- Each token is scoped to a single snapshot and organization
- Expired tokens are automatically invalidated

Before you can run backups, you need at least one storage configuration that tells Breeze where to send backup data. You can create multiple configurations — for example, an S3 bucket for off-site cloud storage and a local disk for fast restores.

---

## Creating a Storage Configuration

The storage configuration wizard walks you through four steps:

<Steps>
1. **Select a provider.** Choose Amazon S3 or Local Disk. Each option shows a brief description to help you decide.

2. **Enter provider settings.** The fields change based on your provider:

   <Tabs>
     <TabItem label="Amazon S3">
       - **Region** — AWS region (e.g., `us-east-1`)
       - **Bucket Name** — the S3 bucket to store backups in
       - **Path Prefix** — optional key prefix within the bucket (e.g., `breeze-backups`). New snapshots are stored under `<prefix>/snapshots/`; see [Key prefix](#key-prefix) below
       - **Access Key** and **Secret Key** — IAM credentials with `s3:PutObject`, `s3:GetObject`, `s3:ListBucket`, and `s3:DeleteObject` permissions (scoped to `<prefix>/*` when you set a prefix)

       Also works with S3-compatible services like MinIO, Wasabi, and Backblaze B2 — just set the endpoint URL accordingly. Enter the endpoint as a host (`s3.example.com`) or host and port (`minio.local:9000`), optionally prefixed with `http://` or `https://`; a scheme-less endpoint is treated as `https://`. Other schemes (such as `s3://` or `ftp://`) are rejected with a validation error rather than failing later at backup time.
     </TabItem>
     <TabItem label="Local Disk">
       - **Local Path** — a dedicated directory on a disk attached to the device (e.g., `/var/backups/breeze` or `D:\BreezeBackups`). Network shares (SMB and NAS shares, UNC paths and mapped network drives) are not supported; see [Network shares](#network-shares).
       - **Retention Tier** — storage tier classification
       - Use a dedicated directory for backup data. New roots, written directories and new or replaced objects are private to the agent service account. Existing roots must already restrict access to that account; otherwise local backup operations pause with a migration diagnostic, without changing the root permissions. Before upgrading, verify the path is dedicated to backup data and migrate it to a new private directory or harden it explicitly; see [Local destination permissions](#local-destination-permissions). Review all existing object permissions as well, especially Windows ACLs. The filesystem must support these permissions.
     </TabItem>
   </Tabs>

3. **Set a schedule.** Choose how often backups run:
   - **Daily** — pick a start time and backup window duration
   - **Weekly** — pick days of the week, start time, and timezone
   - **Cron** — enter a custom cron expression for advanced scheduling

4. **Configure retention.** Choose a preset or customize:
   - **Standard** — 30 days, 5 versions
   - **Extended** — 90 days, 10 versions
   - **Compliance** — 365 days, 20 versions
   - **Custom** — set your own day count and version count

   Optionally enable encryption. This is only enforceable for S3 destinations with server-side encryption (SSE-S3 or SSE-KMS) configured — see [Encryption](/backup/encryption/) for details. Local disk destinations do not support enabling this toggle.

   <Aside type="note" title="What retention removes today">
     When a restore point passes its retention window, Breeze removes it from the snapshot list — it can no
     longer be restored or verified — and marks its data for reclamation. A background storage sweep then
     deletes the restore point's exclusive data from the storage target on its next scheduled run. Data
     another surviving restore point still depends on (for example, a file shared with an incremental backup)
     is never deleted, no matter how old it is. A short safety grace period (48 hours by default) additionally
     protects any loose object that might still be mid-upload before it is considered for deletion at all. An
     upload that never finished, or whose record could not be reconciled, is reclaimed once it has sat idle
     for about 9 days — giving Breeze time to recognize and finish adopting it first.

     If a device's Breeze backup helper predates version 0.112.0, storage reclamation beyond an expired
     snapshot's own row stays deferred on that device's destination until every device sharing it has
     upgraded — update the agent to enable full reclamation.

     Permanently deleting (purging) a device or erasing an organization removes its restore points from
     Breeze, but from v0.122.1 it does **not** reclaim their storage: the backup files stay in the storage
     target, and the storage sweep never deletes them later, including data already past its retention
     window. They are kept until an explicit backup-deletion feature ships. A legal hold on a snapshot,
     on the backup policy it ran under, or in a configuration policy's backup settings blocks a device purge
     (`409`, `BACKUP_PROTECTED`) and an organization erasure until the hold is released.
   </Aside>
</Steps>

Click **Publish Configuration** to make it active, or **Save as Draft** to finish later.

## How Backup Data Is Stored

File backups are written to the target as one object per file, under a `snapshots/<snapshot-id>/files/` prefix. Every file object's name ends in `.gz`, but whether the bytes are compressed depends on the provider:

| Provider | Object name | Stored bytes |
|----------|-------------|--------------|
| **Amazon S3 and S3-compatible** (MinIO, Wasabi, Backblaze B2) | ends in `.gz` | **Not compressed.** The object is the original file, byte for byte. |
| **Local disk** | ends in `.gz` | gzip-compressed, decompressed again on restore |

On S3 storage the `.gz` suffix is only part of the object name. Expect an S3 target to use roughly as much space as the files you protect, and size buckets and quotas on that basis. If you download a file object directly from the bucket, it is the original file. Rename it to drop the `.gz` instead of running `gunzip` on it, which fails with `not in gzip format`.

Breeze relies on this layout: restores, bare-metal recovery media, integrity verification and older agents all read S3 objects as raw bytes. Don't rename, compress or recompress objects in the bucket.

### Key prefix

An S3 destination's **Path Prefix** decides where its new snapshots are written:

| Destination | New snapshot objects |
|-------------|----------------------|
| No prefix | `snapshots/<snapshot-id>/...` at the bucket root |
| Prefix `msp/acme` | `msp/acme/snapshots/<snapshot-id>/...` |

Each snapshot records the location it was written to, and Breeze reads, verifies, restores and cleans it up there for its whole life. As a result:

- **Existing snapshots are never moved.** Snapshots taken before you set or changed the prefix stay where they are and keep restoring normally.
- **Changing the prefix makes the next backup a full backup.** An incremental never builds on a snapshot stored under a different prefix, so the first run scheduled after a change uploads everything again (see [When a run uploads everything again](/backup/incremental-backups/#when-a-run-uploads-everything-again)). An incremental run that was already scheduled against a base under the old prefix when you changed it fails with a message saying so; the next scheduled run takes the full backup.
- **Several organizations can share one bucket** with a prefix each. The storage cleanup sweep lists and deletes under one prefix at a time and never touches another prefix's objects.
- **Scope IAM policies to the prefix.** A policy that only allows `bucket/snapshots/*` stops working once a prefix is set; allow `bucket/<prefix>/*` instead. **Test connection** writes a probe object under the prefix, so it catches this before the first backup fails.

A valid prefix is at most 256 characters, made of `/`-separated segments that use only letters, digits and `! _ . * ' ( ) -`. Leading and trailing slashes are ignored. Empty segments (`a//b`), `.` and `..` are not allowed, and no segment may be `snapshots` (in any letter case), so one prefix can never contain another prefix's snapshots. The form flags an invalid prefix as you type and the API rejects it on save. A destination saved with an invalid prefix by an older version is not backed up to the bucket root instead: its backups fail with a message asking you to correct the prefix, and **Test connection** fails naming the rule the prefix breaks.

Bare-metal recovery of a snapshot stored under a prefix always downloads through Breeze (token-mode download), which is the default for recovery media. Agent-side tools that read a bucket directly with a hand-supplied configuration take the prefix as their own option, and never read it from a pasted `providerConfig.prefix`:

- **`breeze-backup rebuild --provider-config`**: pass `--key-prefix <prefix>`, where `<prefix>` is the path in front of `snapshots/<snapshot-id>/` in the bucket. That is the prefix the snapshot was **written** under. After a prefix change it differs from the destination's current Path Prefix. Snapshots taken before the prefix was set sit at the bucket root and need no `--key-prefix`. If the configuration file has a `providerConfig.prefix` and you leave out `--key-prefix`, the command prints a note and reads from the bucket root.
- **The `agent.yaml` backup manager** (`backup_provider: s3`): set `backup_s3_prefix: <prefix>` to write and read its snapshots under `<prefix>/snapshots/`. Snapshots it took before you set the prefix stay at the bucket root, and the manager no longer sees them. If the prefix is invalid, the manager is disabled: backup commands that need it fail with a message naming `backup_s3_prefix`, and a local vault that uses it as its source does not start. It never falls back to the bucket root.

Both options follow the same prefix rules as the destination form, and the agent maps keys under the prefix exactly as the server does.

### How destination credentials are stored

From v0.121.0, the credentials in a storage configuration (access keys, secret keys, session tokens, and the equivalent Azure, Google Cloud Storage and Backblaze B2 fields) are stored encrypted with your instance's application encryption key. Bucket, region, endpoint and prefix stay readable. Existing configurations are encrypted by a background sweep on the first start after the upgrade, which logs one `[startup] Backup destination credentials sealed: …` line.

<Aside type="caution" title="Roll forward only">
  Once that sweep has run, do not roll back to a release older than v0.121.0. Older releases would hand the encrypted values to agents as storage credentials and S3 backups would fail. If you rotate `APP_ENCRYPTION_KEY`, follow [Secret Rotation](/security/secrets/#rotating-app-encryption-key); the re-encryption script covers these credentials.
</Aside>

### Local destination permissions

The agent writes local backups, and local vault copies, as the account its backup service runs as (normally root on Linux and macOS and LocalSystem on Windows). It requires the destination directory to be private to that account:

- **New destinations.** When the configured path does not exist yet, the agent creates it, and every directory it creates inside it, with owner-only access (`0700` on Linux and macOS, a protected access list for SYSTEM, Administrators and the service account on Windows). Objects are written owner-only (`0600` on Linux and macOS; on Windows they inherit the protected access list), including objects that replace an existing one.
- **Existing destinations.** An existing directory must already be owned by the service account (on Windows, the service account, SYSTEM or Administrators) and grant no access to other accounts:
  - Linux and macOS: no group or other permission bits. On Linux the directory must carry no ACL: no POSIX access or default ACL, and no NFSv4 or SMB/CIFS ACL exposed by a network filesystem. On macOS it must carry no extended ACL (`ls -lde` shows none).
  - Windows: every entry in the access list, whether inherited from the parent or set on the directory, must allow SYSTEM, Administrators or the service account and be inherited by subfolders and files, and SYSTEM (and the service account, when it is not SYSTEM) must have full control. A destination that older agents created under the Breeze data directory meets this through its inherited entries.

  Otherwise backup, restore, listing, retention and vault operations against that destination stop with a "local backup store is not private" message, and bare-metal recovery and other restores that read from that destination stop with it. The agent does not change the permissions of an existing destination for you.
- **Upgrading from an earlier agent.** Earlier agents created local destinations, including the default `<data directory>/backups` (`/var/lib/breeze/backups` on Linux), with mode `0755`. Those destinations are refused after the upgrade until you migrate them.
- **The configured path must be a real, dedicated directory.**
  - A drive or filesystem root (`C:\`, `D:\`, `/`) is refused.
  - On Linux, no component of the path may be a symbolic link. On macOS, only the system's own root-owned links (such as `/var` → `/private/var`) may appear in the path, and the last component may not be a link. On Windows, no component may be a reparse point: a symbolic link, a junction or a mounted folder.
  - Inside the destination, any entry that a backup object path passes through must be a plain directory or file. Links, junctions, named pipes and other special files are refused.
- **The filesystem must support these permissions.** On Windows, FAT and exFAT volumes have no access lists and are refused. On Linux and macOS, a FAT or exFAT volume is checked against the ownership and mode its mount options present.

**Migrating an existing destination** (do this before upgrading, or as soon as backups to the destination report the message above):

1. Pause the backup jobs and vaults that use the destination, and confirm the path is dedicated to Breeze backup data. Never apply recursive permission changes to a system directory or a share that holds other data.
2. Prefer a new dedicated location provisioned for the agent service account, and point the configuration at it. If you harden the existing dedicated location instead, first record its links, ownership and access lists so you can roll back, then restrict it in a maintenance window.
3. Review the backup objects already in the destination separately. Protecting the root does not change objects written by earlier versions. Remove or replace any entry not owned by the service account, any link, junction or special file, and any file with more than one hard link. Review existing file permissions as well, especially Windows file ACLs.
4. Check that the agent can use the destination: run a backup and a test restore of a representative snapshot, then resume the jobs.
5. Keep any rollback copy in a private location. If you roll the agent back, leave the affected jobs paused until the destination is private: an older agent version does not make the old permissions safe.

#### Network shares

SMB and NAS shares are not supported as local backup destinations or vaults. Use a disk attached to the device for local backups and vaults, and S3-compatible storage for off-device copies.

- **Refused when saved.** Breeze refuses to save a vault of type SMB share. The path of a local destination or vault must be an absolute path on a volume of the device: a drive path (`D:\Backups`), a volume GUID path (`\\?\Volume{GUID}\Backups`) or, on Linux and macOS, an absolute path (`/var/backups/breeze`). Any other form is refused, including UNC paths (`\\server\share\...`, `//server/share/...`), other `\\?\` and `\\.\` device paths, and relative paths. This applies to the web app, the API and the AI tools.
- **Refused on the device.** On Windows, the agent asks the system whether the volume holding the destination, and the destination directory once it is opened, is reached over the network, and refuses it if so. That covers a drive letter mapped to a share, whatever the path looks like. A UNC path is refused before anything is opened. The message reads "network shares (UNC paths, mapped network drives, SMB and NAS shares) are not supported for local backup destinations or vaults".
- **Why.** The agent runs as LocalSystem on Windows and reaches a share as the device's computer account. The owner and access list it checks are the ones the file server reports, where SYSTEM and Administrators are the server's own accounts and the device's computer account is neither, so a share cannot show that the directory is private to the agent.
- **Volumes the agent cannot recognise.** A Windows volume that reports itself as a local disk but is backed by a share or a user-mode filesystem (a VHD or iSCSI disk whose file lives on a share, WinFsp or Dokan filesystems, rclone mounts, cloud-drive clients) is not detected as a network share. Do not use one as a local destination or vault.
- **Do not add the device's computer account to the file server's Administrators group** to make a share pass these checks. That gives the device, and anything running on it as LocalSystem, administrative control of the file server.
- **Linux and macOS.** Do not use an NFS, SMB or other NAS mount as a local destination or vault either. The agent does not recognise every mounted network filesystem: it applies the checks above to the owner and mode the mount presents, which reflect the mount options rather than the permissions the server enforces. A mount that exposes an NFSv4 or SMB/CIFS access list on Linux, and an NFS export that maps root to another user (`root_squash`), are refused.
- **Configurations saved earlier.** A vault or local destination saved on a share before this release keeps its settings. The device refuses it each time it is used, and saving its settings again is refused until you point it at a disk attached to the device or move the backups to an S3 destination. You can still deactivate or delete such a vault.

### Recommended bucket settings for S3-compatible storage

When backups go to a bucket you or your customer own on an S3-compatible service (AWS S3, Wasabi, Backblaze B2, iDrive e2 and similar), set the bucket up so that backup data cannot be silently removed with the same key Breeze uses to write it:

- **Turn on Object Lock, or at least versioning.** Object Lock (often called immutable or WORM storage) keeps each object version for a retention period you choose, even if a delete request arrives. Most providers only let you enable it when the bucket is created, so decide before the first backup. If your provider or plan has no Object Lock, enable bucket versioning instead, so a deleted or overwritten object leaves a recoverable previous version.
- **Add a lifecycle rule for old versions.** With Object Lock or versioning on, Breeze's retention sweep still sends deletes for expired restore points, but on a versioned bucket a delete only hides the object and the data is kept as a noncurrent version. Add a lifecycle rule that expires noncurrent versions after the number of days you want to keep them (no shorter than your Object Lock retention), or storage use keeps growing.
- **Use a key scoped to that one bucket.** Create a dedicated access key for Breeze that can only reach the backup bucket (and, if you set one, its base path), with the object permissions listed above and nothing else: no access to other buckets, no permission to change bucket settings, Object Lock configuration or lifecycle rules, and no permission to bypass retention. If you use provider-enforced immutability on individual snapshots, the key also needs to read the bucket's Object Lock configuration and set object retention (`s3:GetBucketObjectLockConfiguration` and `s3:PutObjectRetention` on AWS).

Breeze does not create buckets or manage these settings: it does not turn on Object Lock or versioning, write lifecycle rules, or create or scope access keys. Configure them in your storage provider's console. When Object Lock is already enabled on the bucket and a snapshot is made immutable with provider enforcement, by its backup policy or by hand (`POST /backup/snapshots/:id/immutability` with `"enforcement": "provider"`), Breeze places a Governance-mode retention date on that snapshot's objects. If the bucket does not have Object Lock enabled, the manual request is refused with `409`, and a policy-driven snapshot falls back to Breeze's own application-level immutability and records the reason on the snapshot (`immutabilityFallbackReason`).

## Testing Connectivity

After creating a configuration, test that Breeze can reach the storage target:

<Steps>
1. Find the configuration in your storage list.
2. Click the **Refresh** (test) action on the configuration row.
3. A success or failure message appears. The configuration's **Last Tested** timestamp updates on success.
</Steps>

<Aside type="tip">
  Always test connectivity after creating or updating a configuration. This catches credential errors or network issues before your first scheduled backup fails.
</Aside>

## Local Destinations on the API Server

A local destination's **Local Path** is the path the agent uses on the device. The API server never uses that path for its own file access.

Some features read a local destination from the API server: the connectivity test, file-level browsing of a snapshot (index hydration), server-side integrity verification, the storage sweep and reconciliation, token-based recovery downloads, and bare-metal recovery media. These work only when the self-hosting operator sets [`BACKUP_LOCAL_ROOT`](/deploy/environment/#backup-enterprise-agent-backup) and provides one directory per destination:

```text
<BACKUP_LOCAL_ROOT>/<organization ID>/<storage configuration ID>/
```

- `BACKUP_LOCAL_ROOT` must be an absolute path and not `/`. The organization and configuration directories must already exist; Breeze does not create them.
- Breeze takes both IDs from its own records, not from the destination settings. Each destination can only reach its own directory.
- Symbolic links are refused at every level below `BACKUP_LOCAL_ROOT`, including the per-destination directory itself, and so is anything that is not a regular file or directory. Use a bind mount to expose existing storage there, and mount it with `nodev,nosuid`.
- Mount the same storage at the same path in every `api` and `worker` container.
- Two configurations of one organization may share storage: mount it at each configuration's directory. The storage sweep handles each directory on its own. It only reclaims a snapshot that belongs to that configuration or that no Breeze record names; a snapshot another configuration recorded, retired or reserved is left for that configuration's own sweep. A snapshot that one configuration retired but another still records as live is kept, and its retirement stays open, until no configuration records it as live.
- Keep each organization's storage separate at the storage level (its own share, volume or dataset). Never mount one organization's storage in another organization's directory. Breeze reads whatever file is in a destination's directory as that organization's data, including a hard link to a file stored elsewhere on the same filesystem.
- Linux API servers (the shipped containers) are supported. macOS works for development only. On Windows the API refuses server-side local access.

Without `BACKUP_LOCAL_ROOT` (the default, and always the case on the hosted service), these features are off for local destinations. The connectivity test reports the destination as **Not tested here** rather than as a failure, because only the agent uses its Local Path. Server-side integrity verification stays pending. The storage sweep skips the destination, keeps its objects and deletes nothing. Agents keep writing backups to the device's local path.

With `BACKUP_LOCAL_ROOT` set, the connectivity test checks that the destination's directory exists and that the API can read and write it. It creates no files or directories, and it does not test whether the device can reach its Local Path. It fails with one of two messages:

- **The API-side directory for this destination does not exist**: create `<BACKUP_LOCAL_ROOT>/<organization ID>/<configuration ID>/` on every `api` and `worker` server.
- **The API-side directory for this destination cannot be used**: it is a symbolic link (or sits below one), is not a directory, or the API cannot read and write it.

The other server-side features stop for that destination with the message *API local backup storage is unavailable for this destination* until the directory is fixed.

### Upgrading an install that uses API-side local storage

Earlier versions read local destinations on the API server from the **Local Path** setting. After upgrading, those reads stop until the directories above exist. Breeze does not move data or rewrite settings for you:

<Steps>
1. List the local configurations whose API-side features you use (configuration ID, organization ID and current path).
2. For each one, create `<BACKUP_LOCAL_ROOT>/<organization ID>/<configuration ID>/` and bind-mount the existing storage there, in every `api` and `worker` container. The data stays where it is.
3. Set `BACKUP_LOCAL_ROOT` and restart the `api` and `worker` containers.
4. Run the connectivity test for each configuration. Then check a file-level browse, a recovery download and the next storage sweep in the `worker` log. Each local destination is reported as `Identity local::<path> config <configuration ID>`, followed by one of:
   - the number of objects deleted (a debug line when it is zero);
   - `skipped — no API-side local storage directory for this destination` while its directory has not been created, or `skipped — API-side local storage is not configured` while `BACKUP_LOCAL_ROOT` is unset. Nothing is read or deleted;
   - `listing failed` (an error, also sent to error tracking) when the directory exists but cannot be used, for example because it is a symbolic link. Fix the directory; nothing is deleted until then.
</Steps>

Leave the **Local Path** setting unchanged; agents still use it. Do not delete objects or edit storage settings to make a test pass.

A snapshot whose storage configuration was deleted, or that was recorded without a configuration, has no destination directory. It stays unavailable for API-side local reads until its configuration link is restored.

When a configuration moves to another organization, its directory moves to `<BACKUP_LOCAL_ROOT>/<new organization ID>/<configuration ID>/`. Snapshots and retirements recorded under the earlier organization stay in that directory and the storage sweep never reclaims them. Once they are no longer needed, an operator can remove those snapshot folders (`snapshots/<snapshot ID>/`) by hand.

To turn API-side local access off again, unset `BACKUP_LOCAL_ROOT`. The stored data is not touched.

## Editing a Configuration

Click the **Edit** action on any configuration to reopen the wizard. Changes are merged — updating a single field (like the bucket name) won't erase your other settings.

## Deleting a Configuration

Click **Delete** on a configuration to remove it. Configurations that are actively referenced by a backup policy should have the policy reassigned first.

<Aside type="caution" title="Destinations with job history">
  A configuration that has any backup job history can't be deleted: Breeze returns `409` and names what blocks it (v0.120.0 returned a server error instead). Disable it — reassign its policies, then set `"enabled": false` with `PATCH /backup/configs/:id`.
</Aside>

<Aside type="caution">
  Deleting a storage configuration does not delete the backup data already stored at that target. The data remains in S3 or your local path until you remove it manually.
</Aside>

## Multiple Configurations

You can create different configurations for different use cases:

| Use case | Recommended setup |
|----------|-------------------|
| **Critical servers** | S3 (off-site) + local vault (fast restore) |
| **Workstations** | Local disk with 30-day retention |
| **Compliance** | S3 with 365-day retention and server-side encryption |
| **Development/test** | Local storage with minimal retention |

Assign each configuration to the appropriate devices through [backup policies](/backup/policies/).

<Aside type="note">
  From v0.118.0, a bucket, endpoint or local path that an organization under **another partner** already uses is refused. Organizations under the same partner can still share one.
</Aside>

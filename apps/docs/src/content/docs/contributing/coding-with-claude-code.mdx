This guide is for people who want to **write code** for Breeze. It assumes you'll
work with [Claude Code](https://claude.com/claude-code) (or a compatible agent).
The repo ships a `CLAUDE.md` and a set of project skills that give the agent
most of the project's conventions automatically. Your job is to point it at the
right work and to hand back finished, self-reviewed, green PRs.

If you only want to report a bug or pitch an idea, you don't need any of this —
see the top of [`CONTRIBUTING.md`](https://github.com/LanternOps/breeze/blob/main/CONTRIBUTING.md).

## Set up the agent

<Steps>

1. Clone the repo and run Claude Code **from the repo root**. That's what loads
   `CLAUDE.md` and the project skills in `.claude/skills/`. Don't re-explain the
   conventions to the agent; they're already in context.

2. Install the [superpowers](https://github.com/obra/superpowers) plugin. The
   process skills this guide names (`brainstorming`, `writing-plans`,
   `executing-plans`, `subagent-driven-development`, `test-driven-development`)
   come from it, not from the repo.

3. Install the `pr-review-toolkit` plugin for the self-review step below.

</Steps>

The project skills you'll use most:

| Skill | Use it for |
|---|---|
| `breeze-testing` | Test conventions: Drizzle mocks, Go table tests, the coverage checklist |
| `issue-to-pr` | Runbook for carrying one issue from claim to a reviewed PR |
| `worktree-stack` | A running, seeded stack (API, web, portal) for your worktree, for browser checks |
| `feature-testing` | End-to-end verification of a feature across UI, API and agent |
| `agent-info`, `ai-agent`, `breeze-helper` | Architecture quick references for the agent, AI, and Helper subsystems |

## The one idea to internalize

Non-trivial work on Breeze starts as a **plan document**. A plan spells out the
goal, the architecture, and a checklist of tasks. It's a ready-to-implement work
order, written for an agent to execute.

That means a plan is two things at once:

- **The work definition**: what there is to build.
- **The approval**: once a plan is approved, the *what* and the *how* are
  agreed. You don't need a separate sign-off to start.

<Aside type="caution" title="Don't write feature code without an approved plan">
The plan **is** the approval gate. If there's no plan for what you want to do,
the first deliverable is the plan, not the code. Write it, get a 👍, *then*
build. A small, well-described bug fix doesn't need a plan; a new feature,
table, or API surface does.
</Aside>

## 1. Find something to build

Work is tracked on **GitHub issues**. The public roadmap at
[breezermm.com/roadmap](https://breezermm.com/roadmap) shows shipped,
in-progress, planned, and exploratory items from the same tracker.

Don't mine `docs/superpowers/plans/` for work. It's an archive of plans that
have already shipped, kept for history.

<Steps>

1. Pick an unassigned issue that fits your appetite. Some are small UI or CRUD
   jobs; some touch deeper systems.

2. Comment on the issue that you're taking it, so two people don't grab the
   same one.

3. If it's more than a contained fix, start with a plan (below).

</Steps>

<Aside type="note" title="Multi-wave features">
Larger features are tracked as a parent issue labelled `feature` with one
`wave` sub-issue per PR. If you pick up a wave, work only that sub-issue, and
put `Closes #<wave sub-issue>` in the PR — never the parent.
</Aside>

## 2. …or propose your own

Want to scratch your own itch? The plan comes first.

<Steps>

1. Open (or find) a GitHub issue describing the problem.

2. In Claude Code, use the **`brainstorming`** skill to pin down intent and
   requirements, then **`writing-plans`** to produce the plan.

3. Attach the plan to the issue and wait for a 👍 on the *plan*. Once approved,
   it's an open work order like any other.

</Steps>

<Aside type="tip">
Propose via the issue, not a draft PR. That keeps the PR queue meaning exactly
one thing: "ready to merge."
</Aside>

## 3. Build it

<Steps>

1. Work on a branch in its own worktree, cut from current `main`. Fetch and
   rebase before you start exploring — a stale tree sends the agent after code
   that has already changed.

2. Follow the plan's `REQUIRED SUB-SKILL` note (usually
   `subagent-driven-development` or `executing-plans`). Work the `- [ ]` tasks in
   order and check them off.

3. Write the test first and watch it fail, then implement. `breeze-testing`
   covers the repo's patterns. Tests live next to the source file
   (`routes/devices.ts` → `routes/devices.test.ts`). New features ship with
   tests.

4. For UI changes, bring up a stack with `pnpm wt-stack up` (or the
   `worktree-stack` skill) and check the change in a browser. Tear it down with
   `pnpm wt-stack down` when you're done.

</Steps>

<Aside type="caution" title="High-blast-radius surfaces">
`CLAUDE.md` spells out exact contracts for tenant isolation / RLS, database
migrations, auth, billing, the org-erasure cascade lists, and partner-wide
config tables. If your work leads into one of these, follow the contract to the
letter and call it out in the PR. A few that catch people:

- **New tenant-scoped table**: RLS policies in the same migration, plus the
  cascade, merge, and export-policy registries. Adding a *column* to a
  registered table still needs an export-policy entry.
- **New config/policy table**: partner-wide first (`org_id` XOR `partner_id`),
  not org-only.
- **Migrations**: hand-written SQL, idempotent, named so they sort after the
  newest committed migration, and never edit one that has shipped.
- **Settings**: one concept, one home. The PR template asks for the setting's
  home, level, and resolver.

When in doubt, ask on the issue before you touch it.
</Aside>

## 4. Before you hand it over

Two things are **your** responsibility. A PR that skips them isn't ready.

<Steps>

1. **Make CI green yourself.** Mirror the gate locally before you open
   anything, and fix your own reds. The single required check is
   **CI Success**, which aggregates every blocking job: lint, type check,
   Test API, Test Web, Test Agent, the security audit, and the sharded
   Integration Tests.

2. **Self-review your own diff.** Run `/code-review` or
   `/pr-review-toolkit:review-pr` against your changes, fix what's real, and
   say in the PR what the review found.

</Steps>

<Aside type="caution" title="Local green isn't CI green">
`pnpm test` does **not** run the RLS and integration contract suites. If you
touched tenancy, cascade, or migration code, run them against a real database:

```bash
pnpm test-stack up        # private Postgres + Redis for this worktree
DB_CONTEXTLESS_WRITE_STRICT=true pnpm --filter=@breeze/api test:rls-coverage
pnpm test-stack down
```

To run one test file, use `cd apps/api && npx vitest run src/routes/auth.test.ts`.
Don't write `pnpm --filter … test -- --run <path>`: the extra `--` makes vitest
run the whole suite in watch mode.
</Aside>

## 5. Open the PR

A PR means **done, green, self-reviewed, ready to merge**. It isn't a
discussion venue or work in progress.

<Steps>

1. Use [Conventional Commits](https://www.conventionalcommits.org/)
   (`feat:`, `fix:`, `docs:`, …).

2. Keep it to **one concern**. Don't mix a feature, a refactor, and a docs
   sweep. Small, single-purpose PRs review fast.

3. Fill in the PR template. Use `Closes #NNN` when the PR fully resolves the
   issue, `Refs #NNN` when it only covers part of it. Repeat the keyword for
   each issue (`Closes #1, closes #2`).

4. Open it against `main`. A PR based on another branch gets no CI run.

</Steps>

<Aside type="note">
`main` uses GitHub's merge queue. A maintainer enqueues your PR once it's green
and reviewed; the queue rebuilds it on top of current `main`, re-runs CI, and
squash-merges it. If the queue run fails, the PR is dequeued with a comment —
fix it and it goes back in.
</Aside>

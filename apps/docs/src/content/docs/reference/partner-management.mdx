Partners are the top-level tenants in Breeze's multi-tenant hierarchy. A partner typically represents a Managed Service Provider (MSP), an enterprise IT department, or an internal team. Partners own organizations, which in turn contain sites, device groups, and devices. Breeze supports both administrator-provisioned partners (created by system-scoped users) and self-service partner registration (where MSPs sign up directly through the web interface).

Partner management encompasses the full lifecycle: registration, configuration, user association, organization management, and feature flag controls. This reference covers the self-registration flow, the partner hierarchy model, administrative operations, and the environment variables that govern partner-related features.

---

## Partner Hierarchy

Breeze organizes all managed infrastructure into a strict tenant hierarchy. Partners sit at the top:

```
Partner (MSP)
  +-- Organization (Customer)
        +-- Site (Location)
              +-- Device Group
                    +-- Device
```

Every API query automatically scopes data to the caller's position in this hierarchy. A partner-scoped user can only access organizations they have been granted access to. Organization-scoped users can only see their own organization and its sites. System-scoped users have unrestricted access across all partners.

### Partner Types

| Type | Description |
|------|-------------|
| `msp` | Managed Service Provider managing multiple customer organizations. This is the default type assigned during self-registration. |
| `enterprise` | A single enterprise managing its own infrastructure. |
| `internal` | Internal IT team or development environment. |

### Plan Tiers

| Plan | Description |
|------|-------------|
| `free` | Free tier with default limits. Assigned during self-registration. |
| `starter` | Starter tier for initial paid onboarding. |
| `community` | Community tier with basic paid features. |
| `pro` | Professional tier with expanded limits. |
| `enterprise` | Enterprise tier with advanced features. |
| `unlimited` | No enforced limits. |

### Partner Status

| Status | Description |
|--------|-------------|
| `pending` | Newly registered partner awaiting payment or admin approval. Blocked from API access by the partner guard middleware (403 with `PARTNER_INACTIVE` code). |
| `active` | Fully operational partner with API access. |
| `suspended` | Temporarily suspended (e.g., payment failure). Blocked from API access. |
| `churned` | Permanently inactive partner. Blocked from API access. |

### Organization Access Levels

Partner users are associated with their partner through the `partner_users` table. Each association includes an `orgAccess` field that controls which organizations the user can see:

| Access Level | Behavior |
|-------------|----------|
| `all` | User can access every organization under the partner. This is the default for the admin user created during self-registration. |
| `selected` | User can only access organizations whose IDs are listed in the `orgIds` array on the `partner_users` record. |
| `none` | User cannot access any organizations. Useful for partner-level users who only manage partner settings. |

## Self-Registration

Partner self-registration allows MSPs and IT companies to create their own Breeze account without administrator intervention. The registration flow is **email-verified and two-step**: no partner, role, user, or token exists until the emailed verification link is clicked.

### Registration Flow

<Steps>
1. **User visits `/register-partner`** -- The frontend checks the `ENABLE_REGISTRATION` feature flag. If registration is disabled, the user is redirected to `/login?reason=registration-disabled`.

2. **User fills out the registration form** -- Required fields are company name (min 2 characters), full name, email address, password (min 8 characters), password confirmation, and terms of service acceptance.

3. **Frontend submits to `POST /auth/register-partner`** -- The API validates the request body against the `registerPartnerSchema` Zod schema, enforces a rate limit of **3 attempts per IP address per hour** (`429` if exceeded), and checks server-side password strength (`400` with the first error message if it fails).

4. **No account is created yet.** The endpoint performs **no email-existence lookup** -- doing so would let an attacker learn whether an address already has an account from response timing alone. Instead the API hashes the password, parks a pending registration keyed by a hashed, single-use verification token, and queues a verification email. Every accepted request -- new address or one that already has an account -- gets the same generic body: `{ "success": true, "message": "If registration can proceed, you will receive next steps shortly." }`.

5. **User clicks the verification link** in the email, which submits the token to `POST /auth/verify-email`.

6. **Slug generation and account creation** -- Inside a single database transaction, the API derives a URL-safe slug from the company name (lowercased, non-alphanumeric characters replaced with hyphens, trimmed to 50 characters, with a numeric suffix appended on collision), then creates four records:
   - A **partner** with type `msp` and plan `free`
   - A **Partner Admin role** with `scope: partner` and `isSystem: true`
   - A **user** with the hashed password and `status: active`
   - A **partner_users** association with `orgAccess: all`

7. **JWT tokens issued** -- Access and refresh tokens are created with `scope: partner` and the new partner ID. The refresh token is set as an HTTP-only cookie.

8. **Redirect to dashboard** -- The frontend stores the tokens and redirects the authenticated user. If this is the first-ever user in the system, the setup wizard may appear.
</Steps>

<Aside type="note">
  Because account creation happens inside a real database transaction in step 6, a failure partway through rolls back cleanly rather than leaving orphaned partner/role records. `POST /auth/register` (the legacy, pre-verification signup path) is now a **no-op**: it performs the same rate limit and password checks and returns the identical generic success body, but never creates a user. It exists only so old clients don't observe a breaking response shape.
</Aside>

### Registration Form Fields

| Field | Type | Validation | Description |
|-------|------|------------|-------------|
| `companyName` | string | min 2, max 255 chars | The partner/company display name |
| `name` | string | min 1, max 255 chars | The admin user's full name |
| `email` | string | Valid email format | The admin user's email address |
| `password` | string | min 8 chars, strength checked | The admin user's password |
| `confirmPassword` | string | Must match password | Client-side only; not sent to API |
| `acceptTerms` | boolean | Must be `true` | Terms of service acceptance |

### Password Strength Indicator

The registration form includes a client-side password strength meter that scores passwords on five criteria:

| Criterion | Score |
|-----------|-------|
| At least 8 characters | +1 |
| Contains uppercase letter | +1 |
| Contains lowercase letter | +1 |
| Contains digit | +1 |
| Contains special character | +1 |

| Score | Label |
|-------|-------|
| 0-1 | Too weak |
| 2 | Weak |
| 3 | Fair |
| 4 | Good |
| 5 | Strong |

The server-side password check (`isPasswordStrong`) performs its own validation independently of the client-side indicator.

## Feature Flags

### `ENABLE_REGISTRATION` / `ENABLE_PARTNER_REGISTRATION`

Partner self-registration is controlled by an environment variable that can be set on both the API and the frontend.

<Tabs>
  <TabItem label="API (Server-side)">
    The API reads `ENABLE_REGISTRATION` from the environment using the `envFlag` utility. When set to `false`, both `POST /auth/register` and `POST /auth/register-partner` answer with a plain `404 Not Found` (`{"error": "Not Found"}`), so the endpoints are indistinguishable from routes that do not exist.

    **Default:** `true` (registration is enabled unless explicitly disabled).

    ```bash
    # Disable registration
    ENABLE_REGISTRATION=false

    # Enable registration (default)
    ENABLE_REGISTRATION=true
    ```

    Accepted truthy values: `1`, `true`, `yes`, `on`
    Accepted falsy values: `0`, `false`, `no`, `off`
  </TabItem>
  <TabItem label="Frontend (Client-side)">
    The frontend reads `PUBLIC_ENABLE_REGISTRATION` via Astro's `import.meta.env`. When `false`, the `/register-partner` page issues a `302` redirect to `/login?reason=registration-disabled` before the page even renders.

    ```bash
    # Disable registration on the frontend
    PUBLIC_ENABLE_REGISTRATION=false
    ```

    **Default:** `true`.

    The login page also conditionally shows or hides the "Register" link based on this flag.
  </TabItem>
</Tabs>

<Aside>
  Both the API and frontend flags should be set consistently. If the frontend allows access to the registration page but the API has registration disabled, the user will see the form but receive an error on submission. Set `ENABLE_REGISTRATION=false` on the API **and** `PUBLIC_ENABLE_REGISTRATION=false` on the frontend for a clean experience.
</Aside>

## Admin IP Allowlist

A partner can restrict dashboard and API access to a list of approved source IPs. The allowlist lives in `partners.settings.security.ipAllowlist` as an array of literal addresses and/or CIDR ranges, and accepts both **IPv4 and IPv6** (including IPv4-mapped IPv6 forms). An **empty array means the allowlist is disabled** — no restriction is applied.

When the allowlist is non-empty, it is enforced at three points:

- **At login** — after credentials are verified but before any token is minted, a request from a non-allowed IP is rejected (`401`, `IP_NOT_ALLOWED`).
- **On every authenticated request** — a guard runs after authentication resolves the partner context and denies non-allowed IPs (`403`, `IP_NOT_ALLOWED`).
- **On partner-scoped MCP / OAuth API keys** — partner-scoped programmatic access is held to the same allowlist.

**Agents are exempt.** Agent enrollment, heartbeats, and command traffic authenticate through a separate path that never passes through the user IP-allowlist guard, so restricting admin access does not strand the device fleet.

### Configuration

| Field | Type | Notes |
|-------|------|-------|
| `settings.security.ipAllowlist` | `string[]` | Literal IPv4/IPv6 addresses and CIDR ranges (e.g. `203.0.113.10`, `10.0.0.0/8`, `2001:db8::/32`). Each entry is validated on write; invalid entries are rejected with `400`. Empty array = disabled. |

Because the allowlist depends on knowing the true client IP, the API refuses to enable it unless trusted-proxy parsing is configured (`TRUST_PROXY_HEADERS` plus `TRUSTED_PROXY_CIDRS`); turning it on without that returns `400 proxy_trust_required`. If the source IP cannot be trusted at runtime (a proxy misconfiguration), enforcement fails **closed** and denies the request (`403`, `untrusted_ip`) rather than letting an unverifiable IP through; a database/read error during the check also fails **closed** (`503`). A `PATCH` to partner settings that omits `ipAllowlist` preserves the existing list — you must send `ipAllowlist: []` to deliberately clear it.

Platform admins are exempt from the allowlist entirely, on every check, so a locked-out partner can still be reached by system support.

<Aside type="caution">
  An incorrect allowlist will lock you (and every other admin) out of the dashboard and API. Before saving, confirm your current IP — and any VPN/egress ranges your team uses — are covered, and prefer CIDR ranges over single addresses for connections with dynamic IPs. Changes propagate to other API instances within roughly 30 seconds (the allowlist is cached per partner). A deployment-wide break-glass switch (`IP_ALLOWLIST_ENFORCEMENT_MODE=off`) disables all enforcement if you are locked out and have host access.
</Aside>

## Managing Partners

<Aside type="tip" title="Provisioning tenancy unattended">
  Organizations, sites, and enrollment keys can all be created by a partner service principal rather than a signed-in user, which is how a migration script or an onboarding integration stands a customer up end to end. `POST /partner-api/v1/enrollment-keys` completes that set — see [Partner API (Service Principals)](/reference/api/#partner-api-service-principals) for the routes, scopes, and the tighter mint limits that apply to enrollment keys specifically.
</Aside>

### Creating Partners (System Scope)

System-scoped users can create partners directly via the API. This bypasses self-registration and allows setting fields that self-registration does not expose (type, plan, device limits).

```bash
curl -X POST https://breeze.example.com/api/v1/orgs/partners \
  -H "Authorization: Bearer <system-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Acme MSP",
    "slug": "acme-msp",
    "type": "msp",
    "plan": "pro",
    "maxOrganizations": 50,
    "maxDevices": 5000,
    "billingEmail": "billing@acme-msp.com"
  }'
```

### Partner Fields

| Field | Type | Description |
|-------|------|-------------|
| `id` | `uuid` | Auto-generated primary key |
| `name` | `varchar(255)` | Display name. Required |
| `slug` | `varchar(100)` | URL-safe unique identifier. Required |
| `type` | `enum` | `msp`, `enterprise`, or `internal`. Default: `msp` |
| `plan` | `enum` | `free`, `starter`, `community`, `pro`, `enterprise`, or `unlimited`. Default: `free` |
| `maxOrganizations` | `integer` | Optional cap on organization count |
| `maxDevices` | `integer` | Optional cap on total devices across all organizations |
| `settings` | `jsonb` | Partner-level settings (timezone, business hours, contact info) |
| `serviceManagementMode` | `enum` | `native`, `external`, or `off`. Default: `native`. See [Service Management mode](#service-management-mode) |
| `serviceManagementPsaConnectionId` | `uuid` | The partner-wide PSA connection bound to `external` mode. Required when the mode is `external`, and must be null otherwise |
| `ssoConfig` | `jsonb` | SSO configuration |
| `billingEmail` | `varchar(255)` | Billing contact email |
| `createdAt` | `timestamp` | Record creation time |
| `updatedAt` | `timestamp` | Last modification time |
| `deletedAt` | `timestamp` | Soft-delete marker. Null when active |

### Updating Partner Settings (Self-Service)

Partner-scoped users can update their own partner's name, billing email, and settings via the `/partners/me` endpoint. Settings are merged on update -- only the keys included in the request are overwritten.

```bash
curl -X PATCH https://breeze.example.com/api/v1/orgs/partners/me \
  -H "Authorization: Bearer <partner-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Acme IT Services",
    "settings": {
      "timezone": "America/Chicago",
      "businessHours": { "preset": "business" },
      "contact": {
        "name": "Jane Doe",
        "email": "jane@acme-it.com"
      }
    }
  }'
```

### Service Management mode

Not every MSP runs its service desk in Breeze. **Service Management mode** is a
partner-level switch that decides whether Breeze's own service desk and customer
billing are part of this MSP's product at all. Find it on the **Modules** card
under **Settings → Partner → Company**.

| Mode | What the MSP gets |
|---|---|
| **Breeze service desk & billing** (`native`) | Everything. The default, and what every existing partner keeps. |
| **Off — RMM only** (`off`) | Breeze is monitoring and management only. The **Service Desk** section (Tickets, Timesheets) and the **Billing** section (Quotes, Invoices, Contracts, Product Catalog) disappear from the sidebar, and **no new ticket can be created anywhere**. |
| `external` | For an MSP whose tickets live in a third-party PSA. **No UI in this release** — see below. |

**What `off` actually refuses.** Turning the module off is a product decision, not
a permission: it hides the service-desk and billing surfaces and refuses *new*
ticket creation on every path — the web UI, the customer portal, inbound
email-to-ticket, the AI assistant's ticket tool, and vulnerability-driven ticket
creation all answer `409 service_management_off`. **Existing tickets stay
readable** and nothing is deleted, so turning the module back on restores the
surfaces with their history intact.

<Aside type="note" title="`external` has no selector yet">
  `external` is reachable only through the API in this release, and only for a
  partner that already has a **partner-wide** PSA connection bound to it — the
  mode and the connection are enforced as a pair, so neither can be set without
  the other. The Modules card deliberately offers only `native` and `off`; a
  partner already on `external` keeps it and sees a note that changing it is not
  available here yet. A UI selector ships with the external service-desk feature.
  See [PSA Integrations](/features/psa-integrations/).
</Aside>

Both the mode and the bound PSA connection are top-level fields on
`PATCH /partners/me` — they are **not** keys inside the merged `settings` object:

```bash
curl -X PATCH https://breeze.example.com/api/v1/orgs/partners/me \
  -H "Authorization: Bearer <partner-token>" \
  -H "Content-Type: application/json" \
  -d '{ "serviceManagementMode": "off" }'
```

An unrecognised or missing mode is read as `native`, so a partner is never
accidentally locked out of its own service desk by bad data.

### Soft Deleting a Partner

Partners use soft deletes. When deleted via `DELETE /partners/:id`, the `deletedAt` timestamp is set. The partner and its data remain in the database but are excluded from all queries.

<Aside type="caution">
  Soft-deleting a partner does **not** cascade to its organizations, sites, or devices. Those records remain active in the database. Clean them up separately before or after deleting the partner.
</Aside>

## Partner User Association

Users are linked to partners through the `partner_users` join table. Each record contains:

| Field | Type | Description |
|-------|------|-------------|
| `partnerId` | `uuid` | FK to the partner |
| `userId` | `uuid` | FK to the user |
| `roleId` | `uuid` | FK to a role (determines permissions) |
| `orgAccess` | `enum` | `all`, `selected`, or `none` |
| `orgIds` | `uuid[]` | Array of organization IDs when `orgAccess` is `selected` |

When a user authenticates, the API resolves their token context by looking up the `partner_users` record. The JWT includes the `partnerId`, `scope: partner`, and the `roleId`. The `orgAccess` and `orgIds` fields are used at query time to filter which organizations the user can access.

### Inviting Users to a Partner

Partner admins can invite users via the user management endpoints. Invited users receive an email with an invite link that leads to a password-setting form. Upon acceptance, the user is associated with the partner via `partner_users` with the specified role and organization access level.

## API Reference

### Self-Registration

Registration is two calls: `POST /auth/register-partner` requests the signup and `POST /auth/verify-email` completes it once the emailed link is clicked. No user, partner, or token exists between the two calls.

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| `POST` | `/auth/register-partner` | None | Request self-service partner registration. Rate limited to 3/IP/hour. Creates nothing; queues a verification email. |
| `POST` | `/auth/verify-email` | None | Complete registration with the emailed token. Creates the partner, admin role, user, and association, and issues tokens. |

**Request body (`POST /auth/register-partner`):**

```json
{
  "companyName": "Acme IT Services",
  "email": "admin@acme-it.com",
  "password": "securePassword123!",
  "name": "Jane Doe",
  "acceptTerms": true
}
```

**Response (200)** -- identical for every accepted input, including an email that already has an account, so the response cannot be used to enumerate registered addresses:

```json
{
  "success": true,
  "message": "If registration can proceed, you will receive next steps shortly."
}
```

**Request body (`POST /auth/verify-email`):**

```json
{
  "token": "<token from the verification email link>"
}
```

**Success response (200):**

```json
{
  "verified": true,
  "user": {
    "id": "uuid",
    "email": "admin@acme-it.com",
    "name": "Jane Doe",
    "mfaEnabled": false
  },
  "partner": {
    "id": "uuid",
    "name": "Acme IT Services",
    "slug": "acme-it-services",
    "status": "active"
  },
  "mfaRequired": false,
  "tokens": {
    "accessToken": "eyJ...",
    "expiresInSeconds": 900
  }
}
```

**Error responses:**

| Status | Condition |
|--------|-----------|
| `400` | `/auth/register-partner`: validation error (weak password, missing required fields, terms not accepted). `/auth/verify-email`: invalid or expired token -- one identical body for every failure reason, to avoid leaking which reason applied. |
| `429` | Rate limit exceeded (3 attempts per IP per hour on `register-partner`; a separate limit on `verify-email`) |
| `503` | Redis unavailable (rate limiter cannot function) |

### Partner Administration (System Scope)

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/orgs/partners` | List all partners. Supports `page` and `limit` query params (default 50, max 100) |
| `POST` | `/orgs/partners` | Create a new partner |
| `GET` | `/orgs/partners/:id` | Get partner by ID. Returns `404` if not found or soft-deleted |
| `PATCH` | `/orgs/partners/:id` | Update partner fields. Returns `400` if no fields provided |
| `DELETE` | `/orgs/partners/:id` | Soft-delete partner. Sets `deletedAt` |

### Partner Self-Service (Partner Scope)

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/orgs/partners/me` | Get the authenticated user's partner details |
| `PATCH` | `/orgs/partners/me` | Update partner name, billing email, or settings (merged, not replaced) |

### Organization Management (Partner Scope)

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/orgs/organizations` | List organizations accessible to the partner user. Supports pagination |
| `POST` | `/orgs/organizations` | Create a new organization under the user's partner |
| `GET` | `/orgs/organizations/:id` | Get organization by ID (access-controlled) |
| `PATCH` | `/orgs/organizations/:id` | Update organization fields |
| `DELETE` | `/orgs/organizations/:id` | Soft-delete organization |

<Aside>
  All partner and organization endpoints require JWT authentication. Organization endpoints enforce access control based on the user's `orgAccess` level. Partner-scoped users with `orgAccess: none` will receive empty results from organization list endpoints.
</Aside>

## Security Considerations

### Rate Limiting

Partner registration is rate-limited to **3 attempts per IP address per hour** using the Redis-backed sliding window rate limiter. This is stricter than the general user registration limit (5 attempts per IP per hour). The rate limit key is derived from the client IP address extracted from the `X-Forwarded-For` header or the direct connection IP.

### Email Enumeration Prevention

When a registration request uses an email that already exists, the API returns a generic success-like response rather than an explicit "email already exists" error:

```json
{
  "success": true,
  "message": "If registration can proceed, you will receive next steps shortly."
}
```

This prevents attackers from using the registration endpoint to enumerate valid email addresses.

### Slug Collision Handling

Partner slugs must be unique. The registration flow automatically appends a numeric suffix (`-1`, `-2`, etc.) if the generated slug already exists. This process attempts up to 100 suffixes before returning a `500` error. Slugs are capped at 50 characters from the base company name before the suffix.

### Cleanup on Failure

If user creation fails after the partner and role records have been inserted, the API manually deletes the orphaned role and partner records. This is not wrapped in a database transaction, so in edge cases (e.g., the cleanup query itself fails), orphaned records may remain.

## Troubleshooting

**Registration form redirects to `/login?reason=registration-disabled`.**
The `PUBLIC_ENABLE_REGISTRATION` environment variable is set to `false` on the frontend. To enable registration, set `PUBLIC_ENABLE_REGISTRATION=true` in the frontend environment and restart the web server. Also verify that the API has `ENABLE_REGISTRATION=true` (or unset, since the default is `true`).

**"Too many registration attempts. Try again later." (429).**
The rate limiter has blocked the IP address after 3 registration attempts within one hour. Wait for the rate limit window to expire, or use a different IP address for testing. In production, verify Redis is running -- if Redis is down, the endpoint returns `503` instead.

**Registration succeeds but user cannot access any organizations.**
After self-registration, the partner has no organizations yet. The admin user is created with `orgAccess: all`, but there are no organizations to access. Create the first organization via `POST /orgs/organizations` or through the setup wizard.

**"Unable to generate unique company identifier" (500).**
The slug generation exhausted 100 suffix attempts. This happens if many partners have been registered with very similar names. Provide a more distinctive company name, or create the partner manually via the system API with an explicit slug.

**Partner not appearing in the partner list.**
Only system-scoped users can list all partners via `GET /orgs/partners`. Partner-scoped users cannot see other partners. Verify the user has `scope: system` in their JWT. Also check whether the partner was soft-deleted -- soft-deleted partners are excluded from all list queries.

**"Service temporarily unavailable" (503) during registration.**
Redis is not accessible. The rate limiter requires Redis to function. Check that Redis is running and the `REDIS_URL` environment variable is correctly configured on the API server.

**Self-registered partner has `free` plan and `msp` type.**
This is the default behavior. Self-registration always creates partners with `type: msp` and `plan: free`. To change the plan or type, a system-scoped user must update the partner via `PATCH /orgs/partners/:id`.

**Registration link not visible on the login page.**
The login page conditionally renders the registration link based on the `PUBLIC_ENABLE_REGISTRATION` feature flag. If the flag is `false` or unset as `false`, the link is hidden. Set `PUBLIC_ENABLE_REGISTRATION=true` to show it.

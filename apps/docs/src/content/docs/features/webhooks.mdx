Webhooks let you push real-time event notifications from Breeze to any external HTTP endpoint. When a device enrolls, an alert fires, a script completes, or any other tracked event occurs, Breeze sends a signed JSON payload to each webhook configured for that event type. Webhooks are scoped to an organization and support custom headers, HMAC-SHA256 signature verification, automatic retries on a fixed schedule, and a full delivery history with per-delivery status tracking.

---

## Creating a Webhook

<Steps>
1. Choose the events you want to subscribe to (see [Event Types](#event-types) below).

2. Send a POST request with the webhook name, destination URL, signing secret, and event list:

   ```bash
   POST /webhooks
   Content-Type: application/json

   {
     "name": "PagerDuty Alerts",
     "url": "https://events.pagerduty.com/integration/abc123/enqueue",
     "secret": "whsec_your_signing_secret",
     "events": ["alert.triggered", "alert.acknowledged", "device.offline"],
     "payloadVersion": 2,
     "headers": [
       { "key": "X-Custom-Source", "value": "breeze-rmm" }
     ]
   }
   ```

3. The API validates the URL against the SSRF safety rules (see [URL Safety Validation](#url-safety-validation) — HTTPS to a publicly routable address on hosted Breeze; self-hosted deployments may also target private addresses), encrypts the secret, and returns the new webhook:

   ```json
   {
     "id": "d290f1ee-6c54-4b01-90e6-d701748f0851",
     "orgId": "11111111-1111-1111-1111-111111111111",
     "name": "PagerDuty Alerts",
     "url": "https://events.pagerduty.com/integration/abc123/enqueue",
     "events": ["alert.triggered", "alert.acknowledged", "device.offline"],
     "payloadVersion": 2,
     "headers": [{ "key": "X-Custom-Source", "value": "breeze-rmm" }],
     "status": "active",
     "hasSecret": true,
     "createdAt": "2026-02-18T12:00:00.000Z",
     "updatedAt": "2026-02-18T12:00:00.000Z",
     "lastDeliveryAt": null
   }
   ```

4. Send a test delivery to verify connectivity (see [Testing a Webhook](#testing-a-webhook)).
</Steps>

<Aside>
  Both the `secret` and the `url` are encrypted at rest using AES-256-GCM. The `secret` is never returned in API responses — only the `hasSecret` boolean indicates whether one is configured. The `url` is returned by GET responses, but any credentials embedded in it (HTTP basic-auth userinfo and signed query tokens) are stripped before the value is sent to the client.
</Aside>

### Create request fields

| Field | Type | Required | Meaning |
|-------|------|----------|---------|
| `name` | string | Yes | Webhook name |
| `url` | string | Yes | Destination URL |
| `events` | string[] | Yes | Subscribed event types; `*` receives all events |
| `payloadVersion` | `1` or `2` | No | Payload version; defaults to `2` |
| `secret` | string | With HMAC | Signing secret; use a Bearer token header instead when appropriate |
| `headers` | array of key/value objects | No | Custom request headers |
| `orgId` | UUID string | For partner or system scope | Organization that owns the webhook |

### Organization Scoping

Webhooks follow the standard multi-tenant access model:

| Auth Scope | Behavior |
|------------|----------|
| **Organization** | `orgId` is set automatically from the authenticated context. |
| **Partner** | `orgId` must be provided in the request body. The API verifies the partner has access to that organization. |
| **System** | `orgId` must be provided in the request body. |

## Event Types

Webhooks subscribe to events emitted by the Breeze event bus. Pass one or more event type strings in the `events` array when creating or updating a webhook. Use `*` to receive every event. The API rejects an event type that Breeze never publishes with a `400`, so a typo cannot save a webhook that silently never fires. The legacy name `alert.created` is accepted and stored as `alert.triggered`.

### Device Events

| Event | Description |
|-------|-------------|
| `device.enrolled` | An agent has completed enrollment (first enrollment or re-enrollment; payload `reenrollment` distinguishes them) |
| `device.online` | A device has come online (heartbeat received) |
| `device.offline` | A device has stopped sending heartbeats |
| `device.updated` | Device metadata or configuration has changed |
| `device.reinstalled` | A reinstalled machine was reattached to its existing device record: the record keeps its id, org, site and history, a new install takes it over, and the install incarnation advances. Payload: `deviceId`, `sourceDeviceId`, `orgId`, `sourceOrgId`, `siteId`, `installIncarnation`, `previousIncarnation`, `evidenceLevel`, `actorUserId`, `reattachmentId` |

### Alert Events

| Event | Description |
|-------|-------------|
| `alert.triggered` | A monitoring rule has fired a new alert |
| `alert.acknowledged` | An alert has been acknowledged by a user or service principal |
| `alert.resolved` | An alert condition has cleared |
| `alert.suppressed` | Breeze AI has suppressed an alert. Suppressing an alert from the dashboard or `POST /alerts/:id/suppress` does not publish this event yet |

`alert.escalated` is not sent by Breeze; the API rejects a new subscription to it with `400`; a stored one shows as "Never delivered" in the dashboard, and the dashboard edit form removes it on save.

### Script Events

| Event | Description |
|-------|-------------|
| `script.started` | Script execution has begun on a device |
| `script.completed` | Script execution finished successfully |
| `script.failed` | Script execution failed or timed out (a cancelled run emits neither) |

### Automation Events

| Event | Description |
|-------|-------------|
| `automation.started` | An automation workflow has begun |
| `automation.completed` | An automation workflow completed successfully |
| `automation.failed` | An automation workflow failed |

### Policy Events

| Event | Description |
|-------|-------------|
| `policy.evaluated` | A configuration policy has been evaluated against a device |
| `policy.violation` | A device is non-compliant with a policy |
| `policy.compliant` | A device has returned to compliance |

### Patch Events

| Event | Description |
|-------|-------------|
| `patch.available` | New patches are available for a device |
| `patch.approved` | A patch has been approved for installation |
| `patch.installed` | A patch was installed successfully |

| `patch.rollback` | A patch has been rolled back |

### Ticket Events

Ticket events are published from the ticketing transactional outbox with **id-only payloads**: identifiers, enum labels and field *names*, never a subject, description, resolution note or comment body. Read the full record through the API (staff JWT, or the Partner API `tickets:read` feed) when you need it. Rely only on the fields listed below: a payload can also carry other internal identifiers, which are not part of this contract.

| Event | Payload (besides `ticketId`) | Description |
|-------|------------------------------|-------------|
| `ticket.created` | `internalNumber`, `source`, `assigneeId`, `actorPrincipalId` | A ticket was opened (from the portal, email, an alert, the UI, the Partner API or AI). `actorPrincipalId` is the service principal that opened it (`null` otherwise) |
| `ticket.commented` | `commentId`, `isPublic`, `originPrincipalKind`, `originPrincipalId` | A comment, note or feed entry was added. `originPrincipalKind` and `originPrincipalId` are the comment's stored origin, the same values the Partner API feed returns for it: `service_principal` with the principal's id, `ai_agent` with the agent's id, `user` for people, and `system` for Breeze's own system notes, such as caller verification (`originPrincipalId` is `null` for the last two). A comment Breeze writes on a customer's behalf is `user` by design: a reply that arrives by email (or a public email linked from the Outlook add-in) and the reopen that reply triggers. A mirroring integration skips exactly the comments it wrote by matching `service_principal` and its own principal id |
| `ticket.status_changed` | `from`, `to`, `statusId` | The core status changed (`statusId` is the partner's custom status row, when one was used) |
| `ticket.updated` | `changed` (field names) | Fields were edited — subject, description, priority, category, due date, device, tags, requester |
| `ticket.assigned` | `assigneeId` (`null` when unassigned), `actorPrincipalId` | The assignee changed. `actorPrincipalId` is the service principal that made the change (`null` for people and the system), so a mirroring integration can skip its own assignments |
| `ticket.merged` | `sourceTicketId`, `targetTicketId`, `sourceInternalNumber`, `targetInternalNumber` | A ticket was merged into another. Sent once, on the surviving ticket (`ticketId` = `targetTicketId`). The source stays as a read-only record: a Partner API read of it returns `mergedIntoTicketId` and `mergedAt`. The source also gets a `ticket.status_changed` to `closed` when it was not already closed, and the survivor a `ticket.updated` with `changed: ["merge"]`. Comments moved by the merge are not re-sent as `ticket.commented` |
| `ticket.sla_breached` | `assigneeId` | A response or resolution SLA target was missed |

### Migration Window Events

A ticket migration window lets a partner admin import ticket history from another system without notifying anyone or firing per-ticket events. Nothing the import writes produces a ticket event. When the window closes, each organization in it gets one summary event.

| Event | Payload | Description |
|-------|---------|-------------|
| `migration.window_closed` | `windowId`, `partnerId`, `sourceLabel`, `openedAt`, `endsAt`, `closedAt`, `closedReason`, `ticketsImported`, `commentsImported`, `attachmentsImported` | A migration window closed. Sent once per organization in the window, with that organization's counts. `attachmentsImported` counts the files attached to imported comments. `closedReason` is `expired`, `closed_by_admin`, `principal_inactive` or `opener_inactive`. The event id is `<windowId>:<orgId>`, so a retried delivery is recognizable |

### Integration Events

Integration events report the health of an organization's own connections: an integration, a sync or an OAuth grant. A health incident opens when a connection breaks and resolves when it recovers or is retired.

| Event | Payload | Description |
|-------|---------|-------------|
| `integration.health_opened` | `incidentId`, `orgId`, `sourceKind`, `sourceId`, `condition`, `severity`, `fixHref`, `openedAt`, `resolvedAt`, `resolution` | A connection health incident opened. `resolvedAt` and `resolution` are `null` |
| `integration.health_resolved` | `incidentId`, `orgId`, `sourceKind`, `sourceId`, `condition`, `severity`, `fixHref`, `openedAt`, `resolvedAt`, `resolution` | A connection health incident resolved |

| Field | Type | Description |
|-------|------|-------------|
| `incidentId` | string (uuid) | The incident. Both events for one incident carry the same value |
| `orgId` | string (uuid) | The organization that owns the connection |
| `sourceKind` | string | The kind of connection, for example `m365_connection`, `dns_filter` or `webhook` |
| `sourceId` | string or `null` | The connection's id. `null` for `oauth_grant`, because that id embeds a user id |
| `condition` | string | A fixed code for what is wrong, for example `sync_failed` or `reauth_required` |
| `severity` | string | `permanent` (needs someone to act) or `transient` (may clear on its own) |
| `fixHref` | string | A relative path in the Breeze web app where the connection can be repaired |
| `openedAt` | string (ISO timestamp) | When the incident opened |
| `resolvedAt` | string (ISO timestamp) or `null` | When the incident resolved. `null` while it is open |
| `resolution` | string or `null` | `recovered` or `retired`. `null` while the incident is open |

- **No free text.** The payload never contains provider error text or the connection's display name. Use `fixHref` and the API to look up more.
- **Organization connections only.** Only incidents about an organization's own connections emit events. Partner-wide connections do not.
- **Level-triggered.** Events follow the state seen at each health check, about every 15 minutes. A connection that breaks and recovers between two checks may emit nothing. A consumer can also receive an `integration.health_resolved` event for an incident it never saw open, for example an incident that existed before the feature shipped.
- **Stable event ids.** The event id is stable for a given incident and state, so retried deliveries are deduplicated.
- **No self-delivery.** An incident about a webhook is never delivered to that same webhook.

### Other Events

| Event | Description |

| `remote.session.ended` | A remote access session has ended |

## Delivery Mechanism

When an event is emitted on the Breeze event bus, the webhook delivery system routes it to all active webhooks in the same organization that are subscribed to that event type. Each delivery follows this sequence:

<Steps>
1. The event bus fires the event. The webhook subscriber matches the event type against all configured webhooks for the organization.

2. A delivery record is created in the `webhook_deliveries` table with status `pending` and `attempts` set to `0`.

3. A BullMQ job carrying only the delivery and webhook ids, generation, and attempt count is queued on `webhook-delivery`.

4. The worker claims the delivery row as `retrying`, validates the destination URL (including DNS resolution to block SSRF), and sends an HTTP POST with the signed payload.

5. A `2xx` response marks the row `delivered`. A failure marks it `scheduled` with the next attempt time, or `failed` after the last attempt.
</Steps>

### Payload Format

The original v1 JSON POST body has this structure. See [Payload versions](#payload-versions) for the v2 envelope.

```json
{
  "id": "event-uuid",
  "type": "device.offline",
  "timestamp": "2026-02-18T12:34:56.789Z",
  "orgId": "11111111-1111-1111-1111-111111111111",
  "data": {
    "deviceId": "abc123",
    "hostname": "WORKSTATION-01",
    "lastSeen": "2026-02-18T12:30:00.000Z"
  }
}
```

| Field | Description |
|-------|-------------|
| `id` | Unique event ID (UUID) |
| `type` | The event type string (e.g., `alert.triggered`) |
| `timestamp` | ISO 8601 timestamp of when the event was created |
| `orgId` | The organization the event belongs to |
| `data` | Event-specific payload; contents vary by event type |

## Payload versions

Each webhook has a `payloadVersion`: `1` or `2`. Webhooks created before this release stay on `1`; their payload is unchanged byte for byte. New webhooks default to `2`. Webhooks created through the API without `payloadVersion` also default to `2`.

Choose the version in the edit form, or send `PATCH /webhooks/:id` with `{ "payloadVersion": 2 }`. You can switch back to `1`. Each delivery keeps the payload version it was recorded at, including manual replays and legacy rows. Editing the webhook stops its scheduled retries when they next come due.

The v2 envelope is `{ id, type, timestamp, orgId, schemaVersion: 2, replayOf, data }`, in that order. The v1 envelope has no `schemaVersion` or `replayOf`. For non-alert events, v2 changes only the envelope; `data` is the same as v1. A test delivery (`POST /webhooks/:id/test`) uses the webhook's version with sample `data`; it does not enrich that sample.

### Replays and deduplication

A manual retry creates a new event with a new `id`. It carries `X-Breeze-Replay-Of: <original event id>` in either version, and `replayOf` in the v2 body. A replay of a replay keeps the original event id as its root.

Deduplicate transport on the original event id: `replayOf ?? id` for v2, or `X-Breeze-Replay-Of` falling back to `id` for v1. Deduplicate tickets on `alertId` plus your own ticket state, not on `alertId + type`: a suppressed alert can return to active and be acknowledged again.

### Request Headers

Deliveries use these headers; signature and replay headers apply as noted:

| Header | Description |
|--------|-------------|
| `Content-Type` | `application/json` |
| `User-Agent` | `Breeze-Webhooks/1.0` |
| `X-Breeze-Delivery-Id` | Unique ID for this delivery attempt |
| `X-Breeze-Event-Id` | The event ID from the payload |
| `X-Breeze-Event-Type` | The event type string |
| `X-Breeze-Timestamp` | Unix timestamp (milliseconds) of the delivery attempt |
| `X-Breeze-Signature` | HMAC-SHA256 signature (only if a secret is configured) |
| `X-Breeze-Signature-Timestamp` | Timestamp used in the signature computation |
| `X-Breeze-Replay-Of` | Original event id on a manual retry, in either payload version; absent on original deliveries |

Any custom headers configured on the webhook are merged into the request after the standard headers.

## Retry Logic

Every non-2xx response, timeout, or transport error is retried on this fixed schedule. Each request has a **30-second timeout**.

| Attempt | Delay after the previous attempt |
|---------|----------------------------------|
| 1 | Immediately |
| 2 | 1 minute |
| 3 | 5 minutes |
| 4 | 30 minutes |
| 5 | 2 hours |
| 6 | 6 hours |
| 7 | 12 hours |

Each delay has **±20% jitter**. The base schedule spans about **21 hours** from the first attempt to the last; a seventh failure leaves the delivery `failed`. The per-webhook `retry_policy` is ignored.

Retry state lives in Postgres, with BullMQ delayed jobs waking each attempt. A wake-up lost to a failed enqueue or to Redis data loss is re-driven by the recovery sweep once the delivery is more than 15 minutes overdue. Each attempt is claimed before sending, so two workers cannot send the same attempt. If a worker stops mid-request, recovery marks the delivery `failed` with an unknown outcome instead of re-sending a potentially delivered request.

Editing or disabling a webhook stops its scheduled retries; each is marked `failed` (`superseded_by_edit:`) when it next comes due, including retries re-driven by the recovery sweep. Replay it manually if needed. A delivery keeps the payload version it was recorded at; this also applies to manual replays and legacy rows.

The Redis dead-letter queue is retired. On first start after upgrading, Breeze drains the old Redis delivery list and DLQ: pending rows and old in-memory retries are re-driven; entries whose delivery no longer exists or already finished are dropped and counted. DLQ entries become `failed` deliveries available for manual replay when their webhook still exists. Entries that fail to process stay in Redis and are retried by the recovery sweep.

<Aside type="caution">
  Redirects are rejected (`redirect: "error"`). If your endpoint returns a 3xx redirect, the delivery will be treated as a failure and retried.
</Aside>

## Bearer Token Authentication

If your endpoint expects a static token rather than a signature, authenticate with a bearer token instead of a signing secret. In the dashboard, choose **Bearer token** under **Authentication**. Through the API, send the token as an `Authorization` custom header and omit `secret`:

```json
{
  "name": "Ticketing intake",
  "url": "https://intake.example.com/breeze",
  "events": ["ticket.created"],
  "headers": [
    { "key": "Authorization", "value": "Bearer your_token" }
  ]
}
```

The token is stored encrypted with the other custom headers and is never returned: GET responses show the header with a redacted value and report `"authType": "bearer"` (`"hmac"` for a signing secret, `"none"` for neither). A webhook needs either a `secret` or an `Authorization: Bearer <token>` header; other `Authorization` schemes (such as `Basic`) can be added as custom headers alongside a signing secret. To switch an existing webhook from HMAC to bearer, send `"secret": null` together with the `Authorization` header in the same `PATCH`. To keep a stored token while you edit other headers, send its value back as `********`.

## Signature Verification

When a webhook has a signing secret, every delivery includes an HMAC-SHA256 signature in the `X-Breeze-Signature` header. Use this to verify that the payload was sent by Breeze and has not been tampered with.

### How the Signature Is Computed

The signature input is the concatenation of the timestamp and the raw JSON payload body, separated by a dot:

```
signature_input = timestamp + "." + payload_body
signature = HMAC-SHA256(secret, signature_input)
```

The `X-Breeze-Signature` header value is prefixed with `sha256=`:

```
X-Breeze-Signature: sha256=a1b2c3d4e5f6...
```

The `X-Breeze-Signature-Timestamp` header contains the same timestamp value used in the signature computation. The signature covers the raw body for both payload versions.

### Verification Examples

<Tabs>
  <TabItem label="Node.js">
    ```javascript
    import { createHmac, timingSafeEqual } from 'crypto';

    function verifyWebhookSignature(payload, secret, signatureHeader, timestampHeader) {
      const expectedSig = signatureHeader.replace('sha256=', '');
      const signatureInput = `${timestampHeader}.${payload}`;
      const computedSig = createHmac('sha256', secret)
        .update(signatureInput)
        .digest('hex');

      return timingSafeEqual(
        Buffer.from(expectedSig, 'hex'),
        Buffer.from(computedSig, 'hex')
      );
    }
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    import hmac
    import hashlib

    def verify_webhook_signature(payload: bytes, secret: str, signature_header: str, timestamp_header: str) -> bool:
        expected_sig = signature_header.removeprefix("sha256=")
        signature_input = f"{timestamp_header}.{payload.decode('utf-8')}"
        computed_sig = hmac.new(
            secret.encode('utf-8'),
            signature_input.encode('utf-8'),
            hashlib.sha256
        ).hexdigest()

        return hmac.compare_digest(expected_sig, computed_sig)
    ```
  </TabItem>
</Tabs>

<Aside type="tip">
  Always use a constant-time comparison function (such as `timingSafeEqual` in Node.js or `hmac.compare_digest` in Python) to prevent timing attacks.
</Aside>

## Example: alert to ConnectWise Manage through middleware

This outline uses a low-code automation platform such as Rewst between Breeze and ConnectWise Manage. Adapt the fields and priority mapping to your Manage configuration.

1. Create a v2 webhook subscribed to `alert.triggered`, `alert.acknowledged`, and `alert.resolved`. Point it at the middleware's incoming webhook URL.
2. Verify the request before processing it. Use the HMAC recipe above with `X-Breeze-Signature-Timestamp` and the raw body. If the platform can only check a static header, use Breeze's Bearer token option and validate the `Authorization` header instead.
3. Deduplicate received requests on `replayOf ?? id`. Store the key after processing succeeds so a failed middleware attempt can be retried.
4. On `alert.triggered`, map `data.severity` to your Manage priority ids. For example, map `critical` and `high` to your urgent queue, and send null severity for review. Use `data.orgName` to look up the company, `data.deviceHostname` and `data.title` in the ticket summary, and `data.alertUrl` in the description. Keep the lookup explicit when organization names are ambiguous or enrichment is incomplete.
5. Store an `alertId` → ticket id mapping. On `alert.acknowledged`, update the mapped ticket according to your workflow. Use the alert id and current ticket state to decide whether to create or update; repeated alert states must not create duplicate tickets.
6. On `alert.resolved`, close the mapped ticket with your configured Manage closed status. If no mapping exists, send the event for review rather than creating a new closed ticket.
7. Grant a dedicated principal `alerts:write`. When the Manage ticket closes, call `POST /api/v1/partner-api/alerts/<alertId>/resolve` with an optional `note`. Ignore webhook events whose `acknowledgedByPrincipalId` or `resolvedByPrincipalId` is your own principal id so the write-back does not loop.

<Aside type="note">
  The exact Rewst trigger setup is not yet confirmed, including whether its webhook trigger verifies an HMAC signature or only a static header. This section will be updated when that setup is confirmed.
</Aside>

## Delivery History

Every webhook maintains a paginated delivery history. Each delivery record captures the event type, payload, response details, and retry state. The list returns status and timing only; the event payload and the receiver's response body are not included. Reading the history requires `webhooks:read`.

From v0.124.0, delivered and failed records are kept for **90 days** by default and then removed by a nightly job; records that are still pending, scheduled or retrying are never removed. Self-hosters can change the window with the webhook delivery retention variables in [Environment Variables](/deploy/environment/). A webhook whose delivery ends `failed` after its last attempt, with no later success, opens a connection-health incident on **Integrations**. For a dead endpoint, that is about 21 hours after the first failed attempt, rather than minutes. Decrypt failures open an incident immediately. See [Connection Health Checks](/features/notifications/#connection-health-checks).

### Retrying a Failed Delivery

You can manually retry any delivery that has a `failed` status. The retry creates a new delivery record with the same event type and payload, and queues it for immediate processing. The endpoint returns 202 Accepted even when queuing fails: the delivery stays `pending`, and the recovery sweep sends it within about 15–20 minutes.

```bash
POST /webhooks/:id/retry/:deliveryId
```

Response (202 Accepted):

```json
{
  "message": "Delivery retry queued",
  "delivery": {
    "id": "new-delivery-uuid",
    "status": "pending",
    "attempt": 0
  }
}
```

<Aside>
  Only deliveries with status `failed` can be retried. Attempting to retry a delivery with any other status returns a `400` error.
</Aside>

## Testing a Webhook

Send a test delivery to verify that your endpoint is reachable and correctly processing payloads:

```bash
POST /webhooks/:id/test
Content-Type: application/json

{
  "event": "webhook.test",
  "payload": {
    "message": "Hello from Breeze RMM"
  }
}
```

Both `event` and `payload` are optional. If omitted, the test uses event type `webhook.test` and a default payload containing a message, timestamp, and webhook ID.

Response (202 Accepted):

```json
{
  "message": "Test delivery queued",
  "delivery": {
    "id": "delivery-uuid",
    "webhookId": "webhook-uuid",
    "status": "pending",
    "event": "webhook.test",
    "attempt": 0
  }
}
```

The test endpoint returns 202 Accepted even when queuing fails: the delivery stays `pending`, and the recovery sweep sends it within about 15–20 minutes. The AI `test_webhook` tool likewise reports the delivery as accepted when queuing fails. A test delivery uses the same HMAC signing, URL validation, and delivery pipeline as real events; a failing endpoint follows the full retry schedule.

## Updating a Webhook

Update any combination of name, URL, secret, events, headers, status, or payload version:

```bash
PATCH /webhooks/:id
Content-Type: application/json

{
  "events": ["device.enrolled", "device.offline", "alert.triggered"],
  "payloadVersion": 2,
  "status": "paused"
}
```

| Request field | Type | Meaning |
|---------------|------|---------|
| `name` | string | Webhook name |
| `url` | string | Destination URL |
| `events` | string[] | Replacement subscription list |
| `payloadVersion` | `1` or `2` | Version for future deliveries; stored deliveries keep their recorded version |
| `secret` | string or null | Signing secret; null removes it when switching to Bearer authentication |
| `headers` | array of key/value objects | Replacement custom headers |
| `status` | string | One of the values below |

All update fields are optional.

| Status Value | Description |
|--------------|-------------|
| `active` | Webhook is enabled and will receive deliveries |
| `paused` | Webhook is temporarily disabled; no deliveries are sent |
| `failed` | Webhook has been marked as failed (can be set manually or by the system) |

<Aside>

## URL Safety Validation

Breeze validates webhook URLs at both creation time and delivery time to prevent SSRF (Server-Side Request Forgery) attacks.

**At creation and update time**, the API performs synchronous validation including DNS resolution. On hosted Breeze:

- URL must use HTTPS
- Hostname must not be `localhost`, `*.localhost`, or `*.local`
- IP addresses must not be private, loopback, or link-local (covers RFC 1918, RFC 6598, RFC 5737, and IPv6 equivalents)
- DNS resolution is performed to catch hostnames that resolve to blocked address ranges

**Self-hosted deployments** (`IS_HOSTED=false`) may point webhooks at private RFC 1918/ULA addresses on their own network — an on-prem SIEM or ticketing system, for example — and plain `http://` is permitted **only** when the target resolves to such a private address. Public destinations still require HTTPS, and cloud-metadata, loopback, and link-local addresses are blocked in every configuration.

**At delivery time**, the worker re-validates the URL before every delivery attempt. If the URL has become unsafe (e.g., DNS now resolves to a private IP), the delivery fails immediately without making an HTTP request.

| Method | Path | Description |
|--------|------|-------------|
| **GET** | `/webhooks` | List webhooks for the organization (paginated, filterable by `status` and `orgId`) |
| **POST** | `/webhooks` | Create a new webhook |
| **GET** | `/webhooks/:id` | Get webhook details including delivery statistics |
| **PATCH** | `/webhooks/:id` | Update webhook name, URL, secret, events, headers, status, or payload version |
| **DELETE** | `/webhooks/:id` | Delete a webhook and all its delivery records |
| **GET** | `/webhooks/:id/deliveries` | List delivery history (paginated, filterable by `status`) |
| **POST** | `/webhooks/:id/test` | Send a test delivery |
| **POST** | `/webhooks/:id/retry/:deliveryId` | Retry a failed delivery |

All webhook routes require authentication and are scoped to `organization`, `partner`, or `system` roles. They also require a permission:

- **Reading** (`GET /webhooks`, `GET /webhooks/:id`, `GET /webhooks/:id/deliveries`) requires `webhooks:read`. The AI assistant's `query_webhooks` tool requires the same permission.
- **Managing** (create, update, delete, test, retry) requires `organizations:write`.

`webhooks:read` is granted by default to Org Admin, Org Technician and Partner Technician; Partner Admin holds it through `*:*`. In the dashboard, a user without `webhooks:read` does not see the Webhooks tab under Integrations, and a user without `organizations:write` sees webhooks and their delivery history without the create, edit, delete, test, pause/resume or retry controls. See [Users & Roles](/reference/users-and-roles/#permission-model) to grant either permission to a role.

<Aside type="caution" title="Upgrading to v0.122.1: some roles lose webhook visibility">
  Before v0.122.1, `organizations:read` was enough to view webhooks. The upgrade grants `webhooks:read` to the built-in roles above and to every custom role that holds `organizations:write`, but not to viewer, billing or security-approver roles. **Partner Viewer** and **Partner Security Approver** no longer see webhooks, and a **custom role with `organizations:read` but not `organizations:write` loses access to webhooks and their delivery history until an administrator adds `webhooks:read` to it** under **Settings → Roles**. Self-hosters can find those roles in the upgrade log: the migration logs a `webhooks-read-permission:` warning with their count and up to 20 names.
</Aside>

## Troubleshooting

**"Invalid webhook URL" error when creating a webhook.**
On hosted Breeze, the URL must use HTTPS and must not resolve to a private, loopback, or link-local IP address (on self-hosted deployments, private RFC 1918/ULA targets are allowed — see [URL Safety Validation](#url-safety-validation)). Hostnames like `localhost`, `*.localhost`, and `*.local` are always blocked. If the hostname cannot be resolved via DNS, creation will fail.

**Webhook is not receiving events.**
Check the webhook status -- if it is `paused` or `failed`, deliveries are not processed. Verify that the `events` array includes the event types you expect. Use `POST /webhooks/:id/test` to confirm the endpoint is reachable.

**Deliveries remain in `scheduled` status.**
Check `nextAttemptAt`: retries wait 1 minute, 5 minutes, 30 minutes, 2 hours, 6 hours, then 12 hours, each with ±20% jitter. The recovery sweep re-drives deliveries more than 15 minutes overdue. After the seventh failed attempt the delivery becomes `failed`; use manual retry once the endpoint is repaired.

**Signature verification fails on my endpoint.**
Ensure you are computing the HMAC over the correct input: the raw `X-Breeze-Signature-Timestamp` header value, followed by a dot (`.`), followed by the raw request body. Use the `X-Breeze-Signature-Timestamp` header (not `X-Breeze-Timestamp`) as the timestamp component. The signature uses SHA-256 and is hex-encoded.

**"Unsafe webhook URL" error during delivery.**
The worker re-validates the URL before each delivery attempt. On hosted Breeze, if your DNS records have changed and the hostname now resolves to a private IP range, deliveries will fail — update the webhook URL to point to a publicly routable address. On self-hosted deployments, private targets are deliverable; only metadata/loopback/link-local resolutions fail.

**"Only failed deliveries can be retried" error.**
The manual retry endpoint (`POST /webhooks/:id/retry/:deliveryId`) only accepts deliveries with status `failed`. Deliveries that are `pending`, `scheduled`, `retrying`, or already `delivered` cannot be retried through this endpoint.

**"Organization context required" error.**
Webhook routes require an organization scope. If you are authenticated with a partner or system scope, pass the `orgId` query parameter (for list) or include it in the request body (for create) to specify which organization's webhooks you are managing.

**Response body is truncated.**
Webhook delivery response bodies are truncated to 1,000 characters to prevent excessive storage consumption. If you need the full response for debugging, check your endpoint's own logs.

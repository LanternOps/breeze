## Overview

The UniFi integration discovers your Ubiquiti network fleet -- gateways, switches, and access points -- across every customer site and reconciles it into Breeze's unified network view, so UniFi hardware appears alongside your agent-discovered assets instead of duplicating them. It is strictly read-only: Breeze never changes your UniFi configuration.

You configure it on the **UniFi** tab of the Integrations page: **Integrations → UniFi** (`/integrations#unifi`).

There are two ways to connect:

- **Cloud (Site Manager)** -- a single Ubiquiti Site Manager API key that covers your whole account. Breeze reaches every console through Ubiquiti's cloud, so there is nothing to install on site. You can optionally pair each console with an on-site Breeze agent for deeper per-port and per-client telemetry.
- **Self-hosted controller** -- no Ubiquiti cloud account at all. A Breeze agent that already has LAN access to your on-prem UniFi Network controller polls it directly over the local Network Integration API. The agent is the only path Breeze uses to reach the controller.

<Aside type="note">
  The UniFi Network integration is available to **partner accounts only**. Organization-scoped users who open the tab see a message that the integration is available to partner accounts, and no connection controls are shown.
</Aside>

## Connecting UniFi

On the not-yet-connected screen, choose a connection type -- **Cloud (Site Manager API key)** (the default) or **Self-hosted controller** -- then follow the matching walkthrough below.

<Tabs>
  <TabItem label="Cloud (Site Manager)">

  A single Site Manager API key covers your entire Ubiquiti account. Breeze validates the key before saving, then discovers every UniFi console and its sites.

  **Required credential**

  | Field | Required | Description |
  |---|---|---|
  | UniFi Site Manager API key | Yes | A read-only API key generated in your Ubiquiti account (UniFi Site Manager). Stored encrypted; never echoed back to the UI. |

  <Steps>

  1. Open **Integrations → UniFi** and keep **Cloud (Site Manager API key)** selected.

  2. Generate a **Site Manager API key** in your Ubiquiti account (UniFi Site Manager).

  3. Paste it into the **UniFi Site Manager API key** field and click **Connect to UniFi**. Breeze validates the key before saving -- a bad key is rejected with a clear message, and a UniFi outage is reported separately so a working key isn't wrongly blamed.

  4. In the **Site mapping** card, Breeze lists every UniFi site the key can see, next to the host that runs it. Mapping is manual: Breeze does not match UniFi sites to Breeze sites by name, so choose the matching **Breeze site** (grouped by organization) for each UniFi site, then click **Save mappings**. The organization is derived from the site you pick; unmapped UniFi sites are simply not synced. Use **Refresh** to re-pull the live host/site list from UniFi.

  5. Inventory syncs automatically about every half hour. Click **Sync now** to pull immediately, and review each run's created / updated / unchanged / removed counts in the **Sync history** table.

  </Steps>

  <Aside type="tip">
    The site list in the mapping card is a live call out to UniFi, so it can be slow or fail on a bad key or a UniFi outage. That card carries its own loading and error state and never blocks the rest of the panel.
  </Aside>

  **Which hosts and sites appear**

  - Breeze lists every Site Manager host that runs at least one UniFi Network site. That covers UniFi OS consoles (such as a UniFi gateway) and self-hosted **UniFi Network Application** servers on Windows, Linux, or a VPS, which Site Manager reports as `network-server` hosts.
  - A host with no UniFi Network site is left out, because there is nothing on it to map.
  - A site whose host is missing from Site Manager's host list is shown under **Unknown console** so you can still map it.
  - Breeze reads the full host and site lists page by page, so accounts with hundreds of sites are listed in full.

  **Device inventory needs a single-site host.** Site Manager reports devices per host, not per site. Breeze syncs a mapped site's devices only when its host runs that one UniFi site. For a host that runs several sites, such as a self-hosted Network Application that serves several customers, Breeze still syncs each mapped site's WAN health but not its devices, so one customer's devices are never filed under another. The sync run shows **partial** and names the host. To inventory devices site by site on such a controller, use a **Self-hosted controller** connection, whose agent reads devices per site. A partner has one UniFi connection, so switching replaces the cloud connection.

  <Aside type="caution">
    The API key sees only what the Ubiquiti account that created it can see: the consoles that account owns or administers. If a site is missing from the mapping card, check that the same account can see it in UniFi Site Manager, or create the key from an account that owns or administers every console. Ubiquiti returns device inventory only for consoles where that account is an owner or super admin.
  </Aside>

  </TabItem>
  <TabItem label="Self-hosted controller">

  In self-hosted mode there is no Site Manager API key anywhere. A Breeze agent on the controller's LAN polls it directly over the read-only local **Network Integration API** (controller firmware **9.3 or newer**).

  **Required fields when registering a controller**

  | Field | Required | Description |
  |---|---|---|
  | Controller URL | Yes | The controller's local address, for example `https://192.168.1.1`. |
  | Site this controller serves | Yes | The Breeze site (grouped by organization) the controller primarily serves. |
  | Collector agent | Yes | An enrolled Breeze agent at that site that can reach the controller over the LAN. |
  | Local API key | Yes | The controller's local Network Integration API key. Stored encrypted and pushed to the chosen agent. |

  <Steps>

  1. Open **Integrations → UniFi**, choose **Self-hosted controller**, optionally give it an **account label** (for example, "Acme HQ controllers"), and click **Connect**. This just creates the self-hosted integration -- there is nothing to validate yet, since no controller has been registered.

  2. In the **Controllers** card, register each controller: enter the **Controller URL**, pick the **Site this controller serves**, choose a **collector agent** (only agents at the selected site are offered), enter the controller's **local API key**, and click **Register controller**.

  3. Once the assigned agent reaches the controller (within about a minute), the controller's own local sites are discovered automatically and appear in the **Site mapping** card. Map each discovered controller site to whichever **Breeze site** it corresponds to, then click **Save mappings**. Use **Refresh** to re-check for newly discovered sites.

  4. Devices and clients polled from each mapped site are reconciled into that site's discovered assets, using the same telemetry pipeline as agent-collected deep telemetry.

  </Steps>

  <Aside type="note">
    Sites are mapped individually rather than per controller, so **one self-hosted controller can feed many UniFi sites across several different Breeze organizations**. In this mode the collector agent isn't optional -- it is the only way Breeze reaches your controller. If the assigned agent goes offline, polling for that controller stops until it reconnects or you point the registration at a different agent.
  </Aside>

  </TabItem>
</Tabs>

## Deep telemetry (cloud connections)

A cloud Site Manager key is deliberately shallow -- it can't see per-port PoE, throughput, or the clients attached to each device. To get that depth on a cloud connection, designate a Breeze agent already running at the site as a **collector** for a given console.

<Steps>

1. In the **Deep telemetry collectors** card, for each console set the **Breeze site** it serves, a **collector agent** (only online agents at that site can be selected), the **Controller URL** (for example `https://192.168.1.1`), and the console's **local Network Integration API key**.

2. Click **Enable deep telemetry**. Breeze encrypts the local key, pushes the configuration to the chosen agent, and the agent begins polling on schedule (about once a minute). To change an existing collector, edit the fields and click **Update collector** -- leave the key blank to keep the stored one.

3. Open the **Deep telemetry** card and select a site to view its device table (PoE ports up/total and total watts, client counts) and its connected-clients table.

</Steps>

Each collector shows a status badge reflecting reachability: `pending`, `connected`, `unreachable`, `error`, or `firmware_too_old`. The local Network Integration API requires controller firmware **9.3 or newer**, and deep telemetry requires an agent build that includes the UniFi collector -- promote your fleet to a current agent version before relying on it.

<Aside>
  Self-hosted controllers use this same telemetry pipeline: once a controller is registered and its sites are mapped, its devices and clients are collected with the same per-port PoE, throughput, uptime, and connected-client detail.
</Aside>

## Wi-Fi monitoring

For access points, the **Deep telemetry** card shows per-AP Wi-Fi detail next to the existing device table. It is available on cloud connections with a collector and on self-hosted controllers, because both use the same agent collector.

**What appears for each access point**

- Online or offline state, the raw controller state, and uptime.
- **Wireless clients** -- the number of clients currently attached to the AP over Wi-Fi. Wired, VPN, and other client types are not counted. This is not a per-radio count.
- One line per radio: band (2.4, 5, or 6 GHz), **Channel**, **Width**, **WLAN standard**, and **TX retries**.
- CPU and memory use.
- **Uplink RX** and **Uplink TX** rates.

**Freshness**

- Breeze does not poll every AP on every cycle. Wi-Fi statistics use a limited, rotating request budget, so each AP is refreshed in turn and its values can lag behind the latest poll. When an AP's values are older than the current poll, the card shows **As of** with the time they were last refreshed.
- If an AP is **Offline** but the controller still reports a non-zero uplink rate, the card labels the rate **Last reported / stale** with its timestamp. Treat it as the last value seen, not current traffic.
- A value shown as `—` was not measured, was unsupported, or was not collected in the current rotation. A value shown as `0` was measured and is zero. For example, `0%` TX retries means the controller reported no retries.

**How it is collected**

- The agent polls the local UniFi controller.
- Only access points receive statistics collection. Switches and gateways keep their existing telemetry.
- This feature shows measured facts only. It does not raise AP alerts, keep radio history, or add a customer-facing Wi-Fi view, and it does not change the existing UniFi data.

<Aside type="caution">
  **Upgrade order.** Update the Breeze API first, then the agents. Wi-Fi collection needs agent **v0.125.0 or later**. An agent only sends Wi-Fi data when the API tells it that it is accepted for that collector, so an older agent keeps working and simply sends no Wi-Fi detail.
</Aside>

**Rollback.** Wi-Fi collection is gated by the topology feature flag `interfaceHealth`, shown as **Interface health** in the partner **Modules** settings. Turning it off makes the API stop accepting Wi-Fi data from agents; they fall back to the previous payload and the existing UniFi telemetry is unchanged. The same flag also controls SNMP interface health on topology links, so turning it off affects both.

## What Breeze pulls from UniFi

| Data | Source | Detail |
|---|---|---|
| **Consoles / hosts and sites** | Cloud or agent discovery | Each UniFi host (a UniFi OS console or a self-hosted UniFi Network Application server) and the sites within it, so you can map them to Breeze sites. |
| **Device inventory** | Cloud sync | Model, MAC, device type, firmware version and whether an upgrade is available, uptime, and adoption state. On a cloud connection, only for sites whose host runs a single UniFi site. |
| **WAN / ISP health** | Cloud sync | The latest WAN/ISP health per mapped site. |
| **Per-device deep telemetry** | Collector agent | Device health (uptime, client count) and per-port PoE detail -- power draw, link speed, mode, and up/down state. |
| **Connected clients** | Collector agent | Hostname, IP, MAC, which AP or switch they're attached to, wired vs Wi-Fi (and SSID), and signal strength. |

UniFi devices and connected clients flow into Breeze's discovered-assets view, matched by MAC (then IP), enriching existing assets rather than creating duplicates.

<Aside>
  This layer is strictly read-only. Restart, PoE-cycle, and client-block actions are not part of the integration.
</Aside>

## Connection status and sync history

Once connected, the panel shows the account label, last sync time, and last sync status, with a status badge on the header (**Active**, **Sync error**, or **Reconnect required**). If the stored key becomes invalid, UniFi enters a **reauth required** state with a prominent banner and a **Reconnect** action; a failed sync surfaces the backend's error message rather than failing silently.

On **cloud** connections, the **Sync history** table lists the most recent sync runs (newest first) with each run's trigger, status (`success`, `partial`, `failed`, or a transient `running`), hosts seen, and devices created / updated / unchanged / removed.

<Aside type="caution">
  Connecting, mapping sites, registering controllers, and managing collectors are sensitive partner actions. Use **Disconnect** to remove the integration; on a reauth-required connection, disconnecting is also how you clear the stale key before reconnecting.
</Aside>

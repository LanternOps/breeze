Breeze includes a built-in AI assistant powered by the Claude Agent SDK that can query your fleet, diagnose device issues, and take action on your behalf. The assistant runs as a managed agent with a query loop — it receives your question, plans a sequence of tool calls, executes them against live fleet data, and returns a synthesized answer. All tool executions are governed by a tiered approval system with full audit logging and per-tool rate limits.

Six capabilities extend and govern this system:

- **AI Risk Engine** — governance dashboard for controlling and auditing AI-assisted operations
- **Fleet Orchestration Brain** — command center for fleet-scale AI-driven management
- **AI Device Context Memory** — persistent per-device memory that the AI carries across conversations
- **Helper AI Chat** — end-user-facing AI assistant in the Breeze Helper tray app
- **AI Cost Tracking** — per-session and per-organisation usage and cost monitoring
- **AI Input Sanitization** — guardrails that validate and sanitize all AI inputs before execution

## AI Risk Engine

The AI Risk Engine categorises every AI tool into one of four tiers that control how it executes. Navigate to it via **Security → AI Risk** in the sidebar.

### AI-authored scripts

You can also extend the assistant with your own tools: point Breeze at an MCP server you run and its tools appear alongside these, with the same tiers and approvals — see [Tool Sources](/features/tool-sources/).

The assistant and background agents can author a script mid-conversation, have it independently reviewed, and run it once you approve — see [AI Script Authoring & Review](/features/ai-script-authoring/) for the full walkthrough. The AI Risk Dashboard's **Script Proposals** panel tracks proposals per day, unattended runs, and how often a human's decision disagrees with the independent reviewer's recommendation.

### Tool tiers

| Tier | Execution | Examples |
|---|---|---|
| **Tier 1** | Auto-execute (read-only, no approval) | `query_devices`, `analyze_metrics`, `get_security_posture`, `get_active_users`, `disk_cleanup` (preview), `system_cleanup` (status), `propose_action_plan`, `list_configuration_policies`, `get_effective_configuration`, `preview_configuration_change`, `get_configuration_policy`, `configuration_policy_compliance`, `get_service_monitoring_status`, `query_monitors`, `manage_monitors` (get/create/update/delete), `query_backups`, `get_backup_status`, `browse_snapshots`, `get_incident_timeline`, `generate_incident_report`, `list_playbooks`, `get_playbook_history`, `get_vulnerability_report`, `find_proven_fixes`, `get_device_vulnerabilities`, `search_documentation`, `propose_script`, `get_script_proposal` |
| **Tier 2** | Auto-execute + audit logged | `manage_alerts` (acknowledge/resolve), `manage_services` (list), `manage_processes` (list), `manage_scheduled_tasks` (list), `system_cleanup` (list), `analyze_disk_usage` (refresh), `analyze_boot_performance` (triggerCollection), `set_device_context`, `resolve_device_context`, `apply_configuration_policy`, `remove_configuration_policy_assignment`, `manage_configuration_policy` (activate/deactivate), `create_incident`, `collect_evidence`, `file_operations` (list), `execute_command` (list_processes/file_list/event_logs_list) |
| **Tier 3** | Requires human approval before execution | `execute_command` (kill_process/start_service/stop_service/restart_service/file_read/list_services/event_logs_query), `run_script`, `disk_cleanup` (execute), `system_cleanup` (run), `network_discovery`, `security_scan` (quarantine/remove/restore), `file_operations` (read/write/delete/mkdir/rename), `manage_configuration_policy` (create/update/delete), `manage_processes` (kill), `trigger_backup`, `restore_snapshot`, `execute_containment`, `execute_playbook`, `remediate_vulnerability`, `manage_ai_agents` (authorize_supervised_key) |
| **Tier 4** | Blocked — never executed | Cross-org operations |

`manage_monitors` supports `get` only. Its retired `create`, `update`, and `delete` actions return guidance without approval or write permission. Author network checks with `manage_monitor_definitions` using kind `network_check`; retire unconverted checks through the conversion ledger to preserve history.

<Aside>
  Tier classification is action-level, not tool-level. For example, `disk_cleanup` is Tier 1 when previewing and Tier 3 when executing. `system_cleanup` follows the same split — reading a run's status is Tier 1, listing the OS-native cleaners a device offers asks the device live and is Tier 2, running them is Tier 3; `analyze_disk_usage` and `analyze_boot_performance` read stored data at Tier 1, and only a fresh scan (`refresh`) or collection (`triggerCollection`) from the device is Tier 2; `manage_alerts` is Tier 1 for list/get and Tier 2 for acknowledge/resolve. `execute_command` resolves per `commandType`: `list_processes`, `file_list`, and `event_logs_list` are Tier 2; `list_services` and `event_logs_query` stay Tier 3 despite being reads, because they can return unredacted credential- or PII-bearing content (service binary paths, raw event-log messages); mutating types and `file_read` are Tier 3 too. The AI resolves the tier for each specific action at runtime. Within Tier 2, strictly read-only entries — the `execute_command` types above, `file_operations` (list), `manage_services` (list), `manage_processes` (list), `manage_scheduled_tasks` (list), `system_cleanup` (list), a fresh `analyze_disk_usage` or `analyze_boot_performance` read, and the single-purpose get/list/search catalog, contract, invoice, and quote tools — auto-execute (with the audit-trail entry) under **every** approval mode, including the default per-step mode. Tier-2 *mutations* still take a lightweight inline confirmation under per-step approval, and a paused session always confirms everything Tier 2 and above.
</Aside>

<Aside type="note">
  When a partner-scoped agent lists configuration policies (`list_configuration_policies`), the results now include **partner-wide ("All orgs") policies** — those that belong to the partner rather than a single organization — alongside org-owned ones. Previously partner-wide policies were invisible to the AI, so a policy defined once for every customer wouldn't show up in a fleet-wide question; it now appears as expected.
</Aside>

### Approval workflow

When the AI proposes a Tier 3 action, it enters a **pending** state and waits for human approval. Tier 3 actions fall into one of two approval scopes:

- **Supervised** (the default) — the technician who asked for the action approves it themselves, directly in chat. The model here is that the AI is the actor and *you* are the approver: routine device work you could do by hand should not need a second person.
- **Four-eyes** (a fixed high-stakes list) — a **second** person must approve. Reviewing a proposed high-stakes action and authorising it are kept as separate responsibilities.

#### Supervised actions — approve in chat

Routine device work is supervised: running commands and scripts, file and registry operations, starting/stopping services, killing processes, installing patches, disk cleanup, agent upgrades, triggering backups, and policy, deployment, monitor, group, and automation changes.

The chat approval card offers a plain **Approve** / **Deny**. Approving is gated on your **own** permissions for the underlying action — if your role lets you do the operation by hand, you can approve the AI doing it; no second person is involved. The request is still stored durably and the execution is written to the audit trail, marked as a self-approval. A supervised request raised in chat waits for your decision for the [approval timeout](#approval-timeout) — 5 minutes unless your partner or organization has changed it.

<Aside type="note">
  If your partner enforces an authentication-assurance floor, approving a supervised action prompts the corresponding step-up verification (for example Touch ID / Windows Hello) instead of accepting a plain click.
</Aside>

#### Four-eyes actions — a second person approves

A small, fixed set of actions always requires a different user to approve:

- **Financial or externally binding** — issuing invoices, recording or voiding payments, activating or cancelling contracts, sending quotes
- **Tenant shape** — creating organizations, changing an organization's status, moving tickets between organizations
- **Identity and account control** (Microsoft 365 / Google Workspace) — password and 2FA resets, mail forwarding and delegates, mailbox permissions, disabling or offboarding users, device wipe
- **Restores and rollbacks** — VM checkpoint delete/apply, restore-as-VM and DR plan runs, patch rollback, snapshot and database restores
- **Computer control** and unattended remote session creation
- **Releasing security containment** — un-isolating a device, rolling back threats. (Isolating or quarantining stays supervised — urgent protective containment should not wait on a colleague.)
- **AI agent governance** — granting an agent a pre-authorized action key, so its future runs may take that action unattended

To decide a pending four-eyes request:

<Steps>

1. Open **Security → AI Risk**.

2. Click **Approval History**.

3. Find the pending request and review the action details.

4. Click **Approve** to allow execution, or **Reject** to cancel it.

</Steps>

Approved actions execute immediately. Rejected actions are logged and the AI is notified. A four-eyes request raised in chat stays open for **60 minutes**. The chat turn itself only waits for the [approval timeout](#approval-timeout); an approval that arrives after the chat turn has moved on still executes, and the session shows the result when you return to it.

If what the request refers to changes while it waits — the script is edited, the quote or invoice is revised, the organization's state moves on — the approved action does **not** run against the drifted content. It fails with a content-changed error instead, and the AI has to raise a fresh request.

#### Approval timeout

A chat turn that is waiting on an approval is held open, so the wait is bounded. The **approval timeout** is how long the chat waits for someone to approve a gated action before it gives up:

- **Default:** 5 minutes. **Range:** 5 to 60 minutes.
- **Partner default:** **Settings → Partner → AI Approval Timeout**. Applies to every organization that has not set its own value.
- **Organization override:** **Settings → Organization → AI**. Choose a value to override the partner default, or **Inherit** to follow it. The organization's value always wins. The selector shows the inherited value and where it comes from.
- A change applies from the next chat message. It does not change a wait that is already in progress.

**A timeout never approves anything.** When the timeout elapses with no decision:

- A **Tier 2** inline confirmation is rejected. The AI is told, and nothing runs.
- A **supervised** Tier 3 request stops waiting and expires at the same moment. It never runs. To proceed, ask the AI again.
- A **four-eyes** request stops holding the chat, but it stays open for its full 60 minutes. If a second person approves it in that time, it still runs.

The timeout is for interactive chat only. It deliberately stops at 60 minutes. Work that must wait longer, such as scheduled or overnight AI agent runs, goes through the durable approvals queue (**Security → AI Risk → Approval History** and the mobile app), where a request stays open for 24 hours.

#### Approving your own request when you are the only approver

If the technician who asked for a four-eyes action is also the **only** user eligible to approve it (a sole-operator setup), the chat's approval card offers **Verify & Approve** directly inline. Clicking it runs a **Touch ID / Windows Hello** (WebAuthn platform authenticator) verification in the browser, and that verification — not the click — is what satisfies the assurance requirement for approving your own request. Cancel the prompt and nothing is approved.

When other users are eligible to approve, the inline button does not appear: someone else must approve from **Approval History** or the mobile app. That four-eyes separation is deliberate. Disabled and invited (not-yet-accepted) users do not count as eligible approvers, so a team whose only other admin account is disabled behaves as a sole-operator setup.

#### Who can approve

Opening the assistant at all requires the **`ai_sessions:use`** permission, granted by default to Org Admin, Org Technician and Partner Technician (Partner Admin holds it through its full-access role). Roles without it do not see the assistant button, the **AI Assistant** sidebar entry, or the full-page AI Workspace at `/workspace`. The permission opens the conversation only — each tool the assistant calls is checked against the same permission the equivalent page or API route requires.

Approving or rejecting a **four-eyes** action requires the **`approvals:decide`** permission. It is granted by default to **Org Admin** (and to Partner Admin through its full-access role) and is deliberately **not** granted to Org Technician or Org Viewer. Approving a **supervised** action needs no extra permission — only the requester's own permission for the underlying action, which was already checked when the AI proposed it.

To let another role approve four-eyes actions, add `approvals:decide` to it under **Settings → Users & Roles**. See [Users and Roles](/reference/users-and-roles/).

<Aside type="note">
  If an organization has no user whose role grants `approvals:decide`, a four-eyes request has nobody who can act on it and is automatically cancelled rather than left pending indefinitely.
</Aside>

#### Pending approvals survive a restart

Tier 3 requests raised from AI chat or the MCP server are stored durably, so a pending approval is no longer tied to the session that created it. If the server restarts — or you simply close the browser and come back later — the request is still waiting in **Approval History**, and approving it there executes the action.

This also means an approved identity action against a connected Google Workspace or Microsoft 365 tenant (for example a password reset, sign-out, or user disable) runs against that organization's connection without needing the original chat session to still be open. Microsoft 365 write actions additionally require the Graph-actions executor to be enabled — see [Customer Microsoft 365 Graph-actions (write) executor](/deploy/environment/#customer-microsoft-365-graph-actions-write-executor-optional).

When an approved Microsoft 365 **password reset** executes this way, the requesting technician retrieves the temporary password afterwards with a one-time **Reveal temporary password** action in **Approval History** — see [Identity Console → Retrieving a reset password](/features/identity-console/#retrieving-a-microsoft-365-reset-password).

### Rate limits

Many tools have a per-tool sliding window rate limit. Requests that exceed the limit are rejected and logged in the **Rejection & Denial Log**. Read-only or lower-risk tools not listed here (for example `get_user_experience_metrics`, `query_backups`, `get_backup_status`, `browse_snapshots`, `create_incident`, `get_incident_timeline`, `generate_incident_report`, and `list_playbooks`) currently have no rate limit.

| Tool | Limit | Window |
|---|---|---|
| `execute_command` | 10 requests | 5 min |
| `run_script` | 5 requests | 5 min |
| `disk_cleanup` | 3 requests | 10 min |
| `system_cleanup` | 30 requests | 60 min |
| `network_discovery` | 2 requests | 10 min |
| `security_scan` | 3 requests | 10 min |
| `file_operations` | 20 requests | 5 min |
| `manage_services` | 10 requests | 5 min |
| `analyze_disk_usage` | 10 requests | 5 min |
| `manage_configuration_policy` | 20 requests | 5 min |
| `manage_processes` | 15 requests | 5 min |
| `query_monitors` | 30 requests | 5 min |
| `manage_monitors` | 10 requests | 5 min |
| `get_service_monitoring_status` | 30 requests | 5 min |
| `trigger_backup` | 5 requests | 10 min |
| `restore_snapshot` | 3 requests | 10 min |
| `execute_containment` | 5 requests | 10 min |
| `collect_evidence` | 10 requests | 5 min |
| `execute_playbook` | 5 requests | 10 min |

The limits above are the shipped defaults. The counter is kept per user and per tool, across every organisation that user works in.

#### Raising the per-tool limits

A self-hosted or smaller model usually retries and re-plans more than Claude does, so it reaches these limits sooner. To give it more room, set **Per-tool rate limit multiplier** in the AI budget settings. It takes a whole number from 1 to 10, and the default is 1.

Every per-tool limit becomes `ceil(limit × multiplier)`. At a multiplier of 3, for example, `run_script` allows 15 requests per 5 minutes instead of 5. The window stays the same. The multiplier applies to the built-in assistant and to the [MCP Server](/features/mcp-server/#per-tool-rate-limits).

- The multiplier can only raise a limit. It never lowers or removes one. The API rejects a value outside 1–10, and a stored value that is out of range is treated as 1.
- You set it in the same two places as the other budget fields (see [Configuring thresholds](#configuring-thresholds)): **Org settings → AI** for one organisation, or the **AI Budgets** tab of Partner Settings for every organisation under the partner. A partner value overrides the organisation value and locks the field.
- The organisation of the current call selects the multiplier: the chat session's organisation, or the MCP API key's organisation. A partner-scoped MCP caller that has no organisation uses the partner's value. Because the counter is shared across organisations, a user who works in two organisations with different multipliers is checked against the limit of the organisation they are working in now.
- **AI Risk → Rate Limits** shows the limits that are in effect for the selected organisation, with the multiplier applied, and shows the default next to each limit that was raised.

### Action Plans

The AI can propose multi-step action plans for complex operations that require human review before execution. When the AI invokes `propose_action_plan`, it creates a structured plan with pre-flight checks for each step. Plans operate in two modes:

| Mode | Description |
|------|-------------|
| `action_plan` | A sequence of concrete steps to be executed after approval |
| `hybrid_plan` | A mix of informational analysis and executable steps |

Action plans are subject to the same approval workflow as Tier 3 tools — the plan must be approved before any steps execute.

## AI attribution on the device page

Scripts and commands that an AI assistant or an autonomous AI agent dispatches to a
device are now recorded as such. Each `script_executions` and `device_commands` row
carries who *decided* the work — `ai_assistant` (a person asked, in chat or over MCP)
or `ai_agent` (an autonomous agent run decided, with no human in the loop) — plus the
conversation or agent run it came from, and an `ai.command.executed` / `ai.script.executed`
audit event is written alongside the dispatch.

This answers a question the audit trail could not answer before: *who decided to do
this to my machine*. It is deliberately separate from three other facts the row already
carried — who **wrote** the script (authorship), what **scheduled** the run
(`trigger_type`), and who the request **authenticated as** (the principal). An AI can
start a policy-driven run, and a person can hand-run an AI-authored script, so
collapsing them would destroy information.

<Aside type="caution" title="What is not yet attributed">
Work an AI **schedules** rather than dispatches — patch jobs, software deployments,
automation runs, playbook executions, elevation requests and backups — is still recorded
without an AI marker, because the device command is issued later by a background worker
that runs under its own context. SentinelOne isolation and threat actions are performed
through the vendor's API and never create a Breeze command, so they are unmarked too.
</Aside>

<Aside type="caution" title="Rows created before this release are unmarked">
An unmarked row means *AI initiation was not recorded* — **never** *a human did this*.
There is no backfill: every AI-run library script that already exists was stamped with
the invoker's user id and a `manual` trigger, so historical AI work is indistinguishable
from human work. The UI renders an unmarked row as the absence of a marker, not as a
"human" badge.
</Aside>

<Aside type="caution" title="Best effort, not a guarantee">
The AI marker on the audit event is written alongside the dispatch on a fire-and-forget
path, so a dispatch that already succeeded is never failed by a lost audit write. A
dropped write leaves a real action unmarked; it never marks a human action as AI.
The columns on the command and execution rows themselves are written in the same
statement as the row, so they are not subject to this.
</Aside>

### Tenant boundaries

The origin pointers are severed whenever the row could otherwise reach across tenants:

- **Device moved to another organisation** — the execution follows the device, but its
  session and agent-run pointers are nulled (agent-run history stays with the source
  organisation). The `ai_initiator_kind` marker is kept: the fact that an AI did the work
  survives the move, the cross-tenant pointer does not.
- **Organisation merge** — the execution is re-tenanted to the surviving organisation
  with the same detach, because the originating agent run stays with the merged-away shell.
- **Erasure** — deleting an AI session nulls the pointer on any surviving execution while
  leaving the marker intact.

All three columns are included in the tenant data export, so a customer asking "who did
this to my machine" gets the answer in the one artifact designed to hold it.

## Suggested fixes and fix memory

On an alert or anomaly, **Suggested Fixes** lists things a technician could do about it. The panel groups suggestions as **Proven fixes** (fixes your fleet has already seen work), **AI suggestions** (from the built-in research agent), **Similar fixes**, and a collapsed **Earlier keyword matches** group. AI suggestions carry an **AI researched** badge. The feature is controlled by the `ml.remediation_suggestions.enabled` flag (see [ML Insights](/features/ml-insights/)); research also needs AI credits (or the organization's AI budget) to be available, and a manual request needs the `ai_sessions:use` permission.

### Generate and Research deeper

- **Generate** attaches proven fix memory first: a fix that worked for the same kind of problem on the same operating system is suggested straight away with its track record. It then also starts a **quick** research run, whether or not a proven fix exists, provided you have `ai_sessions:use`. Without that permission the panel tells you so.
- **Research deeper** starts a **deep** research run for the same alert or anomaly. It gets a larger turn and budget ceiling than a quick run, and is meant for when the first answer was not enough.

Every attempt ends in an explicit state on the panel, never a silent blank: researching; "AI found no safe fix for this problem"; research failed, with a **Retry** button; still researching after about five minutes ("check back", with **Refresh**); busy, when concurrency or rate limits are reached; no permission; or one of the other reasons a run could not start, such as the feature being off for the organization, AI credits being used up, or the alert having no single device. Asking again while a run is active shows that run instead of starting a second one.

**Research never runs anything.** The research agent is read-only: it can look at device details, logs, your script and playbook catalog and proven fixes, and it submits suggestions. It cannot execute, change or draft a script on its own. A technician always chooses what to accept and run.

### What a suggestion can be

| Kind | What it is |
|---|---|
| Catalog script or playbook | One from your own catalog that runs on the device's operating system. Anything else the agent names is dropped by the server. |
| Built-in action | One of `reboot`, `restart_service`, `kill_process` or `disk_cleanup`, with typed parameters (a service name, a process name, or cleanup action IDs). |
| Manual steps | A short list of steps for a person to follow. |
| Script draft request | A brief for a script that does not exist yet. |

**Built-in actions and approval.** Running a built-in action needs `devices:execute` in addition to `scripts:execute`. Each action has a minimum risk level the server enforces regardless of what the agent proposed: `reboot` is always high risk, so it always goes through approval before it runs; `restart_service` and `kill_process` are at least medium; `disk_cleanup` is low. `kill_process` resolves the process by name when you run it and refuses if none or more than one process matches.

**Draft a script.** On a script draft request, **Draft a script** opens the script builder with the brief and language pre-filled (it needs `scripts:write`). If the hand-off cannot be stashed in your browser, the brief is copied to the clipboard as a prompt instead. Nothing is sent or saved until you do it yourself.

### Written by AI and reviewed steps

Manual steps written by the research agent are labelled **Written by AI — review before following**, and that label stays on the suggestion. After checking the steps, a user with `scripts:write` and partner-wide management rights can use **Save as reviewed steps** to keep a reusable copy for an operating system. When a technician later marks a manual-steps suggestion **Done**, a picker offers the reviewed steps (or "Steps as written (not shared)"). The choice is recorded with the outcome, and once verified outcomes accumulate the fix appears as a proven fix labelled with the reviewed title, visible to your organizations' users. The research agent does not read reviewed steps; it only sees that a proven manual-steps fix exists and its track record.

### The Fix memory page

**Fix memory** (in the AI Agents section of the navigation) has two tabs. **Fixes** lists what Breeze has learned from observed outcomes, each with its condition, operating system, kind, scope (this client or all clients), status (including Demoted and Stale) and track record. **Reviewed steps** lists the saved reviewed steps and lets you retire them. Only counts are shared across clients, never another client's details. Retire an entry to stop it being suggested. Retiring a fix on the **Fixes** tab needs the AI agents write permission and MFA, and retiring an all-clients fix also needs partner-wide management rights. Saving reviewed steps, and retiring a saved entry on the **Reviewed steps** tab, each need partner-level access, `scripts:write`, partner-wide management rights and MFA.

### The "Fix research (built-in)" agent

- **Provisioned for you.** Each partner gets one built-in agent, named "Fix research (built-in)", created the first time research is requested. It cannot be created by hand at partner level.
- **Only a few things are editable.** You can enable or disable it, rename it and adjust its research caps. Its instructions, tools and mode are fixed.
- **Default ceilings.** A quick run is limited to 4 turns and 5 cents; a deep run to 10 turns and 25 cents. These are configurable ceilings, not typical costs. There are also per-hour and concurrency limits.
- **Organization override.** An organization can have its own override of the agent, for example to disable it or set tighter caps for that client. The override carries only those same editable settings.
- **Automatic research.** For **high** and **critical** alerts that have no proven fix, research starts on its own, once per alert and depth, and is capped per organization per hour (6 by default). Medium and low alerts are only researched when a technician asks.
- **Credits.** Research runs are billed like other AI agent runs. If credits are exhausted, runs are refused and the panel says why.

## AI Device Context Memory

The AI can remember device-specific facts across conversations. When you ask the AI about a device, it automatically loads that device's context entries and incorporates them into its analysis — so it won't re-alert on known quirks or forget about open follow-ups.

### Context types

| Type | Purpose | Example |
|---|---|---|
| `issue` | Known problems to track | "Recurring BSOD on boot since Jan 2026" |
| `quirk` | Normal but unusual behaviour | "Slow startup is expected due to a legacy driver" |
| `followup` | Pending actions | "Check disk health after replacement on 2026-03-01" |
| `preference` | User or device preferences | "Maintenance window: Sundays 2 AM–4 AM only" |

### Managing context

Context is managed through the AI assistant — there is no separate UI. Ask naturally:

- _"Remember that this device has a recurring BSOD issue."_
- _"Mark the disk check follow-up as resolved."_
- _"What do you know about HOSTNAME?"_

Context entries can have an **expiry date**, which is useful for time-bound follow-ups. Expired entries are excluded from future queries but are not deleted.

The AI uses three tools internally to manage context:

| Tool | Tier | Description |
|---|---|---|
| `get_device_context` | Tier 1 | Load context entries for a device |
| `set_device_context` | Tier 2 | Create a new context entry |
| `resolve_device_context` | Tier 2 | Mark an existing entry as resolved |

<Aside>
  Context is scoped to your organisation. Entries created by one user are visible to all users in the same organisation when they ask the AI about the same device.
</Aside>

<Aside type="note">
  Direct REST endpoints for device context are not yet available. Context is currently managed exclusively through the AI assistant.
</Aside>

## AI Cost Tracking

Every AI session tracks token usage and estimated cost. The `aiCostTracker` service records input tokens, output tokens, and total cost per session, per user, and per organisation.

### Viewing costs

Navigate to **Settings → AI Usage** to view:

| Metric | Description |
|---|---|
| Total sessions | Number of AI conversations |
| Total tokens | Combined input + output tokens consumed |
| Estimated cost | Dollar cost based on Claude API pricing |
| Per-user breakdown | Token usage grouped by user |
| Per-session detail | Individual session cost and token counts |

Cost data is stored alongside the conversation history.

### Model quality

The **AI usage by model** card has two views. **Spend** shows cost, tokens and refusals by the model that served each call. **Quality** shows how conversations went, grouped by model, feature, or model family:

| Column | What it counts |
|---|---|
| Conversations | Chat sessions and agent runs whose last model call in the period was on that row |
| Cost / conversation | Average spend on that row for each conversation that used it |
| Refusal rate | Calls the model declined, per call |
| Failover rate | Calls that moved to a backup model because this one failed or was unavailable |
| Flag rate | Sessions a person flagged. Automatic flags after a tool error are listed separately |
| Left for another model | Conversations that switched model, or continued in a new session on another model |
| Turns to resolve | Median messages a technician sent in sessions that finished without a person's flag or a move to a new session |
| Agent runs completed | Agent runs that completed, out of runs that finished |

A call served by a refusal fallback or a backup model counts toward the model that was **chosen**, so a model that often needs its fallback shows it. A conversation counts toward the model it last used, and a switch counts toward the model it left. A session counts as finished when it is closed, expired, or idle for 24 hours.

Breeze has no explicit "this was solved" signal, so **Turns to resolve** is an estimate. Compare rows with many conversations; rows with fewer than 20 are marked. Columns that need data this server does not record yet show "—".

### Billing credit integration

When a billing service is configured (`BILLING_SERVICE_URL` and `BILLING_SERVICE_API_KEY`), AI sessions check the organization's credit balance before starting. If credits are exhausted, the user sees a message to purchase more credits. After each chat turn, that turn's estimated cost is deducted from the balance. Each turn is charged only for its own usage (v0.120.0+; earlier releases charged some chat turns the running total of the conversation so far).

When billing is not configured, AI usage is unlimited — cost tracking still records usage for visibility, but no spending limits are enforced.

**Credits remaining.** A partner-scoped login sees a **Breeze AI credits remaining** tile at the top of the AI Usage page, and the same figure follows the AI cost indicator elsewhere in the app — so you find out you are running low while you can still do something about it, not when a session refuses to start. The tile breaks the balance into what came with your plan and what you have bought on top. It is absent when you are signed in to a single organization rather than the partner, when the organization bills for its own AI usage, when no billing service is configured, or when the balance could not be fetched. An absent tile never means zero credits.

<Aside type="tip">
  Cost tracking is automatic — no configuration required. It works for both the main AI assistant and the Helper AI chat. Billing credit enforcement is optional and requires the billing service environment variables. See [Environment Variables](/deploy/environment/) for details.
</Aside>

### Budget alerts

Independent of hard budget enforcement, an organisation can get warned as its AI spend approaches its cap. Each period (daily and monthly) is checked against a ladder of percentage thresholds, and once spend crosses a rung, an alert fires for that rung.

Alerts only fire for an organisation that has AI enabled and a daily or monthly cap set. With no cap there is nothing to measure a percentage against, so no rung can be crossed.

The default ladder is 50%, 80%, and 95% of the configured budget. On top of the ladder, a 100% "cap reached" alert always fires when the budget is exhausted, even if the ladder is empty or disabled, since that alert cannot be turned off. Each rung fires once per period; the ladder resets automatically when the daily or monthly period rolls over.

Alerts are delivered to active users with the `billing:manage` permission, whether they belong to the organisation directly or are partner users whose access covers that organisation. Delivery has two channels:

- Monthly rungs and the 100% cap-reached alert are delivered both in-app and by email.
- Daily 50/80/95 rungs are delivered in-app only, to avoid an email per day as spend climbs toward a much smaller cap.

### Configuring thresholds

The threshold ladder is configured in two places:

- **Organisation**: **Org settings → AI** (v0.114.0+; previously on the AI Usage page). The **AI Usage** page itself is now usage-only, and shows a read-only **Effective budget** panel with each field's value and where it came from (Set by partner, Set by organization, or Default).
- **Partner**: the **AI Budgets** tab of Partner Settings, which can set a value that applies across every organisation under the partner.

A partner-set value locks the corresponding field in **Org settings → AI**: the field is grayed out and shows a **Managed by partner** note, so the org can see the value but can't edit or submit it. If every field is locked, the org's Save button is disabled entirely. A partner-scoped user with permission to manage partner-wide policies also sees a **View partner-wide budgets** link from the locked field straight to the Partner Settings AI Budgets tab.

Either field takes two kinds of input: leave it empty to inherit (the org inherits the partner value, or the 50/80/95 default when the partner sets nothing), or type an explicit ladder of up to five whole percentages, such as `60, 90`. Turning pre-cap warnings off entirely requires storing an empty list, which the UI cannot produce; do that through `PUT /ai/budget` with `"alertThresholdPercents": []`. The 100% cap-reached alert still fires regardless.

## AI Input Sanitization

The `aiInputSanitizer` service validates all user inputs before they reach the AI agent. This layer prevents prompt injection, command injection, and other adversarial inputs from being passed to AI tool calls.

Sanitization includes:
- Input length limits
- Pattern detection for known injection techniques
- Escaping of shell metacharacters in tool arguments
- Validation against Zod schemas defined in `aiToolSchemas.ts`

All rejected inputs are logged in the security event trail accessible via the Risk Engine dashboard.

## Model refusals

Some Claude models decline requests that resemble harmful work. The category is reported with the refusal, for example `cyber` for malware analysis or exploit-like scripts. Security triage in an RMM can trigger this even when the work is legitimate.

When a model declines, Breeze:

- records the refusal and its category against the model in AI usage;
- shows the technician "The model declined this request (category: …)", lists the other models they are allowed to switch to, and links here;
- ends an AI agent run as **Blocked — model refused**, with the category in the run outcome.

### Configuring a refusal fallback

An administrator can give a model a **refusal fallback** under **Partner Settings → AI Providers & Models**. The fallback must be another enabled model on the **same connection**, so it never changes who pays for the request. On the Claude API, Breeze asks Anthropic to retry the turn on the fallback model in the same request. On a catalog provider, Breeze retries once itself. The turn is billed at the rate of the model that served it.

## Choosing a model in chat

When your partner allows it, the chat composer has a model menu. It lists the models you may use, with each model's context size and price per million tokens. A model your role can't use is shown greyed out with the role that grants it. Next to the menu, set the options the chosen model supports:

- **Effort** — how much the model reasons before answering (adaptive-thinking models).
- **Fast** — a faster, more expensive mode, shown where your administrator enables it and the model supports it; its rate is shown next to the switch.
- **Thinking** — an on/off switch for models that think with a fixed budget.

Your choice applies from your next message. While the model reasons, the chat shows **Thinking…**. Under each answer, the chat shows the model and options that actually answered. A model can decline a request and hand it to another, and Fast can be unavailable for a moment, so this can differ from what you picked.

Administrators can lock a feature to one model under **Partner Settings → AI Providers & Models → Defaults by feature** (turn off **Users may choose**). The menu is then hidden for that feature.

## Switching models mid-conversation

Switching to another model keeps the conversation when the new model is on the same AI connection and the conversation fits its context window. Breeze counts the conversation with the new model before switching. Otherwise Breeze offers **Continue with the new model in a new chat**: the newly chosen model summarises the conversation and a linked chat starts from that summary. Your message is kept either way, and you can choose **Keep the current model** instead.

## The model an AI agent uses

An agent's settings include a **Model** field: use the AI agents default, or pick one of the models allowed for AI agents. Picking a model that needs a permission requires you to hold that permission.

## Failover and escalation roles

### Backup models

Each feature's default model can have an ordered list of up to five **backup models** (**Partner Settings → AI Providers & Models → Defaults by feature**). Breeze moves to the next usable backup when the model:

- is disabled or retired, or its connection stops working;
- is rate-limited, overloaded or returns a server error;
- rejects its API key, or the provider account is out of quota.

Backups follow the same rules as the default: the feature's allowed models, plan, data residency and tool support. A backup that was just tried, or that is cooling down after a recent failure, is skipped. A model cools down for about a minute after a rate limit, overload or server error, and for up to 15 minutes after a key or quota failure. Replacing the connection's API key clears that wait at once. If every backup is unusable, Breeze still uses the default rather than failing the feature.

A timeout is never a reason to fail over, because the provider may still have run the request. A model you picked yourself in the chat model menu is never swapped for a backup.

### Billing

Each attempt is billed to the source that served it: Breeze AI credits for a Breeze-provided model, or your provider account for a model on your own API key. An attempt the provider rejected costs nothing. Failover moves between Breeze credits and your own API key only when **Allow failover between Breeze credits and your own API key** is on for that feature. Before a backup on Breeze credits is used, Breeze checks your credit balance and AI budget again.

### Chat

A chat message is never re-sent to another model partway through a reply. If a message fails before the model writes anything, the model cools down and your next message uses a backup. A conversation that already has history only moves to a backup on the same AI connection, and only when the conversation fits that model; otherwise it stays on its model. Your own model choice is kept, and Breeze goes back to it once it recovers. If the model you were using was disabled or retired, the conversation moves to the backup for good.

### Escalation roles for AI agents

The AI agents feature has three roles, each with its own default and backups:

| Role | Runs |
|---|---|
| **Triage** | Alert verdicts, ticket triage, and sweeps in shadow mode |
| **Analysis** | Investigations, narratives, designs, patch planning, and full runs in shadow mode |
| **Remediation** | Full runs and sweeps in act mode, which can change devices |

A role you leave unset uses the AI agents default. An agent pinned to a specific model in its own settings keeps that model; the role's allowed models and backups still apply to it. An agent run fails over only before the model has written anything or run a tool, so no action is ever run twice.

### Organization overrides

**Organization Settings → AI → Model defaults** can narrow a feature's backup list (or set it to no backups) and can turn cross-funding failover off. An organization cannot add backups the partner did not allow, and cannot turn cross-funding failover on. An organization that overrides the AI agents default keeps the partner's triage, analysis and remediation defaults, within the models it allows.

### Usage

The **Failovers** column on the AI usage page counts calls that a backup model served.

## Troubleshooting

**Tier 3 action pending but never executing**

Tier 3 actions require manual approval. Open **Security → AI Risk → Approval History** and approve or reject the pending request.

**AI Risk Engine dashboard shows no data**

The dashboard requires at least one AI tool execution to have occurred. Ask the AI assistant a question about your fleet to generate initial data.

**Fleet Orchestration stat cards showing zeros**

Some endpoints (deployments, reports) return empty results if no data exists yet. Cards populate independently — a zero on one card does not indicate a general problem. Partial endpoint failures are shown as warnings in the UI.

**Context entries not appearing for a device**

The AI loads context only for the specific device you ask about. Try: _"What do you know about [hostname]?"_ to trigger explicit context loading.

**`set_device_context` not working**

`set_device_context` is Tier 2 (auto-execute + audit logged) and requires `devices:write` permission. Confirm your role includes write access to devices.

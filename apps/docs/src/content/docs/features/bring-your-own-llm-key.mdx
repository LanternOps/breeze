import { Steps, Aside } from '@astrojs/starlight/components';

Breeze supports two ways to use your own LLM provider configuration:

- **Hosted BYOK** lets a partner use its own Anthropic API key for Breeze AI.
- **OpenAI-compatible connections** let a partner connect its own vLLM, Ollama, LiteLLM, or OpenRouter endpoint with full tool calling.
- **Self-hosted instance configuration** routes platform-keyed AI usage to an Anthropic-compatible or OpenAI-compatible endpoint.

If both are configured, a partner's BYOK configuration takes precedence. Instance environment variables apply only to AI usage that would otherwise use the platform key.

## Hosted: use your own Anthropic key

When you connect your own Anthropic API key, all AI features for your partner use that key and are billed directly to your Anthropic account. Breeze AI credits are not consumed.

Workspace content enrichment also uses your configured AI provider, so it's billed the same way as your other AI features and appears in your AI usage.

### Requirements

You must be a partner admin with access to all organizations and the billing management permission. You must also complete MFA when you connect, replace, or disconnect a key.

### Connect a key

<Steps>

1. Open **Partner Settings → AI Providers & Models**.

2. Paste your Anthropic API key into the write-only key field.

3. Optionally select a default model from the supported model list.

4. Click **Save**. Breeze verifies the key with Anthropic before storing it.

</Steps>

The page shows that your key is active and displays only its last four characters. Breeze never returns the full key after you save it.

To rotate the key, paste the replacement and save it. Breeze verifies the replacement before changing the stored key, so a failed verification leaves the existing working key in place.

To return to the Breeze platform key and Breeze AI credits, click **Disconnect** and complete MFA. Breeze does not switch back automatically.

### Usage, budgets, and failures

Organization AI budgets and rate limits still apply. With BYOK enabled, those controls limit usage billed to your own Anthropic account rather than consumption of Breeze AI credits.

While the partner key is active, the AI usage page shows the note **"Billed to your key — AI usage goes to your own Anthropic account, not Breeze AI credits."**

<Aside type="caution">
  If the key is invalid, revoked, or rejected by Anthropic, AI is unavailable and Breeze shows an error banner. Breeze never silently falls back to the platform key, because doing so could consume Breeze AI credits without your intent. Replace the key or disconnect it explicitly to restore service.
</Aside>

### Route your key through a platform-vetted endpoint

Once a key is connected, partners on deployments with the endpoint catalog enabled can send their AI traffic through a third-party endpoint instead of Anthropic directly — for example an OpenRouter or LiteLLM deployment that Breeze has verified against the Anthropic `/v1/messages` API. Your Anthropic key is still what gets billed; the endpoint only changes where the traffic is routed.

Breeze maintains this list itself. **You choose from the list — you never enter a URL.** Every entry is a platform-vetted endpoint that Breeze has run through its own fidelity and safety checks before it can appear as an option; there is no free-form "custom endpoint" field anywhere in the partner UI.

<Steps>

1. Open **Partner Settings → AI Providers & Models**. Whenever at least one catalog entry is available — or you already have an endpoint selected — an **Endpoint** card appears below the key card, listing **Anthropic (direct)** plus one radio option per vetted endpoint. Selecting an endpoint requires a connected key: if you try it before connecting one, Breeze rejects the change with *"Connect an Anthropic API key before selecting an endpoint."* rather than storing a selection that could not be used.

2. Selecting **Anthropic (direct)** applies immediately — it always requires zero confirmation, since it is the safe fallback.

3. Selecting a third-party endpoint opens a confirmation dialog. If the endpoint has a data-handling note, the dialog quotes it verbatim and requires you to check **"I understand my AI traffic and content will be processed by \<endpoint name\>"** before you can confirm. The note describes what that specific endpoint does with your traffic and content — read it before agreeing, since it varies per endpoint and Breeze cannot vouch for a third party's own data handling beyond the technical checks it ran.

4. Confirm. As with connecting or disconnecting a key, changing your endpoint requires MFA.

</Steps>

While a third-party endpoint is selected, the AI usage page's "billed to your key" note also names the endpoint, so it's clear both that billing goes to your Anthropic account and which endpoint carried the traffic.

<Aside type="caution">
  **If Breeze delists an endpoint you're using, AI is paused — not silently rerouted.** Breeze shows a banner explaining the endpoint was delisted, and no further AI requests succeed until you either pick another listed endpoint or switch back to **Anthropic (direct)**. The same fail-loud behavior applies if your selected endpoint stops verifying a model you rely on: Breeze pauses AI for that model rather than silently falling back to the platform key or a different provider.
</Aside>

This platform-vetted endpoint list is a hosted-only feature. If you're self-hosting, you point the instance at any Anthropic-compatible or OpenAI-compatible endpoint yourself with environment variables — see [Self-hosted: configure an instance-wide provider](#self-hosted-configure-an-instance-wide-provider) below for the variable matrix. Hosted partners can also [connect an OpenAI-compatible endpoint](#connect-an-openai-compatible-endpoint) of their own. There is no vetting step on self-hosted deployments: you're trusting whatever endpoint you configure.

### Connect an OpenAI-compatible endpoint

Connect any server that speaks the OpenAI `chat/completions` API with function calling, such as vLLM, Ollama, LiteLLM, or OpenRouter. Once a model passes verification, every AI feature works on it, including tools: chat, the helper, the script builder, AI agents, and Office chat.

<Steps>

1. Open **Partner Settings → AI Providers & Models → Connections** and click **Add connection → OpenAI-compatible endpoint**.

2. Enter a **name**, the **base URL** (it ends at the API root, for example `https://llm.example.com/v1`), and optionally an **API key** (at least 8 characters). The key is write-only.

3. Get models onto the connection. Breeze discovers them from `GET {base_url}/models`, or you can click **Add model** and enter a model ID by hand. Discovered and manual models arrive **disabled, unpriced, and unverified**.

4. Open the model and set a **price** in US dollars per million tokens. `0` is fine for a local model. A model without a price cannot be enabled.

5. Click **Verify**. Breeze runs a fidelity test through the endpoint, including a tool call. This spends a few thousand tokens on your own endpoint; Breeze does not bill for it.

6. Enable the model, then assign it as the default for the features you want under **Defaults by feature**.

</Steps>

Until a model is verified it has no tool calling and cannot be used for chat, the helper, the script builder, AI agents, or Office chat. If you change a connection's base URL, its models are marked **Re-verify: endpoint changed** and must be verified again. Rotating the API key does not require re-verification.

<Aside type="caution">
  These models do not support thinking or effort controls, documents and PDFs in chat, or server tools such as web search. A partner with **Require data residency** switched on cannot use them, because Breeze cannot attest where your endpoint processes data.
</Aside>

#### Network and key security

- **Hosted Breeze connects only to public `https` endpoints.**
- **Self-hosted deployments** may use private (RFC 1918 / ULA) addresses only when `IS_HOSTED` is explicitly set to `false`. Cleartext `http` is allowed only to a private address.
- **Loopback, link-local, and cloud-metadata addresses are never reachable**, in either mode. Redirects are not followed.
- **Your key stays on the Breeze API server** and is never given to the agent process. Requests go through Breeze's loopback model gateway, which attaches the key on the way out.

#### Troubleshooting

| Message | Cause and fix |
|---|---|
| **Verification failed: no tool_use block** | The server or model does not support function calling. For vLLM, start the server with `--enable-auto-tool-choice --tool-call-parser <parser>`. For Ollama, use a model that supports tools, such as `qwen2.5`. |
| **egress_blocked** | The address is not allowed for this deployment: a private address on hosted Breeze, a private address on a self-hosted install without `IS_HOSTED=false`, `http` to a public address, or a loopback/link-local address. Use a public `https` URL, or fix the deployment setting. |
| **Re-verify: endpoint changed** | The connection's base URL changed after the model was verified. Click **Verify** again. |

## Default model and the offered model list

The platform default model is **Claude Sonnet 5.5** (`claude-sonnet-5-5`) with adaptive thinking at medium effort (v0.120.0+; earlier releases defaulted to Sonnet 4.6). A self-hosted `ANTHROPIC_MODEL` still overrides the default. Existing chats keep the model they were started with; only new chats pick up the new default.

A new chat can only use a model the platform offers, the configured default, or (on a vetted endpoint) a model that endpoint maps. Requesting anything else when creating a chat returns `400` with code `invalid_model`, and no chat is created.

## Platform AI models (platform administrators)

Platform administrators manage the models Breeze knows about at **Administration → AI Models** (`/admin/ai-models`, v0.120.0+). Each row shows the model's discovery status (**Available**, **Missing**, or **Retired**), its thinking support, its input and output price per million tokens, whether it is offered, and whether it is the platform default. Open a row to edit:

- **Prices** in US dollars per million tokens (input, output, cache read, cache write). Breeze asks you to confirm any change of more than 10× from the stored value, to catch unit mistakes.
- **Fast mode prices**, optional. Fast mode can't be selected for a model until all four fast prices are set.
- **Option support**: effort levels, thinking display, fast mode, and inference geographies.
- **Minimum plan** that may use the model, and the **prompt profile** Breeze uses with it.
- **Offered on the platform key**. A model can only be offered once all four standard prices are set.
- **Platform default**. In v0.120.0 this choice is recorded but does not yet change routing; the deployment default still comes from `ANTHROPIC_MODEL` or the built-in default.

Every change requires MFA. The **AI Providers & Models** settings and the **LLM Provider Catalog** page read their model lists from this catalog.

**Discovery.** Once a day (06:38 UTC) Breeze lists the models available to the platform Anthropic key. A model it has not seen before appears with a **New** badge and the platform operators are alerted. Discovery only flags models for review: it never offers, prices, or removes a model on its own, and a new model stays unpriced and offered to no one until you set it up. A model that stops appearing is marked **Missing** after several successful checks and two days, and **Retired** after 14 days; a model discovery has never seen is never moved. **Refresh models** queues a discovery run immediately. Discovery is skipped when no platform key is configured or when `ANTHROPIC_BASE_URL` points at a gateway rather than Anthropic.

## AI Providers & Models

**Partner Settings → AI Providers & Models** is the single home for where AI requests are sent, which models are available, and which model each feature uses. It requires the billing management permission. The sections below describe each card. Per-model spend by feature, technician, and organization is under **Settings → AI Usage**.

### Connections and residency

The **Connections** card lists the Breeze platform connection plus any connection you add, with its status, key state, inference region, and who is billed. Adding or editing a connection opens a drawer where you can set a name and inference region, replace the write-only API key, pick a catalog endpoint, or disconnect; **Refresh models** queues a fresh model discovery for that connection. The **Require data residency** switch restricts every feature to models that can keep data in the required region. Before it applies, Breeze shows which features and organization overrides would stop working so you can confirm or cancel.

### Models

The **Models** card groups the models each connection offers, with context size and per-1M-token prices. The switch on a row enables or disables the model and saves immediately; a model with no price cannot be enabled, and disabling a model that is still a feature default asks you to confirm and lists the affected features. A row's details drawer sets a display name, price, premium flag, default and allowed effort or speed options, and an optional refusal fallback, which must be another enabled model on the same connection.

### Defaults by feature (and org overrides)

The **Defaults by feature** card sets the default model, effort, and speed for each AI feature (chat, helper, script builder, script reviewer, and so on), which models are permitted, and whether users may choose their own. Changing the script reviewer's model requires the approvals decide permission. Each organization can narrow these under **Settings → Organizations → (organization) → Model defaults**: leave a field on **Inherit** to follow the partner default, or override it. An organization can only narrow what its partner allows, and the partner can lock user choice. The script-authoring and client-AI policy pages link here instead of holding their own model fields.

## Self-hosted: configure an instance-wide provider

Self-hosted operators can configure an LLM backend for platform-keyed usage with environment variables. These settings apply across the instance, except for partners that have their own BYOK configuration.

If you're a hosted partner instead, see [Route your key through a platform-vetted endpoint](#route-your-key-through-a-platform-vetted-endpoint) above — hosted deployments select from Breeze's vetted catalog rather than setting these variables.

### Anthropic-compatible endpoint with tool calling

Use this path to route the full, tool-capable Breeze Agent through an endpoint that implements the Anthropic `/v1/messages` API, such as vLLM 0.23+ or LiteLLM.

| Variable | Required | Purpose |
|---|---|---|
| `ANTHROPIC_BASE_URL` | Yes | Base URL for the Anthropic-compatible endpoint. It must be a valid HTTP or HTTPS URL. |
| `ANTHROPIC_AUTH_TOKEN` | As required by the endpoint | Authentication token sent by the Anthropic SDK. |
| `ANTHROPIC_MODEL` | Optional | Overrides the default model ID, including for a raw vLLM model name or a LiteLLM alias. |

`ANTHROPIC_BASE_URL` is self-hosted only. Breeze refuses to start with this variable set unless `IS_HOSTED` is explicitly set to `false` (or another recognized false value). Hosted deployments cannot use a custom per-partner or instance-wide base URL.

### Instance-wide OpenAI-compatible endpoint

Use this path to give every partner on a self-hosted instance a shared OpenAI-compatible backend. At boot, Breeze creates an **env-managed connection** for each partner from these variables. It appears in **AI Providers & Models → Connections** as read-only, labelled *managed by environment*, with one priced, enabled model that Breeze verifies automatically.

| Variable | Required | Purpose |
|---|---|---|
| `MCP_LLM_PROVIDER` | Yes | Set to `openai-compatible`. Breeze refuses to start with this value unless `IS_HOSTED` is explicitly set to `false` (an unset `IS_HOSTED` is refused too). |
| `MCP_LLM_BASE_URL` | Yes | Base URL for the OpenAI-compatible endpoint. It must be a valid URL. |
| `MCP_LLM_MODEL` | Yes | Model ID exposed by the endpoint. |
| `MCP_LLM_API_KEY` | Optional | API key used to authenticate with the endpoint. Leave unset for a keyless local server; when set it must be at least 8 characters. |
| `MCP_LLM_PRICE_INPUT_PER_M_USD` | Optional | Input-token price in USD per million tokens. Defaults to `0`. |
| `MCP_LLM_PRICE_OUTPUT_PER_M_USD` | Optional | Output-token price in USD per million tokens. Defaults to `0`. |

Both price values must be zero or greater.

- **Chat moves to this model only where chat used the platform default.** A partner that picked its own model or connection keeps it.
- **The old chat-only runtime is removed.** The model now runs through the same verified path as a partner-added connection, so tools work.
- **A model that fails tool verification cannot serve chat.** See [Troubleshooting](#troubleshooting) above; the most common cause is a server started without function calling enabled.
- The same network rules apply as for a partner-added connection: loopback is never reachable, and private (RFC 1918 / ULA) addresses and cleartext `http` to a private address require `IS_HOSTED=false`. Point `MCP_LLM_BASE_URL` at the model host's container service name or LAN address, not `localhost`.

<Aside type="note">
  Provider precedence is **partner BYOK configuration → instance environment**. A partner-owned Anthropic key always overrides these instance settings. The instance environment applies only when Breeze resolves the request as platform-keyed usage.
</Aside>

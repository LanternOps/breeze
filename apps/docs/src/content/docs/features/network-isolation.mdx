---
title: Network Isolation
description: Isolate a device while retaining Breeze management access, and recover safely using console release, expiry, or offline break-glass.
---

Network isolation drops network traffic except the traffic needed to manage the device through Breeze. Each isolation episode is linked to an incident and has a mandatory expiry. The incident's recorded containment status alone does not prove that isolation is enforced: check the live episode state.

The feature is **off by default** behind `NETWORK_ISOLATION_ENABLED`. Merging the console or server code activates nothing. Start also requires an eligible partner, supported agent version, advertised isolation capability, and agent readiness. Windows activation remains disabled: agents advertise capability 0, and the minimum version gate stays at `999.0.0`. No recovery executable is distributed or bundled yet, so Windows readiness also fails closed. The behavior described below is the intended Windows rollout; the feature is **not available in this release**. Linux and macOS support is planned.

## Start and release

In device actions, choose **Isolate from network**, enter an existing incident ID or a title for a new incident, enter a reason, and choose a duration. The default is **72 hours**, with a maximum of **720 hours**. Enable the remote relay option when remote desktop is needed. Isolating a server can interrupt services for other devices, including domain authentication and file access.

The header shows whether isolation is applying, verifying, or verified, plus the remaining duration. The incident detail also shows linked device episodes. The **Isolated** device filter includes unresolved episodes, including local or self-releases awaiting acknowledgement; it is not proof that rules are currently enforced.

**Release isolation** remains available for active episodes when start eligibility fails: flag disabled, partner not enabled, old or unready agent, trust restriction, device lifecycle restriction, closed incident, or offline device. Offline release is queued until reconnect. Extension, acknowledgement, and code viewing remain available independently of the start flag. Human routes require an interactive session, device execution permission, appropriate organization/site access, and MFA when enabled; API keys cannot perform these operations. A self-host with 2FA disabled provides **password-only assurance**.

Release requests are not confirmation that rules are gone. Wait for the agent to report release. After investigating `released_locally` or `self_released`, use **Acknowledge local release** to resolve the episode. Other states do not offer this action.

## What stays reachable

The server builds the allowlist; operators cannot supply arbitrary destinations in an isolation request. The allowlist permits the Breeze control plane, configured backup endpoint, ECH DNS-over-HTTPS endpoints, and configured TURN relay when remote relay is enabled. A transport proxy is permitted only as needed for Breeze traffic.

The baseline permits loopback, DHCP lease renewal, DNS to currently configured resolvers, IPv6 neighbor/address discovery and path-MTU traffic, required IPv4 fragmentation notifications, and replies for permitted flows. Everything else is dropped in both directions. Existing non-permitted connections are cut, not grandfathered.

Breeze terminal, file browser, tunnels, and script control traffic continue through the agent management connection. On Windows and Linux, script and terminal child processes do not inherit the agent's network permit: a remediation script cannot download arbitrary tools. Agent updates use the control plane while isolated.

Remote desktop uses **TURN relay only**, with no direct/STUN fallback. A self-host without TURN loses remote desktop while isolated. Direct inbound RDP, SSH, SMB, and VNC are blocked, as are general web access, lateral movement, Windows Update, package mirrors, NTP, and VPN client traffic.

## OS mechanisms and limits

| OS | Mechanism | Permit boundary |
| --- | --- | --- |
| Windows (first release) | Windows Filtering Platform (WFP), with a dedicated Breeze provider and sublayer | Breeze application identity **and** destination/port; persistent and boot-time filters protect restart |
| Linux (planned; not active in any release) | Dedicated nftables table (`inet breeze_isolation`) with input, output, and forward chains | The agent's own cgroup **and** destination/port; child processes are placed in a separate cgroup before they start |
| macOS (planned, not activated) | Dedicated pf anchor `com.breeze/isolation`, attached only to a compatible ruleset; Breeze releases only its own pf enable reference | Destination/port only; pf cannot identify the process |

Breeze removes only its own isolation rules on release. Other firewall or EDR isolation can still block connectivity after Breeze isolation is released. A failed management reachability or enforcement probe causes rollback; a separate recovery component enforces expiry even if the main agent fails. Recovery still depends on working storage, OS scheduling, and firewall facilities. Powered-off devices run overdue recovery at boot or resume.

### Windows recovery, uninstall, and upgrade

The separate `breeze-isolation-recovery.exe` component handles provisional rollback, expiry, and boot recovery even when the main agent cannot run. Its installation path is `<agent install directory>\isolation-recovery\<version>\breeze-isolation-recovery.exe`, alongside the protected agent installation. Versions are installed side by side and are never overwritten in place. An unresolved episode keeps its scheduled tasks pinned to its journaled recovery path. A version must pass trust verification and its self-test before task actions can adopt it.

Self-host agents trust the recovery binary through the signed release manifest hash; hosted editions require Authenticode. Public self-host Windows builds ship unsigned, so a self-host agent checks the executable's SHA-256 against the `breeze-isolation-recovery-windows-<arch>.exe` entry in the Ed25519-signed release manifest for that exact version. The manifest is stored as `release-manifest.json` in the same version directory, and its signature is checked against the same keys the agent's updater trusts, on every check. Any of these reports `recovery_untrusted`, and the device is not ready:

- the manifest is missing or its signature does not verify;
- the manifest is for a different version;
- the manifest has no entry for the recovery executable;
- the executable's hash does not match the entry.

An unsigned binary is never trusted just because it is present. A device made ready this way reports `self_host_manifest_hash` as its readiness detail. Like the rest of Windows isolation, this path is off by default and inactive in this release.

The agent's self-uninstall and the Windows MSI uninstall release Breeze-owned isolation rules first. If release cannot be confirmed, uninstall fails before removing the agent files or recovery state. A clean, never-isolated device can still uninstall normally. The detached Windows teardown script checks release again before stopping or deleting services.

An MSI upgrade never runs the uninstall release action and does not un-isolate the device. The agent does not start a self-update while the device is isolated. If isolation begins after an update has already been downloaded, the update is checked again just before the binary swap. When executable paths change, both old and new paths are permitted before the swap. After restart the agent reads the journal, re-verifies isolation, and removes the old-path permits. The swap is refused if the new agent's journal schema cannot be confirmed compatible.

### Linux (planned)

Linux isolation is **not available in any release**. Linux agents advertise capability 0 and do not move between cgroups, place child processes, or apply rules. This section describes the intended behavior.

**Mechanism.** Isolation is one nftables table, `inet breeze_isolation`, applied as a single atomic batch after a kernel dry run. A host without `nft` cannot be isolated; there is no iptables fallback. Breeze touches only its own table: `ufw` and `firewalld` reloads leave it in place, and an accept in another table cannot override a drop in this one. Applying isolation flushes the connection-tracking table so that open connections cannot outlive the apply; flows Breeze permits re-establish themselves. A host without the `conntrack` tool still drops those connections' packets, and the episode journal records `conntrack_unavailable`.

**Cgroup split and `Delegate=yes`.** The `breeze-agent` unit runs with `Delegate=yes`, which hands its cgroup subtree to the agent. The agent moves itself into `<unit>/agent`, and every child it starts (terminal, script, helper) is created directly in `<unit>/children`, so it never runs in the permitted cgroup. The firewall permit matches only sockets created in `<unit>/agent`. The `breeze-backup` helper stays in the agent's cgroup because it reaches the backup server, and places its own children in `<unit>/children`. `Delegate=yes` is not a sandbox directive: child processes keep the unrestricted environment remote scripts rely on. An install whose unit predates `Delegate=yes` reports `cgroup_not_delegated` and cannot be isolated until the agent is reinstalled.

**Readiness.** Linux isolation requires **Linux 5.13 or later**: nftables can match a socket's cgroup only from 5.13, and child placement at creation needs 5.7. A Linux agent names the first prerequisite it lacks:

- `nft_missing`
- `cgroup_v1`: cgroup v1 and hybrid hosts are not supported.
- `cgroup_not_delegated`
- `cgroup_spawn_unavailable`: the kernel or a seccomp policy cannot place a child at creation.
- `cgroup_unavailable`: any other failure to split the cgroup.
- `nft_cgroupv2_unsupported`: the kernel cannot match a socket's cgroup.
- `recovery_unavailable`
- `scheduler_unavailable`

**Systemd units and recovery.** The separate `breeze-isolation-recovery` binary lives in `/usr/local/lib/breeze/isolation-recovery/<version>/`; versions are installed side by side and are never overwritten. It runs from:

- `breeze-isolation.service`, ordered before `network-pre.target`. nftables rules do not survive a reboot, so this reinstalls a still-valid episode before networking starts. At that point the agent's cgroup does not exist, so the boot rules carry only the baseline and policy destinations; management access returns when the agent starts and re-applies the full rules. An expired or unconfirmed episode is released instead.
- `breeze-isolation-poll.timer`, one minute after boot and every 15 minutes, as the expiry backstop.
- Two one-shot `systemd-run` timers: the 90-second provisional rollback (`breeze-isolation-rollback-<attempt>`) and the expiry (`breeze-isolation-expire`).

**Uninstall.** Self-uninstall and `uninstall.sh` release Breeze-owned rules first. If release cannot be confirmed, nothing is removed, and self-uninstall re-enables and restarts the agent service. The units and recovery binaries are removed only after a confirmed release, or when `nft` shows no Breeze rules installed. A failed `nft` query never counts as "no rules". A never-isolated device uninstalls normally.

**Limits specific to Linux.** Isolation filters at the IP layer. Traffic a Linux bridge switches at layer 2 between a guest and a physical interface (bridged VMs or containers) does not pass the forward chain and needs separate network controls; routed and NAT container traffic is dropped. Hardware-offloaded flows are also a documented limitation.

### macOS (planned)

macOS support is implemented but **disabled in this release**: agents report capability 0 with the reason `not_activated`, and no signed recovery executable is distributed, so readiness also fails closed. The design below applies once it is activated.

- **pf anchor.** Breeze rules live only in the anchor `com.breeze/isolation`. The main ruleset must reference that anchor, and the only way to add the reference is to reload the main ruleset from `/etc/pf.conf`. Breeze does that only when the reference is missing, with its anchor ahead of Apple's, and otherwise changes only its own anchor. Breeze does not disable pf: it takes, and later releases, only its own pf enable reference, so pf stays on while anything else holds one.
- **Incompatible configurations are refused, not overwritten.** The apply fails with `mechanism_unavailable` and the console shows why when Internet Sharing is on (the reload would destroy its anchors), when another anchor or rule is live that `/etc/pf.conf` would not restore, when `set skip` covers a network interface that is up, or when a `quick pass` or `rdr pass` rule would let traffic bypass the Breeze anchor. A refused apply changes nothing.
- **Re-verification.** Every 5 minutes, the agent checks that the anchor holds its rules, that the main ruleset still references it, that pf is enabled, and that no `set skip` or `quick pass` has appeared since. Anything that reloads the main ruleset silently detaches the anchor. The agent re-attaches it while the ruleset is still compatible, and otherwise reports the drift and its reason.
- **No per-process scope.** pf cannot match a process, so every permit is destination and port only and applies to every process on the Mac. See the shared-address risk below.
- **Recovery.** A separate root LaunchDaemon, `com.breeze.isolation`, runs the versioned `breeze-isolation-recovery` executable from `/Library/Breeze/isolation-recovery/<version>/` at boot and every 15 minutes. It releases an expired episode and, because pf keeps no rules across a reboot, installs a still-valid one again. While an apply is provisional, `com.breeze.isolation.rollback` checks every 15 seconds and rolls the apply back once its deadline has passed; `com.breeze.isolation.expire` runs once at the expiry time. Versions are installed side by side and never overwritten in place.
- **Boot window.** launchd starts the LaunchDaemon with no ordering against the network, so an exposure window exists after each boot. Its length has not been measured yet; the macOS lab test does that before activation.
- **Uninstall releases first.** The agent's self-uninstall and `breeze-agent service uninstall` release isolation before stopping any Breeze daemon, falling back to the recovery executable, and stop with the agent still installed if the release cannot be confirmed. They confirm the release again once the agent has stopped, then remove the recovery LaunchDaemons and executables; if that second check fails, the agent is loaded again and recovery stays in place. The downloadable `uninstall.sh` does not perform this release.

Residual risks remain:

- **Shared CDN/anycast addresses:** Windows and Linux restrict the permit to Breeze processes as well as destinations. macOS permits destinations only, so another process can reach unrelated services sharing an allowed address.
- **DNS tunnelling:** permitted resolvers and DoH endpoints leave a possible channel. Removing DNS entirely would prevent management reconnection when addresses change.
- **Captive portals and 802.1X:** EAPOL is unaffected, but a captive portal cannot be completed while isolated. Use expiry or offline break-glass when management cannot reconnect; do not assume an automatic dead-man release is enabled.
- **Domain-joined Windows:** domain-controller Kerberos, LDAP, and SMB are blocked. Cached logons remain usable; Group Policy pauses. Server isolation is an intentional service outage.
- **Traffic outside host filtering:** Hyper-V external vSwitch/WSL2 NAT, macOS Internet Sharing, and hardware-offloaded forwarding need separate network controls. Linux drops forwarded traffic but hardware offload is a limitation.
- **macOS boot window:** the LaunchDaemon cannot guarantee isolation loads before networking. A brief exposure window exists after boot. Incompatible pf configurations are refused rather than overwritten.

## Offline break-glass runbook

1. Open the device episode and explicitly click **Show break-glass codes**. This calls an audited endpoint; codes are never prefetched. The console displays the current and next-hour codes.
2. Verify the person at the device and read the appropriate code to them. They must open an elevated Administrator/root terminal and run:

   ```sh
   breeze-agent containment release --code <code>
   ```

3. The code works without network connectivity. Attempts are limited to five per hour. Use the next-hour code as its time window begins; request fresh codes if the episode generation changes.
4. On reconnect, investigate the reported local release and acknowledge the episode in the console. Do not treat a code view as proof of a release.

A local administrator can also run `breeze-agent containment release --force`. **`--force` raises an alert** and records a forced local release. Use it only when recovery requires it, and investigate the audit trail afterward. Do not delete firewall rules manually: re-verification can restore them.

## Emergency fleet un-isolate

Emergency fleet release is a **scripted per-episode console release**, never a feature flag change. Turning `NETWORK_ISOLATION_ENABLED` off prevents new starts but leaves current isolation in place.

1. Sign in with an authorized interactive console session and satisfy MFA when required. Use the Isolated filter to enumerate devices in the intended organization/site scope. Account for pagination.
2. For each device, read `GET /api/v1/devices/:id/network-isolation`, inspect its episodes, and select active states (`requested`, `dispatched`, `applying`, `applied`, `verified`, `release_requested`). Review the target list before submitting.
3. In a controlled script using that console session and its normal request protections, call `POST /api/v1/devices/:id/network-isolation/:isolationId/release` separately for each selected episode with a JSON body such as `{"reason":"Emergency fleet recovery"}`. Do not use an API key, bypass interactive authentication, or log session credentials. Record per-episode response status and failures; retry failed requests after addressing their cause.
4. Poll episode state until release is confirmed. An offline endpoint retains a queued release and receives the desired release state on reconnect. Use the break-glass runbook or mandatory expiry where reconnection is impossible.
5. Investigate and acknowledge local/self-release episodes separately; retain the audit record of the recovery.

The incident `POST /incidents/:id/contain` endpoint is **record-keeping only**. It cannot release isolation or attest to endpoint enforcement. AI `release_containment` is planned for a later release; use console release now.

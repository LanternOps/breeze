Configuration Policies let you bundle device settings — patches, alerts, maintenance windows, compliance rules, and more — into reusable templates and apply them to any scope of your fleet. Policies evaluate automatically on a schedule and can auto-remediate drift without manual intervention.

Policies are **hierarchical**: settings cascade from the broadest scope down to the most specific, and more specific assignments always win.

```
Breeze Defaults  (lowest priority — read-only, always present)
  └── Partner
        └── Organization
              └── Site
                    └── Device Group
                          └── Device  (highest priority — always wins)
```

### Policy ownership: organization vs. partner-wide

A policy is owned at one of two scopes:

- **Organization** — the policy belongs to a single customer organization and can only be assigned within that org's hierarchy. This is the default.
- **Partner-wide (all orgs)** — the policy belongs to your partner account and can apply across **every** organization you manage. Use this for fleet-wide standards you want enforced everywhere without recreating the policy per customer.

You choose the ownership scope when creating the policy. Partner-wide policies can only be created and managed by partner-level users with full access to every organization under the partner (not users restricted to a subset of organizations); organization-scoped users see partner-wide policies in their effective configuration but cannot edit them.

Backup settings cannot be configured on a partner-wide policy — see [Backup](#backup) below.

## Baseline policies (inheritance)

A policy can optionally have one **parent** — a baseline policy it inherits feature settings from. This lets an MSP define a standard baseline once (e.g. "Standard Workstation Baseline") and have every customer-specific policy build on it, instead of copy-pasting the same patch schedule, alert thresholds, and maintenance windows into every org.

**Effective links of a policy** = the policy's own feature links, plus, for any feature type the policy has no link of its own for, the parent's link for that type. In other words: a child's own configuration always wins; anything the child hasn't touched falls through to the parent.

You set the parent when **creating** a policy: choose **Link to Existing** on the New Policy screen and pick a baseline from the list. The parent cannot be changed after the policy is created.

### Which policies can be a parent

| A child that is... | ...can inherit from |
|---|---|
| Organization-owned | a policy in the **same organization**, or a **partner-wide** policy owned by the same partner |
| Partner-wide | only another **partner-wide** policy owned by the same partner |

Only **one level** of inheritance is supported — a baseline policy cannot itself have a parent. If a candidate baseline already has a parent, it won't appear as an eligible baseline for a new policy.

### Overriding and reverting an inherited feature

Open any feature tab on a child policy. If the feature comes from the parent, the tab shows a **Configured (inherited)** badge and the settings are shown read-only, seeded from the parent's configuration:

- Click **Override** to save a copy of the inherited settings as the policy's own link — the tab becomes editable and future parent changes no longer affect this policy for that feature.
- Click **Revert to Parent** on an overridden feature to delete the policy's own link and fall back to the parent's again.

<Aside type="caution">
  **The parent's `Active`/`Inactive`/`Archived` status does not gate inheritance.** Archiving a baseline policy does not silently strip security, patch, or backup configuration from every policy that inherits from it — only the *child's own* status controls whether its assignments are evaluated, exactly as for a policy with no parent. Before archiving a widely-inherited baseline, check its Overview tab for the "Inherited by N policies" list to see the blast radius.
</Aside>

### Deleting a baseline

A policy that other policies inherit from cannot be deleted while those children still reference it — the delete is refused with a list of the policies that need to be moved off it first (deleted, or given a different or no parent) before the baseline itself can be removed. This prevents deleting a widely-used baseline from silently un-configuring every policy built on it.

### MFA and inherited patch / maintenance settings

If a baseline carries a Patch Management or Maintenance Windows feature — both of which require a session with satisfied multi-factor authentication to add or change directly — creating a **new** policy linked to that baseline requires the same MFA session, since the new policy immediately gains that gated configuration through inheritance.

## Feature types

A policy can bundle multiple feature types:

| Feature | What it controls |
|---|---|
| **Patch Management** | Auto-approval, schedule, reboot policy |
| **Maintenance Windows** | Recurrence, duration, alert/patch/automation suppression |
| **Compliance Rules** | Desired-state rules, enforcement level, remediation script |
| **Backup** | Schedule and retention |
| **Security** | Security policy settings |
| **Monitors** | Attaches [monitors](/features/monitors/) -- objects that bundle a condition, severity, delivery, and response actions -- to this policy's scope |
| **Automation** | Event triggers, cron schedules, bulk actions |
| **Privileged Access** | Windows UAC elevation prompt capture for [privileged access management](/features/pam/) |
| **Vulnerability Scanning** | Turns on daily CVE correlation for the scope (off by default) -- see [vulnerability management](/features/vulnerability-management/) |
| **Event Log Forwarding** | Destination and filters for shipping device event logs to an external store -- see [Event Log Forwarding](/features/event-log-forwarding/) |
| **Software Policy** | Allowlist/blocklist/audit enforcement evaluated during software inventory scans -- see [Software Policies](/features/software-policies/) |
| **Sensitive Data Discovery** | Scan schedule and rules for PII, credentials, and other sensitive data on endpoints -- see [Sensitive Data Discovery](/features/sensitive-data/) |
| **Peripheral Control** | USB, Bluetooth, and Thunderbolt device allow/block rules -- see [Peripheral Control](/features/peripheral-control/) |
| **Warranty** | Warning and critical expiry thresholds that raise alerts before a device's warranty lapses -- see [Warranty Tracking](/features/warranty-tracking/) |
| **Breeze Helper** | Tray icon and menu options (portal link, device info, request support) for the [Breeze Helper](/agents/helper/) app |
| **Remote Access** | MFA and consent requirements for Remote Desktop and Remote Terminal sessions -- see [Remote Access](/features/remote-access/) |
| **OneDrive Helper** | Silent sign-in, Files On-Demand, Known Folder Move, and SharePoint library auto-mount -- see [OneDrive Helper](/features/onedrive-helper/) |
| **Device Lifecycle** | Days to retain a removed device before it is permanently purged |
| **System Protection** | Whether Breeze asks Windows devices for a System Restore checkpoint before patch installs, scripts and software installs -- see [System Protection](#system-protection) |
| **Workload inventory** | Lists the containers and VMs on a host (Docker, Podman, Hyper-V, Proxmox); off by default -- see [Workload Inventory](/features/workload-inventory/) |

Each feature can be configured in one of two modes:

- **Linked** — points to an existing policy object by ID (e.g., an existing update ring). Changes to the linked object propagate automatically.
- **Inline** — settings are stored directly in the policy. Useful for simple configurations that don't need to be shared. Required for `backup` and `security` feature types.

## Monitors and alerting

A single policy carries every alert condition — service and process watches,
thresholds, offline detection, event-log patterns — as monitors attached on its
**Monitors** tab, plus one agent-collection setting, *Check interval*.
See [Monitors](/features/monitors/).

Select **Add to inherited monitors** for cumulative deployment, or review
**Replace inherited monitors** when preserving converted inline-rule behavior.
Broad reactive automation belongs to **Jobs → Alert workflows**.

## Enforcement modes

Compliance rules support three enforcement levels:

| Mode | Behaviour |
|---|---|
| `monitor` | Report non-compliance only. No alert, no action. |
| `warn` | Raise a **medium** alert for each non-compliant device. It is delivered like any other alert and resolves itself once the device is compliant again. |
| `enforce` | Raise a **high** alert and auto-remediate using the linked remediation script. Without a script it behaves like `warn` at high severity. |

Compliance alerts always belong to the device's organization, including for partner-wide policies. Changing a rule to `monitor` resolves the alerts it already raised at its next evaluation.

## Creating a policy

<Steps>

1. Navigate to **Fleet Management → Config Policies**.

2. Click **New Policy**, then choose **Configure New** to start from scratch, or **Link to Existing** to inherit from a baseline policy (see [Baseline policies](#baseline-policies-inheritance) above). Choosing **Link to Existing** adds a picker of eligible baselines — filtered to the ones your chosen ownership scope is allowed to inherit from.

3. Enter a **Name** and optional **Description**.

4. If you're a partner-level user with full access to every organization, an **Apply to** picker appears: choose **All organizations (partner-wide)** to apply the policy across every organization you manage, or **A specific organization** and pick the target org from the dropdown. Users scoped to a single organization (or with access to only some organizations) don't see this picker — their policy is always scoped to their own organization. Note that Backup settings can't be configured on a partner-wide policy.

5. Set **Status** to **Active**. Inactive and archived policies are not evaluated by the scheduler.

6. Click **Save** to open the policy detail editor.

</Steps>

## Adding features to a policy

Open the policy detail editor and click the tab for the feature you want to configure.

### Patch Management

| Field | Description |
|---|---|
| **Auto-approve** | Automatically approve patches matching the configured criteria |
| **Schedule** | Frequency (daily/weekly/monthly) and time of day for patch runs |
| **Reboot policy** | How to handle required reboots after patching |
| **Manage Windows Update exclusively through Breeze** | Windows-only. Off by default. When on, the agent suppresses the device's native Windows Update automatic-install channel (it sets the `NoAutoUpdate` registry value under `HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate\AU`) so that device only receives updates through Breeze's schedule and approval rings — no surprise reboots or out-of-band patches. Turning it back off returns update control to native Windows Update. |

Patch Management is available on partner-wide (all organizations) policies — an [update ring](/features/update-rings/) can be linked directly, and the policy patches devices across every organization you manage. Behind the scenes, deployments are still tracked per organization: creating a deployment job from a partner-wide policy produces one job per organization with matching devices, so each customer's patch history and compliance reporting stay separate even though the schedule and approval rules are defined once.

### Monitors

Open **Monitors**, attach an existing definition or create one, then save the
policy. Configure the condition, responses and Notify settings on that monitor.
Use [Delivery](/features/notifications/) for shared notification routing.
During conversion, review **Needs conversion** before confirming; resolve every
blocked or unconvertible row deliberately.

### Maintenance Windows

| Field | Description |
|---|---|
| **Recurrence** | Day of week or month when the window applies |
| **Start time** | Local time the window begins |
| **Duration** | Length of the window in **hours** |
| **Suppress Alerts** | Silence alert notifications during the window |
| **Suppress Patching** | Skip scheduled patch jobs during the window |
| **Suppress Automations** | Skip automation triggers during the window |
| **Suppress Scripts** | Skip scheduled script execution during the window |

### Compliance Rules

| Field | Description |
|---|---|
| **Name** | A label for this rule |
| **Rule definition** | The desired-state condition to evaluate |
| **Enforcement level** | `monitor`, `warn`, or `enforce` |
| **Check interval** | How often to re-evaluate (minutes) |
| **Remediation script** | Script to run when `enforce` mode detects non-compliance |

### Backup

<Aside type="caution">
  Backup is **not available on partner-wide (all organizations) policies**. Backup settings are always tied to a single organization, so a policy owned at the partner level has no organization to attach them to — attempting to add or save a Backup feature link on a partner-wide policy is rejected. Configure Backup on an organization-owned policy instead.
</Aside>

Backup feature links use **inline settings** stored in the `config_policy_backup_settings` table (one row per feature link).

| Field | Type | Description |
|---|---|---|
| **Backup Mode** | enum | What to back up: `file` (default), `hyperv`, `mssql`, or `system_image` |
| **Schedule** | JSONB | Frequency (`daily`, `weekly`, `monthly`), time (`HH:MM`), timezone, day of week/month |
| **Retention** | JSONB | `keepDaily`, `keepWeekly`, `keepMonthly` snapshot counts |
| **Paths** | JSONB array | Directories to include (file mode only) |
| **Targets** | JSONB | Mode-specific targeting with optional exclude lists (Hyper-V and MSSQL modes) |

**Backup modes:**

- **File** — backs up directories listed in the Paths field.
- **Hyper-V** — exports all discovered VMs by default. Set `targets.excludeVms` to skip specific VMs by name.
- **MSSQL** — backs up all discovered databases by default. Set `targets.excludeDatabases` to skip specific databases.
- **System Image** — full system image capture with no additional targeting needed.

Hyper-V and MSSQL modes use **all-by-default targeting** — newly created VMs or databases are automatically included on the next scheduled backup run without any policy changes.

When a backup feature is linked to a configuration policy, the schedule, retention, and mode settings in the policy override whatever is set on the standalone backup configuration. The policy system resolves which backup settings apply to a device using the same hierarchical precedence rules as other feature types (device-level wins over group, site, org, partner).

<Aside type="tip">
  Use the effective configuration endpoint to verify which backup schedule a specific device will receive: `GET /configuration-policies/effective/:deviceId`
</Aside>

### Security, Monitoring, Automation

Configure security policy settings for **Security**; check intervals and targets for **Monitoring**; and event triggers, cron schedules, and action chains for **Automation**.

Saving **Security** settings with IOC auto-quarantine turned on needs `devices:execute` and MFA, and scheduled scans quarantine only under a user who still holds that permission; otherwise they run detect-only. See [Auto-quarantine runs under an approving user](/features/security/#auto-quarantine-runs-under-an-approving-user).

### Vulnerability Scanning

The **Vulnerability** feature is a single on/off toggle that controls whether the devices in the policy's scope are scanned for CVEs. It is configured **inline** (the on/off state lives in the policy) and is **off by default** -- a device with no vulnerability policy is never scanned, and its Vulnerabilities tab stays empty.

Open the policy's **Vulnerability** tab, switch **Enable vulnerability scanning** on, save, and assign the policy. Because resolution is closest-wins, a device- or group-level setting of *off* overrides an organization-wide *on*. Once a scope is enabled, Breeze correlates its software and OS inventory against the CVE feeds once a day. If a policy exists but no device resolves to *on*, the daily job is simply a no-op -- it never falls back to scanning everything. The findings themselves are reviewed and acted on in [Vulnerability Management](/features/vulnerability-management/), not on this tab.

### System Protection

<Aside type="caution" title="Agent-side checkpoints roll out with a future agent release">
  The **System Protection** policy tab, server-side resolution, the attempts ledger, the per-action badges and the device **System Restore** tab are available now. **The agent side is not.** Asking a Windows device to create a System Restore checkpoint, and reporting what happened, will start with a future agent release. Until a device runs that release, saving this policy only records what Breeze *asks for*: every attempt stays at **Awaiting the device**, and no outcome is reported. Do not read an empty or "Awaiting" history as a failure, and do not read a saved policy as a restore point that exists.
</Aside>

The **System Protection** feature controls whether Breeze asks a Windows device for a System Restore checkpoint just before it takes a risky action. It is configured **inline** and has three toggles:

| Toggle | Default | Applies before |
|---|---|---|
| **Before patch installs** | On | Installing operating system updates |
| **Before scripts** | Off | Running a script on the device |
| **Before software installs** | Off | Installing or updating software |

It also has a **Checkpoint label prefix** (up to 64 characters, blank means the default) that is shown at the start of each restore point's description in Windows.

Like other features, System Protection resolves closest-wins (Device → Device Group → Site → Organization → Partner) and can be set on a **partner-wide (all orgs)** policy, so one policy can cover every organization you manage. With no System Protection feature in scope, the platform default applies: a checkpoint is requested before patch installs only.

**What stays the same for patching.** Patch installs keep their existing best-effort checkpoint behavior. A device whose command carries no System Protection setting is treated the legacy way: patch installs are requested, scripts and software installs are not. Turning **Before patch installs** *off* cannot be enforced on a device until that device's agent reports support for the new setting, and the policy tab says so. Scripts and software installs take no checkpoint until you switch them on **and** a device runs an agent release that supports it.

#### What System Restore does and does not do

System Restore protects system files, the registry, installed programs and settings. **It is not a backup and does not protect personal files.** Windows limits restore-point creation to once every 24 hours by default, so a second action inside that window reuses the existing point; Breeze reports this as **Existing point reused** and never as a new checkpoint. A restore point that was created can later be removed by Windows or become unusable. Breeze reports what happened at the moment of each action and makes no promise about anything later.

#### Where you see the result

- **Patch history, script execution details and software deployments** show a one-line badge for the attempt that belongs to that action.
- The device's **System Restore** tab lists every request recorded for the device: when it was requested, what triggered it (patch install, script run, software install) and the outcome.

#### Status reference

The badge text is what a technician sees; the status is the value recorded in the ledger.

| Status | Badge text | What it means and what to do |
|---|---|---|
| `requested` | Awaiting the device | Breeze asked; the device has not reported back. Today every attempt stays here, because no agent reports yet. Once a supporting agent is deployed, a row that stays here for a device that has been online means the agent is older than the release that reports outcomes. Update the agent. |
| `created` | Restore point creation confirmed | The device reported that Windows created a restore point and that it could be found afterwards. Treat it as a record of that moment only; it can be removed or become unusable later. |
| `existing_accepted` | Existing point reused | Windows' 24-hour limit meant no new point was made, and an earlier one was accepted. Nothing to do. The badge shows the age of the reused point when the device reports it. |
| `skipped_disabled` | Skipped — System Restore is turned off on this device | System Restore is off for the system drive. **Breeze will not turn System Restore on for you.** If you want checkpoints on this device, enable System Protection for the system drive in Windows (System Properties → System Protection, or `Enable-ComputerRestore` from an elevated PowerShell) and the next action can request one. |
| `skipped_definition_only` | Skipped — definitions-only update | The patch run only contained definition updates, which do not need a checkpoint. Nothing to do. |
| `skipped_no_mutation` | Not needed — no changes were made, so no restore point was created | The command stopped before it changed anything (for example the package was already installed, or the request was rejected during validation or preflight), so no System Restore point was needed. Nothing to do. |
| `unsupported` | Not available on this device | System Restore is not present on this Windows edition (for example the system library or provider is missing). Nothing to enable. See the support matrix below. |
| `busy` | Skipped — the volume snapshot service was in use | Another volume snapshot operation held the service. Retry the action later if you want a checkpoint. |
| `insufficient_privileges` | Skipped — not enough privileges | The agent was not running with the rights System Restore needs. Check how the agent service runs on this device. |
| `verification_failed` | Could not be verified | A request was made but the device could not confirm that the restore point exists. Do not assume one exists; check Windows directly (`Get-ComputerRestorePoint`). |
| `failed` | Failed — *message* | Windows or the agent returned an error, shown in the badge. Use the message to troubleshoot. |

In this version a checkpoint outcome never blocks the action it was requested for. A badge value your console does not recognise (for example after a partial upgrade) shows as "Outcome not recognised by this version of the console".

## Assigning a policy

Open the policy detail editor → **Assignments** tab. What you see depends on who owns the policy.

### Partner library policy

The tab is an organization checklist, not a level picker.

<Steps>

1. Optionally set **Role Filter** and **OS Filter**. Leave them empty to apply to every device in the chosen organizations.

2. Turn on **All organizations (partner-wide)** to apply the policy across every organization you manage, or check individual organizations.

3. Assigned rows show the role and OS filters that were saved with that assignment. To change filters, turn the assignment off and on again with the new chips selected.

</Steps>

A partner-wide "servers only" assignment reaches server-role devices in every assigned organization. Workstations skip it. You cannot put two different role sets on the same policy at the same target; make a second policy if servers and workstations need different settings.

### Organization policy

<Steps>

1. Choose a **Level**: Organization, Site, Device Group, or Device.

2. For Site, Device Group, or Device, select the specific target. An organization-level assignment always targets the policy's own organization.

3. Optionally set the same **Role Filter** and **OS Filter**. Empty means every device in that target.

4. Set a **Priority** number. When two policies at the same level both define the same feature, the lower priority number wins (priority `1` takes precedence over priority `2`). On an exact tie, the assignment created first wins.

5. Click **Assign**.

</Steps>

<Aside>
  A device-level assignment always takes precedence over all group, site, organization, and partner assignments, regardless of priority number. A partner-wide assignment is the broadest scope and is overridden by any more-specific assignment.
</Aside>

## Per-device compliance status

Each device's detail page surfaces how that device measures against every compliance rule from its assigned policies — separate from the Effective Configuration view. Open any device page and select the **Compliance** tab to see a row for every assigned policy's compliance rules, including the rule name, current status (compliant, non-compliant, pending, or error), the last evaluation time, and any remediation attempts. This makes it easy to audit a single machine's standing without leaving the device page.

The underlying endpoint is:

```
GET /policies/compliance/device/:deviceId
```

## Breeze Defaults baseline

Every Breeze deployment ships with a built-in set of **Breeze Defaults** that sit at the bottom of the resolution hierarchy. These defaults are read-only — you cannot edit or delete them — but every policy you create at any level overrides them.

To inspect the current defaults, navigate to **Fleet Management → Config Policies → Defaults** (or go directly to **/configuration-policies/defaults**). The page lists every setting that Breeze ships with, shows its current value, and indicates whether it is **Active** (in effect for devices with no overriding policy) or **Not enforced** (the feature is present in defaults but not turned on by default).

Examples of shipped defaults:

| Setting | Default state |
|---------|---------------|
| Remote Access | Active (on) |
| PAM / UAC capture | Not enforced (off by default) |
| Vulnerability Scanning | Not enforced (off by default) |

Each row on the Defaults page includes a **Create override policy** shortcut that opens the policy editor pre-configured for that feature, so you can add a partner- or org-level override without navigating away.

### Defaults in the Effective Configuration tab

When a device has no policy assigned for a particular feature, the **Effective Configuration** tab on the device page attributes that value to **Breeze Defaults** and shows a **Not enforced** badge next to it, making it clear that the setting comes from the built-in layer rather than an explicit policy.

## Viewing effective configuration

To see the merged settings a specific device will receive:

1. Navigate to the device's detail page.
2. Open the **Effective Configuration** tab.
3. The page shows the resolved settings for each feature type and which policy in the inheritance chain provided each value — including **Breeze Defaults** for any feature not covered by an assigned policy. When the assigned policy itself has no link for a feature and the value came from its [baseline parent](#baseline-policies-inheritance) instead, the card also shows **"Inherited from &lt;baseline name&gt;"** — two different kinds of inheritance can stack: the hierarchy chain (which *policy* is assigned) and the baseline relationship (which *policy's own settings* apply).

```
GET /configuration-policies/effective/:deviceId
```

Use `POST /configuration-policies/effective/:deviceId/diff` to preview how a policy change would affect a device's effective configuration before saving. The request body accepts:

```json
{
  "add": [{ "configPolicyId": "uuid", "level": "site", "targetId": "uuid", "priority": 1 }],
  "remove": ["assignment-uuid"]
}
```

The response returns both `current` and `proposed` effective configurations for comparison.

## Patch jobs

Policies with a Patch Management feature can trigger deployment jobs:

```
POST /configuration-policies/:id/patch-job
```

Request body:

```json
{
  "deviceIds": ["uuid-1", "uuid-2"],
  "name": "Optional job name",
  "scheduledAt": "2026-03-01T02:00:00Z"
}
```

For each device, Breeze checks:

- Whether the device exists and is accessible — inaccessible devices are listed in `skipped.inaccessibleDeviceIds`
- Whether the device is inside an active maintenance window with patching suppression — suppressed devices are listed in `skipped.maintenanceSuppressedDeviceIds`
- Whether the device ID is valid — invalid IDs are listed in `skipped.missingDeviceIds`
- Whether the device belongs to the policy's organization (org-owned policy) or to an organization under the policy's partner (partner-wide policy) — devices outside that scope are rejected with a `403` rather than silently skipped, since patching someone else's fleet is never allowed

The job is created with the schedule defined in the policy's patch settings (e.g., weekly on Sunday at 2 AM). Targeting devices from a partner-wide policy creates one job per organization that has matching devices, so a single request can produce several jobs — the response lists every job created, each with its own `orgId` and device count.

When creating a policy, set `ownerScope` to `organization` (the default) or `partner`. With `ownerScope: "partner"` the policy is owned partner-wide and any supplied `orgId` is ignored — the partner is always derived from the caller's own token, never trusted from the request body. Creating a partner-wide policy requires partner scope (a `403` is returned otherwise). When assigning a partner-wide policy, use `level: "partner"`; the target is resolved from the caller's own partner, so no `targetId` is required.

To create a policy that inherits from a baseline, pass `parentPolicyId` in the create request body — see [Baseline policies](#baseline-policies-inheritance) above for which parents a given ownership scope may reference. An invalid, cross-tenant, or already-nested parent is rejected with `400 { "error": "INVALID_PARENT_POLICY" }` — a single error for every rejection reason, so the response can't be used to probe which policy IDs exist.

When calling the features endpoints, the `featureType` value must be one of: `patch`, `backup`, `security`, `maintenance`, `compliance`, `automation`, `event_log`, `software_policy`, `sensitive_data`, `peripheral_control`, `warranty`, `helper`, `remote_access`, `pam`, `onedrive_helper`, `vulnerability`, `device_lifecycle`, `monitors`, `hardware_monitoring`. `monitors` is the authoring/deployment feature. The retired values `alert_rule` and `monitoring` are rejected with `410 Gone`.

## Troubleshooting

**Policy not applying to a device**

Check that the policy is assigned at some level in the hierarchy. Open the device's Effective Configuration tab — if the policy is not listed in the inheritance chain, it has not been assigned to any scope the device belongs to.

**Compliance check not running**

Ensure the policy status is **Active** and `checkIntervalMinutes` is set. The evaluation worker scans for due policies every 60 seconds; setting `checkIntervalMinutes` to 1 means a rule will be checked within 60 seconds of becoming due.

**Patch job skipping devices**

Check all three skipped lists in the response: `missingDeviceIds`, `inaccessibleDeviceIds`, and `maintenanceSuppressedDeviceIds`. A device in an active maintenance window with **Suppress Patching** enabled will be skipped automatically.

**Enforcement not remediating**

Enforcement mode must be set to `enforce` and a remediation script must be linked. Without a script, `enforce` falls back to `warn` behaviour.

**Feature type conflict between policies at the same level**

When two policies at the same hierarchy level both define the same feature type, the one with the lower **Priority** number wins (priority `1` beats priority `2`). If the assignments tie on every ranking key, the one created first wins. Before v0.122.1 an exact tie had no defined winner, so a device decided by one may change once after upgrading. Assign distinct priorities to make the choice explicit.

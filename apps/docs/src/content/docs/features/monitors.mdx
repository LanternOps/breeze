title: Monitors
description: Define alert conditions, device responses and delivery once, then attach them to configuration policies.
---

A monitor combines **what to watch**, **severity and alert lifecycle**, **responses**,
**delivery**, and **escalation**. Author it at **Alerts → Monitors**.

## Create and deploy

1. Select **New monitor**, choose a kind and configure its condition.
2. Choose severity, then automatic resolution, re-arm and cooldown, or let them
   inherit. See [Alert lifecycle](#alert-lifecycle).
3. Add up to ten responses. Responses execute on the device that breached.
4. In **Notify**, use **Inherit**, **use these channels instead**, or **inbox only**.
   The inherited preview shows eligible channels, skipped destinations with their reasons, escalation and the winning source.
5. Choose an escalation policy if needed and configure recurrence escalation.
6. Save, test on a device, and attach to a configuration policy. Assign that
   policy to an organization, site, group or device.

Policy **Monitors** tabs also offer **Attach existing**, **Create monitor** and
recommendations for unattached built-ins. Creating a definition alone does not
enable policy-based alert evaluation. An enabled network-check definition does
provision an active probe before attachment. Definitions retain their organization or partner ownership; incompatible
attachments are refused rather than widening access.

## Built-in monitors

Breeze ships a set of built-in monitors with sensible defaults. They appear in a
policy's **Monitors** tab as recommendations until you attach them, and you can
edit thresholds once attached. All of them resolve their own alert automatically
when the condition clears. The current set (source of truth:
`apps/api/src/services/monitors/builtInMonitors.ts`, `BUILT_IN_MONITOR_DEFAULTS`):

| Monitor | Fires when | Severity |
|---|---|---|
| High CPU usage | CPU above 90% for 15 minutes | High |
| High memory usage | Memory above 90% for 15 minutes | High |
| Disk almost full | System disk 90% used or more for 30 minutes | Critical |
| Low patch compliance | Patch compliance below 80% | Medium |
| RAID array degraded or failed | Two critical array or controller hardware snapshots | Critical |
| Physical disk failed or predicted to fail | Two critical or predictive-failure disk snapshots | High |
| Controller cache battery problem | Three unhealthy controller cache battery snapshots | Medium |
| Hardware monitoring tool failing | Three failed or backing-off hardware collector snapshots | Low |
| Time source problem | Two accepted snapshots reporting a time source problem (for example no external source, local clock, unreachable NTP) | High |
| Time sync stale or disabled | Two accepted snapshots reporting stale or disabled synchronization | Medium |
| Timezone mismatch | Two accepted snapshots reporting a timezone mismatch | Low |
| Time policy not applied | Two snapshots reporting failed time-policy enforcement | Low |
| Container image out of date | A running container image has been behind its registry tag for 7 days | Low |

## Conditions

The kind picker includes resource thresholds, offline state, event logs,
patch compliance, service/process state and resources, agent mTLS certificate
expiry, bandwidth, disk I/O, network errors, software/security/backup conditions,
script probes and network checks. `GET /monitor-definitions/kinds` returns the
exact kinds and supported condition fields on your server.

A few kinds have units or evidence rules worth knowing:

- **Bandwidth** thresholds are in megabits per second; **Disk I/O** thresholds are
  in megabytes per second. Every sample in the duration window must breach.
- **Network errors** counts the errors that *occurred* during the window (the
  increase of each interface's error counters, with counter resets handled), not
  the running totals the agent reports. It needs two samples of the interface to
  evaluate.
- **Patch compliance** uses the latest hourly posture score. A score older than
  24 hours, or one computed for a device with no patch telemetry, counts as no data.
- **Certificate expiry** watches the Breeze agent's own mTLS certificate only. It
  does not inspect certificates installed on the device or served by its services.

Composite monitors contain two to ten server-evaluated child conditions,
matching all or any. They cannot nest or contain agent-delivered/worker-provisioned
children. Composite conditions do not support per-policy threshold overrides.

**Service stopped**, **Process stopped** and **Process resource** monitors are
delivered to the agent directly from the policy's attached monitors; the per-policy
*Check interval* on the **Monitors** tab sets how often the agent evaluates them.
Their consecutive-failure setting accepts 1–100. A service restart response carries
its own maximum attempts (0–50, default 3) and cooldown (30–86400 seconds, default
300). Agent-local restarts continue through the delivered watch configuration.
The policy's **Agent collection → Check interval** accepts 10–3600 seconds, default 60.

### Network check

| Kind | Condition | Default severity | Evaluation |
|---|---|---|---|
| Network check | An ICMP, TCP, HTTP or DNS probe run from an agent fails N times in a row (optionally: is degraded or slow) | High | Agent (probe) + server (verdict) |

Create network checks here; inspect their history under **Network → Results**.
The optional asset picker binds an organization-owned check to an asset's site
and guides alert-device selection. Evaluation is once per check per organization,
even if that alert device is offline; an online agent runs the probe.

#### Network check fields

| Field | Values |
|---|---|
| Check type and target | ICMP, TCP, HTTP or DNS; IP address, hostname or URL |
| Asset | Optional asset in the same organization |
| Type options | Ping count; TCP port/banner; HTTP method, expected status/body, TLS and redirects; DNS record/value/nameserver |
| Treat degraded as failure | Optional; default false |
| Fail when slower than | Optional response limit, 1–600,000 ms |
| Poll interval / timeout | 10–86,400 seconds / 1–300 seconds |
| Consecutive failures | 1–100; default 2 |

The HTTP API field is `expectStatus`, sent as `expectedStatus` to the agent.
See [Network Checks](/features/network-monitors/) for per-type options, delivery,
asset binding, operational probes and retained history.

## Inheritance and overrides

**Add to inherited monitors** is cumulative. A policy contributes its attachments
alongside inherited monitors; the resolver chooses the effective attachment for
each monitor using assignment scope and priority, including role and OS filters.
A closer attachment can disable or override a monitor without editing its definition.

**Replace inherited monitors** preserves converted inline rules' replacement
behavior. The policy tab shows inherited attachments being ignored. Conversion may
set this mode automatically; change it only after reviewing the resulting device
coverage. The device Monitoring tab shows the effective result.

## Alert lifecycle

An **episode** is one alert from the moment it opens until it closes. Three
settings decide how an episode ends and when the next one can start. The re-arm
setting, the **Lifecycle defaults** card and **Clears when** are available in
releases after v0.126.0.

| Setting | What it does | Built-in default |
|---|---|---|
| **Auto-resolve** | Closes the alert when its condition clears, including an alert someone acknowledged or suppressed. | Off |
| **Re-arm** | Decides what can open the next alert once this one closes. | New evidence |
| **Cooldown** | Waits this long after an alert closes before another can open (0–1440 minutes). | 5 minutes |

Re-arm has two modes:

- **New evidence** opens a new alert only for an event the closed alert has not
  seen. An event still inside the monitor's window does not page you twice.
- **After N minutes** (1–1440) also lets those older events re-open the alert
  once N minutes have passed since it closed. Use it if you want a reminder
  while a problem persists.

Re-arm applies to evidence-based conditions, such as event logs. A new event
during the cooldown is delayed rather than lost, unless the monitor's window is
shorter than the cooldown and the event ages out first. The editor warns you
when that can happen.

Alerts that need a person never auto-resolve, and a device with no current data
never resolves an alert. See
[When alerts close on their own](/features/alerts/#when-alerts-close-on-their-own).

### Where to set it

Each setting resolves in this order, and the first level with a value wins:

1. **The monitor**, in the editor's **Alert lifecycle** section. Each field offers
   Inherit, and shows which default it overrides when you set a value.
2. **The organization**, in the **Lifecycle defaults** card on **Alerts → Monitors**,
   with that organization selected.
3. **The partner**, in the same card at partner scope.
4. **The built-in default** in the table above.

A partner-wide monitor resolves against each device's organization, so two
organizations can get different values from one monitor.

An alert keeps the values it opened with. Changing a setting affects the next
episode, not one already open. The alert's page shows what it is using, for
example _Re-arms on new evidence · cooldown 5 min (partner default)_. The brackets
name where the cooldown came from. Alerts opened before this line existed do not
show it.

### Clears when

By default an alert clears when its trigger stops matching. For an event-log
condition that means when the matching events age out of the window, which says
nothing about whether the problem is actually over. **Clears when** names the
event that does.

It appears on event-log monitors when auto-resolve is on. Select **Add a recovery
condition**. The form starts from the trigger's category and source, at
Information level with a 60-minute window. Add a message so that only the
recovery event matches. A condition with no source or message clears on any event
in that category that the agent collects.

An alert clears only on an event logged after its own trigger event, so a recovery
event left in the log by an earlier incident cannot close a new one.

Level is a minimum: **Information** also matches Warning, Error and Critical
events. Below Error, Application events are collected only from the agent's
built-in providers and the
[providers you add in a policy](/features/event-log-forwarding/#collect-warning-and-information-events-from-more-application-providers). The editor warns
you when a recovery event would not be collected, because that alert would never
clear.

Other monitor kinds always clear on the inverse of their trigger.

A condition saved through the API in the older raw format appears read-only as
**Custom recovery condition (API)**. Saving the monitor keeps it unchanged.
**Replace** swaps it for an editable condition when you save. If the editor says
the condition can't be evaluated, that monitor's alerts never auto-resolve until
you replace it. Changing such a monitor's kind removes the condition.

### Recipe: a UPS on battery

Alert when a Windows server's UPS goes on battery, and clear when power returns.
APC PowerChute logs both events to the Application log, and its provider is a
built-in one, so it needs no policy entry. Check that the device's Event Logs
policy collects the Application category at Information level.

| | Category | Level | Source matches | Message matches |
|---|---|---|---|---|
| **Trigger** | Application | Warning | `APCPBEAgent` | `On Battery` |
| **Clears when** | Application | Information | `APCPBEAgent` | `Power Restored` |

Set **Auto-resolve** to **On** on the monitor, or inherit it from a default that
is on. Check the exact message text against the events your UPS software writes.

### Upgrading from before v0.126.0

These changes apply to every event-log alert, with no setting to enable them:

- An event-log alert no longer re-opens on events an earlier alert already saw, so
  you may see fewer alerts and fewer `alert.resolved` events.
- A recovery event clears an alert only if it is newer than the trigger.
- Acknowledged and suppressed alerts now auto-resolve when auto-resolve is on.
- Breach episodes for event-log monitors now end when the alert closes rather than
  when events age out of the window. `recurrenceThreshold` may therefore count
  more, shorter episodes.

In releases after v0.126.0, you can get repeat alerts back while a problem
persists: set re-arm to **After N minutes** on a monitor or in the lifecycle
defaults.

## Legacy rules

v0.117.0 introduced conversion of legacy alert rules and service/process
watches to monitors. From v0.118.0 the API processes remaining sources at startup and
retires those that cannot convert with a reason (set `BREEZE_LEGACY_ALERTING_SWEEP=false`
to skip this; leftover rows are then counted and logged at every boot). **Alerts → Monitors** lists these items in a
banner that you can dismiss after review. Source rows and alert history are retained.
Open alerts from unconvertible retired rules stay open until someone resolves them;
converted sources' open alerts move to the compiled monitor path.

**Conversion history → Undo** is no longer available for legacy alert rules,
templates, inline policy rules or service/process watches after upgrading to
v0.118.0. Review and complete conversion on v0.117.0 before upgrading (see the
[v0.118.0 upgrade notes](/deploy/upgrades/#v01180--legacy-alerting-retired-network-checks-become-monitors)).
Network checks retain their runtime and are excluded from automatic conversion and retirement.

**Converting network checks:** use the banner on **Network → Results** to preview
and confirm supported checks, or explicitly retire unwanted ones. Conversion
adopts the probe, keeps results and open-alert status/provenance, and attaches the
monitor to a cumulative organization-level **Network checks — &lt;org name&gt;**
policy. Non-alerting probes, mixed rules and unsupported predicates or thresholds
are refused; a missing runtime prerequisite blocks network preview. Network
**Conversion history → Undo** remains available while that runtime is retained.
See [conversion details](/features/network-monitors/#converting-existing-checks).

The retired legacy write endpoints, including `POST /alerts/rules/:id/test`, return `410 Gone`; historical reads remain available.
Test monitors with `POST /monitor-definitions/:id/test`.

### Built-in alerts

Breeze raises some alerts itself rather than through a monitor: **Patch job failures**,
**Reboot pending too long**, policy-violation alerts, and
[new remote access tool alerts](/features/management-posture/#new-remote-access-tool-alerts).
Each rule belongs to one organization (policy violations get one per policy, new
remote access tools one per tool), is created the first time its
alert fires, and is never offered for conversion. **Alerts → Monitors** lists them under **Built-in alerts** with an
**Active** switch per organization. Switching one off stops new alerts of that kind
for that organization and stays off; alerts that are already open stay open until
you resolve them. The switch needs `alerts:write` and MFA, and is recorded in the
audit log as `alert_rule.update`. Through the API, send
`PATCH /alerts/rules/:id/active` with `{ "isActive": false }`. Any other legacy rule
returns `410 Gone`.

## Device Monitoring and recurrence

Open a device's **Monitoring** tab (`#monitoring`) to see effective monitor, kind,
source policy, healthy/breaching/unknown state, open episode and escalation status.
No evidence means unknown. Disabled winning attachments remain visible.

Recurrence counts breach episodes rather than repeated samples of one continuous
breach. When escalation pauses responses, **Reset escalation** clears the latch and
resumes responses. Reset does not close the open episode or resolve its alert.
The server enforces alert-write permission and MFA for the reset action.

## Automation and AI tools

Use **Jobs → Alert workflows** for broad event-triggered behavior. Severity and kind
filters are optional; monitor responses stay device-bound. Fleet Designer proposes
monitor definitions and applies them as policy attachments. Historical proposals
using the old rule shape must be regenerated before applying.

`manage_monitor_definitions` authors monitors. Attach through
`manage_policy_feature_link` with `featureType: "monitors"`.
`manage_service_monitors` lists effective service/process monitors only.

## API and troubleshooting

Monitor CRUD, attachments, device tests and activity live under
`/monitor-definitions`. Conversion routes live under
`/monitor-definitions/conversion`. The device view reads `/devices/:id/monitors`;
escalation reset posts to `/monitor-definitions/:id/devices/:deviceId/reset`.

If a monitor does not appear on a device, check policy assignment, role/OS filters,
inheritance and enabled state. If notifications are missing, inspect the resolved
delivery preview and [Delivery](/features/notifications/). If a response is paused,
inspect recurrence escalation before resetting it. Compiler-managed rows are
implementation details; change the monitor definition rather than editing them.

**The Monitors page shows *N legacy rules could not be converted*.** Open the list;
each row names the policy and the reason. Recreate the condition as a monitor
(Composite for multi-condition rules), then dismiss the banner.
